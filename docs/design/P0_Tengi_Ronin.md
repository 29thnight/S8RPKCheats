# P0 전기·무장 감시 기능 조사

기준: S8RPKCheats `068ca1d881edf870f7cf06f935cf50e286004af8`. 아래는 정적 호출과 상태 추적 결과다. 게임 객체를 읽거나 쓰는 스레드의 안전성은 실제 호스트에서 별도 확인해야 한다.

## 전기 캡처와 주기

- `ConfigBase.inc:821`은 설정 적용 중 `SetTengiCapture(true)`를 호출한다. `TengiCave.cpp:104`는 요청만 기록하고 `bInfTengi`가 꺼져 있으면 cave 설치를 미룬다. `TengiCave_Tick`은 요청이 있고 기능이 켜졌으며 미설치일 때 설치를 다시 요청한다.
- 설치 worker는 알려진 RVA 검증 또는 바이트 패턴 탐색 후 원본 7바이트를 보관하고 cave를 설치한다. 생성된 thread handle은 바로 닫는다. OFF는 설치 요청과 캡처 주소를 지우고 이미 설치된 경우 원본 7바이트를 복원한 뒤 cave를 해제한다. OFF가 설치 worker의 완료를 기다리는 코드는 이 경로에 없다. worker 생성 실패 시 `g_tengiRunning`을 되돌리는 분기도 보이지 않는다.
- `SetTengi`는 캡처된 게이지 주소에 값을 쓰고 값이 100 이상이면 관련 포인터 두 개가 존재할 때 발생 플래그를 쓴다. 주소 검증 결과는 500ms 캐시한다. 게임 객체 수명이 그 기간 동안 유지된다는 증거는 아니다.
- `Menu_impl.inc:470`은 유효한 p1 또는 0을 `TickTengiCycle`에 전달한다. 이 함수는 레이아웃 검증과 200ms 관찰 제한을 사용하며 p1·관리자 변경, 월 역행, 관찰 실패를 별도 상태 전이로 처리한다. 로드/연결한 달은 발생 요청을 하지 않고, 분기 평정월에 기능이 켜져 있고 허용 후보가 있을 때 요청을 한 번 보낸다. 요청과 실제 이벤트 객체 생성 확인을 구분한다.
- `TickTengiAllowedFilter`는 15개 허용 여부와 cooldown을 게시하고 게임 데이터 준비 후 세 개의 MinHook 필터를 설치한다. 설치 시도는 준비 전 2초 간격이지만 실제 `InstallTengiAllowedFilter` 호출 직전에 attempted를 설정하므로, 설치 자체가 실패한 이후 자동 재시도하는 경로는 해당 함수에 없다. 이 필터는 캡처 cave와 별개다.
- `TickTengiListDurations`는 15개 이벤트의 설정 기간을 적용한다. 현재 주소가 바뀌면 저장한 원본 상태를 버리고, OFF 시 현재 값이 자신이 쓴 값과 같을 때만 원본 복구를 시도한다. 최초 원본 기간이 0인 즉발 이벤트는 덮어쓰지 않는다. 기본 호출 주기는 2초이며 렌더 유지 작업에서 실행된다. UI가 전부 닫힐 때 Overlay가 호출되지 않는 조건은 [오버레이 조사](P0_Overlay.md)를 따른다.

활성 평정 메뉴의 `bInfTengi` 체크박스는 flag 변경 후 알림과 설정 저장만 수행한다(`CouncilCompactSectionBase.h:131-135`). OFF 시 캡처 setter를 호출하지 않으므로 이미 설치된 캡처 cave나 별도의 허용 필터를 이 조작이 해제하지 않는다. OFF는 주기 강제 요청 조건을 막지만, 허용 필터와 기간 설정은 별도 경로에서 계속 처리된다. 이 구분은 현재 확인된 직접 호출에 대한 것이며 실제 화면과 메모리 상태는 확인하지 않았다.

기준 자체 cpp·h·inc에서 `SetTengi`와 `GetTengi`는 선언·정의 외 직접 호출을 찾지 못했다. `RequestCycleTengi`의 `SetTengi(100)` 표기는 주석이며 실제 구현은 별도의 관리자 게이지를 직접 쓴다. 캡처 주소는 `TengiCave_Tick`의 로그와 평정 메뉴의 주소 변화 로그에서 조회된다. 따라서 `SetTengi`의 쓰기 구현이 존재한다는 사실만으로 현재 메뉴가 그 함수를 호출한다고 판단하지 않는다. 간접·외부 호출은 이 검색 범위 밖이다.

캡처 cave는 `r15+0x1E4B18`을 기록하고 원래 바이트 쓰기를 수행한다. 주기 요청은 `GetScenarioDataCenterAddress()`에서 얻은 관리자 `+0x1EBDE0`에 쓴다. 소스의 PDB 분석 주석대로 `r15`가 해당 관리자의 worldData `+0x72C8`이라면 `0x72C8 + 0x1E4B18 = 0x1EBDE0`이므로 두 주소는 같아진다. cave가 실행될 때 r15와 관리자의 실제 관계는 정적 산술만으로 확인되지 않았다. 주기 요청은 캡처 주소가 아닌 직접 해석한 관리자 주소를 사용한다.

`TickTengiCycle`은 최초 호출에서 PE의 CodeView `RSDS` GUID `B18A027E-19F4-4C35-8749-5B6F0FF814D8`와 age 1을 검사한 결과를 함수 정적 `const bool`에 한 번 저장한다. 기능 OFF 중 첫 호출의 조회 실패도 false로 고정되며, 이후 조건이 달라져도 이 함수는 같은 프로세스에서 검사를 다시 하지 않는다. false일 때는 강제 전기 주기 요청을 막고, ON이면 불일치 로그를 한 번 남긴다(`TengiCave.cpp:346-383, 817-833`). 이는 PDB 파일을 여는 검사가 아니라 로드된 PE의 debug 정보 대조다. 기간 설정의 `TickTengiListDurations`에는 이 `verifiedLayout` 분기가 없다. 실제 첫 호출과 검증 결과는 게임을 실행하지 않아 확인하지 않았다.

현재 설치된 `SAN8RPK.exe` 파일의 PE debug directory를 section RVA에서 파일 오프셋으로 변환해 읽은 결과 CodeView 서명 `RSDS`, GUID `B18A027E-19F4-4C35-8749-5B6F0FF814D8`, age 1로 소스의 기대값과 일치한다. 파일 SHA-256은 `000D450345728C23BEBCA581AB37B8BCF25266172767B5E6DEFB10A72A8C9457`이다. 이 결과는 파일 정보의 정적 일치이며 실제 로드된 이미지의 접근 가능성이나 최초 호출 결과를 증명하지 않는다. 게임은 실행하지 않았다.

동일 설치 파일의 캡처 고정 RVA `0x1338830`도 section을 통해 대조했다. 파일 바이트 `80 C0 48 11 55 8F 03`은 `ResolveKnownTengiHook`이 요구하는 `41 88 87 18 4B 1E 00`과 다르다. 고정 위치 검사가 실패하면 소스는 로드 이미지에서 같은 패턴을 별도 검색한다. 동일 파일 전체를 7바이트 패턴 `41 88 87 18 4B 1E 00`으로 검색한 결과도 일치 0건이었다. 소스의 fallback은 로드된 이미지 메모리를 검색하므로 이 파일 검색만으로 실행 중 결과를 판단하지 않는다.

같은 설치 파일에서 전기 허용 필터의 다섯 검사 RVA를 PE section을 통해 파일 오프셋으로 변환해 대조했다. `0x132E340`, `0x132E5A0`, `0x132E920`, `0x10A20`, `0x132EE4D`의 파일 바이트는 각각 `28 59 5B EC B1 7E`, `23 0D 12 40 37`, `37 1C EE 8E 13 D7`, `D0 AE 75 95 11 79`, `65 EE 41 DC F6`로 소스의 기대 바이트와 모두 다르다(`TengiCave.cpp:397-400, 621-633`). 앞서 확인한 CodeView 일치만으로 코드 서명까지 일치한다고 판단할 수 없다. 소스가 검사하는 대상은 로드된 실행 메모리이므로 파일 결과만으로 실제 hook 설치 실패를 단정하지 않는다.

주기 요청의 조건에는 `s_allowedFilterInstalled`나 `s_allowedFilterReady`가 없다. `TickTengiCycle`은 허용 항목이 하나라도 있고 나머지 주기 조건이 맞으면 게이지를 100으로 올리는 요청을 할 수 있다(`TengiCave.cpp:734-746, 881-897`). 필터 설치가 실패한 경우에도 이 요청 경로는 별개로 남지만, 허용 후보·쿨다운 제한은 해당 필터의 detour 설치 여부에 달려 있다. 따라서 필터 실패 시 단순히 주기 기능 전체가 중지된다고 기록하지 않는다. 실제 이벤트 선택 결과는 실행하지 않았다.

주기 요청의 게이지 쓰기와 재읽기가 성공하면 `pending=true`가 되며, 유효한 관찰이 계속되지만 새 전기 객체가 생성되지 않는 동안에는 시간이 지나거나 기능을 OFF/ON해도 pending을 해제하는 분기가 없다. 새 전기 data·시작 월을 관찰하거나 세션·관리자 변경, 월 역행 또는 관찰 실패에 따른 상태 초기화에서 pending이 지워질 수 있다. 관찰 실패는 별도로 `needsEventObservation=true`를 남겨 실제 객체 관찰 전 추가 요청을 막는다. 또한 분기 평정월은 ON 여부와 요청 성공을 판단하기 전에 처리된 월로 기록되므로 그 달에 나중에 ON하거나 쓰기에 실패해도 같은 달 재요청하지 않는다(`TengiCave.cpp:837-897`). 실제 이벤트 생성과 관찰은 실행하지 않았다.

## 재야 감시와 알림

- `Menu_impl.inc:523`의 `RoninMonitor_Tick(p1)`은 ClientBGThread에서 호출된다. `bMonitorRonin`과 `bOfficerChangeNotify`가 모두 꺼지면 감시 기준과 알림을 초기화한다. 전투 중이거나 설정 안정화 전이면 스캔을 하지 않는다.
- 비영(0이 아닌) p1 주소가 기존 주소와 달라지면 무장 배열·도시 주소와 ID별 재야·상태 기준 및 알림을 초기화한다. p1이 0이 된 순간에는 이 주소 변경 분기가 실행되지 않는다. 재연결이 같은 주소인 경우와 실제 객체 세대의 관계는 추가 확인 대상이다.
- 기능을 켠 직후 현재 상태를 기준선으로 저장한다. 내정→평정 전환에서 재야 상태를 비교하고 사망·등용 비교 기준을 저장하며, 평정→내정 전환에서 사망·등용을 비교한다. 기존 상태를 기능 활성화 직후 소급 알림으로 처리하지 않는다.
- 결과 표시용 알림 목록은 mutex로 보호한다. `RoninMonitor_Draw`는 Overlay에서 호출되며 재야 알림 표시 중 공용 알림 타이머를 멈춘다. 표시와 시간 진행도 Overlay 호출 조건에 종속된다.

`RoninMonitor_Tick`의 `IsConfigReady()`는 설정 파일을 성공적으로 읽었는지 확인하지 않는다. 공통 적용 루프가 기록한 첫 P1 감지 시각이 0이 아니고 3초가 지났는지만 확인한다(`ConfigBase.inc:828-832`). 파일 로드 실패 후에도 이 시간 조건은 만족할 수 있다. 재야 감시는 그 밖에 전투 여부와 별도의 base 해석·게임 상태를 검사한다. P1 주소가 0이 아닌 다른 값으로 바뀌면 감시 쪽은 준비 검사보다 먼저 기준선을 초기화하지만, 공통 설정 적용의 안정화 시간은 유효 주소 간 직접 교체만으로 초기화되지 않는다. 따라서 두 구성 요소의 세대 판정은 서로 다르다. 실제 세이브 전환은 실행하지 않았다.

개별 감시 OFF의 기준선 무효화는 전투·설정 준비·base 해석·게임 상태 검사 뒤에 있다(`RoninMonitor.cpp:541-556`). 다른 감시가 켜진 채 한 기능을 끈 상태에서 그 검사 중 하나 때문에 반환하고, 다음 유효 tick 전에 다시 켜면 OFF 상태를 무효화 분기가 관찰하지 못해 이전 기준선을 유지할 수 있다. 두 기능이 모두 OFF인 경우에는 이 검사보다 앞에서 전체 상태를 초기화한다. 회귀 조건은 한 기능만 OFF인 상태가 유효 tick에 관찰된 경우와 관찰되지 않은 경우, 전투·주소 해석 실패 중 토글 및 두 기능 전체 OFF다. 실제 토글은 실행하지 않았다.

재야 및 무장 변동 검색은 슬롯 1~5102를 순회해 실제 ID 1~5102의 첫 항목만 사용한다. 페이지 또는 필드 읽기 실패는 해당 슬롯을 건너뛴다. 재야 검색은 읽지 못한 ID를 false로 남긴 새 배열을 기존 기준 전체에 복사하므로, 한 번 읽지 못했던 기존 재야 무장을 다음 비교에서 다시 읽으면 신규 재야로 판정할 수 있다(`RoninMonitor.cpp:248-294`). 사망·등용 기준선도 읽지 못한 ID를 invalid로 저장하며, 비교할 때 이전 기준이 invalid면 해당 무장 변동을 건너뛴다(`RoninMonitor.cpp:311-405`). 부분 읽기 뒤에도 두 기준선은 초기화 완료로 표시된다. 중복 ID, 부분 읽기 후 복구 및 평정 전후 읽기 실패를 이관 회귀 사례로 둔다. 실제 메모리 읽기 실패는 실행하지 않았다.

## 미발견 무장 재야 전환

`StartSetting.cpp:266`의 setter가 lifecycle mutex 아래 감시 worker와 stop event를 소유한다. worker는 gameBase와 p1 변화를 감시하고 요청 버전을 통해 스캔을 처리한다. p1이 0이 된 뒤 같은 주소로 돌아와도 새 로드로 취급한다. OFF는 대기 요청을 취소 표시하고 stop event를 알린 뒤 스레드 종료를 기다린다. 정상 MainThread 종료에도 OFF가 호출된다. 이 작업은 재야 **알림 감시**와 별개의 게임 메모리 변경 기능이다.

요청 버전은 활성화, gameBase 획득·변경, 유효 P1 변경 때 각각 증가한다. watcher가 처음에 유효한 gameBase와 P1을 함께 발견하면 앞의 ON 요청까지 세 번 증가할 수 있지만 처리 함수는 현재의 최신 버전 하나를 읽어 한 번 스캔한다. 처리 중 더 최신 요청을 관측하면 중단하며, 이미 쓴 데이터는 되돌리지 않는다. P1·root·날짜가 아직 유효하지 않으면 처리 버전을 갱신하지 않아 이후 watcher 반복에서 다시 확인한다.

공개 setter의 ON은 기존 worker 핸들이 0ms 대기에서 `WAIT_TIMEOUT`을 반환하면 요청을 추가하지 않고 돌아간다. 그 밖에는 새 스캔 요청 버전을 먼저 올린 뒤 worker 시작을 시도하지만 시작 함수의 성공 여부를 호출자에게 반환하지 않는다. worker가 종료된 후 ON setter가 다시 호출되면 새 요청과 재시작을 시도할 수 있으나, 이 사실만으로 ON 호출이 자동으로 다시 발생한다고 판단하지 않는다. 설정 로드와 메뉴 외의 외부·간접 호출은 확인 범위 밖이다.

메뉴는 체크박스 flag를 바꾼 뒤 이 `void` setter를 호출하고, 시작 성공 여부와 관계없이 변경 알림과 설정 저장을 수행한다(`MenuSectionsOfficerEdit.cpp:202-205`). 일반 설정 로드도 flag가 켜져 있으면 setter 호출 후 watcher 조기 시작 로그를 남긴다(`Config.cpp:315-317`). 따라서 체크·저장 또는 해당 로그만으로 worker 생성 성공을 판정하지 않는다. 생성 함수 자체는 실패 로그를 남긴다.

## 회귀 조건

캡처 설치 대기 중 ON/OFF, worker 생성 실패와 종료, 전기 필터 설치 실패, 허용 목록 비어 있음, 요청 후 이벤트 미생성, 기간 0과 1~120, 외부 기간 변경, p1 0→동일 주소 복귀, 날짜 역행, 평정 전환별 기준선, 재야 알림과 공용 알림 순서 및 사용자 설정 복원을 확인한다.

## 감시 팝업의 표시 시간과 공통 알림 구분

`RoninMonitor_Tick`은 background loop에서 상태를 감시하지만 `RoninMonitor_Draw`는 `Engine.cpp:607`의 overlay 프레임에서 호출한다. 모든 UI가 닫혀 Present가 overlay를 호출하지 않으면 감시는 계속될 수 있어도 팝업 표시와 타이머 차감은 진행되지 않는다. 프레임당 ImGui `DeltaTime`은 최대 0.1초로 제한하고, 재야 알림의 타이머는 `bMonitorRonin`이 ON일 때만 줄인다.

재야 알림이 하나라도 표시되는 동안 `s_sharedPopupQueue`의 앞 항목은 타이머를 줄이지 않는다. 이는 `RoninMonitor.cpp` 내부의 사망·등용 등 공용 **팝업 큐**이며 `NotificationManager.cpp`의 상단 흐르는 알림 pending 큐와 별개다. 목록 팝업의 닫기 버튼은 재야 알림 전체 또는 앞의 무장 변경 팝업을 제거한다. 회귀 조건은 UI 전체 닫힘·재개, 긴 프레임 간격, 재야 ON/OFF와 공용 팝업 대기, 두 종류의 알림 큐 동시 발생 및 닫기다. 실제 화면 표시는 실행하지 않았다.

## 미발견 전환의 실제 수정 범위와 목록 갱신

공개 watcher의 `ProcessPendingUndiscoveredToRoninScan`은 유효한 root·P1과 시나리오 연도 100~399를 기다린 뒤 최대 1000개 슬롯을 순회한다. ID가 1~2000인 슬롯에서 신분 0x68 또는 0x78이면 0x58로 바꾸는 쓰기를 시도한다. 그 뒤 등장·출생·사망 연도 보정은 이 신분 조건의 바깥에 있다. 따라서 ID 조건을 통과한 다른 신분의 슬롯도 연도 조건이 맞으면 수정한다. 등장 연도가 현재보다 늦고 400 미만이면 현재 연도로, 출생 연도가 현재 연도-15 이상이고 400 미만이면 현재 연도-20으로, 사망 연도가 0이 아니면서 현재 연도 이하이면 현재 연도+50으로 쓴다.

슬롯 주소 검사가 실패하면 남은 슬롯을 중단하지만, 새 요청이나 OFF가 없으면 해당 요청을 처리 완료로 표시한다. 신분 쓰기 helper `WriteByte`는 실패를 반환하지 않는데 호출자는 쓰기를 시도한 즉시 변경 카운트를 올린다. 연도 필드 세 개는 주소 검사 후 직접 쓰며, 보정 도중 요청이 취소돼도 이전에 바꾼 필드를 되돌리지 않는다. 알림의 수정 인원은 신분 변경만이 아니라 연도 수정도 포함한다.

`StartSetting.cpp`의 `RequestOfficerListRefresh` 연결은 include되는 구형 구현에서 `AddNotification`을 매크로로 감싼 구간에 있다. 현재 공개 watcher의 완료 알림은 해당 매크로를 해제한 뒤의 별도 함수에서 직접 호출하며, 그 함수 자체에는 목록 refresh 요청이 없다. 다른 경로의 캐시 갱신과 실제 화면 반영은 별도 확인이 필요하다.

refresh 요청이 실제로 발생한 다른 경로에서는 `RequestOfficerListRefresh`가 atomic bool을 true로 설정하고, `DrawOfficerListWindow`가 다음 호출에서 `exchange(false)`로 소비해 내부 갱신 flag를 세운다. 여러 요청은 한 bool로 합쳐지며 wrapper 호출 전에는 소비되지 않는다. 부속 창 렌더 경로는 목록이 닫힌 경우에도 wrapper를 호출할 수 있고, 이때 내부 요청 flag는 창 구현이 처리할 때까지 남는다. 현재 공개 watcher의 완료 알림은 이 요청을 직접 내지 않으므로, 이 메커니즘의 존재만으로 watcher 완료 후 목록 갱신을 보장할 수 없다.

회귀 조건은 미발견·재야·등용 등 신분별 연도 보정, ID와 첫 1000개 슬롯 경계, 중간 주소·신분 쓰기 실패, 변경 도중 OFF·새 요청, 처리 완료 표시와 목록 캐시 갱신이다. 소스 추적이며 게임 데이터 변경은 실행하지 않았다.

## 미발견 전환과 자녀 예약의 연도 필드 충돌 후보

공개 미발견 전환 watcher는 `ResolveRoot()+0x1D4560`에서 1000개 슬롯을 순회하며, 자녀 예약은 별도 roster resolver에서 찾은 자녀 레코드를 사용한다. 두 포인터 체인이 같은 레코드를 가리킨다는 사실은 현재 확인되지 않았다. 다만 두 경로 모두 레코드 기준 등장 `+0x32`와 출생 `+0x34`를 쓴다. 같은 레코드가 두 경로에 포함되는 상황에서는 작업 순서가 결과에 영향을 준다.

자녀 예약은 현재 연도+1~10을 등장 연도로, 그보다 15년 전을 출생 연도로 쓴다. 그 다음 미발견 watcher가 같은 레코드를 처리하면 ID가 1~2000이고 연도 값이 해당 검사 범위에 있을 때 등장 연도를 현재 연도로, 출생 연도를 현재 연도-20으로 바꾼다. 앞서 확인했듯 이 연도 보정은 신분이 미발견인지와 무관하다. 반대로 watcher 처리 뒤 자녀 예약을 적용하면 예약 값이 마지막으로 기록된다.

자녀 유지 갱신은 메모리의 등장·출생 연도를 다시 읽지만, 예약 완료 flag와 백업을 폐기하는 기준은 별도로 보관한 `appliedTargetYear`다. 같은 레코드의 등장 연도가 watcher에 의해 현재 연도로 바뀌고 화면이 그 값을 읽었다면 UI의 임관 여부 판정은 참이어서 선택 체크와 연수 입력을 비활성화한다. 실제 임관 이벤트가 발생했다는 뜻은 아니며, 두 주소의 동일성·실제 실행 순서·UI 결과는 확인되지 않았다.

회귀 조건은 두 base의 레코드 주소 비교, 첫 1000슬롯·ID 경계, 두 작업의 각 실행 순서, 예약 선택 상태에서 연도 외부 변경, 취소·원본 백업과 세대 교체다. 실제 게임 데이터를 읽거나 변경하지 않았다.

## 전기 목록 팝업의 편집과 발생 기준

기간 적용 호출은 허용된 양수 기간이나 기존 활성 override가 없으면 즉시 반환하고 시간 표식을 갱신하지 않는다. 요청이 있으면 메뉴의 `immediate=true`는 2초 대기를 건너뛰지만 같은 `s_lastTengiDurationPollMs`를 순회 전에 갱신한다(`TengiCave.cpp:903-927`). 따라서 저장 버튼에서 주소 조회나 쓰기가 실패한 뒤에도 요청이 유지되는 경우, 일반 렌더 유지 호출은 그 시각부터 2초가 지나야 다시 시도한다. OFF 복구 실패는 아래처럼 활성 기록을 지우므로 별도다. 실제 실패 빈도와 실행 순서는 확인하지 않았다.

기간을 0으로 바꾸거나 허용을 끄면 현재 값이 이전에 쓴 값과 같을 때만 원본 쓰기를 시도한다. 이 복구 쓰기가 실패하거나 현재 값이 달라 복구를 건너뛰어도 `saved.active=false`가 된다. 다른 요청이 없다면 다음 호출은 처리할 항목이 없어 반환하므로 복구 실패를 자동 재시도하지 않는다. 반대로 처음 양수 기간을 적용할 때는 쓰기 전에 원본과 active를 기록해, 쓰기가 실패해도 active가 남는다(`TengiCave.cpp:939-979`). 요청을 유지한 재시도와 OFF 복구 실패는 구분한다. 실제 파일·게임 메모리 쓰기는 실행하지 않았다.

활성 메뉴의 `CouncilCompactSectionBase.h:152`는 팝업을 열 때 15개 허용 여부·기간·쿨다운을 임시 배열로 복사한다. 입력은 기간 0~120개월, 쿨다운 -1~255년으로 제한한다. `닫기`는 임시값을 반영하지 않고 팝업만 닫으며, 다시 열면 현재 설정을 다시 복사한다. `설정 저장`은 15개 항목을 순서대로 전역 허용·기간 배열과 쿨다운 setter에 반영한 뒤 `SaveConfig`, `TickTengiListDurations(true)`를 호출하고 팝업을 닫는다. 저장 함수는 이 호출자에게 성공 여부를 반환하지 않으므로 저장 실패와 관계없이 즉시 기간 적용 호출과 닫기까지 진행한다.

허용 목록 필터는 별도 background `TengiCave_Tick`에서 허용 배열을 읽어 mask와 쿨다운 존재 여부를 게시한다. 주기 감시 `TickTengiCycle`도 background 경로에서 배열을 읽는다. 허용·기간 배열은 일반 bool·int이며 팝업의 15개 항목 갱신과 이 읽기를 하나의 공통 잠금으로 묶는 코드는 확인되지 않았다. 쿨다운 값은 항목별 atomic이지만 15개 항목 전체를 한 번에 게시하는 동작은 아니다. 실제 호출이 겹치는지는 실행하지 않았다.

기간 설정은 실행 파일 기준 `+0x2E98BC8`에서 얻은 관리자 슬롯 `+0x58A670 + slot*8`의 객체 `+0x12`에 16비트 값을 쓴다. 주기 감시는 별도로 현재 전기 data의 ID에 해당하는 같은 관리자 슬롯이 그 data를 가리키는지 확인하고 data `+0x12`를 읽는다(`TengiCave.cpp:315-329, 689-721`). 두 관리자가 같고 현재 ID가 설정 대상 슬롯이면 같은 주소가 될 수 있다. 같은 파일의 PDB 분석 주석은 이 필드를 남은 시간이 아닌 효과 정의 값이라고 설명한다. 현재 코드가 이를 기간으로 사용한다는 사실과 게임에서의 의미는 구분해야 한다. 실제 주소 일치와 게임 효과는 확인하지 않았다.

현재 전기 주기 `s_cycle.earliest`는 전기 객체의 data 주소 또는 시작 월이 바뀐 것으로 관찰될 때 `시작 월 + 당시 기간`으로 계산한다. 같은 객체와 시작 월이 유지되는 동안 팝업에서 기간이나 허용 여부만 변경해도 이 분기는 기준을 다시 계산하지 않는다. 즉시 호출하는 기간 갱신은 게임 정의의 기간을 수정하는 별도 경로이므로, 이미 계산된 주기 기준이 그 호출만으로 새 값이 된다고 판단할 수 없다. 다른 전기 관찰이나 세션 초기화가 일어나면 다시 계산할 수 있다.

회귀 조건은 편집 후 닫기·재열기, 저장 실패, 0과 -1 및 경계값, 15개 항목 게시 중 background 판정, 현재 전기 진행 중 기간 늘리기·줄이기와 허용 OFF, 새 전기·세션 전환이다. 실제 전기 발생과 스레드 순서는 확인하지 않았다.

### 전기 허용 범위와 후보 판정

15개 모두 허용이고 별도 쿨다운이 없으면 목록 detour는 원래 목록 함수를 그대로 호출한다. 모두 허용인 mask는 관리 15개 이외 ID도 허용으로 취급한다. 하나라도 끄면 관리 슬롯 중 체크된 ID만 허용하며, 최종 발동 detour도 현재 mask를 다시 확인한다(`TengiCave.cpp:490-511, 548-595`). 따라서 전체 허용에서 하나를 끄는 변화는 해당 항목뿐 아니라 관리 목록 밖 ID의 허용 여부도 바꾼다.

필터가 준비된 상태에서 후보 조건 detour는 목록 생성 문맥 밖에서도 읽을 수 있는 관리 ID의 쿨다운 적용을 먼저 시도하고 실패하면 false를 반환한다. 목록 문맥에서 원본 조건을 통과한 후보가 하나도 없으면 게임이 별도 조건 검사 없이 추가할 수 있는 ID 23 fallback까지 목록에서 지운다. 쿨다운 설정·복구는 해당 후보가 게임 판정 경로를 지날 때 수행하며, UI 변경이 저장된 즉시 모든 게임 객체에 반영되는 구조가 아니다. 이 내용은 hook이 설치된 코드 경로의 정적 관찰이며 실제 게임 결과는 확인하지 않았다.
쿨다운은 관리 후보의 data `+0x35` 한 바이트에 적용한다. 활성 중 현재 값이 마지막 기록과 다르면 그 값을 새 원본으로 보관한 뒤 설정값을 쓴다. 설정이 -1이거나 해당 전기를 허용하지 않으면 후보 판정 시 현재 값이 마지막 기록과 같을 때만 원본을 복구하고 active를 내린다(`TengiCave.cpp:431-492`). 설정을 바꾼 뒤 해당 후보가 다시 판정되지 않으면 이 경로의 복구도 일어나지 않는다. 주소가 바뀌면 이전 주소의 기록을 버리고 새 주소를 처리한다. 이 상태 배열을 일괄 복구하는 호출은 해당 파일에서 찾지 못했다. 실제 게임 객체의 변경이나 종료 시 값은 확인하지 않았다.

### 전기 필터의 부분 설치와 롤백 소유 범위

`TengiCave.cpp:614`는 3개 대상의 예상 원본 바이트 등을 확인한 뒤 `MH_CreateHook`을 순서대로 호출하고 성공한 개수만 `created`에 센다. 생성이 중간에 실패하면 성공한 앞쪽 등록만 제거 대상으로 삼는다. 배속의 `MH_CreateHookApiEx` 실패 경로와 달리, 생성에 실패한 충돌 대상 자체는 이 반복문에서 제거하지 않는다.

세 등록을 모두 만든 뒤 원본 trampoline 세 개와 보조 함수 포인터를 설정하고, 세 훅을 순서대로 활성화한다. 모두 성공했을 때에만 `s_allowedFilterReady`를 true로 게시한다. 그 전 실행된 detour는 원본 경로로 위임한다. 중간 활성화 실패 시 생성된 세 대상의 비활성화·제거를 시도하며, 비활성화가 성공하거나 이미 비활성인 경우에만 제거한다. 제거 반환값은 확인하지 않는다. 이 코드에서 이미 진입한 detour가 원본 trampoline 호출을 마쳤는지 별도로 기다리는 처리는 보이지 않는다.

회귀 조건은 각 생성·활성화 단계 실패, 같은 MinHook 대상의 기존 등록, 설치 중 게임 호출과 ready 게시 전 원본 위임, 롤백과 실행 중 callback의 겹침이다. 실제 경합·callback 종료 시점은 확인하지 않았다.
