# P0 5번 책략·전투 세대 조사

기준: S8RPKCheats `068ca1d881edf870f7cf06f935cf50e286004af8`. 소스상 상태 전이와 쓰기 경로이며 실제 전투 hook의 스레드·재진입·객체 소멸 순서는 검증하지 않았다.

## 조기 UI 준비와 설정

- `Source.cpp`는 저장된 `bStratagemFiveEnabled`를 조기에 읽어 OFF면 bridge 준비를 건너뛰고 ON이면 렌더 초기화 전에 시도한다. 실제 조건과 대기 치환은 [시작·종료 조사](P0_Lifecycle.md)를 따른다.
- `PrepareStratagemFiveUiBridge` (`StratagemSlotProbe.cpp:4258`)는 초기 레이아웃, 버튼 후처리, reset, 선택 bound/runtime, pre-callback, callback loop 등 7개의 준비 결과를 모두 확인한다. 일부가 실패해도 이 함수에서 이미 성공한 모든 hook을 일괄 해제하는 코드는 보이지 않는다.
- 일반 설정 로드 (`Config.cpp:362`)는 `SetStratagemFiveFeature`에 저장값을 전달한다. 세부 target·effect·power·duration·range·heal 값은 별도로 로드해 `SetSpell5CustomSettings`에 전달한다.

## 요청·전투·세션 상태

- `SetStratagemFiveFeature` (`StratagemSlotProbe.cpp:5495`)는 desired 상태를 기록하고 현재 전투를 직접 수정하지 않는다. `UpdateStratagemFiveBattleLifecycle`은 전투 중이거나 안전한 비전투 상태가 아니면 동기화하지 않고, 확인된 비전투 상태에서 desired와 effective가 다를 때 동기화한다. 현재 전투를 건너뛰는 gate는 다음 안전 경계에서 해제한다.
- ON 동기화 (`ApplyStratagemFiveDesiredStateSafe`)는 bridge·데이터·metadata·count 설정 함수를 호출한 후 effective를 true로 둔다. 개별 호출의 반환값을 ON 성공 판단에 합산하지 않는다. OFF는 metadata·count·데이터 해제의 반환값을 합산하지만 effective는 false로 둔다. 따라서 desired/effective만으로 모든 설치가 성공했다고 단정할 수 없다.
- 안전 경계 호출자는 `ApplyStratagemFiveDesiredStateSafe`의 반환값을 사용하지 않고 skip gate를 해제한다. ON 개별 준비 또는 OFF 해제가 실패해도 effective가 요청값으로 기록되면, 이후 요청값이 유지되는 동안 이 함수의 `desired != effective` 조건만으로는 같은 동기화를 재시도하지 않는다. 개별 데이터 기능의 별도 재시도 경로와는 구분한다.
- `Menu_impl.inc:405`는 p1이 0으로 전환되거나 변경되거나 gameBase가 바뀌면 전투 캐시와 책략 UI·데이터의 세션 상태를 폐기한다. `ResetBattleSessionRuntime`은 세대 카운터를 올리고 이전 전투 객체 주소와 캐시를 비운다. 이전 세이브 주소를 통해 복원하지 않는다.
- `BattleMonitor.cpp:474,863`의 전투 종료 경로는 UI battle-local 상태와 데이터 레코드를 각각 reset한다. UI reset은 gate를 닫고 이전 sidecar 표시 중지와 객체 참조 폐기를 시도하지만 프로세스 단위 hook과 ON 요청은 유지한다. 세션 reset은 이전 세이브의 데이터 주소를 통해 복구하지 않고 버린다.

## 책략 레코드와 게이지

- `Spell5HealProbe.cpp:286`은 실제 5번 레코드의 원본을 보관하고 2번 레코드를 복사한 뒤 사용자 설정을 적용해 5번에 쓴다. 테이블이 아직 준비되지 않거나 쓰기에 실패해도 ON 요청을 유지하고 이후 재시도를 기다리는 경로가 있다. 4번 레코드는 이 경로에서 교체하지 않는다.
- `SetSpell5CustomSettings` (`Spell5HealProbe.cpp:249`)는 입력을 정규화하고 이미 적용된 주소가 유효하면 현재 5번 레코드에 설정을 즉시 반영한다. 이것은 ON/OFF 체크 상태의 비전투 동기화와 다른 경로다. 저장된 주소의 세대와 쓰기 문맥을 이관 시 별도로 확인한다.
- 데이터 OFF는 유효하다고 판단한 주소에 보관한 원본 복원을 시도한 뒤 내부 주소와 적용 상태를 지운다. 전투 종료는 주소가 유효할 때 원본 복원을 시도하지만 ON 요청은 유지한다. 세션 변경은 이전 주소에 복원하지 않고 상태를 폐기한다.
- 공격·수비 책략 게이지 최대화는 `StratagemGaugeMax.cpp:109`의 별도 direct code cave다. 기대 원본 7바이트를 확인하고 설치하며 두 진영의 체크 값을 독립적으로 사용한다. OFF는 원본 복구 후 cave를 해제한다. `UpdateStratagemGaugeMax`는 현재 아무 작업을 하지 않는다.

## 이관 회귀 조건

조기 설정 OFF·ON과 부분 bridge 실패, 전투 중 체크 변경, 비전투 경계 반영, 세부 설정의 즉시 적용, p1→0→동일 주소와 다른 세이브 전환, 전투 종료·중간 전투 로드, 테이블 재생성과 원본 복원 실패, 공격·수비 게이지 조합 및 callback 실행 중 hook 해제를 확인한다. 기존 기능의 성공 로그나 플래그만으로 hook 준비와 객체 수명을 증명하지 않는다.

## 전투 준비와 부대 목록 변화

`BattleMonitor.cpp:43`의 세션 reset은 세대 카운터를 증가시키고 준비 flag, 캐시 주소, 전투 유닛 주소와 특수능력·환경 캐시를 버린다. 이전 세이브 소유 주소를 통해 복원하지 않는다. `Menu_impl.inc`에서 P1이 무효가 되거나 주소가 바뀌거나 gameBase 주소가 달라질 때 이 경로를 호출한다. 같은 숫자 주소가 중간 무효 상태 없이 재사용되는 경우는 이 주소 비교만으로 구분하지 못한다.

전투 감시는 유닛 목록과 날짜 주소를 전투 식별자로, 유닛 수와 유효 유닛·멤버 주소의 해시를 roster 식별자로 사용한다. 레코드 미준비 또는 식별 주소 변경이면 준비 상태를 내리고 관련 캐시를 지운다. 날짜·유닛 목록·게임 상태와 P1 세션 및 적어도 한 유효 유닛/멤버가 준비된 상태에서 전투 식별 주소가 1초 유지되면 runtime ready로 표시한다. 유닛 수나 roster 해시만 바뀌는 것은 이 1초 타이머를 다시 시작하지 않는다. 유닛 수나 roster 해시가 바뀌고 캐시가 만들어져 있었다면 특수능력 캐시를 지우고 `s_isCacheBuilt`를 false로 바꾼다. 이후 준비된 전투 경로에서 캐시 생성과 `UpdateBattleUnitSkills`가 다시 실행되므로 원군 등 목록 변화는 전법 횟수 재주입을 유발할 수 있다. 설정 맵만 바뀌고 목록 식별자가 같을 때는 이 조건이 발동하지 않는다.

전투 상태 판정이 불확실할 때는 쓰기를 보류하고, 비전투가 확인되면 전투 캐시 및 battle-local 책략 상태를 정리한다. process-wide hook을 전부 제거하는 것과 이 객체 상태 폐기는 별개다. 회귀 조건은 P1 0 경유·직접 변경·동일 주소 재사용, 목록 주소 변경과 부대 수/멤버 포인터 변경, 일시적 읽기 실패, 안정화 1초, 원군 도착 시 전법 재주입과 이미 사용한 횟수다.

전투 활동 판정은 heartbeat 또는 유효 날짜 또는 유효 유닛 목록 중 하나로 성립하며, runtime ready는 이보다 엄격하다. 준비되지 않은 전투에서는 heartbeat 기록을 지우고 이후 경로를 건너뛰지만, 책략 5번 전투 lifecycle 갱신은 그 준비 검사보다 앞서 호출된다. 위 조건은 정적 소스 조사 결과다.

## 준비 판정의 실패와 재관측

`MonitorBattleStatus`는 세션 reset 요청을 다음 감시 호출에서 소비해 준비 주소·타이머와 전투 처리 flag를 초기화한다. 이 분기에서는 이전 roster 수·해시를 직접 0으로 만들지 않지만 캐시 생성 flag는 false로 내린다. 확정 비전투 분기에서는 roster 수·해시까지 0으로 만든다. `gameBase==0`이나 상태가 불확실한 분기는 준비 상태와 타이머를 내리고 반환한다. 특히 불확실 상태는 이전 전투 객체를 통해 복원하거나 캐시를 정리하지 않고 쓰기를 보류한다.

native 상태가 음수로 일시 판독된 분기는 `s_battleRuntimeReady`와 안정화 시각은 초기화하지만 `s_isCacheBuilt`와 roster 서명은 유지한다. 이후 같은 목록·날짜·유닛 서명이 유효하게 돌아오면 1초 안정화를 다시 거쳐도 일반 감시의 캐시 생성 flag는 그대로 true일 수 있다. 이때 설정 맵 변경만으로 일반 감시 캐시를 새로 만들지는 않는다. 준비 전 fallback은 별도로 같은 특수능력 캐시를 생성할 수 있으므로, 실제 재생성 여부는 두 경로의 호출 순서에 달려 있다(`BattleMonitor.cpp:460-467, 635-661`, `Menu.cpp:57-215`). 실제 전환은 실행하지 않았다.

유닛 수 또는 주소 서명만 바뀌고 날짜·목록 base가 같으며 준비 조건을 계속 만족하면 roster 변경 분기는 특수능력 캐시와 구축 flag만 지운다. 이 분기는 `s_stableSince`를 초기화하지 않으므로 이미 runtime ready였던 경우 1초 안정화를 새로 기다리지 않고 같은 감시 호출의 이후 캐시 구축 경로에 들어갈 수 있다. 반면 준비 조건 실패나 날짜·목록 base 변경은 별도 분기에서 안정화를 다시 시작한다. 실제 호출 간격과 게임 결과는 확인하지 않았다.

준비 검사에서 모든 목록 슬롯의 포인터 위치는 읽기 가능해야 하지만, 슬롯이 가리키는 개별 유닛이나 멤버가 유효하지 않으면 그 항목을 건너뛴다. 하나 이상의 유닛·멤버 쌍이 유효해야 준비되며 해시는 유효 쌍의 주소들로 계산한다. 해시에 넣는 값은 유닛 주소와 구성원 컨테이너 주소이며, 그 안의 무장 ID나 스킬 설정 내용은 포함하지 않는다. 따라서 컨테이너 주소와 유닛 수가 유지된 채 멤버 ID 또는 설정만 바뀌는 경우 그 변화 자체는 이 서명을 바꾸지 않는다. 이 검사는 페이지 읽기 가능성과 포인터 구조의 정적 조건이며 게임 객체의 소유 세대나 쓰기 가능성을 증명하지 않는다. 회귀 조건은 일부 유닛 무효·모든 유닛 무효, 슬롯 자체 읽기 실패, 일시적 불확실 상태, 세션 reset 직후 같은 roster 값의 재관측과 실제 객체 교체다.

## 함선 병기화의 활성 부대 캐시

`BattleEnvironment.cpp:145`의 함선 병기화는 일반 환경 갱신에서 최대 300ms마다 실행된다. 물 지형 11·12에서는 다섯 전법 필드를 4로 쓰고 현재 부대 주소와 `s_lastTriggered=false`를 저장한다. 다른 지형에서는 활성 부대 주소가 바뀐 경우에만 최대 세 무장의 `0x1009` 설정을 읽어 결과를 캐시하고, 결과가 참이면 다섯 필드를 8, 거짓이면 4로 쓴다.

따라서 같은 활성 부대의 설정이나 멤버가 바뀌어도 주소가 그대로면 이전 결과를 사용한다. 또한 같은 부대가 물에서 육지로 이동할 때 물 분기가 저장한 false를 재사용하므로 다른 부대로 바뀌기 전에는 그 부대의 설정을 다시 읽지 않는 코드 경로다. `ClearBattleEnvCache`는 전법·지형 주소와 지형 유닛 캐시는 지우지만 이 함수 내부의 정적 활성 부대·결과는 초기화하지 않는다. 같은 주소가 다음 전투에서 재사용될 때도 별도 확인이 필요하다.

발동·해제 로그와 `s_lastAppliedVal` 갱신은 다섯 필드의 쓰기 성공 여부를 확인하지 않는다. 각 필드는 `WriteByteIfDiff`로 매 호출에서 현재 값과 비교하므로, 후속 호출이 같은 분기에 도달하면 값이 다른 필드는 다시 쓰기를 시도한다. 초기 주소 해석에 실패한 호출도 300ms 제한 시각을 먼저 갱신한다. 로그의 상태와 실제 다섯 바이트가 일치하는지는 별도다.

회귀 조건은 물↔육지 전환, 같은 부대의 멤버·특수능력 변경, 부대 선택 전환, 전투 reset 뒤 같은 주소 재사용 및 전법 주소 재생성이다. 이 결과는 정적 코드 추적이며 게임에서 재현하지 않았다.

## 지형 능력 캐시와 OFF 복구

`BattleEnvironment.cpp`의 지형 유닛 캐시는 목록 주소·유닛 수가 달라지거나 캐시가 비었을 때 재구성한다. 각 항목에는 유닛 주소, 지형 바이트 주소, 병종 값을 보관한다. 지형 값은 적용 때 다시 읽지만 병종과 지형 포인터 체인은 다시 해석하지 않는다. 전투 감시가 같은 목록 주소·수에서 멤버 해시 변경을 감지하면 특수능력 캐시는 지우지만 그 분기에서 지형 환경 캐시는 지우지 않는다. 따라서 같은 수의 유닛 교체나 병종·지형 객체 변경 시 오래된 항목을 사용할 수 있는 정적 경로다.

ON에서는 기준 능력치와 지형 보너스로 결과를 계산해 쓰고, 공격·방어 전용 모드는 나머지 두 능력치를 현재 기준값으로 쓴다. OFF 전환은 `s_terrainBonusActive`를 먼저 false로 바꾼 뒤 현재 목록이 유효하면 캐시 유닛에 기준값을 쓰고 캐시를 지운다. OFF 시 목록을 읽을 수 없으면 복구 없이 flag가 내려가므로 다음 tick에서 같은 OFF 복구를 다시 시도하지 않는다. 전투 환경 캐시 초기화는 이 지역 정적 flag 자체를 초기화하지 않는다.

회귀 조건은 같은 수의 부대 교체, 병종·지형 포인터 변경, 두 보정 모드 전환, OFF 시 목록 부재·부분 쓰기 실패, 전투 종료와 새 세이브 주소 재사용이다. 실제 게임에서 발생 여부는 확인하지 않았다.

## 날씨 옵션과 고정 기본 쓰기

날씨 UI의 간단·대폭 체크는 사용자가 한쪽을 켤 때 다른 쪽을 끄고 저장한다. 기본 설정 로더는 두 bool을 각각 읽으므로 파일에서 둘 다 true인 경우를 이 UI 상호배타 처리만으로 배제할 수 없다. `UpdateBattleEnvironment`는 대폭이 켜지고 날씨·바람 포인터가 모두 있으면 화계·낙석·매복 및 지형 필드를 날씨·바람에 따라 쓴다. 대폭이 꺼졌거나 포인터 하나가 없으면 그 필드에 코드의 고정 기본값을 쓴다.

별도의 공통 화계·수계 값은 간단 또는 대폭 중 하나가 켜져 있고 날씨 포인터가 있으면 날씨에 따라 변경하며, 그 외에는 고정 기본값을 쓴다. 따라서 대폭에서 바람 포인터만 없는 경우 대폭 전용 필드는 기본값을 쓰면서 공통 화계·수계는 날씨에 따라 바뀔 수 있다. 두 옵션이 모두 OFF여도 환경 갱신이 이 지점까지 도달하면 원래 저장값이 아닌 고정 기본값들을 기록한다. 날씨 UI 체크 변경 자체는 설정 저장만 하며 실제 게임 값 변경은 다음 환경 갱신 경로에 달려 있다.

회귀 조건은 OFF·간단·대폭·파일에서 둘 다 ON, 날씨 또는 바람 포인터 부재, 대폭→간단·OFF 전환, 다른 기능이 같은 필드를 바꾼 상태 및 쓰기 실패다. 실제 게임 동작은 실행하지 않았다.

## 공성 두 모드의 초기화와 단계 지연

전투 준비 후 전쟁 기능을 새로 적용하는 경로에서 `bSiegeWarfare`가 true면 두 모드의 runtime 상태를 reset하고 1칸 setter를 호출한다. 그렇지 않고 `bSiegeWarfare2`가 true면 같은 reset 후 2칸 setter를 호출한다. 이후 주기 갱신에서는 두 flag를 각각 검사하므로 설정 파일에서 둘 다 true라면 초기 setter 선택은 1칸 우선이지만 두 update가 모두 실행될 수 있다. UI의 상호배타 체크와 파일 로드는 별개다.

두 모드의 OFF setter는 같은 12개 이동 비용 위치에 255를 쓰지만 자기 모드의 적용 flag만 지운다. 따라서 두 모드가 모두 준비된 상태에서 한 모드만 OFF하면, 남은 모드의 이동 비용 적용 flag는 true인 채 실제 비용은 OFF setter가 쓴 255가 될 수 있다. 남은 모드의 update는 그 flag가 유지되는 동안 `ApplyMoveCostOnce`를 다시 호출하지 않는다. 이 설명은 해당 주소 쓰기가 성공하고 다른 reset·쓰기 없이 진행되는 코드 순서에 한정한다.

두 flag가 모두 켜진 상태에서 두 모드의 준비 단계가 끝나고 같은 날짜에 각각 회복을 처리하면, `BattleMonitor.cpp:817-820`은 1칸 update 다음 2칸 update를 호출한다. 두 모드는 이전 처리일을 별도로 보관하고 동일한 수비 세력·여울 유닛을 검사하므로, 첫 회복 뒤에도 병력이 최대보다 적으면 같은 유닛에 두 번째 회복이 적용될 수 있다. 두 단계의 준비 시점이나 실제 게임에서 이 조건이 성립하는지는 확인하지 않았다.

각 update는 이동 비용과 타일 변경에 같은 모드별 마지막 시도 tick을 사용해 각각 1초 간격으로 시도한다. 이동 비용 성공 직후에는 같은 tick 값 때문에 타일 변경까지 다음 간격을 기다리며, 회복은 두 단계가 완료된 뒤 처리한다. `ResetSiegeBattleRuntime`은 양쪽 적용 flag와 이전 날짜를 지우지만 update 함수 내부의 마지막 시도 tick은 지우지 않는다. reset 후 이전 객체의 타일을 복원하지 않는 정책도 앞서 기록한 OFF와 구분한다.

회귀 조건은 두 flag 동시 ON, 각 단계 실패·부분 성공, reset 직후 1초 경계, 단계 대기 중 전투 종료·로드 및 첫 회복일이다. 정적 분석이며 게임에서 타이밍을 측정하지 않았다.

## 공격·수비 책략 게이지 hook의 실제 쓰기와 소유

`bMaxAttackStratagemGauge`, `bMaxDefenseStratagemGauge`는 별도 설정 키이지만 `SetStratagemGaugeCapture`의 hook 하나를 공유한다. 메뉴는 둘 중 하나라도 ON이면 설치 상태를 유지하고 마지막 ON을 끌 때 해제를 요청한다. 설치 실패 시 메뉴는 방금 바꾼 한 flag만 되돌리고 저장하지 않는다. 설정 로드는 두 값을 읽은 후 하나라도 켜져 있으면 설치를 시도하며 실패 시 두 flag를 모두 false로 바꾼다. 설정에서 둘 다 OFF인 경우 로드 경로는 해제를 호출하지 않는다.

코드 cave는 게임의 해당 비교 지점이 **호출될 때마다** 진영 byte가 0이면 공격, 1이면 수비 flag를 읽고 켜진 진영의 게이지에 10000을 쓴 다음 원래 비교 명령을 실행한다. 다른 진영 값이나 해당 flag OFF면 쓰지 않는다. 따라서 메뉴의 ‘시작 최대’ 문구와 별개로, 이 코드는 최초 1회만 쓰는 조건을 두지 않는다. 이 지점이 게임에서 언제·몇 번 실행되는지는 정적 소스만으로 확인할 수 없다. `BattleMonitor`의 주석은 주기 쓰기를 설명하지만 실제 `UpdateStratagemGaugeMax` 본문은 비어 있다.

설치 과정에서 cave 생성 이후 `ApplyJmp`가 실패하면 `BuildGaugeSideCave`는 cave를 해제하지 않고 false를 반환하며, 호출자는 cave 주소를 0으로 지운다. 해제에서는 `RestoreBytes`가 실패 여부를 반환하지 않고, 호출자는 복원 성공을 확인하지 않은 채 cave를 해제하고 설치 상태를 지운다. 원본 보호 변경 실패 시 원본 코드가 cave를 계속 가리킬 가능성이 있다. 기준 자체 cpp/h/inc에서 setter의 호출은 설정 로드와 메뉴 두 항목뿐이며 정상 종료에서 별도로 해제하는 호출은 찾지 못했다. 게임 실행 중인 다른 스레드가 cave를 사용하지 않는지도 해제 경로에서 확인하지 않는다.

회귀 조건은 공격·수비 4가지 조합, 같은 전투의 게이지 소모 후 hook 재호출, 설정 로드 실패와 UI 실패의 차이, cave 할당 뒤 jump 설치 실패, 원본 복원 실패, callback 실행 중 마지막 옵션 OFF 및 모듈 정상 종료다. 위 내용은 정적 추적이며 실제 실행·경합 결과가 아니다.

### 5번 책략 설정 팝업의 편집과 취소

`MenuSectionsWar.cpp:390`에서 설정 버튼을 누를 때 현재 설정을 별도 `s_stratagem5Edit`에 복사하고 팝업을 연다. 효과를 바꾸면 선택 종류에 따라 위력·기간을 조정하며, 같은 팝업에서 대상·효과 두 개·범위·추가 회복을 편집한다. `현재 기본값 복원`은 이 편집 복사본에 `Spell5CustomSettings{}`를 대입할 뿐 즉시 setter나 저장을 호출하지 않는다. `적용 및 저장`은 setter에 편집값을 넘기고 setter가 정규화한 값을 다시 읽은 뒤 설정을 저장하고 팝업을 닫는다. `취소`는 팝업을 닫으며 편집 복사본을 설정에 반영하지 않는다. 다시 열 때 현재 설정에서 편집값을 새로 복사한다.

### 지형 유닛 캐시의 부분 수집과 적용 계산

`BuildTerrainUnitCache`는 목록 주소·부대 수를 먼저 기록한 다음 각 슬롯의 부대, 병종 및 지형 포인터 체인을 검사한다. 실패한 슬롯은 건너뛰고 유효한 항목만 벡터에 넣는다. 벡터가 완전히 비면 다음 조건 충족 갱신 때 다시 만들지만, 한 개라도 수집됐으면 목록 주소와 부대 수가 유지되는 동안 실패했던 나머지 슬롯이 나중에 유효해져도 그 이유만으로 다시 수집하지 않는다. 이미 수집된 항목의 병종 값도 생성 시 스냅샷이며 지형 값은 보관한 지형 주소에서 매번 읽는다.

유효한 항목은 전역 표에서 병종·지형 보너스를 읽고 각 기준 16비트 값에 `(100 + 보너스) / 100`을 정수 연산으로 적용해 0~32767로 제한한다. 공방만 모드에서는 전투력에만 보너스를 쓰고 무력·지력은 현재 기준값을 기록한다. 전체 모드에서는 세 값에 같은 비율을 적용한다. OFF는 이전에 저장한 보정 전 값이 아니라 그때 읽은 기준 필드를 세 결과 필드에 쓴다.

이 지형 분기보다 앞에서 전법 테이블 주소를 찾지 못하면 환경 함수가 반환하므로, 그 호출에서는 OFF 복구 분기에도 도달하지 않는다. 지형 분기까지 도달한 후 목록이 유효하지 않은 경우에는 앞 절처럼 OFF 상태를 내린 채 복구를 건너뛴다. 회귀 조건은 초기 슬롯 일부만 유효한 경우와 나중에 준비되는 경우, 목록 주소·개수는 같고 병종이나 지형 포인터만 바뀐 경우, 음수 보너스의 정수 계산, 두 모드 전환, 전법 테이블 부재 및 OFF 복구 시 목록 부재다. 게임에서 재현한 결과는 아니다.
