### 연회·중개 사용 비트 유지

두 tick은 `MonthCapture.cpp`의 공통 resolver로 실행 파일의 시나리오 포인터를 읽고 연도 2바이트·월 1바이트 주소가 유효한지 확인한 뒤 각각의 사용 비트 주소를 해석한다. 연·월 값 자체가 유효한 날짜인지는 검사하지 않는다. 대상 비트가 이미 0이면 쓰지 않고 성공을 반환하며, 1이면 바이트를 읽은 값에서 해당 bit만 지워 쓴 뒤 다시 읽어 bit가 0인지 반환한다. 메뉴의 ON 직후 호출과 background의 반복 호출은 이 반환값을 사용하지 않는다. OFF는 이후 반복을 중지하며 이전 사용 비트를 복원하지 않는다.

비트 변경은 원자적 연산이 아닌 바이트 읽기 후 쓰기다. 읽은 뒤 다른 스레드가 같은 바이트의 다른 비트를 바꾸면 이 코드의 이전 바이트 값으로 덮일 수 있다. 메뉴와 background에서 같은 tick이 겹칠 수 있으며 공통 직렬화 잠금은 두 함수에 없다. 보호 복원 성공은 반환값에 반영하지 않는다. 실제 호출 스레드 간 겹침과 게임 결과는 확인하지 않았다. 회귀 조건은 다른 비트의 동시 변경, resolver 실패·비트 쓰기 실패, ON 직후와 반복 tick, OFF 이후 사용 및 시나리오 교체다.

## 주점 청부 4칸 유지

`TavernMonitor.cpp`는 51개 도시의 각 4개 슬롯을 두 번 순회한다. 첫 패스는 현재 읽을 수 있는 name/data 포인터 쌍을 수집하고, 직전에 자체 주입한 쌍과 다른 유효 쌍을 해당 슬롯의 원본 백업 및 다른 도시에 빌려줄 후보로 보관한다. 두 번째 패스는 두 포인터가 모두 0인 슬롯만 복원·보충 대상으로 삼는다. 둘 중 하나만 비었거나 포인터를 읽지 못한 슬롯은 채우지 않는다. 도시 안에서 같은 data 포인터를 중복 사용하지 않고, 빌려온 항목은 원래 도시·슬롯에서 같은 쌍이 살아 있으며 자체 주입 항목이 아닌지 다시 확인한다.

최초 활성화가 내정 상태일 때와 평정→내정 전환 후 2.5초 안정화가 끝난 틱은 다른 도시의 현재 원본 청부를 먼저 찾고, 없으면 기존 백업을 사용한다. 평상시 내정 유지에서는 기존 백업을 먼저 시도한다. 평정 중에는 청부를 쓰지 않고, 중간 게임 상태는 마지막 유효 상태를 바꾸지 않는다. OFF는 백업과 추적 상태를 지우지만 이미 주입한 슬롯의 원래 값을 복구하지 않는다. 도시 배열 주소가 달라지면 추적 상태를 지우고 그 틱은 반환한다. 같은 주소가 다른 게임 세대에 재사용되는 경우는 주소 비교만으로 구분하지 못한다.

쓰기 함수는 두 포인터를 한 보호 변경 구간에서 순서대로 쓰고 읽어 확인하며 실패 시 이전 쌍의 복구를 시도한다. 보호 복원과 실패 시 복구의 성공 여부는 반환값으로 확인하지 않는다. 읽기 가능 여부 캐시는 유지 작업마다 초기화되며 한 작업 안에서 재사용된다. 회귀 조건은 51×4 경계, 한쪽만 비어 있는 슬롯, 원본과 주입된 쌍, 후보 중복, 평정 전환·2.5초 대기, OFF 후 잔존 값, 원본 소멸, 보호 변경·복구 실패와 도시 배열 재사용이다. 이는 정적 코드 추적이며 게임 내 청부 생성을 실행해 확인하지 않았다.

`WriteRequestPair`는 두 포인터의 오프셋 차이 8이 `sizeof(uintptr_t)`와 같지 않으면 보호 변경 전에 실패한다. 따라서 `uintptr_t`가 4바이트인 Win32 구성에서는 이 함수의 청부 쓰기가 항상 거부되는 코드다. x64 구성에서만 이 조건이 성립한다. 이는 소스와 대상 포인터 크기의 대조이며 어느 구성도 빌드하거나 실행하지 않았다.

이 함수의 복구용 `oldName`과 `oldData`는 0으로 초기화된 뒤 차례로 읽힌다. 이전 값 두 개를 모두 확보하기 전에 접근 예외가 발생해도 예외 처리기는 두 변수를 모두 원래 슬롯에 기록하려 시도하므로, 아직 읽지 못한 쪽에는 초기값 0이 사용된다. 보호 복원 실패도 `ok` 반환값에 반영되지 않는다. 이 조건의 실제 발생이나 메모리 결과는 확인하지 않았다.

## 군주 이동 제안

`CouncilCompactSectionBase.h:334`의 체크박스는 ON을 모드 2, OFF를 모드 0으로 `SetRulerTransferProposalMode`에 전달한다. 실패하면 `IsRulerTransferProposalApplied`로 표시할 상태를 정하고, 알림과 일반 설정 저장 후 독립 설정 저장을 호출한다. 저장 함수의 반환값은 확인하지 않는다. 일반 설정 저장은 이 키를 지우므로 메뉴 경로는 그 직후 별도로 키를 다시 기록한다.

setter가 성공하면 자체적으로 독립 설정 저장을 호출한다(`RulerTransferProposal.cpp:141-173`). 따라서 메뉴의 정상 변경은 setter 내부 독립 저장 → 일반 설정 전체 저장 → 메뉴의 독립 저장 순서이며, 각 독립 저장 결과는 무시한다. 일반 저장이 실패하더라도 메뉴는 마지막 독립 저장을 시도한다. 일반 저장을 수행한 다른 메뉴에서는 마지막 단계가 없어 이 키가 다시 사라질 수 있다.

`RulerTransferProposalBootstrap.cpp`의 전역 객체 생성자는 `LoadRulerTransferProposalPreference`를 호출한다. 이 경로는 설정 파일에서 키가 있는 줄에 `true`가 포함됐는지 읽고 true면 모드 2, false면 모드 0으로 적용한다. 키나 파일이 없으면 모드 0 설정을 시도하고 false를 반환한다. 읽기에 성공한 경우도, 파일은 있지만 키가 없어 OFF로 처리하는 경우도 setter가 성공하면 독립 설정 저장을 다시 시도한다. 파일을 열 수 없거나 `config_end`가 없으면 독립 저장은 실패하고 setter는 그 결과를 반환하지 않는다. 전역 객체 초기화 시점의 호출이며, 별도 worker를 만들거나 데이터 준비를 기다리는 코드는 없다. 생성자가 적용 실패를 전달하거나 재시도하는 경로도 없다.

`RulerTransferProposal.cpp:141`의 setter는 실행 파일 기준 주소와 두 원본 바이트 구간을 확인한 다음 상대 CALL을 인근 thunk로 바꾼다. thunk는 RDI·RSI를 전역 변수에 저장하고 hook으로 이동한다. hook은 원래 함수를 먼저 호출하며, 원래 반환값이 0이 아니고 모드별 역할 조건과 게임 객체 관계가 맞으면 0을 반환한다. 모드 1은 역할 4, 모드 2는 역할 2 또는 4에만 적용한다. 이 검사에 해당하지 않거나 메모리 읽기에 예외가 생기면 원래 결과를 돌려준다. 공개 메뉴와 파일 로드는 모드 2만 선택하지만 setter는 모드 1도 받는다.

설치·복구의 상태도 이관 시 구분한다. 최초 ON은 두 원본 구간 검증 후 thunk를 한 번 할당하고 CALL을 기록한다. CALL 기록이 실패해도 할당된 thunk 주소는 유지되어 다음 시도에서 재사용한다. 이미 적용된 상태에서 모드만 변경하면 원본 구간을 다시 검증하거나 CALL을 다시 쓰지 않는다. OFF는 `gApplied`가 참일 때 현재 CALL 바이트를 비교하지 않고 고정 원본 5바이트를 쓴다. 쓰기 실패 시 적용 표시와 기존 모드를 유지하고 false를 반환하며, 성공 시 적용 표시와 모드를 내린다. OFF 뒤에도 thunk 주소는 유지된다. 이 파일에는 thunk 해제 경로가 없다.

thunk가 저장하는 RDI·RSI는 호출별 지역값이 아니라 공통 전역값이며 hook은 원래 함수를 호출한 뒤 이 값을 읽는다. 따라서 중첩 또는 동시 호출이 실제로 가능한지는 게임 실행 문맥을 확인해야 한다. 원본 소스에는 해당 값의 호출별 분리나 동기화가 없다. 이관 검증에는 설치 실패 후 재시도, 적용 중 모드 변경, OFF 쓰기 실패와 호출 중 OFF를 포함한다.

OFF는 `gApplied`가 true일 때 현재 CALL이 이 기능의 패치인지 확인하지 않고 고정된 원본 바이트를 쓴다. 쓰기 함수가 실패를 반환하면 `gApplied`와 모드를 바꾸지 않고 설정도 저장하지 않는다. 성공하면 `gApplied`를 내린 후 모드를 0으로 바꾼다. ON에서 이미 적용된 상태라면 원본 검사나 CALL 쓰기 없이 모드만 바꾼다. 0~2 밖의 모드 값은 OFF로 처리한다. 설치 시 할당한 thunk는 재사용을 위해 유지되며 이 소스에는 해제 경로가 없다. 설치 실패 시에도 이미 할당된 thunk는 남는다. 쓰기는 명령 캐시를 비우지만 보호 속성 복원 결과는 검사하지 않는다. 설정 저장 실패는 setter의 성공 여부에 반영되지 않는다.

실행 문맥은 전역 생성자가 실행되는 스레드, 메뉴 렌더 호출 스레드, 게임의 해당 CALL을 실행하는 스레드로 나뉜다. 두 캡처 레지스터와 모드는 전역값이며 동기화가 없으므로 hook 동시 실행이나 설정 변경과의 경합을 이 코드만으로 배제할 수 없다. 실제 게임의 호출 스레드와 동시성은 미확인이다.

회귀 확인 항목: 저장된 ON/OFF와 누락 키, 로드 시 원본 불일치 및 재시도 부재, 역할 2·4와 다른 역할, 객체 관계가 일치하지 않는 경우, 모드 1 직접 호출과 재시작 시 모드 2 복원, 토글과 callback 동시 실행, 원본 복원 실패, 일반 설정 저장 뒤 키 유지 여부.

## 시나리오 수정

`MenuSectionsScenario.cpp:170`의 `bStartSetting` 체크박스와 기본 설정 적용은 `SetStartSetting`을 호출한다. setter는 lifecycle mutex 아래 이벤트와 worker를 만들고 세대 번호를 증가시킨다. worker는 시작 직후 한 번, 이후 정지 이벤트를 200ms씩 기다리며 `RunOnce`를 실행한다. OFF는 요청을 내리고 세대를 무효화한 뒤 이벤트를 알리고 worker 종료를 기다린다. 이벤트 또는 스레드 생성 실패는 내부 상태를 내리고 로그를 남기지만, 반환형이 `void`여서 메뉴의 체크 상태에 실패가 반영되지는 않는다.

`StartSetting_impl.inc:117`은 root의 연도가 0일 때만 다섯 조건을 검사한다. 0이 아니면 다섯 적용 flag를 초기화하고 끝난다. 조건이 맞을 때 수행하는 쓰기는 다음과 같다.

1. 두 관계 슬롯이 지정된 두 무장 주소와 특정 순서로 일치하면 값을 교환한다. 이미 교환된 상태도 인식한다.
2. 지정 군주 슬롯이 특정 무장 주소와 일치하면 두 기술 값을 각각 3과 4로 쓴다.
3. 두 무장 상태가 모두 200이면 세 번째 상태에 88을 쓴다.
4. 네 슬롯이 모두 23이면 네 슬롯 및 연관된 포인터·바이트 필드를 0으로 쓴다.
5. 두 상태가 모두 200이면 한 무장의 세력·도시 포인터를 다른 무장의 값으로 쓴다.

각 쓰기 helper는 주소와 보호 변경을 확인하지만 반환값이 없고, 호출자는 실제 쓰기 성공 여부와 관계없이 해당 flag를 설정한다. 여러 필드 변경은 순차 실행되며 세대가 중간에 무효화되면 이미 기록한 필드를 되돌리지 않는다. OFF는 worker와 내부 상태를 정리하며 게임 데이터의 변경을 원상 복구하지 않는다. 각 조건의 주소는 `StartSetting_impl.inc:142,215,242,268,313`에 있다.

같은 include에 과거 미발견 무장 처리 코드가 있지만 `StartSetting.cpp`가 실제 flag와 setter 이름을 매크로로 치환한다. 현재 공개 `SetUndiscoveredToRonin`은 별도의 watcher를 사용한다. 두 기능을 같은 worker로 합쳐 해석하지 않는다. 이관 회귀 조건은 연도 0 진입과 이탈, 다섯 조건의 일치·불일치, 각 쓰기 실패와 부분 적용, ON/OFF 중 worker 종료, 새 시나리오에서의 재적용, worker 생성 실패 시 UI 상태다.

## 보주 개방과 보조 보주 선택

`MenuSectionsDomestic.cpp:298`의 전체 개방은 `JewelSettings.cpp:398`을 호출한다. 34바이트 게임 비트맵에서 정의 마스크에 속한 비트만 ON이면 OR, OFF이면 AND NOT 한다. OFF는 기존 저장게임의 개별 개방 상태를 복구하지 않고 해당 정의 비트를 지운다. setter는 게임 주소 확인과 실제 기록보다 먼저 선호 상태를 바꾸므로 적용이 실패해도 선호 상태는 변경된다. 메뉴는 성공한 경우에만 설정을 저장한다. 설정 로드에서 OFF는 기존 비트맵을 지우지 않으며 ON은 즉시 적용을 시도한다. `Menu_impl.inc:457`의 background loop가 선호 ON일 때 250ms 간격으로 확인하고 개방 상태가 덮이면 재적용한다.

보조 보주 설정은 개별·계통·전체 선택을 지원한다. 선택은 8개 64비트 atomic word에 보관하며 첫 ON 때 `SAN8RPK.exe+0x17ABBF0`의 예상 앞 5바이트를 확인하고 MinHook을 설치한다. hook은 선택된 정의 ID가 게임에서 개방되어 있고 해당 런타임 데이터가 존재하면 true를 반환한다. 그 외에는 원래 판정을 호출한다. 강제 선택을 모두 해제해도 이 소스는 hook을 제거하지 않는다. 런타임 데이터 존재는 gameBase 변경 시 캐시를 초기화하고, 부재는 250ms 뒤 재확인한다. 존재 결과는 별도 초기화 전까지 유지한다.

설정은 각 word를 높은 nibble부터 출력한 128자리 16진 문자열 `secondaryJewelForceMask`로 저장한다. 로드 시 길이와 문자 형식을 검사하고 정의 목록 밖의 비트는 버린다. 선택된 항목이 있다면 hook 설치 성공 후 마스크를 반영한다. 마스크 키가 없을 때만 과거 bool `bAllSecondaryJewels`로 전체 선택을 복원하며, 마스크가 유효하지 않거나 hook 설치에 실패하면 전체 해제를 시도한다. 마스크 키가 있으면 과거 bool은 대체값으로 쓰이지 않는다. `bAllJewelsOpen` 누락 기본값은 false다.

실행 주체는 메뉴 렌더 경로의 설정 변경, ClientBGThread의 전체 개방 재확인, 게임의 판정 함수 호출 스레드다. 선택 word는 atomic이지만 런타임 캐시 배열과 base는 일반 변수이며 위 경로의 동시 접근 여부는 게임 실행 없이 확정하지 못했다. 회귀 조건은 개별 기존 개방 비트와 OFF, 즉시 적용 실패 후 선호 상태, 같은 주소에서 저장게임 로드, 선택·미선택과 개방·런타임 존재 조합, 128자리 마스크와 구버전 bool 우선순위, hook 설치 실패 및 여러 호출 스레드다.

## 평정 이동 지속과 재야 무장 처단 후보

두 설정 `bCouncilContinueAfterMove`, `bCouncilExecuteFreeOfficers`는 `Config.cpp:345` 이후 각각 기본 false로 읽어 setter를 호출하고, 실패하면 적용 상태로 설정 flag를 갱신한다. `CouncilCompactSectionBase.h:288,310`의 메뉴도 토글 실패 시 같은 방식으로 표시 상태를 맞추고 저장한다.

- 도시 이동 후 평정 지속: `CouncilContinueAfterMove.h:263`은 일반 이동, 플래그 처리, 자동전투, 수동전투 점령·단계, 배정 이동의 여섯 지점 원본을 모두 검사한다. 16진 템플릿으로 하나의 코드 공간을 구성하고 여섯 절대 점프를 차례로 쓴다. 중간 설치 실패 시 이미 쓴 지점을 역순으로 원복하고, 설치 후 검증 실패 시 전체 원복을 시도한다. OFF는 여섯 지점이 모두 자기 패치인지 확인한 다음 원본을 차례로 쓰며, 중간 실패 시 앞서 복구한 지점을 재패치한다. 복구·재패치 호출의 성공 여부는 확인하지 않는다. 코드 공간은 0x1000바이트이며 0x500바이트 템플릿을 사용하고 OFF 뒤에도 남긴다. 메뉴 설명은 주인공 행동 완료 bit0을 유지하고 평정 종료에 관여하는 bit1을 해제한다고 설명한다. 템플릿의 모든 명령을 별도로 해독하거나 실제 게임에서 검증한 것은 아니다.

OFF는 패치가 자기 바이트인지 확인하고 원본 복원 결과를 검증하며, 코드 공간은 남긴다.

설치·해제는 설정 로드 또는 메뉴 호출 스레드가 수행하고, 각 코드 공간은 해당 게임 코드가 호출되는 스레드에서 실행된다. 게임의 실제 호출 스레드와 동시에 실행 중인 코드가 없는 시점은 정적 소스만으로 확인되지 않는다. 처단 목록의 중복 여부와 게임의 처단 이후 동작도 확인되지 않았다. 회귀 조건은 여섯 설치 위치별 실패·복구, 일반·배정·자동전투·수동전투 이동, 주인공과 다른 무장의 종료 flag, 처단 후보의 신분·세력·활동 조건, 외부 패치와 충돌, 토글 중 실행이다.

## AI 전투 개선 묶음

`Config.cpp:321`의 `bAIWarImprove` 로드와 `MenuSectionsWar.cpp:101`의 체크박스는 `Roadblock.cpp:102`의 `SetAIWarImprove`를 호출한다. 메뉴는 setter가 갱신한 flag로 알림과 설정 저장을 수행한다. setter의 반환형은 `void`다.

ON은 네 정적 패치 위치가 각각 원본 또는 활성 바이트인지 먼저 확인하고, 필요한 위치만 현재 스냅샷과 다르게 기록한다. 이후 `AIRefusalWarFix`를 설치하고 `AIHighHonorSurrenderFix`를 설치한다. 두 hook의 개별 동작은 [전투 패치 조사](P0_War_Patches.md)에 있다. 후크 설치가 실패하면 이번 호출에서 바꾼 정적 위치의 스냅샷 복구를 시도하고 flag를 false로 둔다. 두 번째 hook 실패 시 첫 hook도 해제하려 한다. 복구 호출의 결과는 확인하지 않는다. 정적 바이트가 이미 활성 상태인 경우는 이번 호출의 변경분으로 취급하지 않는다.

OFF는 반대 순서로 두 hook을 먼저 해제하고, 이후 네 정적 위치를 검사·복구한다. 두 번째 hook 해제가 실패하면 첫 hook의 재설치를 시도한다. 정적 쓰기가 실패하면 기록한 스냅샷과 두 hook의 ON 복원을 시도한다. 다만 두 hook을 해제한 뒤 정적 바이트를 읽지 못하거나 원본·활성 어느 쪽과도 일치하지 않으면, 이 경로에서는 hook을 재설치하지 않고 바로 반환한다. 이때 메뉴에서 이미 바뀐 flag 또는 설정에서 읽은 false와 실제 남은 정적 패치가 일치하지 않을 수 있다. 각 복구 시도의 성공은 확인하지 않는다.

메뉴 설명은 공격 대상 판단, 주인공 소속 도시 공격 조건, 공백지 점령과 항복권고를 함께 변경한다고 밝힌다. 각 setter는 설정 로드 또는 메뉴 호출 스레드에서 실행되고 hook은 해당 게임 코드의 호출 스레드에서 실행된다. 회귀 조건은 네 위치의 원본·활성 혼합, 각 hook 설치·해제 실패, OFF 중 정적 바이트 검사 실패, 복구 실패와 기존 타 기능의 hook 사용 여부다. 실제 게임 호출 스레드 및 전투 결과는 미확인이다.

## 게임 내 상성 표시

`bAffinityDisplay`는 기본 false이며 `Config.cpp:467`은 키를 읽었을 때만 적용한다. `Config.cpp:467`과 `MenuSectionsInfo.cpp:100`은 `SetAffinityDisplayWithVisibilityFix`를 호출하며 실패 시 기본 표시 기능의 적용 flag를 사용한다. `AffinityDisplay.h:411`의 기본 기능은 원본 UI 배열·descriptor와 네 callsite를 확인하고 목록 표시 및 정렬 함수를 교체하며 무장 정보와 열전 화면의 초기화·갱신 callsite를 바꾼다. 갱신 thunk는 게임 레지스터를 전역 변수에 캡처한다. 목록의 비공개 무장은 `?`로 표시하고 정렬값을 조정하는 경로가 있다.

`AffinityDisplayVisibilityFix.h:76`은 기본 기능을 먼저 설치한 뒤 목록 표시·정렬 함수 포인터와 정보 갱신 callsite를 다시 교체한다. 보정된 가시성 검사는 검사 구조체에 실제 무장 포인터를 넣는다. 보정 설치 실패 시 기본 기능 OFF를 시도하지만 그 반환값을 확인하지 않는다. 기본 설치 중 일부 쓰기 실패 역시 원본 복구를 시도하나 복구 성공은 확인하지 않는다. 설정·메뉴 호출 경로에서 설치하며 UI hook은 게임의 각 callsite 실행 스레드에서 동작한다. 캡처 레지스터 저장소는 공유 전역값이므로 실제 동시 호출 가능 여부를 확인해야 한다. 메뉴는 관련 화면을 닫고 전환하도록 안내한다. 회귀 조건은 설정 키 누락, 공개·비공개 무장의 목록·정렬·정보·열전 화면, 원본 구조 불일치, 기본 설치 및 가시성 보정의 부분 실패, OFF 복구 실패와 외부 패치 충돌, 화면을 연 채 전환이다.

### 후방지원 자원 이동과 경로 파일

`CityInfoWindow.cpp:1023`의 수동 지원은 실행 직전 전선 정보를 다시 읽고 출발·도착 도시가 서로 다르며 현재 선택 세력 소유인지 확인한다. 금·군량·병력을 고정량 또는 출발 보유량의 0~100%로 계산하고, 보유량과 도착지의 32비트 잔여 범위, 병사 한도에 맞춘다. 값은 출발 차감과 도착 증가를 포함해 최대 여섯 번 순차 기록한다. 쓰기에 실패하면 앞서 성공한 쓰기를 역순으로 원복하려 하지만 복구 결과를 검사하지 않는다. 성공 로그만으로 원자적인 자원 이동이나 다른 스레드와의 경합 부재가 증명되지는 않는다.

자동 노선은 `ExecuteAutoSupportRoute`에서 현재 선택 세력의 후방 도시에서 전선 도시로 가는 조건을 확인한 뒤 같은 수동 이동 함수를 사용한다. 여러 노선은 배열 순서로 실행하므로 앞선 이동이 다음 노선의 가용 자원에 영향을 준다. 저장 파일은 설정 파일과 같은 폴더의 `S8RPK_rear_support_routes.json`이며 연간 활성화와 노선별 활성화, 도시 인덱스, 고정량·비율 모드, 금·군량·병력을 기록한다. 저장은 파일을 직접 잘라 다시 쓰며 실패를 호출자에게 반환하지 않는다.

연간 실행과 도시 창은 같은 노선 벡터와 수동 지원 입력 상태를 사용한다. background의 `RunYearlyRearSupport`는 벡터를 순회하고 `ExecuteAutoSupportRoute`는 벡터 원소를 참조한 뒤 수동 입력 상태를 임시로 바꾸어 `ExecuteRearSupport`를 호출하고 이전 값을 복원한다. 렌더 경로의 `DrawAutoSupportRoutes`는 같은 벡터에 노선을 추가·편집·삭제하고 수동 실행도 호출한다. 이 접근을 함께 직렬화하는 잠금은 해당 함수들에 없다. 따라서 두 경로가 겹치면 벡터 참조·순회와 편집, 임시 입력값과 UI 변경이 서로 영향을 줄 수 있는 구조다. 연간 실행은 전선 분석의 선택 세력도 주인공 세력으로 임시 변경했다가 복원한다. 실제 동시 실행이나 그 결과는 확인하지 않았다. 회귀 조건에 연간 실행 중 노선 추가·삭제·편집, 수동 지원, UI 입력·선택 세력 변경과 실행 후 복원을 포함한다.

## 도시 소속과 전선 판정

`CityInfoWindow.cpp:755`의 도시 소속 조회는 먼저 도시 `+0x98`의 무장 포인터에서 세력 `+0x18`을 읽고, 실패하거나 없으면 도시 `+0x90` 군단의 세력 `+0x10`을 사용한다. 둘 다 확인하지 못하면 0을 반환한다. 주인공 세력은 주인공의 현재 도시를 같은 함수로 조회한다. 선택 세력이 목록에서 사라지면 주인공 세력을 우선 선택하고, 없으면 처음 수집한 세력을 선택한다.

전선 분석은 도시당 여섯 연결 포인터를 읽는다. 유효한 도시 배열 범위와 0x2A0 간격에 맞는 연결만 도시 인덱스로 해석한다. 연결된 도시의 조회 세력이 선택 세력과 다르면 전선이며, 소속 조회가 0인 도시도 다른 세력으로 처리된다. 배열에 맞지 않는 포인터는 미확인 연결 수로 세지만 전선 판정에는 사용하지 않고, 읽기 실패는 빈 연결처럼 취급한다. 무장 배치용 `IsCityFrontlineForForce`도 유효 연결에 대해 같은 세력 비교를 한다. 따라서 미확인 연결과 소속 조회 실패가 각각 전선 여부에 서로 다르게 반영된다.

전선 분석의 자원 읽기는 실패 시 기본 0을 유지하며, 수동 지원은 실행 전에 값을 별도로 읽고 확인한다. 회귀 조건은 태수 없는 도시의 군단 fallback, 무소속·소속 읽기 실패, 잘못된 연결 주소·읽기 실패, 선택 세력 소멸, 같은 주소의 게임 세대 교체와 후방지원·자동배치의 판정 일치다.

## AI 성장과 연간 특수능력의 연결

추가 설정 키는 `bAIOfficerAutoGrowth`, `iAIOfficerGrowthSpeed`, `bAIOfficerGrowthRestoreNone`, `bAnnualSpecialAbilityAutoAssign`이다. `Config.cpp:475`는 연간 특수능력과 AI 성장 설정을 읽은 뒤 성장이 OFF면 연간 특수능력도 OFF로 바꾼다. 성장 속도는 파일 로드 시 1~3으로 제한한다. 메뉴에서 성장을 끄면 연간 특수능력을 끄고, 기능을 켤 당시 게임 성장 설정이 없음이었던 것으로 기록된 경우에만 게임 설정을 없음으로 되돌린다.

`Menu_impl.inc:494`의 500ms 경로는 `TickAIOfficerAutoGrowth`를 먼저 실행한 뒤 `MonitorTechStatus`를 호출한다. 성장 tick은 실제 12월→1월 전이를 본 뒤 평정을 기다리고 처리 전에 해당 연도를 적용 연도로 기록한다. 특수능력 자동 판정은 평정의 월 처리 경로에서 두 설정이 ON이고 실제 시나리오 월이 1월이며 `WasAIOfficerGrowthAppliedForYear`가 현재 연도에 true일 때 시작한다. 이 함수는 기록된 연도만 비교하므로 성장 처리의 모든 무장 쓰기가 성공했는지는 나타내지 않는다. 마지막 적용 연도는 세이브 전환 시 초기화하는 경로가 확인되지 않아, 같은 프로세스에서 이전 세이브의 같은 연도 표식이 남아 있으면 새 세이브의 성장 성공 여부와 무관하게 이 연도 비교가 true일 수 있다. 평정 월 게이트 등 다른 조건도 만족해야 실제 자동배정을 호출한다. 특수능력 작업 시작이 실패하거나 이미 실행 중일 때 호출자는 그 결과를 재시도하지 않고 해당 월을 처리한 것으로 기록한다.

성장·월 판정은 ClientBGThread 경로이며 특수능력 대상 계산은 별도 worker를 사용한다. 회귀 조건은 성장 OFF와 두 설정 조합, 속도 1~3 및 파일 경계, 12월→1월 미관측, 평정 진입 전후 순서, 성장 부분 실패에도 적용 연도 표시, 기존 작업 실행 중 연간 작업 시작 실패, 새 세이브에서 같은 연도가 재사용되는 경우다. 성장 결과와 worker 수명은 [무장 조사](P0_Officer.md)를 함께 따른다.

연간 특수능력 시작 경로는 별도의 실행 연도 기록을 검사하지 않는다. `MonitorTechStatus`는 내정 `0x07` 관측 시 월 처리 표시를 초기화하므로, 같은 시나리오 연도·1월에 다시 평정 `0x05`을 관측하고 성장 완료 표식이 유지되며 이전 작업이 끝나 있다면 연간 작업을 다시 시작할 수 있다. 두 번째 작업은 그때 이미 특수능력이 있는 무장을 시작 스냅샷에서 제외한다. 실제 게임이 같은 연월에 이러한 상태 전이를 만드는지는 확인하지 않았다.

## 사망·등용 무장 알림

`bOfficerChangeNotify`는 `Config.cpp:460`과 `MenuSectionsInfo.cpp:77`에서 읽고 저장한다. `RoninMonitor_Tick`은 재야 감시와 이 알림이 모두 OFF일 때만 공통 상태를 초기화한다. 개별 알림이 OFF인 동안에는 해당 기준선을 무효화하며, 다시 ON하면 현재 상태를 기준으로 잡아 과거 변동을 소급 알리지 않는다. 전투 중, 설정 미준비, 배열 주소 미해결 또는 평정·내정 상태 미확인인 동안에는 진행하지 않는다. 주인공 주소가 다른 0이 아닌 주소로 바뀌면 기준선과 알림을 초기화한다.

내정 `0x07`→평정 `0x05`에서 무장 상태·세력·도시를 ID별로 저장하고, 평정→내정에서 현재 상태와 비교한다. 이전 유효 기록이 없는 무장은 비교에서 제외한다. 상태가 `0x88`로 바뀌면 사망, 사망이 아니면서 세력 포인터가 바뀌고 새 포인터가 유효 범위이면 등용·세력 변경으로 분류한다. 배열을 최대 5102 슬롯 읽고 중복 ID는 첫 번째만 사용한다. 팝업은 등용과 사망을 각각 최대 16개 표시하고 20초 유지하며 공통 큐는 최대 4개다. 별도 알림 기록에는 전체 변동을 추가한 뒤 최근 200개만 남긴다.

감시와 비교는 `Menu_impl.inc`의 ClientBGThread tick 경로, 팝업 그리기는 `RoninMonitor_Draw`의 UI 경로다. 팝업 큐는 mutex를 사용한다. 회귀 조건은 기능별 ON/OFF 조합과 평정 중 ON, 사망과 세력 변경의 우선순위, 유효하지 않은 기존 기록과 중복 ID, 전투 중 상태 전이, 팝업 표시 제한과 이력, 주인공 주소 재사용을 포함한 로드다.

## 도독 포로 처분의 특권 옵션

`bGovernorPrisonerDisposal`과 `bGovernorPrisonerConsumePrivilege`는 별도 저장 키다. 설정 로드에서는 특권 소비 flag를 먼저 읽고 처분 기능을 설치한다. 메뉴의 특권 체크박스는 flag만 변경하고 저장하며 처분 hook을 다시 설치하지 않는다. `GovernorPrisonerDisposal.cpp:251`은 생성하는 payload에 flag 주소를 넣으므로 적용 중 값이 참조된다. 메뉴 설명은 소비 OFF일 때 특권을 쓰지 않고, ON이면 직접 처분 선택 시 특권 한 개를 소비하며 특권이 0개이면 처분할 수 없다고 안내한다. payload의 모든 분기 의미는 기계어 데이터의 정적 해석 및 게임 검증이 더 필요하다.

처분 기능 설치는 세 지점 패치 도중 실패하면 원본 쓰기를 시도하고 cave를 해제한다. 성공 후 OFF는 세 패치가 일치하는지 확인하고 원본 세 지점을 복구하며, 모두 성공하면 cave를 해제한다. 부분 복구 실패 시 cave와 적용 flag를 유지한다. 이관 회귀 조건은 기능과 특권 옵션 네 조합, 기능 ON 중 옵션 변경, 특권 0·1개, 사용자 선택 거부, 설치·해제 중 부분 실패 및 callback 실행 중 cave 해제다.

## 단절 영토 무장 이동 제한

`bIsolatedTerritoryMovement`는 기본값 true이며 `Config.cpp:370`이 설정을 읽고 적용한다. 평정 메뉴는 `CouncilCompactSection.h`의 `Checkbox` 매크로 wrapper가 유목기병 설정 옆에 체크박스를 삽입한다. 메뉴·설정 적용 실패 시 flag는 `IsIsolatedTerritoryMovementFeatureApplied` 결과로 맞춘다. 메뉴 설명은 같은 세력의 연결되지 않은 영토 간 무장 이동을 제한하고 수송·배정은 유지한다고 밝힌다.

`IsolatedTerritoryMovement.h:152`의 연결 판정은 출발·도착 객체와 소유 세력이 유효하고 같아야 하며, 각 도시의 최대 6개 인접 포인터를 같은 세력 내에서 너비 우선으로 탐색한다. 큐는 256개이고 넘치면 false다. 목록 필터는 연결되지 않거나 유효하지 않은 대상을 게임의 삭제 함수로 목록에서 제거한다. `MovementContextAllowed`는 문맥·객체·소속을 판정할 수 없을 때 true로 원래 경로를 허용하지만, `AreConnected`의 직접 호출은 객체 판정 실패를 false로 취급한다. 각 hook은 원래 이동 판정의 결과 및 인수에 따라 연결 검사를 더한다.

연결 탐색은 인접 슬롯 읽기에 실패하거나 이웃 객체·소유자가 유효하지 않으면 그 슬롯을 건너뛰고 다른 연결을 계속 탐색한다. 따라서 해당 슬롯만 실패해도 다른 경로가 있으면 연결될 수 있지만, 실패한 슬롯이 유일한 연결이면 false다. `MovementCheck910`은 원래 이동 판정이 성공한 뒤 목적지의 여섯 이웃 중 하나라도 목적지와 같은 소유자로 연결돼야 원래 결과를 반환하며, 그렇지 않으면 0을 반환한다. 이웃 슬롯과 목록 테이블은 `sizeof(uintptr_t)` 간격이므로 빌드 플랫폼에 따라 읽는 위치가 달라진다. 실제 게임 주소와 호출 결과는 확인하지 않았다.

ON wrapper는 실제 게임 코드 패치 전 stub들을 준비하고 bool 반환의 네 소비 위치를 `test eax,eax`에서 `test al,al`로 교정한다. 이후 원본 코드와 guard를 검사하고 12개 지점의 점프·호출을 순차 기록한다. 각 성공 쓰기의 이전·변경 바이트를 보관한다. 실패 또는 OFF 시 역순으로 현재 바이트가 자기 패치와 일치하는 지점만 복원하고 성공한 기록만 제거한다. 일부 복구 실패 시 OFF는 적용 flag를 유지한다. ON 도중 실패하고 복구까지 실패한 경우에는 flag가 false인 상태로 일부 패치 기록이 남을 수 있다. 준비한 stub은 이 소스에서 해제하지 않는다.

패치 기록은 `RecordAndWrite`가 원본을 읽고 `WriteBytes` 성공을 받은 뒤에 추가한다(`IsolatedTerritoryMovement.h:594-604`). `WriteBytes`는 보호 변경 후 `memcpy` 예외가 나면 false를 반환한다. 이때 일부 바이트가 이미 기록됐다면 해당 지점은 복구 목록에 추가되지 않으므로 `RestoreAllPatches`가 그 지점을 처리하지 못한다. 보호 속성 복원과 명령 캐시 비우기의 반환값도 확인하지 않는다(`IsolatedTerritoryMovement.h:96-117,629-645`). 부분 복사나 API 실패가 실제로 발생했는지는 확인하지 않았다.

bool 소비 위치 교정은 네 지점을 순서대로 검사·수정하며 중간 실패 시 앞서 수정한 stub 바이트를 되돌리지 않는다. 다음 ON은 이미 교정된 바이트를 성공으로 받아들이고 나머지를 다시 시도한다(`IsolatedTerritoryMovementFeature.h:15-47`). 게임 패치의 부분 복구가 실패해 `gApplied`가 false인 경우에는 OFF가 복구를 재시도하지 않고 성공을 반환한다. 다음 ON은 게임 코드 원본 검사를 먼저 수행하므로 남은 자기 패치가 원본 검사에 걸리면 설치를 진행하지 못한다(`IsolatedTerritoryMovement.h:677-702`). 부분 복구 실패는 코드상 경로이며 실제 발생 여부는 확인하지 않았다.

실행은 설정 로드·메뉴의 설치 스레드와 게임의 각 이동 경로 스레드로 나뉜다. 회귀 조건은 같은 세력 연결·단절·빈 소유, 유효성 조회 실패와 256개 경계, 수송·배정, 12개 지점별 실패·외부 수정, 부분 설치 복구 실패 후 재시도, 동시 callback이다. 실제 게임 호출 스레드와 전체 기계어 stub 동작은 아직 검증하지 않았다.

## 단기접전 대기일 설정

`bShortBattleCooldownEnabled`의 초기값은 false이고 `iShortBattleCooldownDays`의 초기값은 3이다. `Config.cpp:522`는 일수를 먼저 읽고 활성 키가 있을 때 setter를 호출한다. 로드한 일수와 `SetShortBattleCooldown`에는 별도 수치 범위 제한이 없다. 메뉴는 `InputInt`의 십진 문자 입력을 사용하며 활성 중에는 값이 바뀔 때마다 즉시 재적용하고, 실패하면 직전 표시값으로 되돌린 뒤 설정을 저장한다. 비활성 중에는 일수만 변경·저장하고 게임 값은 건드리지 않는다. 체크박스 적용 실패 시 적용 flag를 기준으로 표시를 되돌린다.

최초 ON 때 현재 게임 값이 요청값과 이미 같으면 그 값을 원본으로 캡처한다. 이후 일수를 다른 값으로 변경하고 OFF 해도 10이 아니라 최초에 캡처한 요청값으로 복구한다. 활성 중 현재 값이 마지막 적용값과 다르더라도 새 요청값과 같으면 외부 변경으로 거부하지 않고 마지막 적용값을 갱신한다. 반면 OFF는 현재 값이 마지막 적용값과 다르면 복구하지 않는다. 쓰기 실패 시 적용 상태와 마지막 적용값은 성공 경로로 갱신되지 않으며, 최초 ON에서는 쓰기 전에 원본 캡처가 이미 이뤄진다. 다음 최초 ON 시에는 현재 값을 다시 캡처한다. 이 값 조합을 이관 회귀 조건으로 포함한다.

setter는 실행 파일의 32비트 값을 사용하며 최초 적용에서 현재 값이 게임 기본값 10 또는 요청값일 때만 기존 값을 저장한다. 이미 요청값인 외부 변경을 받아들이면 그 값이 복원값이 된다. 이후 변경은 현재 값이 마지막 적용값 또는 새 요청값이어야 하고, OFF는 현재 값이 마지막 적용값일 때 보관한 값을 쓴다. 쓰기 이후 재읽기 검증은 이 setter에 없다. 회귀 조건은 설정 누락, 0·음수·큰 정수, 활성 중 편집 실패, 최초 현재값이 요청값과 같은 경우, 외부 변경 후 OFF와 쓰기 실패다. 실제 게임에서 각 숫자가 만드는 결과는 확인되지 않았다.

## 병력수 공격·방어 반영

`bTroopCountCombatScaling`은 기본 false다. `Config.cpp:537`의 로드와 `MenuSectionsWar.cpp:240`의 체크박스는 setter를 호출하며 실패 시 내부 적용 flag로 표시를 맞춘다. UI 설명은 게임에 남은 병력수 선형 환산 경로를 공격·방어 계산에 사용한다고 설명한다.

### 원군 즉시 행동과 수비 배치의 조합

`ReinforcementArrivalAction.cpp:110`은 디스패치 테이블의 8바이트를 원본 순서 또는 도착 우선 순서로 변경한다. ON은 테이블이 두 상태 중 하나인지, 턴·도착·명령의 세 기준 코드가 원본인지 확인한다. 이미 도착 우선인 테이블도 받아들여 내부 적용 상태를 true로 만든다. OFF는 내부 flag가 false여도 테이블이 도착 우선이면 원본 순서로 쓴다. 따라서 이 모듈이 직접 변경하지 않은 동일 바이트 상태도 OFF에서 복구할 수 있다. 쓰기 후 재읽기 확인은 없다.

두 상태가 어긋난 경우도 처리 방식이 다르다. 내부 적용 상태가 true이고 테이블이 원본이면 ON은 세 기준 코드를 다시 검사한 뒤 도착 우선 순서를 다시 쓰지만, OFF는 활성 테이블이 아니라며 실패하고 내부 상태를 유지한다. 내부 상태가 false이고 테이블이 도착 우선이면 ON은 기준 코드를 검사하고 쓰기 없이 내부 상태만 true로 바꾸며, OFF는 원본을 쓴다. 내부 상태가 true이고 테이블도 도착 우선인 ON 호출은 기준 코드 재검사 없이 성공한다. 두 알려진 테이블 중 어느 쪽도 아니면 ON과 OFF 모두 실패한다. 설정 로드 시 setter가 실패하면 UI flag는 내부 적용 상태로 되돌아가므로, 테이블이 실제로 어느 상태인지와 별개다. 이 조합과 세 기준 코드 변경을 이관 회귀 조건에 포함한다.

수비 배치의 `ValidateTargets`는 같은 테이블을 읽지만 원본과 도착 우선 둘 다 허용하고 테이블을 직접 바꾸지는 않는다. 추가로 원군 생성 및 선택 함수의 기준 바이트와 게임 함수 주소를 확인한다. 따라서 두 기능의 정상 ON/OFF 순서에 따른 테이블 검사는 양쪽 상태를 허용하도록 작성되어 있다. 두 setter가 동시에 실행될 때의 동기화나 전투 턴 도중 안전성은 이 코드에서 보장되지 않는다. 회귀 조건은 두 옵션 네 조합과 토글 순서, 외부에서 이미 바꾼 테이블, 기준 코드 불일치, 테이블 쓰기 실패 및 전투 도착 중 전환이다.

## 전법 횟수·특수능력 설정의 사용

`OfficerDetail.cpp:274`은 전법 오프셋 `0x139~0x160`에 대해 횟수 버튼을 제공하고 0→1→…→9→0으로 바꾼다. 선택된 무장이 있으면 그 무장 ID에도 같은 값을 기록한다. 특수능력은 `0x1000~0x1009`를 별도 논리 키로 사용하고 체크 상태를 양수 여부로 판단한다. 0을 쓰면 매니저가 해당 항목을 제거한다.

`BattleMonitor.cpp:310`의 전투 적용 경로는 부대 무장 슬롯 세 개 중 처음 유효한 주소의 무장 ID를 읽는다. 그 ID가 0이면 뒤 슬롯을 더 찾지 않고 해당 부대를 건너뛴다. 선택한 ID에 설정이 있으면 게임 스킬 ID에 `0x138`을 더한 키의 양수 설정을 찾아 해당 스킬 레코드의 횟수 바이트에 쓴다. 저장값은 int이지만 쓰기는 unsigned byte 변환이다. `SpecialAbility.cpp:140`은 전투 캐시 생성 시 전체 설정 맵을 mutex 아래 복사해 능력을 판정한다. `BattleEnvironment.cpp:187`의 함선 병기화는 활성 부대가 바뀔 때 최대 세 무장의 `0x1009`를 확인하고 그 결과를 캐시한다. 따라서 전법 횟수와 특수능력 모두 같은 파일을 사용해도 실제 반영 시점과 대상 무장 선택은 다르다.

특수능력 0x1000~0x1008의 전투 캐시 생성은 설정 맵을 직접 snapshot하므로 지연 저장 조회를 수행하지 않는다. 함선 병기 `0x1009`는 활성 부대가 바뀔 때 `GetTargetSkillCount`를 호출하므로 이 조회가 300ms 지연 저장을 시도할 수 있다. 같은 활성 부대가 유지되면 캐시된 판정을 사용해 해당 조회를 반복하지 않는다(`SpecialAbility.cpp:140-183`, `BattleEnvironment.cpp:187-205`). 저장 mutex와 마지막 변경 시각 등 조건은 [수치 파일 조사](P0_Resources.md#무장-전법특수능력-수치-파일)를 따른다. 실제 전투와 저장은 실행하지 않았다.

또한 `InitCheats`는 gameBase 탐색 성공 여부를 반환하기 전에 `LoadSkillCounts`를 호출한다. 초기화 재시도마다 이 함수에 다시 들어갈 수 있으므로 파일 로드가 반복되는 조건과 그 사이의 편집을 이관 회귀 사례로 확인한다. 전투 진입·부대 변경, 같은 부대의 능력 편집, 최초 유효 무장과 나머지 무장, 횟수 0·9·파일의 큰 값, 저장 실패를 포함한다.

전투 진입 시 특수능력 캐시와 전법 횟수 주입은 순서대로 호출되지만 같은 설정 snapshot을 공유하지 않는다. 특수능력은 캐시 시작 시 맵을 한 번 복사하고, 이어지는 전법 주입은 원본 맵을 레코드별로 읽는다. 그 사이 설정이 변경되면 두 결과의 기준 시점이 다를 수 있다. 실제 동시 변경 여부는 확인하지 않았다.

전법 주입은 무장 ID가 맵에 있는지 한 번 확인한 뒤 각 스킬 레코드마다 mutex를 다시 잡아 설정값을 읽는다. 순회 중 해당 무장의 맵 항목이 삭제되면 남은 레코드를 중단하고, 개별 오프셋이 없거나 양수가 아니면 그 레코드만 건너뛴다. 유효하지 않은 레코드 주소·인덱스·선두 바이트는 이후 레코드 전체를 중단한다. 따라서 동시 편집이 있으면 한 부대에 서로 다른 시점의 설정이 적용될 수 있고 앞선 쓰기를 되돌리는 경로는 없다. 실제 동시 실행과 부분 적용은 확인하지 않았다.

## 특수능력 전투 캐시

`SpecialAbility.cpp:140`은 전투 부대 목록을 읽으며 설정 맵을 한 번 복사하고, 각 부대의 세 무장 슬롯 중 한 명이라도 해당 키를 가지면 `0x1000~0x1008` 능력 flag를 해당 부대 캐시에 설정한다. 캐시는 부대의 raw 주소로 활성 부대를 찾는다. `0x1009` 함선 병기화는 앞서 기록한 `BattleEnvironment.cpp`의 별도 조회 경로다.

### 전법 횟수 주입 시점

`MonthCapture.cpp`는 실행 파일 기준 `+0x2E98BC8`의 시나리오 객체에서 연도 `+0x72D0`과 월 `+0x72D2`를 읽는다. 객체 포인터와 두 필드의 접근 가능성을 확인해 매 호출에 다시 해석한다. `SetMonthCapture`는 hook을 설치하지 않고 직접 월 조회의 enable flag만 바꾸며 `GetCurrentMonth`는 OFF 또는 읽기 실패 때 0을 반환한다. `SystemMonth.cpp`의 `InstallSystemMonthHook`도 최초 로그만 남기고 별도 hook을 설치하지 않는다. `GetSystemMonthValue`는 같은 `GetCurrentMonth`를 호출한다. 따라서 `Menu_impl.inc:540`에서 별도 방식으로 이름 붙인 두 값은 현재 동일 경로다.

`ReadScenarioYear/Month/Date`는 위 enable flag와 별개로 직접 읽는다. 시나리오 날짜 UI는 편집 종료 시 연도를 unsigned 16비트로 변환해 기록하고, 월은 1~12만 허용한다. `UpdateYear` 자체에는 연도 범위 제한이 없다. 예를 들어 UI 입력 -1은 변환 후 65535로 전달되며, 입력 65536은 0으로 전달된다. 이는 저장 폭의 변환 결과이며 다른 기능이 그 연도를 유효하다고 받아들이는지와는 별개다. `ReadScenarioDate`는 읽은 연도를 범위 검사 없이 반환하지만, 미발견 전환은 100~399를 기다리고 자녀 조기 임관은 171~269를 요구한다. 따라서 0이나 65535가 실제로 저장되고 유지된다면 두 기능의 해당 연도 조건을 통과하지 않는다. 미발견 전환은 이때 요청을 완료 처리하지 않는다. 반면 AI 성장 tick과 연간 후방지원의 날짜 입구는 월만 1~12로 제한하고 연도 0도 별도로 거부하지 않는다. AI 친밀도 가속·전기 주기·연간 특수능력 날짜 확인은 연도 0을 거부하지만 65535의 상한 검사는 이 입구에 없다. 이는 날짜 입구 조건이며 각 기능이 실제 실행되는 다른 조건까지 충족한다는 뜻은 아니다. 날짜 쓰기는 보호 변경 실패 시 반환하며 보호 복구 결과는 확인하지 않는다. `BattleMonitor.cpp:879`의 평정 월 변화 판단은 enable flag의 영향을 받는 월 getter를 쓰지만, 연간 특수능력 조건은 직접 읽은 유효한 시나리오 연월을 별도로 사용한다.

`ReadScenarioDate`는 한 번 해석한 시나리오 주소에서 연도와 월을 순서대로 각각 읽으며 두 값을 묶는 잠금이나 재확인은 없다. 날짜 UI의 연도·월 쓰기도 각각 별도 호출이다. 이 사이 게임이나 다른 호출이 날짜 또는 시나리오 객체를 변경하면 읽은 연·월 조합이 한 시점의 쌍인지 이 함수는 보장하지 않는다. resolver의 `IsValidPtr` 확인 뒤 실제 날짜 읽기와 쓰기는 별도 SEH 보호 없이 이루어진다. 이 날짜는 후방지원·군단 배치·AI 성장 등에서도 사용하므로 각 기능의 전이 판정과 함께 확인해야 한다. 실제 변경과 읽기가 겹쳤는지는 검증하지 않았다.

회귀 조건은 월 조회 ON/OFF와 읽기 실패, 시나리오 객체 변경, UI 연도 변환 및 월 경계, 보호 변경 실패, 평정 진입 시 월 0과 실제 날짜의 차이, 직접 날짜 소비 기능과의 상호작용이다. 로그나 함수 이름만으로 현재 별도 시스템 월 hook이 존재한다고 판단하지 않는다. 이는 정적 조사다.


시나리오 날짜 UI(`MenuSectionsScenario.cpp:87-141`)의 연·월 편집값은 함수 내부 정적 변수이며 최초 표시값은 200년 1월이다. 사용자가 연도 또는 월 중 하나라도 편집 중이거나 그 프레임에 편집을 종료했으면 두 값을 모두 다시 읽지 않는다. 둘 다 비활성이 된 다음에만 마지막 조회에서 최소 250ms가 지났을 때 현재 연·월을 함께 읽어 편집값을 동기화한다. 유효하지 않은 월은 로그만 남기며 입력값을 즉시 되돌리지 않고, 후속 읽기에 성공하면 게임 값으로 갱신된다. 회귀 조건은 한쪽 편집 중 다른 날짜 변경, 연·월 연속 편집, 잘못된 월 입력 후 재동기화, 날짜 읽기 실패 및 250ms 제한이다. 이 동작은 정적 코드 확인이다.

## 전체 무장 랜덤 기재 배정

`MenuSectionsInfo.cpp:127`은 창과 진행 중 작업을 렌더 경로에서 호출한다. 기본 기재 1~70·201·202와 정의된 사용자 기재를 등급별 후보로 만들고, 선택한 등급으로 시작한다. `SelectOfficercapture_impl.inc:991`의 분리 worker는 roster 5102개 슬롯에서 유효 ID 1~5102를 중복 없이 수집해 무장 주소를 게시한다. 이 수집은 앞의 전법·특기 일괄 편집과 달리 ID가 슬롯 번호와 같아야 한다는 조건이 없다.

시작 시 기준 기재 객체와 vtable을 찾지 못하면 작업을 중단한다. 공개 wrapper `SelectOfficercapture.cpp`는 시작 프레임 직후 런타임 기재 포인터 배열을 먼저 확인하며, 필요한 객체가 다 모이지 않으면 렌더 호출마다 읽기 가능한 메모리를 최대 8MiB씩 검색해 찾은 후보만 사용한다. 이후 렌더 호출마다 무장 최대 32명을 처리한다. 기존 기재 세 슬롯 중 빈 슬롯만 대상으로 하며 기존 ID 및 같은 무장에 새로 배정한 ID와 중복되지 않도록 후보를 섞어 기록한다. 이미 가득 찬 무장, 하나 이상 바뀐 무장, 변경하지 못한 무장을 별도 집계한다.

배정 창을 닫아도 작업 flag가 남아 있으면 해당 렌더 경로가 호출될 때 계속 진행한다. 이 호출은 메인 메뉴가 표시되고 펼쳐져 있으며 gameBase가 있고 메인 테이블 생성이 성공할 때 `DrawColumn1` → `DrawOfficerDetailSection`을 통해 이루어진다. 메인 메뉴를 닫거나 접으면 다른 창 때문에 overlay가 계속 그려져도 이 적용 tick은 진행되지 않는다. 수집 worker는 detach하며 수집 결과와 기재 객체는 raw 주소로 보관된다. 수집 이후 적용 시점까지 roster·객체 세대를 비교하거나 작업을 취소하는 경로는 이 작업 상태에 없다. 그동안 분리 worker의 완료와 이후 재개 순서, 게임 로드·종료 중 주소 수명은 확인이 필요하다. 회귀 조건은 기본·사용자 등급 조합, 후보 객체 일부·전체 부재, 중복 ID와 빈 슬롯, 무장 수집 중 로드, 적용 중 세대 변경, 창 닫힘과 오버레이 중지, 분리 worker 종료다. 실제 실행 결과는 아니다.

수집 시 중복 판정에 쓴 무장 ID는 결과 벡터에 저장하지 않고 주소만 남긴다. 적용 시 `AssignRandomTraitsToOneOfficerBatchFast`는 그 주소에서 세 슬롯을 다시 읽지만 수집 당시 ID와 비교하지 않는다. `GetTraitID`는 슬롯 포인터 또는 기재 ID 읽기에 실패하면 0을 반환하고, 일괄 배정은 0을 빈 슬롯으로 취급한다. 이후 `SetTraitObjectFast`는 기재 객체의 ID·vtable 포인터 등을 검사하고 무장 슬롯에 포인터를 쓴 뒤 다시 읽어 비교하지만, 수집 당시 무장 ID나 roster 세대는 검사하지 않는다. 따라서 읽기 실패를 빈 슬롯으로 처리하는 경우와, 수집한 주소가 이후 다른 무장에 재사용되는 경우를 별도 회귀 조건으로 기록한다. 실제 읽기 실패나 주소 재사용 발생 여부는 확인하지 않았다.

기재 객체 후보의 vtable 판정은 확보 경로마다 다르다. `OfficerDetail.cpp:620-636`은 기존 캐시의 유효 객체에서 첫 vtable을 기준으로 잡지만 캐시의 나머지 후보를 그 기준과 비교하지 않는다. `SelectOfficercapture.cpp:17-32`의 runtime 배열 경로도 ID와 0x10000을 넘는 vtable 포인터를 확인하지만 기준 vtable과 비교하지 않는다. 반면 `OfficerDetail.cpp:737-750`의 메모리 검색은 기준 vtable과 정확히 같은 후보만 추가한다. 최종 `SetTraitObjectFast`는 기대 ID는 전달하지만 기대 vtable은 전달하지 않으므로, 쓰기 직전에도 vtable이 기준과 같은지 비교하지 않는다. 이는 각 경로의 정적 검사 차이이며 실제로 서로 다른 vtable의 후보가 있는지는 확인하지 않았다.

기준 객체 확보는 기존 기재 캐시, 선택 무장, 주인공, roster 순으로 진행하며 유효한 객체 하나를 찾으면 성공한다. 찾은 객체가 선택한 등급의 후보가 아니어도 vtable 기준으로 사용할 수 있다. 반대로 이 경로에서 하나도 찾지 못하면 작업 flag가 내려가므로, 공개 wrapper는 그 직후 runtime 기재 배열을 읽지 않는다. 따라서 runtime 배열에 유효한 후보가 있더라도 기준 객체를 다른 경로에서 먼저 찾지 못하면 이번 작업은 시작되지 않는다. 이는 `SelectOfficercapture_impl.inc:1355-1377`과 `SelectOfficercapture.cpp:7-9,44-50`의 호출 순서다.

기존 기재 캐시 `s_traitObjectById`는 `OfficerDetail.cpp`의 정적 `unordered_map`이며 기준 자체 cpp·h·inc의 이름 검색에서 초기화 이후 항목을 지우는 경로를 찾지 못했다. 캐시 사용 시 ID와 읽을 수 있는 vtable 포인터 등은 다시 검사하지만 게임 세대와 연결하지 않는다. 여러 유효 캐시 항목의 vtable이 다르면 unordered_map 순회에서 처음 만난 항목이 메모리 검색의 기준이 된다. 실제 캐시의 세대 간 생존이나 서로 다른 vtable의 존재는 확인하지 않았다.

프레임별 메모리 검색은 8바이트 정렬 주소에서 포인터와 `+8`의 2바이트 ID를 읽되, 두 값이 모두 현재 검색 예산 끝 안에 있을 때만 후보를 검사한다. `OfficerDetail.cpp:729-765`에서 예산 경계로 중단하면 다음 검색 시작 주소를 예산 끝으로 바꾸므로, 그 경계 바로 앞 8바이트 정렬 주소는 ID 2바이트가 경계를 넘는다는 이유로 이번에도 다음에도 검사하지 않는다. 예를 들어 정렬된 시작점과 8MiB 예산이면 `budgetEnd-8`이 빠진다. 이는 예산 때문에 영역 중간에서 중단한 경우의 소스 흐름이다. 해당 주소에 실제 후보가 있었는지는 확인하지 않았다. 회귀 조건에 프레임 예산 경계와 확보 경로별 vtable 차이를 포함한다.

`VirtualQuery`가 실패하거나 조회된 영역의 끝이 현재 주소보다 크지 않으면 검색 함수는 `finished=true`로 종료한다. 호출부는 정상적으로 전체 검색을 마친 경우와 구분하지 않고 그때까지 확보한 요청 기재만 후보 풀로 만든다. 하나라도 있으면 부분 풀로 배정을 진행하고, 없으면 객체를 찾지 못했다는 상태로 중단한다. 검색 실패 여부와 실제 게임에서의 발생은 확인하지 않았다. 회귀 조건은 기준 객체 부재와 runtime 배열 존재의 조합, 검색 중 조회 실패, 일부 후보만 확보된 상태에서의 진행이다.

## 기술 포인트 캡처 소스의 현재 연결 상태

`Cheats/Civilian/Techpointcave.cpp`는 프로젝트 컴파일 항목이지만, 기준 트리의 cpp·h·inc에서 `SetTechPCapture`와 `g_capturedTechPAddr`를 검색하면 이 구현과 헤더 선언 이외의 호출·읽기는 발견되지 않는다. 이 검색 범위에서 메뉴나 설정이 현재 기능을 켠다고 판단할 근거가 없다. 별도 링커·외부 호출 여부를 실행으로 검증한 것은 아니다.

함수 자체는 ON에서 패턴을 찾는 `CreateThread` 작업을 만들고 핸들을 곧바로 닫는다. 발견한 7바이트를 저장하고 인근 cave에서 RBX를 전역 주소에 캡처한 다음 원래 명령을 실행하도록 점프를 쓴다. OFF는 전역 캡처 주소를 지우며 적용 flag가 이미 true면 원본 복원과 cave 해제를 시도한다. OFF와 설치 worker를 동기화하거나 설치 요청 취소를 확인하는 코드가 없어서, OFF가 worker 설치 완료보다 앞서면 이후 설치될 수 있는 구조다. 설치 실패 후 할당한 cave를 해제하는 경로도 이 함수에는 없다. 실제 호출·경합은 확인하지 않았다.

이 소스를 이관할 때는 컴파일 입력이라는 사실과 사용자 기능으로 연결된 경로를 구분한다. 연결 여부, 설치 중 OFF, 패턴 불일치, 적용 실패 시 할당, callback 실행 중 해제와 종료가 검증 대상이다.



## 데모플레이 중지

worker는 전투 날짜가 1~30인 설치 창까지 100ms마다 기다리며 요청 취소를 확인한다. 설치 창 도달 후 알려진 RVA 또는 패턴을 한 번 찾고, 성공하지 못하면 worker 실행 flag만 내린다. OFF는 요청을 취소하지만 설치 직전의 마지막 요청 확인과 실제 설치 사이 전체를 잠그지 않는다. 회귀 조건은 P1 안정화 전 자동 요청, worker 진행 중 공통 재호출, 패턴 검색 실패 뒤 동일 상태 유지, 설치 직전 OFF 및 세션 reset이다. 실제 경합은 실행하지 않았다.

## 자동 환전의 평정 진입 게이트

`MonitorTechStatus`는 gameState가 평정 `0x05`일 때 `GetSystemMonthValue()`가 마지막 처리 월과 다르면 자동 환전을 호출한다. 함수는 환전 ON/OFF나 도시 배열 해석·쓰기 성공과 관계없이 호출 뒤 해당 월을 처리한 것으로 기록한다. 따라서 평정이 유지되는 동안 나중에 환전을 켜거나 일시적 주소 실패가 해소되어도 월 값이 바뀌지 않으면 이 게이트에서 다시 호출하지 않는다. 내정 `0x07`을 관측하면 마지막 월을 `0xFF`로 초기화하므로 같은 월의 다음 평정 진입은 다시 처리할 수 있다.

월 getter가 0을 반환해도 이 게이트는 별도로 1~12 범위를 확인하지 않는다. 이후 유효 월로 바뀌면 서로 다른 값으로 판단해 다시 호출할 수 있다. 환전은 모든 도시를 대상으로 하며 기존 [자동 환전 조건](P0_Feature_Contracts.md)의 0 나누기와 부분 쓰기 가능성은 별도다. 회귀 조건은 평정 중 ON, 월 0→유효 월, 같은 월의 평정→내정→평정, 도시 주소 일시 실패와 세대 교체다. 정적 조사이며 실행하지 않았다.

`RunAutoCityExchange`와 도시 목록 편집은 같은 `GetCityArrBase()` 기준의 도시 금·군량 주소를 사용한다. 후방지원도 같은 shifted city base를 받으면 `GetRawCityBase`에서 `-0x28`을 적용한 같은 금·군량 필드에 접근한다. 자동 환전은 background 경로에서 군량을 읽고 금을 읽은 다음 두 필드를 차례로 쓰며, 도시 목록과 수동 후방지원은 렌더 경로에서 접근한다. 이 작업들을 직렬화하는 공통 잠금은 해당 함수들에 없다. 읽기와 쓰기가 겹치면 한 작업의 오래된 계산값이 다른 작업 결과를 덮을 수 있는 구조다. 또한 환전 함수 자체는 도시 목록의 `s_snapDirty`를 설정하지 않아 다른 갱신 계기가 없으면 표시된 금·군량은 이전 스냅샷으로 남는다. 실제 경합이나 표시 결과는 확인하지 않았다.

파일에서 읽은 음수 설정도 실행까지 전달된다. 예를 들어 현재 군량 100, 한도 0, 남길 군량 -1, 환전 비율 10이면 조건을 통과해 초과분 101에서 금 10을 계산하고 남길 군량 -1을 `uint32_t`로 변환한 `0xFFFFFFFF`를 기록하려 한다. 음수 환전 비율은 음수 금 증가분을 unsigned로 변환해 기존 금에 더한다. 정상 양수 설정에서도 금 합계가 `uint32_t` 범위를 넘으면 unsigned 덧셈으로 순환하며, 초과 군량이 환전 비율보다 작으면 금 증가가 0이어도 군량은 남길 값으로 바뀐다. UI의 최소값 제한은 해당 입력값을 사용자가 변경했을 때만 실행되고 파일 로드 자체에는 적용되지 않는다. 실제 파일 적용과 쓰기는 실행하지 않았다.

## 세 위젯 설정과 표시 조건

`bShowWidgetHero`, `bShowWidgetAllOfficers`의 초기값은 false이고 `bShowWidgetNotif`의 초기값은 true다. 메인 메뉴의 각 체크박스는 flag를 바꾸고 알림과 일반 설정 저장을 호출한다. 세 배지는 `DrawMenu`의 메인 창이 접힌 분기에서만 그려진다. 주인공·모든무장 배지는 추가로 P1이 0이 아니어야 하고, 알림확인 배지는 P1 조건이 없다.

배지 클릭은 각각 무장 상세, 전체 무장 목록, 알림 기록 flag를 토글한다. 앞의 두 창을 열 때는 가운데 배치 요청도 세운다. 메인 메뉴가 펼쳐지면 배지는 표시하지 않고, 메인 메뉴 자체를 닫으면 `Menu::Render`가 `DrawMenu`를 호출하지 않는다. `IsAnyUIOpen`에도 세 위젯 flag는 포함되지 않으므로 위젯 설정만으로 닫힌 overlay를 깨우지 않는다. 다른 보조 창 flag로 overlay가 유지되더라도 메인 메뉴가 닫힌 상태에서는 이 배지 그리기 경로가 실행되지 않는다.

회귀 조건은 세 기본값과 저장·재로드, 펼침·접힘·메뉴 닫힘, P1 0과 유효 상태, 보조 창이 열린 상태, 배지 클릭 및 상세·목록의 가운데 배치다. 실제 화면과 입력은 실행하지 않았다.

## 적극 성향과 능력치 99 보정의 실행 차이

`bAllAggressive`의 `MonitorAllAggressive`는 저장된 주인공 주소가 바뀌거나 OFF일 때 자체 완료 상태를 리셋한다. ON 후 해당 주소를 관측하고 3초가 지나면 무장 배열을 해석해 최대 5102개 슬롯을 검사한다. 각 슬롯은 ID가 슬롯 번호+1이고 신분이 허용 목록에 있어야 하며, 성향이 4가 아니면 `+0x60`에 4를 쓴다. 배열 해석 실패는 다음 감시에서 재시도하지만, 배열을 찾은 뒤에는 유효 무장이 0명이거나 개별 보호 변경이 실패해도 순회 종료 후 완료 상태를 세운다. 이후 같은 주인공 주소와 ON 상태에서는 재시도하지 않는다. OFF는 감시 상태만 리셋하며 이미 바꾼 성향을 복원하지 않는다.

활성 평정 메뉴 `CouncilCompactSectionBase.h:275`의 `능력치 한계돌파` 체크는 `bAutoStatUp99`를 바꾸고 알림·설정을 저장하며 이 클릭 경로에서 즉시 전체 쓰기를 호출하지 않는다. `bAutoStatUp99`의 `UpdateOfficerStats99To100`은 같은 종류의 5102개 슬롯을 검사하지만 위 적극 성향과 신분 허용 목록이 다르고 슬롯 ID 일치 검사는 하지 않는다. 통솔·무력·지력·정치·매력 바이트가 정확히 99인 경우만 100으로 쓴다. `MonitorTechStatus`의 평정·월 변경 게이트에서 호출되므로 평정 중 같은 월에 나중에 ON하거나 배열 읽기·보호 변경이 실패해도, 이 게이트가 이미 해당 월을 처리했다면 그 시점에 다시 호출되지 않는다. 내정 관측 후 같은 월에 평정으로 돌아오는 경우의 게이트 reset은 [자동 환전 절](#자동-환전의-평정-진입-게이트)과 같다.

99 보정의 허용 신분은 `18/28/38/48/E8/D8/C8` 일곱 값이다. 전체 전법·특기 일괄 편집은 이 일곱 값에 `58/68/78/88`을 더한 열한 값을 허용하고 ID가 슬롯 번호 + 1인지도 검사한다. 따라서 두 작업이 같은 5102슬롯을 순회해도 대상 집합은 같지 않다. 99 보정의 로그에서 검색 대상 수는 슬롯 메모리 범위 검사에 통과한 직후 증가하므로 신분 필터를 통과한 무장 수가 아니다. 보정 수는 99 발견 후 보호 변경에 성공한 무장 단위이며 쓰기 뒤 재읽기나 보호 복원 성공은 확인하지 않는다. 이는 정적 코드 집계다.

적극 성향 감시는 `g_savedHeroAddr`를 사용한다. 이 주소는 유효한 새 P1을 찾았을 때 갱신되며 P1이 0이 될 때 이 갱신 경로에서 바로 비워지지 않는다. 따라서 P1이 잠시 사라지거나 같은 숫자 주소가 재사용될 때 이 감시의 세대 판정이 무엇을 관측할지는 별도 검증이 필요하다. 회귀 조건은 허용 신분 차이, 슬롯 ID 불일치, 부분 읽기·보호 변경 실패, 평정 중 ON, 같은 월 재진입, OFF 후 값, P1 무효화와 같은 주소 재사용이다. 실제 게임 쓰기는 수행하지 않았다.

## 모든 세력 기술 초기화 worker의 완료 조건

`Techzero.cpp` worker는 200ms마다 root와 월·경과 값을 확인한다. 월이 1·4·7·10이고 경과가 0이며 완료 flag가 false이면 pending과 시작 tick을 기록한다. 다음 검사부터 200ms가 경과하면 당시 해석한 root에서 최대 100개 세력의 기술 5바이트를 0으로 바꾼다. pending 이후 실행 직전에 월과 경과가 여전히 최초 조건인지 또는 root가 같은지는 다시 비교하지 않는다. 개별 주소 또는 보호 변경이 실패하면 그 세력을 건너뛰고, 중지되지 않은 채 순회가 끝나면 성공한 세력 수와 무관하게 완료 flag를 true로 만든다.

이 완료 flag는 분기월이 바뀌었다는 이유로는 초기화되지 않는다. worker가 월 0과 경과 0을 함께 관측하거나 기능을 OFF/ON할 때 초기화된다. 따라서 이 소스는 매 분기마다 무조건 재실행하는 구조가 아니다. worker의 event 대기가 `WAIT_FAILED`로 끝나면 worker는 종료하지만 enabled flag는 그대로다. 이후 ON setter는 enabled가 이미 true라 반환하므로 OFF로 정리하기 전에는 그 호출로 worker를 다시 만들지 않는다.

회귀 조건은 분기 경계와 pending 중 월·root 변경, 100개 중 일부 주소·쓰기 실패, 0/0 관측과 건너뛴 로드, 대기 실패 뒤 ON 재요청, OFF 중 순회 및 종료 대기다. 이 내용은 정적 코드 조사이며 실제 게임 실행 결과가 아니다.

## 군주 보너스의 게임 데이터와 종료 정리

`FactionLordBonus.cpp` worker는 root를 찾으면 관작 이름 48바이트를 한 번 쓰고, 다섯 보너스 항목의 각 15바이트를 매 pass 보정한다. 최대 120개 세력 중 존재하고 방랑 상태가 아니며 유효 군주 주소가 있는 세력에 대해 관작 등급 1~4는 각각 대응 보너스, 그 밖은 기본 보너스 포인터를 군주의 `+0x330`에 쓴다. 이전에 추적했으나 이번 pass에서 빠진 군주의 필드는 현재 root의 다섯 보너스 주소 중 하나와 일치할 때만 0으로 바꾼다.

관작 이름 적용 helper는 성공 여부를 반환하지 않지만 호출자는 시도 후 적용 flag를 true로 만든다. 해당 주소가 일시적으로 유효하지 않거나 쓰기 보호 변경이 실패해도 같은 활성화 기간에 이름 쓰기를 재시도하지 않는다. root가 바뀌는 경우에도 이 flag를 별도로 초기화하지 않는다. 군주 주소는 실제 포인터 쓰기 성공을 확인하기 전에 추적 집합에 추가된다.

OFF는 worker에 정지 요청을 보내고 기다린 뒤 그때의 root가 유효할 경우 추적된 군주의 현재 값이 그 root의 보너스 주소와 일치하면 0으로 바꾼다. 보너스 표 5곳의 15바이트와 관작 이름 48바이트는 이전 값을 보관해 복원하는 대신 0으로 쓴다. root를 얻지 못하면 `ClearAll`을 호출하지 않아 이 경로에서는 추적 집합과 게임 데이터를 정리하지 못한다. root가 이전 pass와 다르면 기존 세대에서 배정한 포인터는 새 root 기준의 주소 비교에 일치하지 않을 수 있다.

worker가 event 대기 실패로 종료할 때 running flag를 내리므로 별도 ON 호출은 이전 종료 핸들을 정리하고 새 worker를 만들 수 있다. 그러나 공통 설정 적용은 이 setter를 `void`로 호출하고 성공 여부를 받지 않으므로 같은 설정 상태에서 그 재호출이 자동으로 일어난다고 단정하지 않는다. 회귀 조건은 root 교체, 최초 이름 쓰기 실패, 세력·군주 변경, 부분 쓰기 실패, 이전 데이터가 0이 아닌 상태의 OFF, root 미해석 종료와 event 대기 실패다. 실행하거나 게임 데이터를 변경하지 않았다.

## 특수능력의 전투 쓰기·초기화 경로

`SpecialAbility.cpp`는 현재 활성 부대를 캐시의 raw 주소와 맞춰 군악대·무쌍보병·불꽃기병·원격궁병·총사령관·기습부대·대군사 일곱 flag를 얻는다. 이 중 하나라도 바뀌거나 유닛이 있는 상태에서 3초 검증 간격에 도달하면 해당 공통 게임 데이터의 각 대상 바이트에 활성값 또는 코드에 정한 비활성값을 쓴다. 비활성값은 설치 전에 저장한 원본이 아니다. 한 대상의 주소가 유효하지 않으면 건너뛰고, 보호 변경 실패는 해당 능력의 나머지 대상 처리를 중단한다. 마지막 flag 상태는 쓰기 성공과 관계없이 갱신되므로 같은 상태의 다음 시도는 3초 검증 조건 등에 의존한다.

이 공통 데이터의 두 포인터 `s_cachedP`, `s_cachedP2`는 `UpdateSpecialAbilities`의 지역 static이며 0일 때만 체인을 다시 해석한다. `ClearBattleCache`는 부대 벡터와 준비 flag만 지우며 이 두 포인터를 초기화하지 않는다. 새 전투·로드에서 그 포인터의 수명이 계속 유효한지는 별도 확인이 필요하다. 부대가 없을 때의 정리 호출도 같은 함수에 존재하지만, 실제 호출 순서와 이전 값 복구 성공은 정적으로 확정하지 않는다.

등갑군은 자동배정에서 제외되지만 수동 설정된 부대에는 처리 경로가 있다. 활성 부대의 대장 ID가 이전 기록과 달라질 때 300ms 검사 조건을 통과하면 화염 상태를 확인하고, 화염이면 병력 1000과 전의 10을 감산한다. 병력 1100 이하는 무조건 100, 전의 10 이하는 0을 쓴다. 따라서 병력이 이미 100 미만이면 100으로 증가하는 코드 경로다. 대장 ID는 화염 확인 전에 기록하므로 같은 대장의 상태가 이후 화염으로 바뀌어도 다른 대장이나 유닛 수 0을 거치지 않으면 이 조건에서 재검사하지 않는다.

무신은 500ms 전역 검사 시 캐시된 해당 부대의 전법 레코드를 최대 45개 확인하고 병종 제한 바이트를 0으로 쓴다. 인덱스나 선두 바이트가 예상과 다르면 그 뒤 레코드는 검사하지 않는다. 이 경로에 이전 제한값을 보관하거나 능력 OFF 시 복원하는 코드는 없다. 함선 병기화는 [별도 활성 부대 경로](P0_Stratagem.md#함선-병기화의-활성-부대-캐시)다.

회귀 조건은 같은 부대의 설정 변경, 공통 포인터가 바뀐 전투·로드, 대상 바이트 일부 접근 실패, 3초 재검사와 상태 전환, 등갑군 100·1100 경계 및 같은 대장의 화염 상태 변화, 무신 레코드 중간 불일치와 해제다. 실제 게임 쓰기나 실행은 하지 않았다.

## 날씨 전법과 격류·낙석 설정의 공통 바이트

`SetTerrainIgnore`와 `UpdateBattleEnvironment`는 정상적으로 같은 게임 테이블을 해석할 때 `exe+0x02ED7A10 → 0x110 → 0x120 → 0x40 → 0x168` 기준을 공유한다. 이관 대상의 두 기능을 별도 이름으로만 분리하면 다음 여섯 바이트의 실제 쓰기 순서를 놓친다.

| 기준 오프셋 | 격류·낙석 ON setter | 환경 갱신 |
|---|---:|---|
| `0xCAE`, `0xCD0`, `0xCF2` | 각각 11 | 날씨 옵션과 날씨 포인터가 준비되고 날씨가 2 또는 3이면 2, 그 외에는 9 |
| `0xD2E`, `0xD50`, `0xD72` | 각각 11 | 대폭 날씨 옵션과 날씨·바람 포인터가 준비되고 바람이 3이면 2, 그 외에는 27 |

대폭 날씨가 켜져도 바람 포인터를 얻지 못하면 대폭 전용 분기는 기본값을 쓰는 `else`로 간다. 하지만 날씨 포인터가 유효하면 뒤의 공통 날씨 분기는 별도로 실행돼 격류·화염 관련 값을 현재 날씨에 맞게 쓴다. 즉 바람 포인터 부재는 전체 날씨 갱신 중단과 같지 않다. 두 날씨 flag가 동시에 true인 경우에도 같은 조건이 적용된다.

환경 갱신의 조건이 성립해 이 코드를 실행하면 날씨 옵션이 꺼져 있어도 위 기본값 9·27을 쓴다. `BattleMonitor.cpp`의 새 전투 초기화는 격류·낙석 ON setter 다음에 환경 캐시를 준비하고 환경 갱신을 강제로 호출한다. 이후에도 유효한 부대·날짜 조건에서 주기 갱신한다. 따라서 두 함수가 같은 테이블을 가리키고 쓰기에 성공하면 초기 ON setter의 해당 여섯 값은 뒤이은 환경 갱신 값으로 바뀐다. 나머지 위력·범위 필드가 전부 덮인다는 뜻은 아니다.

환경 쪽은 테이블 주소를 캐시하고 setter는 매 호출마다 체인을 해석하므로, 세대 교체 중 두 주소가 다른 경우까지 같은 메모리에 쓴다고 단정하지 않는다. 회귀 조건은 날씨 두 옵션 OFF·간단·대폭과 각 날씨/바람, 격류·낙석 ON/OFF, 전투 진입 시 강제 갱신, UI 재적용과 다음 주기 갱신, 포인터 교체 및 일부 쓰기 실패다. 실제 전투 결과는 확인하지 않았다.

### 격류·낙석 OFF에서 남는 보조 효과 필드

`Terrainignore.cpp`의 선언 `k_terrainTable`에는 ON/OFF 값이 적혀 있지만, 실제 `SetTerrainIgnore`는 이 표를 순회하지 않고 각 주소에 직접 쓴다. 여섯 레벨의 효과2·대상2·특수2·확률2 24바이트는 `if (enable)` 안에서만 기록하므로 OFF에서 값을 쓰지 않는다. ON이 성공한 뒤 다른 코드가 건드리지 않았다면 각각 효과2는 격류 9·낙석 27, 대상2는 1, 특수2는 3, 확률2는 100으로 남는다. 선언된 표의 특수2 ON 값은 2지만 실제 setter의 값은 3이다. 조건·위력·범위 필드의 OFF 쓰기는 이 24바이트와 별개다.

따라서 표의 OFF 값이나 OFF 성공 로그만으로 해당 보조 효과 필드가 원래 값으로 복구됐다고 판단할 수 없다. 전투 세대 교체나 게임 자체의 쓰기에 따라 실제 값은 달라질 수 있다. 회귀 조건은 6개 레벨의 ON→OFF 필드별 값, 다른 경로의 중간 변경, 새 전투 초기화, 부분 쓰기 실패 및 앞 절의 날씨 갱신 순서다. 소스만 확인했고 실행하지 않았다.

## 방어 건물 수치의 입력·기록 범위

`TacticsEditWindow.cpp`의 건물 탭은 도시·관문·망루·성벽 투석기의 내구·사거리·공격·시야와 봉화대 내구·전의·시야를 각각 정수 입력으로 편집한다. 화면에는 시야가 사거리보다 커야 한다는 문구가 있지만, 이 입력 및 적용 경로에는 두 값의 관계를 검사하거나 정수를 범위 제한하는 처리가 없다. 설정 파일 로드도 이 19개 항목에 대해 정수를 읽어 변수에 저장한다.

`SetDefBuildingBoost` ON은 각 `int`를 `uint16_t`로 변환해 19개 필드에 쓴다. 따라서 음수나 65535보다 큰 정수가 입력되면 기록값은 16비트 부호 없는 변환 결과다. OFF는 기존 값을 보관해 복원하지 않고 도시 3000/3/8/5, 관문 2000/3/8/3, 망루 700/3/6/3, 성벽 투석기 1000/4/9/4, 봉화대 700/5/3을 순서대로 쓴다. 적용 버튼은 저장을 먼저 호출하고 현재 ON/OFF flag로 setter를 부른 뒤 setter의 결과와 무관하게 알림을 낸다.

setter는 대상 영역 `0x20BA0`바이트에 대한 최초 `VirtualProtect` 성공을 확인하지만, 원래 보호로 되돌리는 호출의 결과는 확인하지 않는다. 최초 보호 변경 실패 시 이 setter의 필드 쓰기를 수행하지 않는다. 회귀 조건은 19개 필드의 ON/OFF, 시야와 사거리의 같음·역전, 음수·65535·65536 입력, 저장 후 재로드, 주소 해석·보호 변경 실패와 적용 완료 알림이다. 실제 입력·게임 쓰기는 실행하지 않았다.

### 공통 설정 재적용이 같은 루프에 들어오는 경우

`Menu::Loops`는 같은 background 반복에서 먼저 `ProfiledMonitorBattleStatus`를 호출하고 그 뒤 `ApplyStoredConfigs`를 호출한다. 전체 전투 감시가 실제 실행되어 새 전투 초기화의 `SetTerrainIgnore(true)`와 강제 환경 갱신이 끝난 뒤, 같은 반복에서 공통 설정의 1초 검사·P1 안정화·전투 준비 조건도 만족하고 `bTerrainIgnore`가 ON이며 `s_appTerrain`이 false라면 공통 설정이 setter를 다시 호출한다. 이 경우 같은 주소와 성공을 전제로 여섯 조건 바이트의 순서는 `11 → 환경값 → 11`이 될 수 있다. 다음에 환경 갱신이 해당 경로를 다시 실행하면 환경값으로 바뀐다.

따라서 앞 절의 “초기 setter 다음 환경 갱신”은 전투 감시 내부의 순서이며, 같은 background 반복 전체가 끝난 시점의 최종값을 항상 환경값으로 확정하는 말은 아니다. 별도 메뉴 렌더에서 setter를 호출하는 경우와 서로 다른 스레드의 실제 순서도 정적으로 확정하지 않는다. 회귀 조건에는 공통 적용 flag의 기존 상태, 1초 검사와 3초 안정화 경계, 전투 준비 첫 반복, 이후 환경 주기 및 메뉴 적용을 포함한다.

## 교류 횟수 제한의 비트와 실패 상태

`MenuSectionsSocial.cpp`의 기증·담화·대련·토론 체크박스는 setter를 즉시 호출한 뒤 표시 상태로 알림과 설정 저장을 수행한다. 네 setter의 반환형은 `void`다. 별도의 `ConfigBase.inc` 자동 적용은 p1 준비 조건을 통과하면 적용 상태를 먼저 true로 표시하고 setter를 호출하므로, 설치 실패는 저장된 체크나 자동 적용 상태에 반영되지 않는다. 메뉴의 직접 호출은 이 자동 적용 상태를 갱신하지 않는다.

- 담화는 원래 `or [rdi+0x320], 4`를 `and [rdi+0x320], 0xFFFFFFFB`로 바꾼다. 따라서 그 명령이 실행될 때 이미 설정된 bit 2도 지운다. cave 할당 뒤 `ApplyJmp`가 실패하면 cave를 해제하지 않고 적용 flag도 올리지 않는다. 이후 OFF는 적용 flag가 false라 해제하지 않으며, 다시 ON을 시도하면 cave 주소를 덮어쓸 수 있다.
- 대련·토론은 하나의 공통 hook에서 새로 OR할 EAX의 bit 8·9를 활성 옵션에 따라 제거한 뒤 원래 OR을 실행한다. 대상 메모리에 이미 설정된 비트를 지우는 동작은 아니다. 설치 실패 시 해당 내부 enable flag를 내리고 실패한 cave를 해제한다. 다른 옵션이 활성인 동안에는 공통 hook을 유지한다.
- 기증은 원본 `or [rsi+0x320], 0x400`을 `and [rsi+0x320], 0xFFFFFBFF`로 교체한다. 따라서 명령이 실행될 때 기존 bit 10도 지운다. 원본 또는 이미 패치된 바이트만 인식하며 OFF의 복구 쓰기가 실패해도 내부 적용 flag는 false가 된다.

담화 OFF와 대련·토론이 모두 OFF가 된 경로는 `RestoreBytes` 호출 후 복원 성공을 확인할 수 없는데도 cave를 `VirtualFree`하고 적용 상태를 지운다. `RestoreBytes`는 쓰기 권한 변경이 실패하면 원본을 쓰지 않고 반환한다. 따라서 그 실패 경로에서는 원래 점프가 남아 있는데 대상 cave를 해제할 수 있다. 대련·토론의 두 내부 enable 값은 `volatile uint8_t`이고 메뉴·설정 경로의 쓰기와 cave의 읽기를 묶는 동기화는 이 코드에 없다. 실제 보호 변경 실패와 동시 실행은 확인하지 않았다.

담화와 대련·토론은 RDI, 기증은 RSI를 기준으로 같은 `+0x320` 오프셋을 쓰지만, 이 코드만으로 서로 같은 객체라고 확정할 수 없다. 담화의 공통 `ApplyJmp`와 `RestoreBytes`는 명령 캐시를 비우지 않는다. 대련·토론은 OFF 복원 뒤 명령 캐시를 비우며, 기증은 쓰기마다 비운다. `RestoreBytes`는 복원 성공 여부를 반환하지 않는다. 실제 callback 실행 스레드와 토글 중 실행 여부는 미확인이다.

이관 확인 항목: 이미 설정된 비트와 새로 설정되는 비트, 대련·토론의 네 조합, 각 패턴 미발견 및 쓰기 실패, 메뉴 표시와 실제 적용 상태, OFF 복원, 실행 중 토글과 게임 버전 변경.

## 전투 기한과 시작일 스킵의 실제 경계

`Menu_impl.inc:143`의 유동 조절 도움말은 총부대 20 미만·20~29·30 이상을 각각 15·20·25일로 설명한다. 반면 실제 `BattleEnvironment.cpp:240`은 `unitListBase - 0x08`에서 읽은 총부대 바이트가 **15 미만이면 15일, 15~19이면 20일, 20 이상이면 25일**로 기록한다. 따라서 15~29 부대 구간에서 도움말과 실제 분기가 다르다. 이 기록은 정적 소스 기준이며 어느 값이 기획 의도인지는 확인되지 않았다.

메뉴에서 한 모드를 켜면 다른 모드를 끄지만, `UpdateBattleEnvironment`는 두 flag가 모두 true인 경우 상시 15일을 우선한다. 두 모드가 모두 꺼지면 종료일에 30을 쓴다. 유동 모드에서 목록 포인터 또는 부대 수 바이트를 읽을 수 없으면 종료일을 새로 쓰지 않는다. 이후 시작일 스킵은 그 시점의 종료일을 다시 읽어 사용한다. 양수 스킵은 현재 전투일이 1일 때만 적용하며, 스킵 수가 종료일 이상이면 종료일 - 1로 줄이고 결과가 양수일 때 현재일을 `1 + 스킵 수`로 쓴다. `InputInt`는 UI에서 음수를 0으로 바꾸지만 이 실행 함수도 양수 여부를 따로 검사한다.

환경 함수는 실행 파일 기준 주소가 없으면 바로 끝난다. 그 외에는 200ms 간격 검사 직후 시각을 갱신하고 함선병기 처리를 먼저 호출한 다음 날짜 주소와 현재일 1~30을 확인한다. 따라서 유효하지 않은 날짜 때문에 종료해도 간격 시각은 갱신되며, 함선병기는 날짜 검사보다 먼저 실행된다. 강제 호출은 200ms 제한을 우회하지만 시각은 갱신한다. 함선병기 자체에는 별도 300ms 제한이 있다. 날짜 변경 알림 경로는 유동 모드에서 부대 목록이 유효하지 않으면 알림과 강제 환경 갱신을 보류한다.

종료일과 시작일 쓰기에 쓰는 `WriteByteIfDiff`는 `void`이며 보호 변경이 실패하면 값을 쓰지 않고 돌아간다. 종료일 쓰기 성공 여부를 확인하지 않고 직후 메모리에서 종료일을 다시 읽어 스킵 상한으로 사용한다. 시작일 쓰기 역시 성공 여부와 무관하게 스킵 발동 로그를 남긴다. 실패해 현재일이 1로 남으면 후속 환경 호출에서 다시 시도할 수 있다. 보호 복원 결과도 호출자에게 전달하지 않는다. 실제 쓰기 실패나 후속 재시도는 확인하지 않았다.

환경 갱신은 200ms 제한을 통과하면 날짜 주소와 날짜 범위를 확인하기 전에 `lastEnvTick`을 현재 시각으로 바꾼다. 이후 주소·날짜가 유효하지 않아 반환하더라도 다음 일반 호출은 제한 간격을 기다린다. `force=true` 호출은 제한을 건너뛰지만 같은 시각 값을 갱신하므로 그 직후 일반 호출의 제한에도 영향을 준다. 각 바이트 쓰기 helper는 성공 여부를 반환하지 않으며, 다음 갱신이 해당 분기에 다시 도달할 때 현재 값과 목표값이 다르면 다시 쓰기를 시도한다.

`UpdateBattleEnvironment`의 초기 전투 진입 호출과 일반 주기 호출은 `BattleMonitor.cpp`에서 각각 SEH로 감싸지만 날짜 알림을 위한 강제 호출(`:832`)은 해당 호출 지점에서 별도 SEH로 감싸지 않는다. 환경 함수의 날씨·바람 필드 읽기와 `WriteByteIfDiff`의 최초 바이트 읽기는 해당 주소에 대한 별도 SEH 없이 수행된다. 호출 지점별 예외 처리 차이를 이관 조사에 포함하며 실제 예외 발생이나 프로세스 결과는 확인하지 않았다.

### 함선병기 발동 캐시

`ApplyShipWeaponization`은 300ms 간격으로 활성 부대와 지형을 읽는다. 지형이 물 11·12이면 대상 전법 다섯 바이트를 4로 쓰고 현재 부대 주소와 `triggered=false`를 캐시한다. 다른 지형에서는 활성 부대 주소가 이전과 달라졌을 때만 구성원 최대 세 명의 `0x1009` 특수능력 횟수를 조회하고, 같은 주소면 이전 `triggered`를 재사용한다. 따라서 같은 부대가 물에서 육지로 이동하면 물에서 저장한 false를 계속 사용해 부대 주소가 바뀌기 전까지 능력을 다시 조회하지 않는다. 같은 주소에서 구성원이나 능력 횟수가 바뀌어도 그 변화만으로 재조회하지 않는다.

발동 시 다섯 대상에 8, 비발동 시 4를 쓰며 대상 값의 원본은 저장하지 않는다. `ClearBattleEnvCache`는 전법·지형 주소와 부대 지형 캐시는 비우지만 함수 내부 정적 `s_lastActiveUnit`·`s_lastTriggered`를 초기화하지 않는다. 동일 주소가 다른 전투에서 재사용되는 경우도 이 캐시 조건에 포함된다. 실제 부대 전환과 주소 재사용 여부는 확인하지 않았다. 회귀 조건은 같은 부대의 물→육지·육지→물, 구성원·능력 변경, 부대 주소 교체와 전투 간 주소 재사용이다.

무장 상세 창의 함선 병기화 체크는 현재 무장과 선택된 무장의 `0x1009` 값을 `SetTargetSkillCount`로 변경한다. 이 설정 변경은 위 함수 내부의 발동 캐시를 직접 무효화하지 않는다. 또한 설정의 지연 저장은 [특수능력 수치 파일 조사](P0_Resources.md#지연-저장과-종료)처럼 이후 조회에 의존하는데, 함선병기 경로는 같은 활성 부대 주소를 재사용할 때 `GetTargetSkillCount`를 다시 호출하지 않는다. 따라서 창을 닫은 뒤 이 경로의 반복 호출만으로 설정의 즉시 반영이나 지연 저장을 보장할 수 없다. 다른 조회·명시 저장이 일어나는 경우는 별개이며 실제 UI 실행 순서는 확인하지 않았다.

다섯 대상의 상대 오프셋 `0x9A4`, `0xA24`, `0xAA4`, `0xB24`, `0xBA4`를 기준 자체 cpp·h·inc에서 텍스트 검색했다. 이 다섯 표기는 위 함수의 두 배열과 `AffinityDisplay.h`의 `0xBA4` 한 곳에서 나타난다. 후자는 전법 데이터가 아니라 생성 중인 별도 버퍼의 오프셋이다. 이 검색은 동일 주소를 다른 수식·십진수·간접 포인터로 쓰는 경로를 배제하지 않으므로 전체 쓰기 충돌이 없다는 증거는 아니다.

이관 회귀 조건: 부대 수 14·15·19·20·29·30, 도움말과 실제 기준의 차이, 두 모드 동시 활성, 목록 미준비 시 기존 종료일과 스킵, 현재일 1과 그 외 날짜, 종료일 경계, 일반·강제 호출과 날짜 알림 보류. 실제 전투에서의 부대 수 값과 스레드는 확인하지 않았다.

## 지형 보너스 창의 편집·복원과 초기값 차이

`Menu_impl.inc:192`의 버튼은 지형 보너스 창을 연다. 창의 12개 병종 × 11개 지형 입력은 각각 -30~30으로 제한해 전역 `g_TerrainBonusTable`에 바로 쓴다. 편집 전 복사본이 없다. `닫기`와 창 닫기 버튼은 저장 호출이나 값 되돌리기 없이 창만 닫는다. `저장 후 닫기`는 현재 전역 테이블을 `SaveConfig`로 저장하고 닫는다. 따라서 저장하지 않고 닫아도 이 프로세스의 현재 테이블에는 편집이 남는다.

`기본값 복원`도 별도 적용 버튼 없이 13×18 전체 전역 배열을 복사하며 즉시 파일에 저장하지 않는다. 이 배열과 `MenuState.cpp`의 프로세스 초기 배열을 행·열별로 대조하면 234개 칸 중 두 칸이 다르다. 병종 11(정예궁병)의 지형 16(도하)은 초기 10·복원 0이고, 지형 17(암석)은 초기 0·복원 10이다. 초기 행의 명시값이 하나 부족하여 마지막 칸이 0으로 초기화되는 결과다. 나머지 칸은 이 정적 대조에서 같다. 설정 파일 로드 후 시작 상태는 저장 파일의 값에 따라 달라진다.

창 안내는 저장 후 지형 보정을 껐다 켜야 반영된다고 설명한다. 그러나 `BattleEnvironment.cpp:121,395`는 지형 보정이 활성일 때 조건을 만족하는 갱신마다 전역 테이블을 직접 읽는다. 따라서 해당 갱신이 실행되고 유효한 부대·지형에 도달하면 저장이나 재활성화 이전에도 편집된 값을 읽는 코드 경로가 있다. 렌더의 편집과 background 갱신은 서로 다른 호출 경로이며 테이블 접근의 공통 잠금은 이 두 코드에 보이지 않는다. 실제 동시성이나 전투 표시 결과는 확인하지 않았다.

회귀 조건은 초기·복원 배열의 정예궁병 도하/암석, 설정 파일 로드, 편집 후 닫기와 재열기, 복원 후 저장하지 않고 닫기, 저장 실패, 보정 ON 중 편집과 다음 갱신, 다른 세대로의 전환이다.

### 알림 비우기와 기록 삭제의 범위

`Menu_impl.inc:795`의 `알림 비우기`는 현재 표시 벡터 `g_notifications`만 비운 뒤 모든 내역을 초기화했다는 로그를 남긴다. 이미 UI로 옮겨진 `g_notificationHistory`, 생산자 pending 큐, 생략 카운트는 이 버튼에서 지우지 않는다. 반대로 `NotificationManager.cpp:301`의 `기록 삭제`는 history와 그 계측 크기만 지우며 현재 표시와 pending은 유지한다.

`Menu::Render`에서는 메뉴를 그린 뒤 `DrawMarqueeNotifications`를 호출하므로 메뉴 하단에서 표시를 비운 같은 렌더 호출에 남아 있던 pending을 표시·history로 옮기는 경로가 있다. history를 먼저 비워도 아직 pending인 알림은 이후 drain에서 다시 기록된다. 두 동작은 모두 UI 쪽 표시·기록 벡터에 대한 작업이며 생산자 큐는 별도 mutex로 보호한다. 실제 생산과 렌더의 동시 실행 순서는 확인하지 않았다.

회귀 조건은 표시만 존재, history만 존재, pending이 남은 상태의 각 버튼, 두 버튼 순서, 큐 포화 생략 알림, 같은 렌더 단계의 재표시 및 UI가 닫힌 동안 발생한 알림이다.
알림 속도는 `NotificationManager.cpp:18`에서 100.0으로 시작하고 하단 슬라이더는 20~500 px/s 범위에서 변경할 때 설정을 저장한다(`Menu_impl.inc:790`). 설정 로드는 `ConfigBase.inc:328-335`에서 `std::stof` 결과를 범위 제한 없이 대입한다. 따라서 파일의 범위 밖 값도 로드 경로에서는 그대로 남으며, 렌더 단계의 실제 이동량은 `g_notificationSpeed * scale * SpeedHack_GetRealDeltaTime()`이다. 알림은 표시 영역의 왼쪽을 완전히 지난 후 추가로 100픽셀을 벗어나거나, 표시 벡터에 넣은 시각 기준 30초가 지나면 렌더 중 제거된다(`NotificationManager.cpp:46-58, 231-261`). 이 시각은 생산자가 큐에 넣은 때가 아니라 UI가 대기 항목을 꺼낸 때다. 속도 0이나 음수의 설정 파일을 포함해 UI 범위와 로드 값, DPI scale, 배속 변경 및 30초 수명을 이관 시 각각 확인해야 한다. 이는 정적 경로이며 실제 표시 결과는 실행하지 않았다.

### 세력 기술력 편집과 자동 초기화의 동일 필드

`FactionTechEditor.cpp`의 root 체인과 `Techzero.cpp`의 root 체인은 모두 실행 파일 `+0x034C8630`에서 시작해 `+0`, `+8`, `+0x10`, `+0` 순서로 포인터를 읽는다. 편집기는 `root + 0xC6848 + index * 0x998 + 0x205`의 5바이트를 사용하고, 자동 초기화는 `root + 0xC6A4D + index * 0x998`의 5바이트를 0으로 쓴다. 두 상수는 같으므로 같은 root를 해석한 경우 각 인덱스의 기술 필드가 정확히 겹친다.

편집기는 존재 조건을 통과한 최대 120개 세력을 대상으로 캐시 주소에 직접 기록한다. 초기화 worker는 세력 존재 여부를 검사하지 않고 앞의 100개 인덱스에서 유효한 5바이트를 확인해 0으로 만든다. 따라서 0~99번은 조건이 맞으면 두 경로가 같은 값을 쓰지만 100~119번은 편집기에 나타나더라도 자동 초기화의 순회 범위 밖이다. 초기화는 분기월 감지 후 지연 실행하며 완료 flag의 재설정 조건은 [기술 초기화 항목](#모든-세력-기술-초기화-worker의-완료-조건)을 따른다.

편집은 렌더 호출, 초기화는 별도 worker에서 실행되며 두 쓰기를 직렬화하는 공통 잠금은 해당 함수들에 없다. 동일 필드에 어느 값이 마지막으로 남는지는 실행 순서에 달려 있고, 편집기가 캐시한 root와 worker가 새로 해석한 root가 세대 전환 중 다를 수도 있다. 실제 경합은 확인하지 않았다. 회귀 조건은 99·100번째 인덱스 경계, 존재하지 않는 세력, 초기화 지연 중 편집·MAX, 부분 쓰기 실패, 창을 연 채 게임 로드 및 완료 flag 초기화다.

시나리오 시작 설정 `StartSetting_impl.inc:68,215`도 동일한 root 체인을 사용한다. 조건이 맞으면 쓰는 `root+0xC73E7`과 `root+0xC73E8`은 위 기술 배열의 **인덱스 1, 필드 2·3**과 각각 같다(`0xC6A4D + 0x998 + 2/3`). 세력 편집 화면의 필드 순서로는 궁병과 병기다. 시작 설정은 두 값을 각각 3과 4로 쓰고, 기술 초기화 worker는 해당 5바이트를 0으로 쓴다. 두 worker 사이에 이 쓰기를 직렬화하는 공통 잠금은 해당 경로에서 확인되지 않았다.

시작 설정은 root의 연도 필드가 0이고 특정 군주 포인터 조건이 맞을 때 실행하며, 초기화는 분기월·경과 시간 조건을 사용한다. 이 두 조건이 실제 게임에서 동시에 성립하는지는 실행하지 않아 확인되지 않았다. 조건이 함께 성립하고 같은 root를 가리킬 때는 마지막 쓰기에 따라 두 필드가 달라질 수 있으므로, 이관 회귀 조건에 시작 설정·기술 초기화·수동 편집의 세 경로와 세대 전환을 함께 포함한다.

### 도로 차단의 표시·적용 실패와 재시도

### native 전투 상태 표본과 판정 지연

`BattleMonitor.cpp:186`의 `SampleBattleState`는 일반 감시와 특수능력 fallback이 공유하는 정적 표본을 최대 200ms 동안 재사용한다. 게임 기반 주소 또는 전투 세션 generation이 바뀌면 이 시간 안이라도 표본을 초기화한다. 재측정 시 세션 포인터를 확인하고 전투 부대 수가 1~60이면 앞의 최대 네 개 부대만 검사해 native 상태를 찾는다. 각 후보는 root·상태 기계의 역참조와 특정 vtable 주소, state ID 0~20 및 meeting 값 0~1을 확인한다. 다섯 번째 이후 부대에서만 유효한 상태가 발견되는 경우 이 표본에서는 찾지 못한다.

세션과 상태를 읽은 경우 meeting 값이 1이거나 state ID가 19 이상이면 비전투(0), 그 외 ID가 3 이상이면 전투(1)다. ID 0~2는 미확정(-1)으로 남는다. 세션이 유효하지만 native 상태를 찾지 못하고 게임 상태가 평정 5 또는 내정 7이면, 그 상태가 600ms 이상 지속돼야 비전투로 판단한다. 상태를 다시 찾으면 누락 시작 시각을 지우고, 세션이 유효하지 않거나 다른 게임 상태면 누락 시간을 지운다. 세션이 유효하고 ID 0~2인 경우에는 첫 분기에서 누락 시간을 지우며 미확정을 반환한다.

일반 감시가 실행된 뒤 fallback이 같은 wrapper에서 이어 호출될 때 두 경로는 별도 표본 함수가 아닌 이 `SampleBattleState`를 사용한다. 두 호출 사이 200ms가 지나지 않고 generation·gameBase가 같으면 fallback은 일반 감시의 표본을 재사용한다. 시간 경계를 넘거나 세대·base가 달라지면 다시 측정할 수 있다. 따라서 두 경로가 언제나 다른 관측값을 읽거나 언제나 같은 관측값을 읽는다고 단정하지 않는다. 실제 호출 간격은 측정하지 않았다.

`Menu.cpp`의 fallback은 같은 판정이 미확정이면 캐시 정리 없이 반환하고, 비전투면 활성 fallback의 특수능력과 부대 캐시를 정리한다. 일반 감시도 미확정에서 쓰기를 중단한다. 따라서 200ms 표본 재사용, 600ms 누락 판정, 1초 runtime 준비는 서로 다른 단계다. 회귀 조건은 첫 네 부대와 다섯 번째 후보, ID 2·3·18·19·20·21, meeting 0·1, 평정·내정의 일시 누락과 600ms 경계, generation 변경 및 동일 주소 재사용이다. 실제 상태 ID의 게임 내 의미와 스레드는 실행하지 않아 확인하지 않았다.

### 전투 준비 전 특수능력 fallback의 주기와 전환

`Menu.cpp:38`은 일반 전투 감시를 runtime 준비 전에는 최소 500ms 간격으로 실행하고, 준비가 된 뒤에는 호출될 때마다 실행한다. 같은 wrapper는 일반 감시 실행 여부와 무관하게 그 뒤 특수능력 fallback을 호출한다. fallback은 native 상태가 전투이고 일반 runtime이 미준비일 때만 진행한다. 활성화 전 시도 간격은 100ms, 캐시 활성 후 처리 간격은 1000ms다. 이 숫자는 호출에 적용하는 최소 간격이며 실제 호출 주기나 지연의 상한을 보증하지 않는다.

fallback은 게임 기반 주소가 바뀌면 기존 활성 캐시와 특수능력 상태를 정리하고 주소를 다시 해석한다. 부대 목록·날짜 주소의 전체 체인은 마지막 해석 후 500ms가 지나거나, 캐시된 두 주소가 있었는데 읽을 수 없게 된 경우 다음 fallback 처리에서 다시 해석한다. 활성 상태에서는 fallback 자체가 1000ms 간격이므로 500ms마다 반드시 체인을 읽는 것은 아니다. 해석한 주소가 달라지면 기존 캐시를 정리하고 새 값을 저장한다.

부대 수 1~60과 날짜 1~30을 확인한 후 처음 활성화하거나 부대 수가 바뀌면 부대 캐시를 생성하고 특수능력을 갱신한다. 목록 주소·날짜 주소·부대 수가 같을 때 구성원만 바뀌는 경우 이 fallback의 재생성 조건에는 포함되지 않는다. 일반 runtime이 준비되면 fallback 지역 상태를 비우고 반환하며, 이 분기 자체는 `ClearBattleCache`를 호출하지 않는다. 비전투·주소 변경·유효하지 않은 전투 데이터 분기는 활성 상태에 따라 별도 정리를 수행한다.

회귀 조건은 fallback 비활성·활성 간격, 500ms 체인 재해석과 1000ms 실행 제한의 조합, 캐시 주소 읽기 실패, 부대 수 변경과 같은 수의 구성원 교체, 일반 감시 준비 완료로의 전환, native 상태 미확정과 비전투 전환이다. 주기와 실행 결과는 코드에서 확인한 정적 조건이며 실제 측정값이 아니다.

### 세션 P1 감지와 전투 generation 갱신

`Menu_impl.inc:369`의 background loop는 gameBase에서 `+0xE0` 포인터를 읽고 P1·gameBase 주소가 바뀌거나 마지막 검사 후 200ms가 지나면 각각의 읽기 가능 범위를 재검사한다. 주소가 그대로면 그 사이에는 이전 검사 결과를 재사용한다. 기재 설정 tick은 이 루프에서 세션 전환 처리보다 먼저 호출된다.

이전에 추적한 P1이 있을 때 현재 P1 또는 gameBase가 달라지거나 P1이 준비되지 않으면 `ResetBattleSessionRuntime(oldP1,p1)`과 책략·회복 세션 초기화를 순서대로 호출한다. 전투 초기화는 generation을 올리고 준비 상태·캐시된 전투 주소를 비운 뒤 부대·환경 캐시를 폐기한다. 전투 감시 함수의 지역 정적 상태는 pending flag를 통해 다음 감시 호출에서 초기화한다. 유효 P1이 0으로 바뀐 뒤 다시 유효해지면 이탈 시 한 번, 새 P1 연결 시 `ResetBattleSessionRuntime(0,p1)`으로 한 번 더 generation을 올린다. 첫 연결 분기는 책략·회복 세션 초기화를 반복 호출하지 않는다.

주소가 변하지 않는 동안 P1 가독성이 마지막 검사 후 잠깐 실패했다가 다음 200ms 검사 전에 복구되면, 이 루프의 캐시된 `p1Ready`는 그 불연속을 관찰하지 못한다. 그러한 구간에 같은 주소의 새 데이터가 들어와도 P1 주소·base 주소·cached ready만 사용하는 세대 전환 분기는 이를 구분하지 못한다. 이후 다른 상태 검사나 명시적 reset이 이를 감지하는지는 별도이며, 실제 메모리 전환은 확인하지 않았다.

이 판정은 P1과 gameBase의 주소 및 읽기 가능성에 의존한다. 같은 주소가 그대로 유효하게 재사용되고 그 사이 관측 가능한 불연속이 없다면 이 분기만으로는 다른 저장 세대를 구분하지 못한다. P1이 계속 유효하지 않은 동안에는 추적값을 0으로 내려 동일 이탈 초기화를 매 loop 반복하지 않는다. 회귀 조건은 유효→0→같은 주소, 유효→다른 주소, 같은 P1에서 gameBase 변경, 200ms 검사 사이의 일시적 메모리 변화, 감시 호출 전 pending 초기화와 기재 tick의 순서다. 실제 로드 시 주소와 스레드 동작은 확인하지 않았다.

### 행동력과 보주 교체 횟수의 지속 쓰기

`bInfiniteAP`와 `bFastJewel`은 기본 설정에 저장되는 flag지만 공통 설정표의 setter와 적용 추적 포인터는 없다. 메뉴 체크박스는 값을 바꾼 뒤 알림과 설정 저장을 호출한다. 실제 반영은 `Menu::Loops`의 background 경로에서 수행한다. 행동력은 P1 준비 시 `p1+0xEE`의 한 바이트에 매 loop 200을, 보주 교체는 gameBase 준비 시 `gameBase+0x5C49`의 한 바이트에 매 loop 0을 쓴다. 두 경로는 현재 값 비교, 기존 값 백업, 메모리 보호 변경 또는 쓰기 성공 확인 없이 직접 대입한다. `p1Ready`와 `gameBaseReady`는 각각 `IsValidPtr(p1, 0x200)`, `IsValidPtr(gameBase, 0x6000)`의 결과를 주소가 바뀌거나 200ms가 지날 때까지 재사용한다. 해당 검사는 `MEM_COMMIT`과 접근 금지·guard 여부를 확인하지만 쓰기 권한을 확인하지 않으며, 여러 영역 사이의 중간 영역도 모두 검사하지 않는다. 쓰기 시점에 이 조건이 유지되는지와 실제 실패는 실행하지 않았다.

각 flag를 끄면 해당 loop 쓰기를 중단하며 마지막으로 쓴 값을 복구하지 않는다. 주소 유효성은 바로 앞 세션 검사 결과를 사용하고, 같은 주소가 유지되면 최대 200ms 간격으로 재검사한다. 따라서 메뉴의 ON 알림은 즉시 쓰기 성공을 뜻하지 않고, OFF 역시 기존 값을 되돌렸다는 뜻이 아니다. 보주 교체 횟수 flag와 보주 전체 개방·보조 보주 선택은 별도 기능이다.

회귀 조건은 설정 로드 후 첫 쓰기, P1 또는 gameBase 미준비, ON/OFF 후 마지막 값, 대상 주소 변경, 동일 주소의 읽기 가능성 변화 및 보주 개방 기능과 동시 사용이다. 실제 쓰기 주기와 게임 결과는 확인하지 않았다.

### 배우자 후보 갱신과 자녀 표시

`PregnancyManager.cpp:229`은 주인공·roster 또는 관계 조회에 실패하면 기존 `g_pregnancyCurrentSpouses`를 바꾸지 않고 false를 반환한다. 관계 조회가 부분 결과로 성공하면 그 결과의 배우자만 주소로 해석하고, 새 목록 전체를 mutex 아래 기존 목록에 대입한다. 창 열기와 슬롯 교체 직후 호출자는 이 갱신의 반환값을 확인하지 않는다. 교체 성공 직전에는 이전 배우자를 후보 목록에 추가하지만, 뒤이은 갱신이 성공하면 관계 조회 결과로 목록을 다시 교체한다. 갱신이 실패하면 직전에 유지한 목록이 남는다.

각 배우자의 자녀 표시는 roster 최대 5102개를 읽어 ID 1~5102, 출생·등장·사망 연도가 모두 0이 아니고 등장·사망이 출생보다 이르지 않은 레코드만 대상으로 한다. 부모 포인터 둘 중 하나가 주인공이고 다른 하나가 후보 배우자의 정규화된 포인터와 같아야 한다. 자녀 ID 중복은 전체 배우자 후보에 걸쳐 한 번만 허용하고 각 후보의 자녀 ID를 정렬한다. 배우자 출생 연도 읽기 실패는 0을 남긴다.

일반 주기 `RunPregnancyManagerUpdate`는 임신 슬롯 캐시를 다시 읽지만 배우자 후보 전체를 새로 조회하지 않는다. 따라서 후보 목록의 갱신 시점과 세 슬롯의 상태 갱신 시점은 다르다. 회귀 조건은 관계 조회 실패와 부분 성공, 창 재열기, 교체 후 재조회 성공·실패, 중복 자녀 ID, 연도 누락·역전, 부모 포인터 변경 및 같은 주소의 저장 세대 교체다. 실제 UI와 게임 데이터는 실행하지 않았다.

### 군단 관계 그룹의 목표 인원 조정

`CityInfoWindow.cpp`는 선택한 관계로 연결된 군단 무장을 전이적으로 합친 뒤, 그룹 전체가 선택 도시의 남은 목표 인원보다 많으면 그 도시의 `targetCount`를 우선 필요한 수로 늘린다. 부족분은 다른 도시의 미배정 목표에서 두 차례 회수한다. 첫 순회는 각 도시의 이미 배정된 인원과 최소 1명 중 큰 값을 바닥으로 삼고, 두 번째는 이미 배정된 인원만 바닥으로 삼는다.

다른 도시에서 부족분을 전부 회수하지 못해도 늘린 목표 인원을 되돌리지 않는다. 해당 상황은 debug가 켜져 있을 때만 로그에 남긴다. 따라서 관계 그룹을 유지하려는 목표 조정 뒤 도시별 `targetCount` 총합이 원래 총합보다 커질 수 있다. 이 값은 추천·배치 계획의 목표치에 대한 코드 동작이며, 실제 게임 무장 수가 늘어난다는 의미는 아니다.

관계 조회가 실패하면 관계 연결이 없으므로 그룹 보존을 위한 위 조정도 해당 연결에 대해 발생하지 않는다. 회귀 조건은 여러 관계의 전이적 연결, 대상 도시의 기존 배정, 다른 도시의 1명 바닥, 두 번째 회수, 회수 가능한 목표가 부족한 경우 및 부분 관계 조회다. 실제 자동배치는 실행하지 않았다.

### 수동 적용과 평정 자동 적용의 단계 호출 차이

수동 화면의 `배치 적용` 버튼은 추천이 준비되고 일반·군사 이동 또는 태수 변경이 남아 있을 때만 활성화된다. 이동 대상이 있을 때만 1단계를 호출하며, 성공 후 태수 변경 수를 다시 계산해 0보다 클 때만 2단계를 호출한다. 2단계 반환값은 이 버튼 핸들러에서 사용하지 않는다. 1단계 실패면 2단계를 호출하지 않는다. 각 단계 자체의 알림·로그와 복구는 앞 절에 기록한 함수 동작을 따른다.

평정 전이에서 실행하는 자동 경로는 대상 군단마다 추천을 새로 만든 다음 1단계와 2단계를 순서대로 호출하고 두 반환값을 성공·실패 집계에 반영한다. 일반·군사 이동이 없더라도 1단계 함수는 쓰기 목록이 비었다는 알림을 낸 뒤 성공을 반환하므로 2단계로 진행할 수 있다. 사라졌거나 소속이 바뀐 대상은 대상 목록에서 제거하고 성공·실패 카운트에는 넣지 않는다. 마지막 알림의 현재 대상 수는 제거 후 목록 크기다.

회귀 조건은 이동만, 태수만, 둘 다 없음, 1단계 성공·2단계 실패, 삭제된 대상과 여러 군단의 부분 성공, 수동·자동 경로의 알림과 집계 차이다. 실제 배치는 실행하지 않았다.

### 군단 자동배치의 중간 상태와 세션 초기화

단계 감시기는 게임 상태 중 내정 `0x07`과 평정 `0x05`만 유효 상태로 기록한다. 그 밖의 상태 또는 상태 읽기 실패는 0으로 취급해 이전 유효 상태를 바꾸지 않고 반환한다. 따라서 내정 관측 뒤 다른 상태를 거쳐 평정을 관측해도 마지막 유효 상태가 내정이면 `07→05` 전이로 처리한다. 반대로 시작 후 처음 관측한 유효 상태는 기준으로만 저장한다.

자동 대상이 하나 이상이면 이 단계 판정보다 먼저 P1·도시 배열·주인공 세력 주소 및 날짜 읽기를 확인한다. 하나라도 실패하거나 저장된 주소와 다르면 `ClearCorpsAutoDeploymentSession`을 즉시 호출한다. 이 함수는 자동 실행 flag를 끄고 대상 목록을 지우며 배우자·상생·의형제 묶기 선택을 모두 true로 되돌린다. 날짜가 이전에 관측한 연월보다 뒤로 가도 같은 초기화를 수행한다. 이 코드는 일시적인 읽기 실패와 실제 저장 세대 변경을 구별하지 않는다.

이 감시기는 background loop에서 실행되는 반면 `DrawCorpsDeploymentRecommendation`은 렌더 경로에서 같은 자동 실행 bool·관계 옵션과 대상 벡터를 읽고 변경한다. 감시기는 대상 검증·삭제 후 포인터를 별도 벡터에 복사하지만, 원본 벡터의 확인·순회·복사 자체와 UI의 추가·삭제를 함께 직렬화하는 잠금은 해당 경로에 없다. 자동 실행은 도시 선택과 무장 목록 상태도 변경한 후 이전 도시 인덱스로 복원하고 목록을 다시 읽는다. UI가 이 상태를 동시에 편집하거나 읽는 실제 순서는 확인하지 않았다. 회귀 조건은 감시 중 대상 추가·삭제, 관계 옵션 변경, 세션 초기화와 렌더, 자동 실행 중 도시 선택 변경이다.

회귀 조건은 `07→다른 상태→05`, 첫 관측이 05, 평정 상태 반복, 대상이 있을 때 일시 읽기 실패, 날짜 역행, 같은 주소 재사용과 초기화 후 묶기 선택값이다. 실제 로드·평정 전이는 확인하지 않았다.

### 보조 보주 훅의 캐시와 설치 실패

`JewelSettings.cpp:257`은 예상 원본 바이트 검사 후 `MH_CreateHook`이 성공한 경우에만 활성화를 시도한다. 생성 실패 시 기존 등록을 제거하지 않는다. 활성화 실패는 새로 만든 대상을 `MH_RemoveHook`으로 제거하고 원본 함수 포인터를 null로 바꾸지만 제거 결과를 확인하지 않는다. 선택 bit는 훅 설치가 성공한 뒤 저장하므로 ON 설치 실패는 해당 선택을 새로 켜지 않는다.

런타임 데이터 존재 검사는 `gameBase + sizeof(uintptr_t) × (보주 ID + 0xB11DE)`에서 포인터를 읽고, 그 포인터가 가리키는 값을 한 번 더 읽어 둘 다 0이 아닌지 확인한다. 따라서 같은 ID라도 x64와 Win32는 슬롯 오프셋과 각 읽기 크기가 다르다. 주소 접근 예외는 데이터 없음으로 처리한다. 실제 Win32 게임 데이터의 배치는 확인하지 않았다.

판정 callback의 런타임 데이터 캐시는 일반 배열·일반 기준 주소·일반 시각 배열이다. 게임 기준 주소 변경이나 메뉴에서 보조 보주를 켜는 경로 등은 배열 전체를 초기화한다. 선택 bit는 atomic이지만 캐시의 초기화와 callback의 조회·갱신을 묶는 공통 잠금은 이 파일에 없다. 게임 callback과 메뉴·설정 적용이 서로 다른 스레드에서 겹치는지, 실제 캐시 결과가 어떻게 보이는지는 실행하지 않아 확인되지 않았다. 같은 gameBase에서 한번 존재로 판정된 항목은 명시적인 캐시 초기화 전에는 재조회하지 않는다.

회귀 조건은 원본 바이트 불일치, 기존 MinHook 등록, 생성·활성화·제거 실패, 선택 ON 실패, gameBase 교체와 같은 주소의 런타임 객체 교체, 캐시 초기화 중 callback이다.

### 보조 보주 마스크의 게시 단위

`JewelSettings.cpp`는 8개의 64비트 atomic word를 각각 relaxed load/store해 128자리 16진 마스크를 저장·로드한다. 개별 word는 atomic이지만 여덟 word 전체를 하나의 스냅샷으로 교체하거나 읽는 잠금·버전은 없다. 전체 선택 ON은 먼저 여덟 word를 0으로 바꾼 다음 정의 목록의 비트를 순서대로 켠다. 전체 OFF는 여덟 word를 차례대로 0으로 만든다. 설정 로드는 형식·정의 ID·필요한 훅 설치를 확인한 뒤 정제된 여덟 word를 차례대로 게시한다.

따라서 게시 중 게임 판정이 실행되면 개별 ID의 새 선택과 이전 선택이 섞인 중간 상태를 볼 수 있다. 저장 측이 동시에 읽는 경우에도 여덟 word가 같은 시점의 선택이라는 보장은 이 코드에 없다. 이는 코드의 동기화 범위에 대한 정적 분석이며 실제 호출이 겹치는지는 확인하지 않았다. 훅 설치 실패를 포함한 로드 실패 시 호출자가 전체 해제하는 동작과 구버전 키 우선순위는 앞 절을 따른다.

회귀 조건은 서로 다른 word에 걸친 선택, 전체 ON·OFF 중 callback, 설정 저장과 선택 변경의 겹침, 정의 밖 비트와 빈 마스크, 훅 설치 실패다.

### 지형 보정 부대 캐시의 재구성 기준

`BuildTerrainUnitCache`는 목록 주소와 부대 수를 먼저 저장한 뒤 각 슬롯의 부대 주소, 병종 포인터 체인, 지형 주소를 확인한다. 유효하지 않은 슬롯은 건너뛰며, 성공한 항목에 부대 주소·지형 바이트 주소·그때 읽은 병종 값을 보관한다. 갱신 시 목록 주소 또는 수가 바뀌거나 캐시가 비어 있을 때만 다시 만든다. 따라서 일부 슬롯만 준비되지 않아 부분 캐시가 만들어졌다면 그 슬롯이 나중에 준비돼도 같은 목록 주소·수와 비어 있지 않은 캐시만으로는 재구성하지 않는다.

회귀 조건은 일부만 준비된 목록, 빈 캐시의 다음 tick 재시도, 같은 수의 슬롯·병종·지형 포인터 변경, 목록 주소 변경, 전투 환경 캐시 초기화 및 OFF 복원이다.

### 특수능력 캐시의 부분 생성과 준비 표시

`SpecialAbility.cpp:140`은 캐시를 지우고 설정 맵을 복사한 뒤 목록의 각 슬롯을 읽는다. 슬롯·부대·구성원 포인터가 유효하지 않으면 해당 슬롯을 건너뛰고 계속한다. 입력 인자가 최초 조건을 통과하면 유효 부대가 0개이거나 일부만 읽혔어도 마지막에 `g_CacheReady=true`를 설정한다. 이 함수는 `void`이므로 호출자는 읽은 부대 수를 반환받지 않는다.

회귀 조건은 모든 슬롯 미준비, 일부 슬롯 준비 뒤 같은 수로 나머지 준비, 멤버 포인터 변경, fallback에서 일반 감시로 전환, 예외와 조기 반환이다. 실제 게임 상태는 확인하지 않았다.

### 전투 특수능력 정리 호출의 조건

`BattleMonitor.cpp:472`의 확정 비전투 정리는 `ClearBattleCache` 후 `UpdateSpecialAbilities(0, 0, exeBase)`를 호출한다. 반면 `Menu.cpp:69-71,108-110,124-126,169-171,198-200`의 fallback 정리 경로는 이 순서가 반대다. `UpdateSpecialAbilities`는 부대 수가 0이어도 `ScanActiveUnitAbilities`를 호출하므로, fallback에서는 캐시를 지우기 전 활성 부대가 여전히 일치하면 해당 flag가 true일 수 있다. 일반 감시처럼 캐시를 먼저 비워 활성 부대 조회가 실패한 경우 일곱 능력 flag는 false로 남는다. 캐시를 먼저 비운 경로에서 직전 flag 중 하나가 true였다면 상태 변화로 공통 데이터 쓰기 분기에 들어가 모든 능력의 코드상 비활성값을 시도한다. 직전 flag가 모두 false이면 부대 수가 0인 호출에서는 3초 주기 검증도 성립하지 않아 이 공통 쓰기 분기에 들어가지 않는다.

일반 감시에서 `gameBase==0`이면 캐시와 전투 적용 flag는 지우지만 이 분기는 `UpdateSpecialAbilities(0, 0, ...)`를 호출하지 않는다(`BattleMonitor.cpp:435-456`). 반면 base가 있고 native 상태가 음수이면 쓰기와 캐시 정리를 건너뛰고 반환하며, 명확한 비전투 상태에서만 위 정리 호출을 시도한다. fallback도 음수 상태에서는 정리하지 않고 반환한다(`Menu.cpp:66-78`). 따라서 base 소실·상태 확인 실패·비전투 확정은 같은 복원 결과가 아니다. 실제 로딩 중 포인터와 상태 변화는 실행하지 않았다.

일반 감시의 base 소실 분기는 `s_nativeBattleSeen`, `s_isWarModsApplied`, `s_isCacheBuilt`를 모두 false로 만든다. 이후 base가 돌아왔을 때 별도 새 전투 관찰 없이 곧바로 비전투로 판정되면, 세 flag를 조건으로 하는 일반 감시 정리 호출도 건너뛰는 코드 경로다. 이 결론은 일반 감시의 상태 변수에 한정하며, 별도의 fallback 또는 다른 호출이 개입하는 순서는 실행하지 않았다.

fallback 정리 호출에서 기존 캐시의 활성 부대와 이전 일곱 flag가 그대로 일치하면, 부대 수가 0이므로 주기 검증도 꺼져 공통 쓰기 분기에 들어가지 않는다. 그 다음 fallback은 캐시를 비우고 `s_fallbackActive=false`로 바꾸므로, 같은 fallback 정리 분기가 반복 호출되어 비활성값을 반드시 쓰는 구조는 아니다. 이후 일반 감시 등 다른 호출이 일어나면 그 경로에서 다시 판정할 수 있다. 같은 `ProfiledMonitorBattleStatus` 호출에서는 일반 감시가 실행 조건을 통과하면 먼저 실행되고, 그 뒤 fallback이 실행된다(`Menu.cpp:261-271`). 일반 감시가 주기 제한으로 생략된 호출에는 fallback만 실행된다. 실제 활성 부대 포인터와 어떤 호출에서 상태가 바뀌는지는 확인하지 않았다.

공통 대상별 접근 불가 주소는 건너뛰고 보호 변경이 실패하면 해당 능력 목록의 나머지를 중단한다. 캐시를 먼저 비운 경로는 반환값 없이 함수 끝에서 일곱 이전 상태를 false로 저장하므로, 정리 중 일부 복원이 실패한 뒤 부대 수 0 상태의 같은 호출만 반복해서는 상태 변화에 의한 재시도가 발생하지 않는다. 이는 코드에 정한 비활성값 쓰기의 흐름이며 적용 이전 값 백업 복원이 아니다. 실제 종료 순서와 메모리 쓰기 성공은 확인하지 않았다.

회귀 조건은 이전 활성 flag 유무, 캐시를 먼저 지운 정리 호출, 주소 해석·보호 변경 부분 실패, 반복 정리, 다음 전투와 이전 테이블 주소의 수명이다.

### 날씨 전법과 특수능력의 직접 바이트 오프셋 대조

`BattleEnvironment.cpp`에서 텍스트 형태의 `tacticBase + 16진수` 직접 참조 15개와 `SpecialAbility.cpp`의 `{16진수, 정수, 정수}` 대상표 항목 92개를 PowerShell 정규식으로 추출해 오프셋 집합을 비교했다. 두 집합에서 같은 숫자 오프셋은 발견되지 않았다. 특수능력 추출에는 별도 `p2` 기준 총사령관 대상도 포함된다.

이 비교는 지정한 표기 형태의 숫자 대조다. 상대 주소가 다른 포인터 체인, 다바이트 쓰기의 인접 바이트, 간접 계산, 다른 소스 파일 및 실제 런타임 주소의 동일성은 다루지 않는다. 따라서 두 기능의 모든 메모리 쓰기가 충돌하지 않는다는 증거로 사용하지 않는다. 앞서 확인한 격류·낙석과 날씨 갱신의 직접 중복은 그대로 별도다. 게임과 빌드는 실행하지 않았다.

## 성능 진단과 로그 출력 조건

`PerformanceDiagnostics.h`는 게임 기능과 별도로 성능 집계를 제공한다. `bFileLog`가 true면 진단이 활성화된다. 그 외에는 프로세스 환경 변수 `S8RPK_PERF_DIAGNOSTICS`를 처음 확인할 때 32바이트 버퍼로 읽어 대소문자 구분 없이 `1`, `true`, `on`, `yes`만 활성으로 판정하고 결과를 정적 값으로 보관한다. 파일 로그가 켜져 있는 동안에는 환경 변수 판정에 도달하지 않으므로 이 정적 판정은 처음 파일 로그가 꺼진 상태에서 확인될 때 이루어진다. `helper.h`의 `DEBUG`는 이 진단의 활성화 스위치가 아니다. `_DEBUG`는 환경 기록에 출력할 Debug/Release 문구를 고르는 데 쓰인다.

환경 로그의 아키텍처 문구는 `_WIN64`가 정의되면 `x64`, 아니면 `x86`이다. 따라서 이 문구는 64비트 여부를 기준으로 선택하며 다른 64비트 아키텍처를 따로 구별하지 않는다. 모듈 집계는 최대 1024개 핸들을 대상으로 네 DLL 이름만 세고, 모듈 열거 실패는 모두 0인 집계와 구분해 기록하지 않는다. 실제 지원 대상의 아키텍처 판정이나 전체 모듈 목록으로 사용하지 않는다.

`PerfScope`는 활성 상태를 생성 시 확인하고 파괴 시 경과 시간을 기록한다. 시작 브리지·초기화, 배속 갱신, 전투 감시, 전법·특기 수치 저장, 알림 생산·렌더와 로그 호출·뮤텍스 대기·파일 IO가 코드에 연결돼 있다. `PerfMetric`에 이름이 있는 `MenuLoopHeartbeat`, `IsValidPtr`, `FindPattern`, `MonthCaptureScan`은 기준 자체 cpp·h·inc 텍스트 검색에서 이름 정의와 출력 분기 외의 계측 호출을 찾지 못했다. 이름이 선언됐다는 이유만으로 이 네 측정값이 기록된다고 간주하지 않는다.

시간은 `QueryUnbiasedInterruptTime`을 우선하고 실패 시 시스템 시간을 사용한다. `PerfRecord` 또는 `PerfScope`가 기록할 때 보고 시각을 확인하며, 첫 기록은 5초 뒤 시각만 설정한다. 그 후 기한을 넘긴 기록이 발생해야 보고하며 별도 보고 스레드는 없다. 보고는 현재 배속과 알림 큐·기록 크기 및 측정별 호출 수·총/평균/최대 시간·바이트·변경 수를 `AddLog`에 전달하고 각 카운터를 원자적으로 개별 교환한다. 로그 계측은 `PerfRecordNoReport`를 사용해 보고가 다시 보고를 호출하는 재귀를 피한다. 개별 카운터 교환은 한꺼번에 묶인 스냅샷이 아니므로 다른 스레드의 기록이 보고 경계에 걸칠 수 있다.

`AddLog`는 `bShowDebug`와 `bFileLog`가 모두 false면 즉시 반환한다. 따라서 환경 변수만으로 진단을 활성화해도 두 로그 출력이 모두 꺼져 있으면 보고 문자열은 출력되지 않는다. 파일 로그가 켜져 있으면 기록은 비동기 큐로 전달되며 큐 제한이나 종료 상태에 따라 버려질 수 있다. 회귀 조건은 파일 로그 ON/OFF와 환경 변수의 최초 판정 순서, 출력 경로가 모두 꺼진 경우, 첫 기록과 5초 이후 기록, 동시 계측과 보고, 로그 큐 포화 및 시작·종료 구간이다. 게임과 빌드는 실행하지 않았다.
### 내정 포상 패치의 재설치·종료 경로

`DomesticRewardCondition.cpp`는 OFF에 성공해도 실행 중인 코드에 대비해 `g_cave`를 유지한다. 하지만 다음 ON에서는 기존 cave가 있더라도 `WritePayload`가 전체 공간을 `0xCC`로 채운 뒤 새 payload를 쓴다. OFF 시 해당 cave의 실행 완료를 기다리거나 다음 ON 전 확인하는 경로는 이 함수에 없다. 모드 전환 중 적용 상태라면 payload를 다시 쓰지 않고 `g_modeValue`만 원자적으로 변경한다. 코드 공간을 보존하는 동작과 재작성 시 실행이 끝났는지는 별도다.

최초 ON의 새 할당은 상대 점프 생성 또는 payload 작성 실패 시 해제한다. 반면 payload 준비 후 설치 직전 원본 비교가 실패하거나 점프 쓰기·설치 후 검증이 실패한 경우, 이미 할당한 cave는 남고 모드는 0으로 돌아간다. 점프 쓰기가 실패로 반환됐을 때 현재 바이트가 완성된 자기 패치와 일치하면 원본 복구를 시도하지만, 설치 후 검증 실패에서는 현재 바이트를 보존한다. OFF에서 복원 쓰기 또는 읽기 검증이 실패하면 이전 모드로 되돌리나 `g_applied`는 true로 유지한다. 실제 바이트가 어떤 상태인지는 실패 지점에 달려 있다.

기준 자체 cpp·h·inc에서 `SetDomesticRewardMode`의 호출은 메뉴 UI에서만 찾았으며 정상 종료에서 OFF하는 호출은 확인하지 못했다. 따라서 이 기능을 켠 채 종료하거나 빠르게 OFF→ON할 때 기존 callback과 DLL의 수명이 어떻게 되는지 실행 근거가 없다. 회귀 조건은 설치 직전 바이트 변경, 부분 쓰기와 검증 실패, OFF 복원 실패, 실행 중 빠른 OFF→ON 및 활성 상태 종료다.
## 수동 특수능력 자동 부여의 진행 창

`MenuSectionsOfficerEdit.cpp:449-555`의 수동 버튼은 실행 중 상태를 한 번 읽어 비활성화를 감싼다. `AutoAssignSpecialAbilities`가 작업 시작에 성공한 경우에만 모달을 연다. 진행 중에는 진행률과 상태를 표시하고 취소 버튼만 제공한다. 취소 버튼은 즉시 창을 닫거나 결과를 적용하지 않고 취소 요청을 기록한다. `TickSpecialAbilityAutoAssign`이 요청을 worker에 전달하고 완료를 확인하면 대기 결과와 표시 결과를 비운 뒤 취소 상태로 바꾼다. 완료 후에는 신규 부여된 무장의 결과 행 또는 신규 결과 없음 메시지와 닫기 버튼을 표시한다.

진행률은 worker가 처리한 슬롯 수를 전체 슬롯 수로 나눈 값이며, 판정 진행률이지 실제 신규 부여의 성공률이 아니다. 진행 상태의 갱신과 결과 반영은 `Menu_impl.inc:520`의 tick 경로에 의존한다. 연말 자동 작업은 같은 작업 상태를 사용하지만 수동 버튼의 모달 열기 경로를 거치지 않는다. 회귀 조건은 시작 실패 시 팝업 미표시, 실행 중 재시작 제한, 작업 중 취소 요청과 worker 완료 사이, 신규 부여가 없거나 이미 보유한 경우의 결과 표시, 연말 작업과의 중복 요청이다. 소스 경로만 확인했고 UI와 worker를 실행하지 않았다.

취소의 경계는 worker 종료 후 tick의 취소 검사다. 그 검사에서 요청을 관찰하면 결과 적용을 건너뛰지만, 검사 후 `FinishAutoAssignJob`에 들어간 경로에는 취소를 다시 확인하거나 이미 반영한 항목을 되돌리는 코드가 없다. 화면 취소 요청과 tick은 서로 다른 호출 경로에서 일반 `cancelRequested`를 읽고 쓰며 공통 잠금이 보이지 않는다. 따라서 취소 버튼 표시만으로 모든 시점에 취소가 보장된다고 판단하지 않는다. 검사 전·후와 결과 적용 중 요청은 별도로 검증해야 한다. 세부 스레드 근거는 [worker 조사](P0_Workers.md#특수능력-자동배정-worker와-결과-적용)에 있다.

## 즉시 경애 코드 패치의 상태와 복구

`Fastrelationship.cpp:37-105`의 `SetFastRelationship`은 첫 ON 때 실행 모듈에서 8바이트 원본 패턴을 찾고 주소를 보관한다. 원본 바이트를 복사한 뒤 8바이트 패치를 쓴다. 패치 쓰기는 보호 변경 성공 후 `memcpy`, 명령 캐시 flush, 보호 복원 순서이며 마지막 두 호출의 결과는 검사하지 않는다. 주소를 한 번 찾은 이후 OFF→ON에서는 캐시된 주소의 현재 바이트를 원본으로 다시 저장하고 패치한다. 그때 현재 바이트가 처음 찾은 원본 패턴과 같은지 재검사하지 않는다.

OFF는 현재 코드가 자기 패치인지 확인하지 않고 `RestoreBytes`를 호출한 후 명령 캐시를 flush하고 내부 적용 flag를 내린다. `RestoreBytes`는 반환값이 없으므로 호출자는 보호 변경·복사 성공을 확인하지 못한다. 메뉴와 설정 로드의 setter도 반환값이 없는 경로다. 회귀 조건은 검색 실패, 보호 변경 실패, OFF 전 외부 코드 변경, 복원 실패 후 재활성화, 캐시된 주소의 재사용 및 메뉴 flag와 실제 바이트 불일치다. 실제 코드 패치는 실행하지 않았다.

## 충성도 패치의 설치 실패와 재시도

`Loyaltycave.cpp:26-109`의 ON은 worker가 원본 패턴 주소를 찾으면 7바이트를 저장하고 대상 근처에 128바이트 cave를 할당한다. cave는 대상 무장의 `+0xEC`에 100을 쓴 뒤 원래 읽기 명령을 수행한다. `ApplyJmp`가 성공한 경우에만 `g_loyaltyCaveApplied`를 true로 바꾼다.

cave 할당 후 `ApplyJmp`가 실패하면 설치 함수는 false를 반환하지만 해당 할당을 해제하거나 `g_loyaltyCaveAddr`를 비우지 않는다. OFF의 해제 분기는 적용 flag가 true일 때만 실행되므로 이 실패분을 해제하지 않는다. 다음 ON 시도에서 새 할당이 성공하면 같은 전역 주소에 덮어쓴다. 또한 검색한 hook 주소는 보관하고 후속 ON에서는 패턴을 다시 찾지 않고 현재 7바이트를 원본으로 복사한다. 실제 할당 실패나 재시도 결과는 실행하지 않았다. 회귀 조건은 할당 성공 후 점프 범위·보호 변경 실패, OFF, 재시도 시 원본과 남은 할당, 설치 중 OFF와 게임 세대 전환이다.

## 내정 배율의 기준 무장과 세력

`DomesticsMult.cpp:48-103`에서 생성한 cave는 `r12`가 0이면 배율 처리를 건너뛴다. 저장된 기준 무장 주소가 0이면 처음 관찰한 0이 아닌 `r12`를 기준 무장으로 저장하고, 그 무장의 `+0x18` 세력 포인터도 저장한다. 이후 동일 무장 주소에는 플레이어 배율을, 기준 세력 포인터가 0이 아니고 현재 무장의 세력 포인터와 같으면 세력 배율을 적용한다. 이 코드는 첫 `r12`가 현재 주인공임을 별도로 확인하지 않는다.

ON 시작과 OFF는 기준 주소 둘을 0으로 만들지만, 이미 설치된 상태에서 다시 ON하면 초기화 전에 반환한다. `ResetDomesticsPlayer`도 같은 두 값을 지우지만 기준 자체 cpp·h·inc에서 정의·선언 외 직접 호출을 찾지 못했다. 따라서 같은 설치 상태에서 세이브·주인공·세력이 바뀌어도 이 경로만으로 기준 주소가 자동 갱신된다고 판단할 수 없다. 첫 관찰의 실제 게임 의미, 주소 재사용과 세력 변경 결과는 실행하지 않았다. 회귀 조건은 최초 호출 무장, 최초 세력 포인터 0, 주인공·세력·세이브 전환, OFF→ON과 동일 주소 재사용이다.

### 내정 배율 cave의 null 분기 길이

`DomesticsMult.cpp:53-55,150-154`는 `r12 == 0`이면 끝의 공통 복귀 코드로 이동하려고 2바이트 `je rel8`을 만들고, 나중에 `(uint8_t)(idx - pCodeNull - 1)`로 변위를 채운다. 소스의 바이트 출력과 `idx += 8`을 순서대로 세면 분기 operand는 cave offset 11, 의도한 공통 복귀 코드는 offset 183이다. 필요한 상대 변위는 +171이지만 signed rel8의 양수 범위는 0~127이다. 기록되는 `0xAB`는 -85로 해석되므로 실제 분기 대상은 cave 시작보다 73바이트 앞이다.

소스에서 생성할 바이트를 메모리에서 재구성하고 독립 x86-64 디스어셈블러로 확인한 첫 명령은 `test r12,r12` 다음 `je`가 cave 시작보다 앞을 가리킨다. 나머지 같은 함수의 여섯 단거리 분기는 계산한 목적지와 일치했다. 이는 생성 코드의 정적 분석이며 해당 hook을 설치하거나 `r12 == 0`이 실제 발생하는지는 확인하지 않았다. 이관 시 null 분기와 짧은 분기의 signed 범위, 공통 복귀, 원본 명령 재실행을 검증한다.

내정 배율 cave는 원본의 `cmovle r14d, edi` 이후 선택된 대상의 `r14d`를 `cvtsi2ss`로 부호 있는 32비트 정수에서 단정도 실수로 바꾸고, 플레이어 또는 세력 `float` 배율을 곱한 뒤 `cvttss2si`로 부호 있는 32비트 정수로 변환한다. 소수점 이하는 0 방향으로 버린다. 예를 들어 해당 분기에 들어간 값 5와 배율 1.25는 6이 된다. 계산 전 `xmm0`를 스택에 보관하고 이후 복구하며, 원본 `cmovle` 뒤의 flag도 push/pop으로 보존한다. 이는 생성 명령의 계산 계약이고 게임에서 해당 값의 의미나 실제 분기 도달을 검증한 결과는 아니다. 범위 밖 배율은 [설정 조사](P0_Config.md#내정-배율-입력과-설치-실패)의 로드 조건과 함께 확인한다.

## 혐오·상극 hook의 부분 설치와 기록 대상

`InstantLoveCave.cpp:180-228`의 worker는 두 번째 hook을 먼저 찾고 설치한 뒤, 성공 여부와 관계없이 첫 번째 hook도 찾고 설치한다. 두 번째 cave는 대상 명령의 `hookAddr+4`에서 4바이트 offset을 읽어 전역 `g_dynOffset`에 저장한다. 이 값의 초기값은 0이다. 두 번째 hook을 찾지 못했거나 cave 할당에 실패해 offset 읽기에 이르지 못한 첫 설치에서는 첫 번째 cave가 이 0을 쓰기 명령의 displacement로 복사할 수 있다. 첫 cave가 해당 쓰기 분기에 도달하면 `[rax+rbx+0]`에 100을 쓰는 코드가 만들어진다.

첫 cave의 displacement는 설치 시 즉시값으로 복사되므로, 이후 두 번째 cave가 offset을 다시 읽어 전역값을 바꾸더라도 이미 설치된 첫 cave의 명령이 자동으로 바뀌지 않는다. 반대로 기존 실행 중 얻은 offset이 남은 뒤 후속 부분 설치가 일어나면 초기 0이 아니라 그 저장값이 사용될 수 있다. 실제 패턴 발견·주소의 게임 의미·쓰기 분기 도달은 확인하지 않았다. 회귀 조건은 두 hook의 검색·할당·설치가 각각 실패한 경우, 첫 설치와 재설치의 offset, 설치 순서 및 실제 대상 주소다.

첫 cave의 화면 노출 `HateIgnore` 모드는 관계 바이트가 8 이하이거나 99 미만이면 쓰기를 건너뛰므로, 실제 100 기록 분기는 값이 99 이상일 때다. 이는 소스 주석의 “8 미만일 때만” 설명과 다르다. `Normal` 모드는 8보다 크고 bit 3이 켜진 값에서 기록한다. 두 모드 모두 기록 전에 값을 읽고 주소 캡처 명령을 실행하지만, 아래와 같이 전역 변수에 관계 주소를 보존하지 않는다. 실제 게임의 각 값 의미는 검증하지 않았다.

두 번째 hook은 원본 9바이트 비교 명령 뒤의 2바이트 `jne`까지 11바이트를 덮는다. `InstantLoveCave.cpp:149-171`은 비교 명령만 cave에 복사하고 `je`로 동등할 때 100 기록을 건너뛴 뒤, 어느 경우든 원본 `jne` 다음인 `hookAddr+11`로 복귀한다. 원래 `jne`의 상대 분기 대상은 계산하거나 복원하지 않는다. 따라서 비교 결과가 달라 원본 `jne`가 분기할 경우에도 설치된 cave는 원래의 fall-through 주소로 진행한다. 원본 분기 변위가 0이면 두 주소는 같다. `je`, `mov`와 복귀 점프는 비교 플래그를 바꾸지 않는다. 실제 검색된 명령의 분기 변위와 그 대상의 게임 동작은 확인하지 않았다. 회귀 조사에서는 비교가 같은 경우와 다른 경우 각각의 기록 주소·값과 원래 분기 목적지를 함께 확인해야 한다.

첫 cave의 주소 캡처도 주석과 출력 바이트가 다르다. `InstantLoveCave.cpp:63-68`은 먼저 `lea r11, [rax+rbx+0xF0]`로 관계 주소를 계산하지만, 바로 `mov r11, &g_capturedLoveAddr`로 덮어쓴다. 이어지는 `4D 89 1B`는 디스어셈블 결과 `mov [r11], r11`이므로 전역 변수에 관계 주소가 아니라 그 전역 변수 자신의 주소를 저장한다. 이 cave에 도달했을 때의 명령 의미이며 실제 실행은 확인하지 않았다. 기준 자체 cpp·h·inc 검색에서는 값을 반환하는 `GetCapturedLoveAddr`의 선언과 정의 외 호출처를 찾지 못했다.

두 번째 hook 검색 패턴은 첫 두 바이트 `41 80`과 아홉 바이트 뒤 `75` 등만 고정하고 중간 바이트를 와일드카드로 둔다. 따라서 패턴 자체는 처음 9바이트가 주석에 적힌 비교 명령 하나인지, offset이 `+4`에 있는지 보장하지 않는다. 위 분기 설명은 소스가 가정하는 9바이트 비교 및 뒤이은 `jne`에 대한 분석이다. 실제 일치 위치의 명령 경계와 displacement는 별도로 확인해야 한다.

현재 설치된 `SAN8RPK.exe` 파일 전체를 실행 없이 바이트 검색한 결과, 첫 hook의 정확한 패턴 `0F B6 84 18 F0 00 00 00`과 두 번째 hook의 `41 80 ?? ?? ?? ?? ?? ?? ?? 75 ?? 48 8B ?? ?? ?? E8`은 각각 0건이었다. 파일 크기는 57,585,488바이트, SHA-256은 `000D450345728C23BEBCA581AB37B8BCF25266172767B5E6DEFB10A72A8C9457`이다. 두 번째 패턴의 각 `??`는 정확히 1바이트로 검색했다. 파일 전체에서 찾지 못했으므로 파일상 일치 위치의 명령·원래 분기 목적지는 확인할 수 없었다. 원본 코드가 검색하는 대상은 로드된 이미지 메모리이고 첫 hook의 범위는 `exeBase`부터 `0x3000000`바이트이므로, 이 파일 바이트 결과만으로 실행 중 검색 결과를 판단하지 않는다.

## 압축 평정 메뉴의 특권 입력 폭

활성 `CouncilCompactSectionBase.h:38-88,115-123`의 전략 포인트와 공적은 P1 기준 `ModifyStat`을 사용한다. 특권은 `p1=0`, `gameBase+0xEA`, 선언 크기 1로 공통 행에 전달한다. 특권의 직접 입력 완료는 `ModifyStat`으로 1바이트를 쓰지만, `-`와 `+` 버튼의 gameBase 분기는 선언 크기를 사용하지 않고 `unsigned int`를 직접 써 `gameBase+0xEA`부터 4바이트를 변경한다. 이 직접 쓰기에는 같은 행에서 `VirtualProtect`나 쓰기 성공 검사가 없다. 표시 값은 1바이트만 읽는다. x86/x64의 little-endian 표현에서 예를 들어 표시된 특권 1을 `+`로 2로 바꾸면 쓰는 4바이트는 `02 00 00 00`이어서 바로 뒤 세 바이트도 0으로 바뀐다. 이 세 바이트의 게임 내 의미는 확인하지 않았다.

직접 호출을 찾지 못한 `MenuSectionsCouncil.cpp`의 별도 평정 행은 `-`에서 같은 4바이트 직접 쓰기를 하지만 `+`는 `ModifyStat`에 선언 크기를 전달한다. 두 구현의 버튼 동작을 동일하게 집계하지 않는다.

활성 행은 +/-에 최솟값·최댓값 제한을 두지 않는다. 특권 표시가 0일 때 `-`를 누르면 4바이트 `FF FF FF FF`를 쓰고, 255일 때 `+`를 누르면 `00 01 00 00`을 쓴다. 전략 포인트(1바이트)와 공적(2바이트)의 `ModifyStatFast`는 각각 해당 폭으로 변환하므로 이 범위 경계에서 값이 잘린다(`Cheats.cpp:208-215`). 버튼·입력 후 `ModifyStat`의 성공 여부는 행에서 받지 못한다. 행의 표시값 갱신은 입력 완료 직후가 아닌 비활성 프레임에 대상 값을 다시 읽는 방식이다.

평정 전략 포인트는 P1+`0xED`에 1바이트를 쓰고, 무장 상세 전략포인트는 상세 대상+`0xED`에 쓴다. 두 대상 주소가 같으면 같은 바이트지만, 평정 행은 `ModifyStat` 뒤 무장 상세 snapshot 동기화 함수를 호출하지 않는다. 무장 상세가 같은 주소의 기존 snapshot을 재사용하는 동안 변경 전 값을 표시할 수 있다. 실제 주소 동일성 및 화면 순서는 확인하지 않았다.

같은 화면의 주인공 전략 포인트도 오프셋 `0xED`지만 P1 기준이므로 두 주소가 같은 객체를 가리킨다고 단정하지 않는다. 회귀 조건은 특권 직접 입력과 +/-의 인접 3바이트 변화, 읽기 전용 페이지, 값 경계 및 두 base 관계다. 실제 게임 쓰기는 하지 않았다.

## 내정 메뉴의 금·행동력·우호의 증표 입력

활성 첫 열의 `MenuSectionsDomestic.cpp:69-104`는 금(P1+`0x300`, 4바이트), 행동력(P1+`0xEE`, 1바이트), 우호의 증표(gameBase+`0xF8`, 2바이트)를 `InputInt`로 표시한다. 각 입력은 편집 종료까지 기다리지 않고 값이 바뀐 프레임에 `ModifyStat`을 호출하며 별도의 도메인 범위 제한은 없다. 입력이 활성 상태가 아닐 때는 해당 크기로 현재 메모리 값을 다시 읽는다. 읽기 분기는 기준 주소가 `0x10000`보다 큰지만 확인하고 대상 범위의 `IsValidPtr`를 호출하지 않는다. 이 섹션 자체는 P1이 있을 때만 그려진다.

같은 이름처럼 보이는 금액도 입력 대상을 구분한다. 내정 `금`은 P1+`0x300`을 쓰고, 무장 상세 `봉록`은 상세 대상+`0xE8`을 쓴다. 두 곳 모두 4바이트지만 오프셋과 대상 결정이 다르며, `OfficerDetail.cpp`의 `v_Gold`는 파일 지역 static이다. 실제 게임에서 각 필드가 의미하는 재화 관계는 확인하지 않았다.

행동력 입력과 `bInfiniteAP`는 동일한 P1+`0xEE`에 쓴다. 입력은 메뉴 렌더 경로에서 요청값을 쓰고, 무한 행동력은 ClientBGThread에서 활성 상태 동안 200을 반복해서 쓴다. 주인공·선택 무장 상세의 공통 수치 행도 대상 base+`0xEE`에 쓴다. 그 대상 주소가 같은 P1일 때는 무한 행동력의 반복 쓰기와 같은 바이트를 사용한다. 두 호출 사이를 직렬화하는 공통 잠금은 해당 경로에 없다. 같은 P1을 대상으로 두 쓰기가 이어지면 마지막 쓰기가 남으며, 실제 호출 시점과 화면 표시 결과는 확인하지 않았다.

회귀 조건은 입력 도중 값 변화, 1·2바이트 경계, gameBase와 P1 세대 전환, 읽기·쓰기 실패 및 외부 값 변경이다. 실제 입력과 게임 데이터는 실행하지 않았다.
