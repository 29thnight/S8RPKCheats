# P0: 특기 보기 및 설명 편집 조사

기준: `reference/S8RPKCheats`의 정적 소스 조사. 게임 실행이나 빌드는 수행하지 않았다.

## 특기 보기 묶음

`S8RPKCheats/TraitViewerFeature.cpp`의 `SetTraitViewerFeature`는 Roster, Widths, BattlePrep, BattleMap, BattleInfo, OfficerInfo, Kirase, InProgressEditor, BaseEditor 순으로 켠다. 중간 단계가 실패하면 앞서 성공한 단계에 대해 역순으로 끄기를 시도하고 false를 반환한다. 끄기 실패 시에는 이미 끈 단계를 다시 켜려고 시도한다. 두 경우 복구 호출의 반환값은 확인하지 않는다. `IsTraitViewerFeatureApplied`는 아홉 구성 요소가 모두 적용된 경우에만 true다.

묶음에서 성공으로 기록한 구성 요소가 호출 전에 이미 켜져 있었는지는 구분하지 않는다. 예를 들어 Roster는 이미 적용된 경우에도 켜기에 성공하므로, 이후 다른 구성 요소가 실패하면 복구 과정에서 기존 Roster까지 꺼질 수 있다.

`TraitViewerWidths.cpp`는 대상 열과 기존 너비를 확인하고 부대 너비 188→132→160, 상태 너비 104→76으로 변경한다. 해제는 반대 방향이다. 이미 최종 너비인 상태에서 켜거나 이미 원래 너비인 상태에서 끄면 중간값 검사를 통과하지 못하므로 반복 호출이 항상 성공하지 않는다. 쓰기 실패 후 복구 쓰기의 성공도 별도로 보장하지 않는다.

설정 읽기에서 `bTraitViewer`가 없으면 true를 사용한다. 적용에 실패하면 `IsTraitViewerFeatureApplied()`의 결과로 설정 변수를 갱신한다(`Config.cpp`). 무장 편집 메뉴의 체크박스도 같은 방식으로 적용 결과를 반영하고 설정을 저장한다(`MenuSectionsOfficerEdit.cpp`). 따라서 부분 적용이 남아 있어도 이 값은 아홉 구성 요소가 전부 적용되었는지만 나타낸다.

## 개별 패치의 실패·해제

- `TraitViewerNativeEditors.cpp`의 공통 설치는 원본 바이트 확인, 코드 공간 할당 및 재배치 후 패치를 차례로 기록한다. 기록이 실패하면 해제 패치 전체를 시도하지만 각 결과는 확인하지 않고 할당한 코드 공간을 해제한다. 복구 쓰기가 실패하면 해제된 공간을 가리키는 패치가 남을 수 있다. 해제는 원본 복원 쓰기 중 첫 실패에서 반환하며 앞서 복원한 항목을 다시 적용하지 않는다. 성공한 해제는 코드 공간을 즉시 해제한다. Kirase, InProgressEditor, BaseEditor가 이 공통 경로를 사용한다.
- `TraitViewerBattleMap.cpp`의 설치는 정적 패치 이후 호출 및 초기화 패치를 적용한다. 실패 시 바깥 호출은 코드 공간의 가드가 0인 경우 복원을 시도한다. 복원은 원본 쓰기 결과를 확인하지 않고 공간을 해제한다. 가드가 0이 아니면 해제를 거부한다.
- `TraitViewerRoster.cpp`는 원본을 보관하고 패치를 적용한다. 복원은 기록 결과를 확인하지 않은 채 코드 공간을 해제한다.

위 실패 결과는 코드 흐름에서 확인한 가능성이며 실제 게임에서 재현한 결과가 아니다. 새 구현에서는 각 구성 요소의 기존 상태, 기록 성공 범위, 복구 결과와 실행 중인 코드 공간의 수명을 명시적으로 관리해야 기존 기능의 실패 동작까지 판단할 수 있다.

## 설명 편집 후크

`TraitTextDescHook.cpp`와 `TraitTextSpecialDescHook.cpp`는 새 편집 내용을 적용할 때 기존 후크를 먼저 제거한다. 편집 목록이 비어 있으면 제거 후 성공하고, 새 후크 설치에 실패하면 이전 후크를 되돌리지 않는다. 제거 시 현재 모듈 기준 주소를 확인하고 고정된 원본 바이트를 기록하며 현재 패치 바이트가 예상과 일치하는지는 확인하지 않는다. 제거한 코드 공간은 즉시 해제하지 않고 보관 목록에 남긴다. 새 구현에서 교체 실패 시 기존 편집을 유지할지 명시해야 한다.

## 기재 문구 자동 로드와 재시도

`TraitTextEditorWindow.cpp:209`의 `TickTraitTextEditorAutoApply`는 최초 호출에서 기존·내장 편집 파일을 각각 읽는다. 둘 다 실패하면 자동 처리를 종료하며, 둘 중 하나라도 로드돼도 편집 내용이 없으면 종료한다. 편집 내용이 있으면 첫 tick부터 3초를 기다리고 이후 최소 1초 간격으로 최대 30회 `ApplyAll`을 시도한다. 성공하거나 횟수를 다 쓰면 프로세스 정적 `g_autoFinished`를 세워 재시도하지 않는다. 이 함수의 상태에는 게임 세대 변경 감지가 없다.

`ApplyAll`은 모든 행을 검증한 후 이름·일반 설명·특수 설명 hook을 차례로 설치하고 내장 기재 문구를 적용한다. 중간 실패는 앞서 설치한 hook 제거를 시도하지만 제거 결과는 확인하지 않는다. 자동 적용의 `keepLegacyHooksOnUnsupportedEmbedded=true`에서 외부 `version.dll` 때문에 내장 문구가 지원되지 않는 오류가 나오면 이미 설치한 세 hook을 유지하고 실패를 반환한다. 호출자는 이 오류를 별도 종료 조건으로 처리해 더 재시도하지 않는다. 내장 문구 적용 성공 후에는 표시용 사용자 기재 텍스트 캐시도 갱신한다.

이 tick은 `MenuSectionsInfo.cpp:125`에서 호출되므로 [오버레이 조사](P0_Overlay.md)에 기록된 메인 메뉴 표시·확장·gameBase·테이블 조건을 따른다. 시작 3초는 첫 tick 이후의 경과 시간이며 그 사이 메뉴를 닫으면 닫힌 동안 tick은 실행되지 않는다. 회귀 조건은 두 파일 각각의 실패·빈 편집, 첫 tick 지연과 30회 제한, 메뉴 닫기·재개, hook 단계별 실패와 복구 실패, `version.dll` 유무 및 세이브 전환이다. 실제 hook 적용은 실행하지 않았다.

## 전투 준비·전투 정보·무장 정보의 개별 복구

`TraitViewerBattlePrep.cpp`, `TraitViewerBattleInfo.cpp`, `TraitViewerOfficerInfo.cpp`는 각각 원본 바이트와 필요한 지점을 확인한 뒤 독립 cave를 만들고 여러 주소를 순차 패치한다. 각 setter는 요청 상태와 내부 `g_applied`가 같으면 실제 바이트를 재확인하지 않고 성공한다. OFF에서는 cave 선두의 객체 수가 0이 아니면 해제를 거부한다. 이 가드는 등록된 객체가 남았는지만 나타내며, 코드 실행이 모두 끝났다는 근거는 아니다.

전투 준비는 3개 점프를 설치하고 중간 실패 시 앞서 기록한 위치 복구를 시도한다. 전투 정보는 4개 분기, 무장 정보는 크기 값과 6개 분기를 순차 변경한다. 세 경로의 최종 `Restore`는 원본 쓰기 반환값을 확인하지 않고 cave를 해제한다. 설치 중 실패한 경우에는 cave가 있고 선두 값이 0일 때 `Restore`를 호출한다. 선두 값이 0이 아니면 그 복구를 수행하지 않은 채 기준 주소를 0으로 지운다. 실제로 해당 조건이 발생하는지는 확인되지 않았다.

회귀 조건: 원본 검사 실패, 각 패치 위치의 부분 쓰기·복원 실패, 화면 객체가 남은 상태의 OFF, 반복 ON/OFF, 다른 코드가 패치한 바이트와의 충돌, 설치 실패 때 cave 선두 상태, 실행 중 코드와 cave 해제, 묶음 기능의 다른 단계 실패 후 역순 복구다.
