### AI 항복 권고 hook의 실패와 재활성화

고의리 hook은 설치한 16바이트를 다시 읽어 검증한다. 검증 실패 시 원본 쓰기를 시도하지만 복구 성공 여부는 확인하지 않고 적용 상태를 false로 남긴다. OFF는 현재 바이트가 저장된 패치와 모두 일치할 때만 원본을 쓰며, 불일치 또는 쓰기 실패에서는 적용 상태를 유지한다. cave는 OFF 후에도 남고, 다음 ON에서 같은 cave 전체를 0으로 채운 뒤 payload를 다시 쓴다. 원본 복구 쓰기의 결과 바이트를 다시 비교하지는 않는다.

공격 전환 hook은 설치 전 세 위치가 모두 원본인지 검사한 뒤 순서대로 기록한다. 중간 쓰기가 실패하면 앞서 기록한 위치의 복구를 시도하지만 그 결과는 확인하지 않는다. 세 위치 쓰기 후 검증이 실패하면 현재 패치 바이트와 일치하는 위치만 원본으로 복구하려 한다. 어느 경우에도 실패 반환 시 적용 표시는 false이며 실제 바이트가 모두 복구됐다는 보장은 코드에 없다. OFF는 세 위치가 모두 저장된 패치와 일치하는지 먼저 검사하고 순서대로 원본을 쓴다. 중간 복구 실패 시 앞서 복구한 위치에 패치를 다시 쓰려 하지만 이 결과도 확인하지 않으며 적용 표시는 true로 남는다.

공격 전환 cave도 해제하지 않고 다음 ON에서 재사용한다. 매 활성화 때 payload와 함께 통계·거절 기록 영역을 초기화한다. 두 기능 모두 패치 해제 후 cave를 재작성하기 전에 기존 실행이 끝났는지 기다리는 코드는 이 함수들에 없다. 실제 중첩 실행 여부는 확인되지 않았다. 이관 회귀 조건에는 부분 쓰기·복구 실패, 외부 바이트 변경, 재활성화 시 기록 초기화와 실행 중 해제를 각각 포함한다.

정상 해제 후 cave를 유지하는 구현과 즉시 `VirtualFree`하는 구현은 서로 다르다. 이 차이는 현재 코드의 사실이며, 메모리를 유지하는 것만으로 DLL 내부 callback이나 참조 수명의 안전성이 증명되는 것은 아니다. 이관 시 patch 소유·원본 바이트·실행 중 callback을 함께 관리한다.

## 도독 포로 처분의 부분 설치·해제

`GovernorPrisonerDisposal.cpp`의 ON은 세 hook 지점뿐 아니라 질문 함수와 특권 소비 함수의 서명도 확인한다. cave를 만든 뒤 main, collect, relations 순으로 기록하며, 하나라도 실패하면 세 지점 모두에 원본 쓰기를 시도한다. 이 복구의 반환값은 확인하지 않고 cave를 즉시 해제한다. 따라서 앞서 설치된 지점의 복구가 실패하면 cave로 향하는 패치가 남아 있을 수 있지만 적용 상태는 false다. 세 쓰기 성공 후에는 각 지점을 다시 읽어 검증하지 않는다.

OFF는 세 지점이 모두 패치 바이트인지 확인한 뒤 세 원본 쓰기를 각각 시도한다. 일부만 성공하면 적용 상태와 cave를 유지한다. 이후 OFF를 다시 요청해도 이미 원본으로 바뀐 지점 때문에 세 지점 사전 검사를 통과하지 못한다. 세 쓰기가 모두 성공하면 실행 중 cave 사용을 기다리지 않고 해제하며, 해제 결과와 복구 바이트를 재확인하지 않는다. 실제 실패나 동시 실행을 재현한 결과는 아니며, 이관 시 각 쓰기 실패, 재시도 및 실행 중 해제 조건으로 확인한다.

## 포로 관리 묶음의 부분 상태

`IsPrisonerCaptureManagementApplied`는 부장 포획, 고립도시 포획, AI 처형의 세 적용 표시가 모두 true일 때만 true다. 따라서 일부만 적용된 상태도 묶음의 OFF 표시와 구분되지 않는다. ON 실패 시 이번 호출 전에 적용되지 않았던 선행 기능만 해제하려고 하며 해제 결과는 확인하지 않는다. OFF는 AI 처형부터 역순으로 진행하고 하나가 실패하면 이후 해제를 멈춘다. 이미 해제한 기능은 호출 전 적용 표시를 기준으로 재설치하려 하지만 이 결과도 확인하지 않는다.

메뉴의 체크박스는 setter가 실패하면 이 세 표시의 논리곱으로 UI flag를 되돌리고, 그 값을 알림에 사용한 뒤 `SaveConfig`를 호출한다. 따라서 부분 적용이 남은 실패에서도 표시와 저장 요청은 OFF일 수 있다. 설정 로드에서도 setter 실패 시 같은 논리곱을 flag에 사용하지만, 그 자리에서 저장하지는 않는다. 도독 포로 처분과 원군 즉시 행동 메뉴도 실패 시 각각의 내부 적용 표시로 flag를 되돌린 후 알림과 저장을 수행하므로, 실제 패치 바이트와 표시가 어긋나는 경우를 구분해야 한다.

AI 처형의 두 hook 설치에서 두 번째 쓰기가 실패하면 첫 번째 원본 복구를 시도하고 결과는 확인하지 않는다. 설치 후 검증이 실패하면 각 위치가 자신의 패치와 일치하는 경우에만 복구를 시도한다. 실패 시 내부 적용 표시는 false로 남으므로, 실제 바이트가 복구되지 않았다면 다음 ON의 원본 검사에서 거부될 수 있다. OFF는 두 위치를 모두 검사한 후 순차 복구하며 중간 실패 시 앞 위치의 재패치를 시도한다. 재패치 결과는 확인하지 않고 적용 표시는 true로 유지한다. cave와 통계 영역은 재활성화 때 다시 초기화된다. 묶음 표시와 세 개별 표시, 실제 바이트, 각 복구 시도의 결과를 별도 회귀 조건으로 다룬다.

## 패치 API 텍스트 대조의 범위

`Cheats` 아래 cpp·h·inc에서 `ApplyJmp`, `MH_CreateHook`, `VirtualAlloc`, `WriteProcessMemory` 호출 문자열을 찾고 조사 문서에 파일 기준 이름이 없는 후보를 대조했다. 유일한 후보는 `Cheats/legacy/OfficerCaptureCave_legacy.cpp`였다. 이 파일의 구현 본문은 블록 주석 안에 있고, x64 구성 평가의 컴파일 항목과 프로젝트·상위 props에도 파일명이 없다. `Menu_impl.inc:466`의 과거 호출도 주석이다. 따라서 이 후보를 현재 설치되는 hook으로 집계하지 않는다.

이 대조는 네 API의 텍스트 호출만 대상으로 하며 간접 호출, 다른 메모리 쓰기 API, 매크로와 외부 코드, 조건부 활성 여부 및 callback 수명을 망라하지 않는다. 문서에서 파일명이 발견되었다는 사실도 해당 hook의 전체 경로를 확인했다는 증거가 아니다.

## 평정 재야 처단의 cave 보존과 재활성화

`CouncilExecuteFreeOfficers.cpp`는 해제 시 현재 hook 바이트가 자신의 patch와 일치하는지 확인하고 원본을 복원·재검증한 후 적용 상태를 내린다. 이 과정에서 cave는 반환 중인 스레드를 고려해 해제하지 않는다. 설치 실패 시에도 할당된 cave 주소를 유지하며 다음 설치에 재사용한다.

다만 OFF 다음 ON은 기존 cave가 있으면 새로 할당하지 않고 그 메모리를 `memset`과 `memcpy`로 다시 쓴다. OFF 당시 cave 안에 있던 실행이 ON 재작성보다 먼저 끝났다는 것을 확인하는 경로는 이 setter에 없다. cave를 해제하지 않는 것과 그 내용의 재작성 시점을 보호하는 것은 별도 조건이다. 정상 종료에서 이 setter를 OFF로 호출하는 경로도 기준 자체 cpp/h/inc 검색에서는 찾지 못했다. 실제 동시 실행과 종료는 검증하지 않았다.

회귀 조건은 원본·적용 바이트 불일치, 설치·복원 실패, 빠른 OFF→ON과 callback 진행 중 재작성, 적용 상태에서 정상 종료다.

## 공통 직접 점프·복원 함수와 해제 호출자

`MemoryUtils.cpp:111`의 `ApplyJmp`는 32비트 상대 거리와 최초 `VirtualProtect` 성공을 확인하고, 16바이트 지역 배열에 JMP와 NOP를 만든 뒤 요청 크기만큼 복사한다. 복사 후 원래 보호 상태로 돌리는 `VirtualProtect`의 반환값은 확인하지 않으며 이 함수 자체는 instruction cache flush, 기존 바이트 확인, 다른 스레드의 실행 중지 또는 쓰기 결과 재검증을 수행하지 않는다. 호출자가 별도로 수행하는 확인은 각 기능마다 다르다. 이 함수의 16바이트 배열과 5바이트 JMP 전제를 고려해 호출 크기는 이관 시 각 호출점에서 확인한다.

`RestoreBytes`는 원본 주소의 보호 변경이 실패하면 아무것도 쓰지 않고 반환하며, 반환형이 void라 호출자가 이 결과를 받을 수 없다. 성공 시에도 보호 복원 결과를 확인하지 않고 자체 flush나 현재 패치 바이트 비교를 하지 않는다. 이 함수 자체의 공통 동작은 아래 호출자의 후속 처리와 구분해야 한다.

이관 회귀 조건은 최초 보호 변경 실패와 복원 실패, 다른 패치가 hook 바이트를 변경한 경우, 설치 결과·캐시 반영, 두 위치 중 일부만 복원되는 경우 및 cave 실행 중 해제다. 빌드나 패치 실행은 하지 않았다.

### `ApplyJmp` 호출 크기 대조

기준 소스의 자체 cpp·inc에서 함수 정의와 `legacy`·외부 라이브러리를 제외하고 `ApplyJmp` 호출 문자열 24곳을 찾았다. 상수 인자와 해당 지역·전역 배열 선언을 수동 대조한 [호출별 크기 목록](p0/applyjmp_call_sizes.csv)에 따르면 이 호출들은 모두 5~11바이트다. 따라서 확인한 24개 호출에는 공통 함수가 요구하는 최소 5바이트 미만 또는 지역 패치 배열 16바이트 초과 인자가 없다. 이것은 텍스트로 찾은 직접 호출과 현재 선언에 대한 결과이며, 호출 도달성·전처리 활성 여부·간접 호출이나 실행 시 코드 바이트의 유효성을 증명하지 않는다.

## 설치된 게임 파일의 RVA와 원본 서명 대조

`SAN8RPK.exe` 버전 표기 `1.1.3`의 파일(SHA-256 `000D450345728C23BEBCA581AB37B8BCF25266172767B5E6DEFB10A72A8C9457`)에서 PE section의 RVA를 파일 오프셋으로 변환해 읽었다. 평정 재야 처단, 병력 공방, 고의리 항복, 원군 즉시 행동의 원본·검증 서명 총 일곱 위치를 [파일 바이트와 대조](p0/game_file_signature_comparison.csv)한 결과 일곱 곳 모두 코드의 기대 바이트와 다르다.

이것을 실행 중 서명 불일치나 해당 기능의 미작동으로 판단하지 않는다. 일곱 위치가 들어 있는 파일 `.text`의 바이트 엔트로피는 약 8.000 bit/byte이고, PE entry point는 `.text`가 아닌 `.bind` section에 있다. 파일 내용이 일반적인 평문 기계어와 달라 실행 시 메모리 내용과 파일 바이트가 같다는 근거가 없다. section 특성만으로 그 변환 방식이나 원인을 확정하지도 않는다.

실제 hook의 버전 적합성은 게임이 로드한 뒤 각 위치의 메모리 바이트와 해당 기능의 패턴 탐색·원본 검사 결과를 확인해야 한다. 이 파일 대조는 게임 시작, 메모리 읽기, 패치 설치 또는 빌드를 수행하지 않았다.

## 공통 바이트 패턴 검색의 범위와 호출 차이

`Cheats.cpp:57`의 `DX11Base::FindPattern`은 공백을 건너뛰고 `?` 또는 `??`를 와일드카드 한 바이트로 변환한 뒤 시작 주소부터 첫 일치 주소를 반환한다. 검색 길이를 `(end - start) - 패턴 길이`로 계산하고 인덱스가 그 값보다 작은 동안만 비교한다. 따라서 범위를 `[start,end)`로 사용할 때 마지막으로 패턴이 들어갈 수 있는 위치는 검사하지 않는다. 범위 길이와 패턴 길이가 같으면 어떤 위치도 검사하지 않는다. 범위가 패턴보다 짧으면 unsigned 크기 계산이 감산 전 검증 없이 진행된다.

이 함수는 검색 중 주소를 직접 읽으며 페이지별 접근 가능성 검사나 예외 처리를 내부에서 수행하지 않는다. `InitCheats`는 `GetModuleInformation`으로 얻은 이미지 끝을 전달하지만, 담화·기증 등 일부 기능은 `exeBase + 0x3000000`, 민심 패치는 `exeBase + 0x2000000`을 끝으로 전달한다. 이 호출들이 실제 게임에서 읽을 수 없는 영역을 만나는지는 확인되지 않았다. 이미지 크기나 메모리 상태가 다를 때 검색 범위와 첫 일치 대상이 달라질 수 있으므로 새 검색기는 각 호출의 범위·예상 원본·충돌 처리까지 함께 이관한다.

`ResolveRelAddr`는 일치 위치의 상대 변위를 직접 읽어 주소를 계산하며, 그 자체에서 명령어 형태나 읽기 가능한 범위를 검증하지 않는다. 최초 패턴 일치 이후의 원본 바이트 검사·캐시·재검색은 기능별로 다르다. 예를 들어 기증은 원본과 패치 패턴을 각각 찾고 실제 10바이트를 비교하지만 담화는 찾은 주소를 캐시하고 적용 시 그 위치의 7바이트를 저장한다. 따라서 공통 검색 결과만으로 모든 패치의 원본 검증 여부를 판단하지 않는다.

이관 회귀 조건은 시작·마지막 후보 위치, 범위와 패턴 길이가 같은 경우, 검색 범위가 짧은 경우, 와일드카드, 복수 일치, 이미지와 고정 범위 차이, 접근할 수 없는 페이지, 상대 변위와 다른 패치의 선행 적용이다. 검색기나 게임을 실행하지 않은 정적 조사다.

## 공통 인접 코드 공간 할당

`MemoryUtils.cpp:9`의 `AllocNear`는 시스템 할당 단위를 읽고 대상 기준 최대 `0x70000000` 거리의 범위를 설정한다. `VirtualQuery`로 대상부터 높은 주소 쪽을 먼저 순회한 뒤, 실패하면 대상 바로 아래부터 낮은 주소 쪽을 순회한다. 빈 영역은 검색 범위 안으로 잘라 크기가 충분한지 확인하고, 위쪽 검색에서는 영역의 첫 할당 단위 정렬 위치, 아래쪽 검색에서는 영역 끝에서 크기를 뺀 후 정렬한 위치 하나에 `VirtualAlloc(MEM_RESERVE | MEM_COMMIT, PAGE_EXECUTE_READWRITE)`을 시도한다. 첫 조회 영역이 대상을 포함하는 빈 영역일 때는 위쪽 순회라도 정렬된 후보가 대상보다 낮을 수 있다.

한 빈 영역의 선택된 후보에서 할당이 실패하면 같은 영역의 다른 정렬 위치를 재시도하지 않고 다음 영역으로 진행한다. `VirtualQuery` 실패 또는 영역 진행 계산의 이상 조건에서는 해당 방향 검색을 중단한다. 위쪽에서 성공하면 아래쪽의 더 가까운 후보는 탐색하지 않는다. 성공까지 50ms 이상 걸린 경우와 전체 실패는 조회·할당 시도 수를 로그에 남긴다. 실제 주소 배치나 경합 빈도는 측정하지 않았다.

이 함수는 확보한 주소를 반환할 뿐 패치 적용, 명령 캐시 갱신, 실행 중 callback 종료, 원본 복구 및 해제 책임을 관리하지 않는다. 호출자의 크기도 담화 128바이트, 일반 설명 `0x40000`바이트, 전투 정보 `0x10000`바이트처럼 다르며 상대 점프 재배치 검사와 실패 시 반환은 각 구현에 있다. 일부 기능은 해제 cave를 보존하고 다른 기능은 즉시 `VirtualFree`하므로 한 정책으로 뭉뚱그리지 않는다.

이관 확인 항목은 높은·낮은 주소 선택, 정렬 경계와 영역 크기, 조회와 할당 사이 영역 변화, 같은 영역에서 첫 할당 실패, rel32 범위, 실패 후 호출자 복구 및 사용 중 코드·문자열의 수명이다. 할당 함수와 게임은 실행하지 않았다.

### 부분 설치 실패와 OFF의 차이

화면 열기 훅(`StratagemSlotProbe.cpp:1314`)과 callback 반복 훅(`:2673`)은 점프를 성공적으로 쓴 다음 반복 상한 바이트의 쓰기 권한을 얻지 못하면 `false`를 반환한다. 이 경로는 이미 설치한 점프를 되돌리거나 할당한 코드 공간을 해제하지 않으며, 성공 상태와 코드 공간 주소를 기록하는 대입에도 도달하지 않는다. 상한 쓰기 뒤 검증에 실패한 경우에도 같은 성공 상태 기록 전에 반환한다. 이후 준비 함수는 성공 플래그를 기준으로 재시도하므로, 부분 설치 후 재시도의 결과는 원본 바이트 검사와 당시 메모리 상태에 따라 달라진다. 실제 발생 여부와 재시도 결과는 확인하지 않았다.

`PrepareStratagemFiveUiBridge`는 개별 준비 결과를 모두 구한 뒤 결합하므로 앞선 설치가 성공하고 뒤의 설치가 실패해도 앞선 설치를 일괄 복구하지 않는다. 기능 OFF 경로는 전투 데이터와 지속 요청을 정리하고 UI sidecar 표시를 끄되 재사용을 위해 UI bridge와 등록을 유지한다(`:4790`, `:5469`). 따라서 설정 OFF와 코드 훅 제거는 같은 사건이 아니다. 이관 시 부분 설치 상태, 재시도, OFF 후 재활성화와 종료 중 callback의 수명을 각각 검증해야 한다.

### 별도 `WriteBytes` 정의 후보

공통 `RestoreBytes`와 구분하기 위해 기준 `Cheats` 하위 cpp·inc·h에서 `bool WriteBytes(` 정의 표기를 검색한 [후보 목록](p0/writebytes_definition_candidates.csv)을 만들었다. 14개 파일에 같은 이름의 정의가 있다. 각 정의 다음 30줄의 텍스트에 `VirtualProtect`와 `FlushInstructionCache`가 모두 나타나며, 13곳에는 `__try` 또는 `__except` 표기도 나타난다.

이 집계는 이름과 근접 줄에 대한 검색일 뿐 함수 본문 경계, 분기, 각 반환값의 의미, 전처리 활성 여부 또는 모든 코드 쓰기를 판정하지 않는다. 동일한 이름을 공통 함수 하나로 취급하지 않고 기능별 설치·복구 조사와 대조할 수 있도록 위치를 남긴다. 게임 쓰기나 빌드는 하지 않았다.

### `WriteBytes` 정의 본문 대조

앞의 후보 14곳을 각 함수의 중괄호 범위로 다시 대조했다. 13곳은 최초 보호 변경 성공 뒤 `memcpy`를 SEH로 감싸고, 보호 복원을 시도한 뒤 복사가 성공한 경우 instruction cache flush를 호출한다. 이 13곳 중 11곳은 쓰기 전에 `IsValidPtr`도 호출하며, `CouncilExecuteFreeOfficers.cpp`와 `IsolatedTerritoryMovement.h` 두 곳은 주소·입력·크기만 확인한다.

나머지 `RulerTransferProposal.cpp:40`은 최초 `VirtualProtect` 실패만 false로 반환하고 SEH 없이 복사한다. 다른 13곳과 달리 보호 복원보다 먼저 flush를 호출한다. 확인한 14곳 모두 보호 복원과 flush의 반환값을 성공 판정에 반영하지 않는다. 이 공통점이 호출자별 원본 바이트 확인, 복구 검증 및 실패 후 상태까지 같다는 뜻은 아니다.

대조는 현재 함수 본문의 정적 비교다. 호출 도달성과 쓰기 중 예외·보호 복원 실패, 게임 callback과의 겹침은 확인하지 않았다.

### 공통 복구 함수 호출 위치

기준 자체 cpp·inc의 `RestoreBytes(` 호출 텍스트를 [호출 위치 목록](p0/restorebytes_call_sites.csv)으로 남겼다. 함수 정의를 제외하면 14곳이며 이 중 1곳은 `Cheats/legacy`의 무장 캡처 백업에 있다. 나머지 13곳은 위 기능별 복구 표의 대상이다. 선언 헤더는 호출 수에서 제외했다. 이 목록은 호출 표기의 정적 범위이며 조건부 컴파일, 간접 호출, 실제 실행이나 복구 성공을 증명하지 않는다. 각 호출이 `RestoreBytes` 이후 flush 또는 cave 해제 중 무엇을 하는지는 위 기능별 표에 따른다.

### 직접 점프와 공통 복구의 크기 대조

`ApplyJmp`와 `RestoreBytes`가 같은 원본 버퍼를 사용하는 12개 경로를 소스에서 짝지어 대조했다. 내정 배율 9, 기술 포인트 7, 담화 7, 대련·토론 6, 상극 hook 8·11, 충성 7, 공명 선택·조회 6·9, 전기 캡처 7, 전투 유닛 캡처 7, 책략 게이지 7바이트다. 이 범위에서는 설치 크기와 복구 크기 및 해당 원본 배열 크기가 각각 같다. 공명의 크기는 양쪽이 같은 원본 배열의 `sizeof`이고 책략 게이지 복구 크기도 원본 배열의 `sizeof`다.

친밀도 가속은 `ApplyJmp`가 아닌 8바이트 직접 패치이며, 진단용 친밀도 probe와 책략 슬롯의 별도 설치 경로는 이 짝짓기에서 제외했다. 이 비교는 크기만 확인한 것으로 원본 보존 시점·복원 성공이나 명령 실행 중 해제의 안전성은 증명하지 않는다.

### 공통 복구 뒤 명령 캐시 처리

위 13개 직접 호출의 복구 함수 본문을 대조했다. 친밀도 가속과 공용 대련·토론 hook은 `RestoreBytes` 다음에 대상 주소의 `FlushInstructionCache`를 명시적으로 호출한다. 나머지 11개 호출이 속한 복구 경로에는 해당 복구 뒤 flush 호출이 없다. 공명 두 곳과 책략 게이지 파일에 있는 별도 flush는 cave 작성 시점이며 원본 복구 뒤 호출과 구분한다. `RestoreBytes` 자체도 flush를 호출하지 않는다.

이는 코드에 명시된 호출의 차이이며 실제 프로세서의 명령 캐시 상태나 게임에서 관찰되는 결과는 확인하지 않았다. 이관 검증에서는 설치·복구 양쪽의 코드 쓰기와 flush 결과, 복구 실패 및 실행 중 호출을 함께 다룬다.

### 점프 설치 실패 후 cave 정리 차이

공통 `ApplyJmp`가 cave 할당 이후 실패하는 경로를 대조했다. 대련·토론 공용 hook은 실패 시 `VirtualFree`하고 cave 주소를 0으로 만든다. 공명은 설치 실패 시 상위 경로에서 `RemoveResonanceHooks`를 호출해 할당된 두 cave의 해제를 시도한다.

반면 내정 배율, 기술 포인트 캡처, 담화, 상극 두 hook, 충성, 전기 캡처, 전투 유닛 캡처는 해당 설치 함수가 false를 돌려주었을 때 즉시 할당을 해제하는 분기가 보이지 않는다. 책략 게이지는 실패 시 `g_caveAddr`를 0으로 만들지만 그 전에 할당 해제는 호출하지 않는다. 이 구분은 **할당은 성공하고 이후 점프 적용이 실패한 경우**의 소스 경로다. 기술 포인트 setter는 앞서 기록한 대로 기준 자체 소스에서 호출 연결이 확인되지 않았다. 실패 발생 빈도와 실제 메모리 상태는 확인하지 않았다.

## 코드 공간 할당 표기 위치

기준 자체 cpp·h·inc에서 `VirtualAlloc`, `VirtualAllocEx`, `AllocNear`의 직접 표기를 검색한 [후보 목록](p0/executable_allocation_candidates.csv)을 추가했다. `Framework`, `Hooking`, `legacy`를 제외한 38개 파일의 55줄이며 정의·선언·주석과 실제 호출이 함께 들어 있다. 기능별 조사 문서에 파일명 표기가 없는 두 파일은 `InstantLoveCave.h`와 `MemoryUtils.h`의 `AllocNear` 선언이다. 나머지 파일의 이름은 기능별 문서에서 찾았다.

이 목록은 파일명 위치를 찾는 색인이다. `VirtualAlloc`의 모든 용도가 실행 가능한 메모리라는 뜻이 아니며, 해당 줄이 실제 구성에서 활성화되는지·반환 공간의 소유와 해제가 완전한지는 함수별 조사와 전처리·실행 확인이 필요하다. 간접 호출도 이 검색 범위 밖이다.

## 명시적 rel8 패치의 추가 범위 대조

자체 `Cheats`의 cpp·h·inc에서 `(uint8_t)(idx - 변수 - 1)` 형태를 직접 검색하면 내정 배율 외에 `InstantLoveCave.cpp` 3곳과 `Battleunitcapture.cpp` 9곳이 나온다. 소스의 바이트 출력 순서와 정수·포인터 삽입 크기를 따라 변위를 계산했다.

전투 유닛 cave 9개는 목적지까지 +13~+112바이트로 모두 signed rel8 양수 범위 안에 있다. 첫 세 분기는 재구성 바이트를 디스어셈블해 목적지가 공통 복귀 offset 121임을 확인했다. 상극 cave의 첫 분기 두 개는 normal 모드 기준 +24·+19, 두 번째 cave 분기는 +9다. 첫 cave의 다른 모드도 해당 조건 분기에서 출력하는 명령 크기가 같아 같은 길이로 계산된다. 이 결과는 앞서 확인한 내정 배율의 +171 초과와 구분된다.

검색한 cast 표현 밖의 분기 생성 방식, 조건부 전처리, 실제 hook 실행과 게임 데이터는 포함하지 않는다. 이 비교는 동작·스레드·수명 안전성 전체의 증거가 아니다.

### 다른 rel8 작성 방식

`rel8` 표기를 추가로 검색해 내정 포상(`DomesticRewardCondition.cpp`), 임무 강제 배정 제외(`MissionCpuHeroExclusion.cpp`), 책략 게이지(`StratagemGaugeMax.cpp`)와 책략 슬롯(`StratagemSlotProbe.cpp`)의 별도 helper를 확인했다. 네 helper는 대상과 operand 다음 주소의 차이가 -128~127인지 검사하고 범위 밖이면 false를 반환한다. 내정 포상과 임무 제외는 operand 인덱스도 vector 크기와 비교한다. helper의 검사 존재는 설치·복구 전체의 성공을 뜻하지 않는다.

공명 getter의 수동 `jae`는 건너뛸 쓰기 명령이 opcode 4바이트, 동적 offset 4바이트, 값 1바이트로 총 9바이트여서 해당 rel8의 범위 안이다. 이 확인은 찾은 `rel8` 표기와 명시된 cave 코드에 한정하며, 이름이 다른 분기 생성기나 외부 코드는 포함하지 않는다. 빌드와 게임 실행은 하지 않았다.

## 전투 유닛 cave의 레지스터와 정적 파일 대조

`Battleunitcapture.cpp:72-249`가 생성하는 cave는 `r15`를 push/pop하지만, 대상 포인터를 저장하는 경로에서 `r11`에 전역 주소를 넣고 되돌리지 않는다. 또한 여러 `cmp`·`test`로 상태 flag를 바꾸지만 별도로 flag를 저장·복원하지 않는다. 복사해 실행하는 원본 명령은 `movzx eax, byte ptr [rax+0x80]`이며 이 명령 자체는 상태 flag를 바꾸지 않는다. 따라서 전역 주소 처리까지 도달한 경우 반환 시 `r11` 값이 달라지고, 분기 경로에서 상태 flag도 원래 명령만 실행했을 때와 다를 수 있다. 실제 후속 게임 명령이 이 값들을 사용하는지와 실행 중 영향은 확인하지 않았다.

같은 소스는 고정 RVA `0x1E3A5D4`의 7바이트를 먼저 비교하고 실패 시 `08 0F B6 80 80 00 00 00` 패턴을 검색한다. 현재 설치된 `SAN8RPK.exe`를 실행하지 않고 PE 파일로 읽었을 때 해당 RVA의 파일 바이트는 `FF 71 61 02 64 EF FA`로 예상과 다르며, 파일 전체에서 대체 패턴 바이트도 찾지 못했다. 이는 파일 바이트의 결과다. 로드 후 메모리 변환·다른 실행 파일·버전에서의 설치 가능성은 판정하지 않는다. 회귀 조건은 진입·복귀 시 레지스터와 flag, 원본 명령, 버전별 메모리 서명과 실제 후속 명령이다.

### 다른 세 캡처·수치 cave의 명령 비교

기술 포인트 캡처 cave는 `rax`를 임시로 사용해 `rbx`를 전역에 저장한 뒤 원본 `movzx eax, [rbx+0x24A]`를 실행한다. 임시 `rax` 값은 복귀 전에 원본 명령의 결과로 대체된다. 이 setter는 앞서 기록한 대로 기준 자체 소스에서 활성 호출을 확인하지 못했다.

전기 캡처 cave는 `rax`를 push한 뒤 `lea`로 주소를 구해 전역에 저장하고 `rax`를 pop한 다음 원본 `mov [r15+0x1E4B18], al`을 실행한다. 충성 cave는 `[rsi+0xEC]`에 100을 쓴 뒤 원본 `movzx`를 실행한다. 확인한 세 cave의 추가 명령은 `mov`·`lea`·`push`·`pop`이며 앞의 전투 유닛 cave처럼 `cmp`·`test`로 상태 flag를 변경하지 않는다. 이는 생성 명령의 정적 비교이며 게임 문맥의 실제 주소 유효성, 실행 중 해제나 스레드 안전성까지 확인한 것은 아니다.

### 전투 유닛 캡처 두 슬롯의 사용

전투 유닛 cave는 `rax+0x60`과 그 객체의 `+0x18` 포인터가 0이 아니면 두 전역 슬롯과 비교한다. 이미 저장된 주소는 건너뛰고, 다르면 첫 빈 슬롯에 저장한다. 둘이 모두 차면 다른 주소는 저장하지 않는다. 실제 유닛의 소속이나 의미를 이 cave에서 판정하지 않는다.

`BattleMonitor.cpp:500-538`은 두 값을 지역 변수로 읽고, 둘 중 하나가 0이 아니거나 날짜·유닛 목록이 유효하면 `battleActive`로 판단한다. 이 두 주소를 그 자리에서 유닛 목록 포인터로 직접 사용하는 것은 아니다. 정상 전투 처리 끝과 준비 미완료·세션 폐기·비전투 분기 등에서 전역 슬롯을 0으로 비우며, OFF도 둘을 지운다. 생성된 게임 코드와 background monitor는 일반 `uintptr_t` 두 값을 공유하고 이 코드 경로에서 공통 잠금은 확인되지 않는다. 실제 호출 순서·놓친 캡처·전투 감지 결과는 실행하지 않았다.

`ResetBattleSessionRuntime`은 전투 generation을 증가시키고 두 캡처 슬롯을 0으로 비우지만 캡처 cave를 비활성화하거나 실행 중인 cave의 완료를 기다리지 않는다. cave는 슬롯을 기록할 때 generation이나 `g_battUnitInstallRequested`를 읽지 않는다. OFF도 설치 요청을 false로 만들고 슬롯을 비운 뒤 적용된 hook의 복원을 시도한다. 따라서 슬롯 초기화와 이미 실행 중인 cave의 기록이 겹치는 코드 순서에서는 초기화 후 다시 값이 들어올 수 있다. 실제 동시 실행 여부와 이후 전투 상태 판정은 확인하지 않았다. 이관 시 생성·게시 시점의 세대 일치와 OFF 완료 조건을 별도로 검증한다.

내정 배율·전투 유닛·상극 cave의 rel8 분기는 [분기 위치·변위 목록](p0/cave_rel8_displacements.csv)에 operand와 의도된 목적지 offset, 기록된 바이트와 signed 변위 및 실제 목적지로 정리했다. 상극 첫 cave의 두 모드를 별도 행으로 기록해 총 21행이며, 하나만 의도한 목적지와 다르고 내정 배율의 `pCodeNull`이다. 포인터 즉시값 8바이트는 길이 계산용 0으로 채웠으므로 이 목록은 분기 배치 분석이고 실제 실행 바이트나 실행 결과가 아니다. 위 helper 기반 분기는 목록 범위 밖이다.

## 상극 cave의 레지스터 복구 바이트

`InstantLoveCave.cpp:54-108`의 첫 cave는 시작에 `4C 8B D1`을 출력해 `mov r10, rcx`로 기존 `rcx`를 저장한다. 끝의 주석은 `rcx` 복구라고 되어 있지만 실제 출력 바이트 `4C 8B CA`는 x86-64 디스어셈블 결과 `mov r9, rdx`다. 저장했던 `r10`에서 `rcx`로 되돌리는 명령이 아니다. 그 사이 cave는 `ecx`에 관계 값을 읽고 일부 분기에서 다시 변경하므로 원본 `rcx`를 복구하지 않는다. 종료 명령은 `r9`도 변경하며, cave의 `r10`·`r11` 사용과 `cmp`·`and`로 변경한 상태 flag에도 별도 복구가 없다. 원본으로 재실행하는 `movzx eax, [rax+rbx+0xF0]`는 이 레지스터나 상태 flag를 복구하지 않는다.

바이트 해석은 독립 x86-64 디스어셈블러로 확인했다. hook 지점 이후 게임이 각 값을 실제로 사용하는지와 실제 증상은 확인하지 않았다. 이관 시 원본 명령 전후의 레지스터·flag 계약과 두 모드의 분기를 검증한다. 빌드와 게임 실행은 하지 않았다.
