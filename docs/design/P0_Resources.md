## 출처와 고지 조사

- `Framework/imgui.cpp`, `imgui.h`는 Dear ImGui `1.91.0 WIP`와 Omar Cornut 저작권을 표시한다. 저장소 내 파일명 검색에서 별도의 LICENSE/NOTICE 파일은 발견하지 못했다. 상류 후보 및 파일별 비교는 [출처 조사](P0_Proxy_Origin.md)를 따른다. 실제 도입 커밋은확정하지 않았다.
- `Hooking/MinHook.h`에는 MinHook의 저작권 및 2개 항목의 배포 조건이 들어 있다. HDE 및 다른 소스의 개별 고지는 별도로 검토해야 한다. 원본 라이선스 전체의 배포 포함 여부는 아직 확정하지 않았다.
- `Engine.cpp` 등 기존 실행 골격과 게임 기능 코드의 출처는 설계의 NightFyre 기준 커밋과 비교가 필요하다. 포함된 라이브러리의 고지를 자체 구현 전체의 라이선스로 취급하지 않는다.

## 외부 파일의 빈 내용과 읽기 실패 구분

`EmbeddedJsonResources.h:59-78`의 `ReadUtf8TextFile`은 파일 열기 성공 후 스트림 전체를 읽고 BOM을 제거하지만 읽기 중 오류 상태는 확인하지 않고 true를 반환한다. 이름(`OfficerData_impl.inc:1650`)과 효과 정의(`:1934`)는 이 반환값이 true이면 내용이 비어 있어도 내장 대체를 시도하지 않는다. 반면 명품 정의(`SpecialtyInfoWindow.cpp:189-203`)는 첫 열기 성공 후보에서 탐색을 끝낸 다음 내용이 비었으면 내장 대체를 시도한다. 읽기 오류로 일부 바이트만 얻은 경우도 helper의 성공으로 처리되며, 명품은 내용이 비어 있지 않으면 이를 파싱한다. 각 로더는 앞서 설명한 최초 호출 flag 때문에 같은 경로를 자동 재시도하지 않는다. 빈 파일, BOM만 있는 파일과 부분 읽기를 구분해 이관 시 확인한다. 파일 오류는 실행하지 않았다.
## 리소스 파일 실재 확인

`Resources.rc`의 RCDATA 선언 13개를 기준 경로에 대해 확인했고 모두 존재한다. [리소스 입력 목록](p0/resource_inputs.csv)에 ID, 경로, 크기와 SHA-256을 기록했다. 이 목록은 리소스 컴파일이나 DLL 내 포함 결과를 확인한 것이 아니다. `resource.h`에만 선언된 기재 기본 데이터와 무장 이름 ID는 이 13개에 포함되지 않는다.

별도 폰트 파일도 세 개 모두 존재한다. SHA-256은 `malgun.ttf`가 `0086C19E81D293A542E7D75564C645FB58070CC850AEFEBF8FA1C397858E510C`, `malgunbd.ttf`가 `A541834FB9CDDE9BD6D2C3FF1565CB0BB5CCF7A15E4E9DAF2CB58D9B1CF282AA`, `malgunsl.ttf`가 `A7217A2E590C86141BDDADC74A2BCDFF2EFE210DB48469A77A749E0446D91EA9`다. 해시는 현재 파일의 식별값이며 출처나 재배포 조건을 증명하지 않는다.

## 기본 정의 데이터와 기존 읽기 형식

두 기본 파일은 PowerShell JSON 해석 기준으로 유효하다. `effect_definitions.json`은 87개 항목의 배열이며 중복 `type`은 없다. `speciality_definitions.json`은 `items` 배열에 300개 항목이 있고 중복 `id`는 없다. 이 수치는 파일 내용의 문법·중복만 확인한 것이며 게임 로더가 모두 읽었다는 결과가 아니다.

기존 효과 정의 로더 `OfficerData_impl.inc:1935`는 외부 파일을 읽지 못할 때 내장 데이터를 사용하고, 최초 호출 전에 로드 완료 flag를 올리므로 그 호출이 실패해도 다시 시도하지 않는다. 줄 단위로 `type`, `template`, `valueMap`, `paramMap`을 찾고 종료 중괄호에서 항목을 저장한다. 설명은 `{value}`와 `{param}` 각각 첫 번째 위치만 대응 map 또는 숫자로 대체한다. 해당 방식은 일반 JSON의 escape와 임의 개행을 처리하는 파서가 아니므로 기본 파일 및 기존 외부 파일을 새 파서와 비교해야 한다.

명품 정의 로더 `SpecialtyInfoWindow.cpp:171`도 최초 호출 때 로드 flag를 먼저 올린다. 외부 후보 중 먼저 읽힌 파일을 선택하고 내용이 비었을 때만 내장 데이터로 대체한다. 줄에서 `id`, `name`, `description`을 찾고 중괄호가 있는 줄에서 저장하므로 한 객체의 개행 위치와 문자열 따옴표 처리에 영향을 받는다. 외부 파일이 비어 있지 않지만 파싱 결과가 없으면 내장 데이터로 다시 전환하는 경로는 없다. 회귀 조건은 기본 파일의 전체 87·300개 결과 비교, 외부 파일 우선순위, 빈 파일과 잘못된 파일, escape·개행 변형 및 실패 후 재시도 정책이다.

### 효과 기본 파일과 줄 파서의 실제 충돌

기본 파일의 107번 효과는 `type`과 `{value}`가 들어 있는 template을 한 줄에 두고 다음 줄부터 `valueMap`을 쓴다. 기존 파서는 모든 `}` 문자를 객체 종료로 취급하므로, 그 줄의 `{value}` 안 닫는 괄호를 보고 map을 읽기 전에 107번 정의를 저장한다. 이후 map은 이미 type이 -1로 바뀐 임시 객체에 기록된다. 예를 들어 이 기본 파일을 처음부터 읽을 때 107번 값 1은 해당 항목의 `활성` 매핑 대신 숫자 `1`로 표시되는 코드 경로다.

또한 임시 `EffectDef`는 콜론 없는 여는 중괄호 줄에서만 초기화한다. 기본 파일처럼 `{ "type": ...`으로 항목을 시작하면 이전 임시 map을 지우지 않는다. 107번 다음 108번은 그 상태의 map을 이어받을 수 있다. 일반 JSON 해석으로 얻은 87개 정의를 그대로 표시하면 기존 줄 파서 결과와 달라질 수 있으므로, 이관 검증은 원본 JSON 의도와 기존 파서의 실제 결과를 각각 비교해 차이를 명시해야 한다. 위 결과는 소스와 기본 파일의 정적 추적이며 게임에서 실행한 결과는 아니다.

### 기본 효과의 값 매핑 대조 후보

PowerShell로 줄별 상태 전이와 값 매핑 저장 방식을 재현해 JSON 해석 결과와 비교한 [대조 후보](p0/effect_legacy_parser_candidates.csv)를 만들었다. 재현 결과 87개 항목 모두 저장됐고 76개 항목의 `valueMap`이 JSON의 해당 항목과 다르다. 예를 들어 107번은 JSON의 0·1 매핑이 저장 시점에 빠지고, 자체 `valueMap`이 없는 119번은 이전 0·1 매핑을 갖는 결과다. 이 숫자는 `paramMap`, 문장 표시 결과, 다른 파일 형식을 포함하지 않는다.

이 재현은 C++ 함수를 컴파일하거나 실행한 결과가 아니며, 숫자·문자열 추출에 PowerShell 정규식을 사용한 근사치다. 후보의 최종 확정은 원본 로더와 같은 입력에 대한 비교가 필요하다. 이 조사에서는 게임과 빌드를 실행하지 않았다.

값 매핑 대조 후보 중 template에 `{value}`가 실제로 있는 항목은 차이 후보 67개다. 두 매핑에 등장하는 값의 합집합에 대해, 매핑이 없으면 숫자를 사용하는 기존 표시 규칙을 대조한 결과는 [값별 표시 차이 후보](p0/effect_value_display_cases.csv)의 1,514개 조합이다. 예를 들어 107번 값 1은 JSON 기준 `활성`, 재현 기준 `1`이고, 119번 값 1은 JSON 기준 `1`, 재현 기준 `활성`이다. [항목별 후보](p0/effect_display_difference_candidates.csv)는 placeholder 유무를 포함한다. 두 CSV도 앞 절의 PowerShell 근사 재현에 기반하며 원본 C++ 실행 결과가 아니다. 실제 사용되는 게임 값과 `{param}`은 별도 확인 대상이다.

## 무장 전법·특수능력 수치 파일

`S8RPK_skill_counts.json`은 DLL 폴더에 저장되며 `Cheats.cpp:176`이 `LoadSkillCounts`를 호출한다. 파일은 무장 ID 문자열을 객체 키로 하고 그 안에 스킬 오프셋의 10진 문자열과 정수 count를 기록한다. 런타임 맵은 무장 ID → 오프셋 → count다. 읽기는 줄 단위 형식에 의존하며 임의 배치의 일반 JSON을 온전히 처리하지 않는다. 파일이 없으면 version 값은 초기화하지만 기존 맵을 지우지는 않는다. 파일을 열 수 있으면 기존 맵을 지운 뒤 해석한다.

`LoadSkillCounts`는 저장 mutex와 맵 mutex를 함께 잡지만, 로드 전 미저장 변경을 flush하거나 병합하지 않는다. 따라서 재호출 시 파일을 열 수 있으면 아직 저장되지 않은 메모리 편집이 파일 내용으로 교체된다. 파일이 존재하지만 열기에 실패하거나 모듈 경로 조회에 실패하면 맵과 version을 그대로 두고 반환한다. 파일이 없으면 기존 맵은 유지하되 변경·저장 version을 둘 다 0으로 만들어, 이전에 있던 dirty 표시가 사라진다. 이후 다른 값 변경이나 명시 저장이 없다면 기존 미저장 맵만을 이유로 지연 저장하지 않는다. `InitCheats` 재시도에서 이 로드가 반복될 수 있다는 호출 경로는 [기능 보존표](P0_Feature_Contracts.md#특수능력-전투-캐시)와 함께 확인한다. 실제 파일 부재·초기화 재시도와 UI 편집이 겹쳤는지는 확인하지 않았다.

열기에 성공한 뒤 로더는 기존 맵을 지우고 행을 읽어 바로 맵에 넣는다. `getline` 반복이 끝난 이유가 정상 EOF인지 읽기 오류인지 확인하지 않고, 숫자 변환에 실패한 항목도 건너뛴 뒤 version을 모두 0으로 만든다. 따라서 읽기 오류나 잘못된 항목으로 일부만 채워져도 그 로드 결과는 변경 없음으로 표시된다. 실제 파일 오류는 실행하지 않았다.

`SetTargetSkillCount`는 양수만 저장하고 0 이하는 해당 항목을 지운다. 맵 변경과 version 증가는 같은 mutex 구간에서 수행한다. 변경 직후 파일을 쓰지 않고 `GetTargetSkillCount`의 다음 조회가 마지막 변경 후 300ms 경과 및 저장 잠금 획득 조건을 만족하면 snapshot을 truncate 저장한다. 저장 중 새 변경은 snapshot version 이후의 dirty 상태로 남는다. `SaveSkillCounts`는 별도 저장 mutex로 직렬화하고 강제 snapshot을 기록하지만 호출자에게 실패를 반환하지 않는다. 실제 파일 쓰기는 맵 잠금 밖에서 수행하며 임시 파일 교체는 사용하지 않는다.

로드는 setter와 달리 파일의 0 또는 음수 count도 맵에 그대로 넣으며 오프셋의 허용 범위를 검사하지 않는다. 전투 전법 적용은 count가 양수인 경우에만 1바이트로 변환해 쓰므로 파일에 256을 넣으면 해당 분기를 통과한 뒤 0을 쓴다. 저장기는 맵의 숫자를 그대로 출력하므로 이렇게 로드된 0·음수도 별도 변경으로 제거되지 않았다면 다시 저장될 수 있다. 또 한 줄짜리 유효 JSON `{"1":{"313":5}}`는 로더가 그 줄을 무장 객체 시작으로만 처리해 내부 수치 항목을 따로 읽지 않는다. 이 예는 줄 조건의 정적 대조이며 원본 C++ 파서를 실행한 결과는 아니다.

특수능력 자동배정 완료 경로는 맵을 직접 갱신하고 신규 부여가 있으면 `SaveSkillCounts`를 명시 호출한다. 이관 회귀 조건은 기존 파일의 숫자 키·빈 맵·형식 변형, 연속 편집 뒤 조회가 없는 경우, 저장 중 추가 편집, 파일 부재·열기·쓰기 실패, worker 결과 적용과 저장의 순서다.

`WriteSkillCountsSnapshot`은 내용을 출력하고 `flush()`한 직후 `file.good()`를 저장한 다음 `close()`한다. close 후 상태는 다시 확인하지 않고 앞에서 저장한 결과가 성공이면 snapshot version을 저장 완료로 표시한다. 따라서 flush 이후 close에서만 오류 상태가 생기는 경우는 이 반환 판정에 반영되지 않는다. 실제 파일 오류는 실행하지 않았다.

전법 횟수의 다중 편집은 현재 무장 ID를 먼저 `SetTargetSkillCount`로 변경한 뒤 선택 주소들을 순회하며 각각 ID를 읽어 같은 함수를 호출한다. 맵 mutex와 변경 version 갱신은 각 호출 단위다. 전체 선택 집합을 하나의 잠금이나 저장 트랜잭션으로 묶지 않으므로 다른 맵 조회·자동배정·저장이 호출 사이에 일어나면 일부 무장만 변경된 중간 상태를 관측할 수 있다. 실제 동시 실행은 확인하지 않았다.

자동배정의 `FinishAutoAssignJob`은 `SetTargetSkillCount`를 통하지 않고 맵에 직접 1을 기록하므로 변경 version을 증가시키지 않는다. 기존에 dirty가 없는 상태에서 신규 배정 후 명시 `SaveSkillCounts`가 실패하면 그 자동배정 변경만으로는 dirty 표시가 생기지 않아 이후 일반 조회의 지연 저장이 이를 재시도하지 않는다. `SaveSkillCounts`는 성공 여부를 반환하지 않고 완료 상태도 그대로 설정한다. 기존 수동 변경이 이미 dirty이거나 이후 다른 변경·명시 저장이 있으면 해당 경로는 별도로 동작한다. 파일 실패와 재시도는 실행하지 않았다.

### 지연 저장과 종료

기준 소스의 자체 cpp/h/inc 전체에서 `FlushPendingSkillCounts` 호출은 `GetTargetSkillCount` 내부의 `false` 호출만 찾았다. `SaveSkillCounts`의 명시 호출은 특수능력 자동배정 결과 경로다. `Source_impl.inc:387` 이후 정상 종료에는 pending 저장을 강제로 호출하는 코드가 없다. 따라서 마지막 수동 편집 뒤 300ms를 넘긴 조회나 별도 명시 저장이 일어나기 전에 종료하면 변경이 메모리에만 남을 수 있다. `force=true`도 지연 시간만 무시하며 저장 mutex는 `try_to_lock`으로 잡으므로 이미 다른 저장 중이면 기다리지 않는다. 이 결과는 검색한 기준 소스의 정적 호출 경로이며 종료를 실행해 재현한 것은 아니다.

### DLL 경로 조회의 호출별 차이

기준 자체 cpp·h·inc의 `GetModuleFileNameA` 직접 호출을 대조했다. 무장 이름 읽기는 0으로 초기화한 버퍼와 반환값을 사용하고 실패 시 내장 리소스를 시도한다. 무장 이름 저장과 특수능력 수치 파일 읽기·쓰기는 반환값이 0이면 중단한다. 사용자 기재 표시 경로는 실패 시 작업 폴더 후보로 넘어간다. 반면 [설정 경로](P0_Config.md#설정-저장-실패의-알림-범위)와 `Source_impl.inc`의 초기 DLL 이름 로깅은 초기화하지 않은 버퍼를 넘기고 반환값을 확인하지 않는다. `Source.cpp`의 별도 세션 로그 wrapper는 버퍼를 0으로 초기화하고 빈 문자열이면 `unknown`을 사용하므로 두 로그 경로를 구분한다. 이 호출들은 `MAX_PATH` 버퍼의 반환 길이를 버퍼 크기와 비교해 잘림을 판정하지 않는다. 실제 경로 조회 실패나 잘림은 확인하지 않았다.

기재 runtime의 기본 JSON 경로와 `version.dll` 탐색은 `GetModuleFileNameW`를 사용하고 반환 길이가 0이거나 `MAX_PATH` 이상이면 해당 모듈 경로를 사용하지 않는다. 기본 JSON은 모듈 폴더 확인에 실패하면 작업 폴더 후보를 찾고, `version.dll`은 실행 파일 폴더를 확인한다. `TraitTextEditorData.cpp`도 W 경로를 사용하지만 결과를 `std::filesystem::path(...).string()`으로 좁은 문자열로 변환해 반환하고, 이후 `ifstream`에 넘긴다. 따라서 W API 사용만으로 파일 열기까지 모든 단계가 wide 경로인 것은 아니다. 실제 비ASCII 경로와 변환 결과는 확인하지 않았다.

### 내장 Ruda Bold의 공개 파일 대조

`Fonts.h`의 `RudaBold` 배열 24,848바이트는 Google Fonts 저장소의 2015년 커밋 `90abd17b4f97671435798b6147b698aa9087612f`에 있는 [`ofl/ruda/Ruda-Bold.ttf`](https://github.com/google/fonts/blob/90abd17b4f97671435798b6147b698aa9087612f/ofl/ruda/Ruda-Bold.ttf)와 바이트 단위로 일치한다. 양쪽 SHA-256은 `FC181ED4AB78CF4D355BACBD3316F6094ED2CC9BCFC1B43DABC445D4F4270AF3`이다. 반면 Google Fonts의 2017년 커밋 `12992056f1c651c4544b7a8eac8001ede3c20c86` 파일은 24,620바이트이고 SHA-256이 `55E06CB3CA75E916D5A7E8CB91A24B847E384FE361F9CD659A246F6AB60EBDB9`로 다르다. 공개 파일 일치는 동일한 바이트의 출처 후보를 식별하며, 기준 프로젝트가 실제로 어느 경로에서 가져왔는지는 증명하지 않는다. 배열과 공개 파일은 메모리에서 비교했고 빌드·게임 실행은 하지 않았다.

동일한 Google Fonts 커밋의 `ofl/ruda`에는 별도 [`OFL.txt`](https://github.com/google/fonts/blob/90abd17b4f97671435798b6147b698aa9087612f/ofl/ruda/OFL.txt)와 `FONTLOG.txt`가 있다. 이 `OFL.txt`는 4,456바이트이며 SHA-256은 `1C45059CEA5C6798C8591B0A17961A30328747D44214FF9B8F9C62A683BD6598`이다. 머리말은 폰트 내부 메타데이터와 같은 두 제작자 및 예약 이름을 표시하고 SIL Open Font License 1.1 전문을 담는다. 기준 S8RPKCheats 체크아웃의 파일명 검색에서 `OFL`, `LICENSE`, `NOTICE`로 시작하는 별도 고지 파일은 찾지 못했다. 파일명 검색은 다른 이름이나 파일 내부에 들어 있는 모든 고지를 배제하지 않는다. 이관할 폰트와 해당 고지의 배포 반영은 실제 배포 구성에서 따로 확인한다.

## 후방지원 노선 파일의 읽기 조건

`CityInfoWindow.cpp:1344`는 `S8RPK_rear_support_routes.json`의 로드 flag를 파일 열기 전에 세우고 기존 노선 배열을 지운다. 파일이 없거나 열기에 실패해도 이 경로는 같은 프로세스에서 다시 읽지 않는다. UI와 `RunYearlyRearSupport` 양쪽이 로드를 호출한다. 저장은 설정 파일과 같은 디렉터리에서 직접 truncate하고 오류를 호출자에게 반환하지 않는다.

읽기는 일반 JSON 파서가 아니라 줄별 `sscanf_s` 형식이다. 노선 한 개의 일곱 필드는 한 줄에 지정된 순서로 있어야 읽히고, 도시 인덱스가 범위 밖이거나 출발·도착이 같으면 건너뛴다. `mode=1`만 비율로 취급하고 나머지는 고정량이며 음수는 0, 비율은 최대 100으로 제한한다. 저장 파일이 다른 유효 JSON 배치나 필드 순서를 사용하면 일부 노선이 무시될 수 있다.

로드·노선 UI 수정은 렌더 경로와 background loop 양쪽에서 접근한다. 이 함수들의 로드 flag와 노선 배열 접근을 감싸는 공통 잠금은 해당 경로에서 확인되지 않았다. 실제 동시 접근은 확인되지 않았으며 이관 회귀 조건은 파일 부재 후 생성, 잘못된 행·순서, 음수·비율 경계, 저장 실패 및 로드·편집과 연간 실행의 겹침이다.

## 무장 이름 파일의 최초 읽기와 편집 저장

`OfficerData_impl.inc:1650`의 `LoadOfficerNames`는 파일이나 대체 리소스를 열기 전에 `g_namesLoaded=true`로 바꾸므로 둘 다 실패해도 같은 경로에서 자동 재시도하지 않는다. 외부 파일이 읽히면 줄의 `{`에서 임시 항목을 초기화하고 `id`, `name`, `ja`를 추출해 `}`에서 이름 맵에 넣는다. 이름과 일본어 값은 다음 따옴표까지 단순 추출하므로 JSON escape를 해석하는 파서가 아니다. 표시 이름은 일본어가 있으면 `name(ja)`로 조합한다.

`SaveOfficerNameToJson`은 기존 외부 파일을 같은 줄 기반 방식으로 ID 정렬 맵에 읽어 수정하고 파일 전체를 truncate해 다시 쓴다. 파일이 없으면 리소스에서 기본 명단을 읽으려 하지만 현재 `Resources.rc`에는 해당 리소스가 없으므로 성공적으로 로드할 별도 리소스가 없을 때 새 맵에 수정한 한 명만 넣어 파일을 만든다. 기존 파일이 열리지만 파싱 결과가 비어 있어도 읽기 함수는 true를 반환하므로 한 명만 남긴 재작성으로 이어질 수 있다. 기록기는 따옴표·역슬래시·줄바꿈을 escape하지만 읽기 함수는 그 escape를 복원하지 않는다. 출력 파일 열기 이후 쓰기 스트림 오류는 반환값에 반영하지 않는다.

저장 함수가 성공을 반환하면 이름 맵을 갱신하고 호출 UI는 전체 목록 캐시 갱신을 요청한다. 저장 함수의 `g_officerNames` 값은 정규화한 이름에 기존 `ja`가 있으면 괄호로 붙이지만, 목록의 `UpdateOfficerNameInAllCache`는 편집 버퍼 문자열을 첫 일치 행에 그대로 대입한다(`OfficerData_impl.inc:1917-1930`, `SelectOfficercapture_impl.inc:93-100, 2805-2807`). 따라서 일본어 이름이 있는 항목이나 정규화 전후 문자열이 다른 입력은 저장 직후 두 캐시의 표시값이 다를 수 있다. 이후 목록 재구축과 실제 표시는 실행하지 않았다. 회귀 조건은 외부 파일·리소스 부재, 파일 열기 및 쓰기 실패, 빈 파일과 다른 JSON 줄 배치, 따옴표·역슬래시·개행 포함 이름, 중복 ID, 다른 언어 이름 유지와 재시작 후 재읽기다. 실제 파일 저장은 실행하지 않았다.

## 저장소 내 기본 데이터 사본

기준 저장소 최상위와 `Internal DX11 Base/Resources/Defaults`의 동일 이름 파일을 SHA-256으로 비교했다. `S8RPK_cheat_char.json`, `S8RPK_traits_default.json`, `speciality_definitions.json` 세 쌍은 각각 바이트가 같다. `effect_definitions.json`은 최상위 파일에 UTF-8 BOM 3바이트가 추가된 차이만 있다. 최상위 무장 이름 JSON은 PowerShell JSON 해석 기준 1402개 항목이며 ID도 1402개로 중복이 없다. 이는 기존 줄 파서의 결과나 게임 내 표시를 검증한 수치가 아니다.

기본 리소스 네 파일의 현재 경로는 저장소 이력에서 2026-09-24의 각각 다른 `chore: add embedded default data resources` 커밋에 나타난다. `git log --follow`의 이름 변경 추적은 효과 정의와 무장 이름을 2026-04-06의 `f85770da112d601adefdf622cb59b1b75b913974`까지, 명품 정의를 2026-04-11의 `f19c046392c879b5469efba36b185cad160817c9`까지 연결한다. 기재 기본 파일은 2026-09-24의 `c872b53c88a361e7d029c64d7462ae8c8c260bd0`까지 연결된다. 이는 Git의 유사도 기반 경로 추적과 해당 저장소 안의 이력이며 데이터의 최초 작성자나 게임 원본에서의 획득 경로를 증명하지 않는다.

최상위 무장 이름 데이터와 Defaults 사본이 저장소에 존재하는 것과 DLL의 RCDATA에 포함되는 것은 다르다. 현재 `Resources.rc`에는 이름 JSON이 선언되지 않으며 해당 파일명에 대한 출력 복사 지정은 프로젝트·상위 props 텍스트에서 찾지 못했다. 실제 배포 디렉터리의 파일 구성은 빌드하지 않아 확인하지 않았다. 기본 기재 JSON도 내장 ID 요청이 외부 파일 경로로 전환되는 앞 절의 조건을 따른다. 기준 README는 추가 기재 편집을 위해 이 파일을 DLL 폴더에 두도록 안내한다. 프로젝트·상위 props 및 세 빌드 스크립트의 텍스트에는 `S8RPK_traits_default.json` 파일명이나 명시적 해당 파일 복사 지시가 없다. 평가된 post-build 명령도 비어 있지만 외부 import target과 실제 배포 결과는 이 텍스트 검색만으로 확정하지 않는다.

## 기준 무장 이름의 줄 파서 대조 후보

저장소 최상위 `S8RPK_cheat_char.json`에 대해 PowerShell로 기존 로더의 줄별 `{` 초기화, `id/name/ja` 추출, `}`에서 비어 있지 않은 이름만 저장하는 과정을 근사 대조했다. 일반 JSON 해석의 1402개 ID 중 이름이 비지 않은 1224개는 근사 추출의 표시 문자열과 일치했고, 나머지 178개는 이름과 일본어가 모두 비어 있어 기존 로더 조건상 맵에 넣지 않는 후보였다. 이 기준 파일에는 역슬래시가 들어간 줄이 없었다.

이는 현재 파일의 줄 배치에 대한 PowerShell 근사 결과다. C++의 `NormalizeUtf8`·ANSI 변환이나 원본 함수 실행을 재현한 검증이 아니며, 사용자의 수정 파일·escape·다른 개행 형식까지 보장하지 않는다. 빈 이름 항목을 보존할지와 저장 후 재읽기는 앞의 편집 저장 회귀 조건에서 별도로 확인한다.

## 기준 명품 정의의 줄 파서 대조 후보

기준 `speciality_definitions.json`의 300개 항목을 PowerShell로 일반 JSON 해석 결과와 기존 줄 파서의 ID·이름·설명 추출을 근사 비교했다. 이름이 비어 있지 않은 206개가 후보 맵에 들어가고, 이름이 빈 94개는 기존 조건에서 제외된다. 이름이 있는 항목 중 205개는 이름·설명이 일치했고 ID 202 하나는 설명의 `\n`을 기존 방식이 두 문자 그대로 보관하는 반면 JSON 해석은 줄바꿈으로 해석했다. 이 차이는 자동 명품 배분의 이름 존재 판정뿐 아니라 설명 표시에 대한 이관 비교 대상이다.

이 결과는 현재 파일의 줄 배치에 대한 근사치이며 C++ 로더나 UI를 실행한 결과가 아니다. 외부 파일의 escape·따옴표·객체 줄 배치와 빈 내용의 fallback은 별도 회귀 조건으로 남는다.

## 설치된 게임 폴더의 데이터 형식 대조

현재 설치된 `SAN8R` 게임 폴더의 파일을 읽기만 하여 기준 저장소와 비교했다. 사용자의 이름·기재 편집 내용과 설정값은 이 문서에 복사하지 않았다. 기재 파일 식별값은 설치본 73,671바이트·SHA-256 `D4B43B62187E1E7B90F3C85F8E783D79C9525A9B8FC62FF35E94BC51D2405868`, 기준본 102,091바이트·SHA-256 `1848937DA4E1CF9BF999586FE00E5524723732D574DA57ECEE933D8166C3DA8F`이다. 아래 설치본 집계는 이 파일 상태에 한정한다.

- `effect_definitions.json`과 `speciality_definitions.json`은 각각 기준 최상위 파일과 바이트 단위로 동일하다.
- `S8RPK_cheat_char.json`은 바이트는 다르지만 일반 JSON 해석 결과 두 파일 모두 1,402개 항목과 같은 ID 집합이며 각 ID의 객체 내용도 모두 같다. 이는 기존 줄 파서가 두 파일을 똑같이 읽는다는 증거는 아니다.
- `S8RPK_traits_default.json`은 설치본 180개, 기준본 254개 항목이다. 설치본의 ID는 모두 기준본에 포함되고 공통 180개 중 177개 객체가 JSON 구조상 같다. 양쪽의 각 항목은 효과 6개를 가진다. `customNames` 키 수는 설치본 163개, 기준본 213개다. 설치본이 현재 사용자 데이터를 담을 수 있으므로 기준 파일을 덮어쓰거나 빠진 항목을 오류로 판단하지 않는다.
- 설치된 기재 파일의 `customNames` 앞에서 `index`, `id`, `effects`가 같은 줄에 있는 후보는 180줄이며 ID는 중복되지 않았다. 각 줄을 일반 JSON으로 해석해 `id=index+1`, index 범위, 효과 6개와 16비트 값 범위를 대조한 결과 180줄 모두 통과했다. 이는 기존 C++ 줄 파서의 전체 문자열 해석·metadata·런타임 적용을 실행한 결과가 아니다.
- 일반 JSON 해석 기준으로 설치본에서 누락된 74개 기재 인덱스에는 `customNames` 메타데이터가 없다. 이 해석 결과가 기존 runtime에 그대로 로드된다는 가정에서는 누락 슬롯이 donor·배경 메타데이터 복제 대상은 아니며 ID만 정규화하는 분기로 간다. 다만 전체 테이블 쓰기와 다른 슬롯의 donor 참조는 별도다. 현재 `version.dll` 존재로 기준 wrapper는 자체 runtime tick을 건너뛰므로 설치 환경에 실제 적용됐다는 뜻은 아니다.
- 설치본 `customNames`의 일반 JSON 해석에서 이름 또는 설명이 비어 있지 않은 132개를 대상으로 기존 코드의 donor 기본값 30과 자기 참조 대체 규칙을 계산하면, donor가 해당 인덱스보다 앞인 경우 125개, 뒤인 경우 7개다. 기준 파일뿐 아니라 이 설치본에서도 순회 방향에 따라 수정 전후 레코드를 참조할 수 있는 구조다. 이는 데이터와 코드 조건의 계산이며 원본 C++ 파서·실제 게임 레코드의 결과는 아니다.
- 같은 게임 폴더의 `trait_texts.ini`는 이번 읽기 전용 확인 시 존재하지 않았다. 이 파일은 DLL 폴더를 우선 사용하므로 이 결과는 해당 폴더의 파일 존재만 뜻하며, 실제 로드된 DLL의 위치나 다른 작업 폴더의 편집 파일 부재를 증명하지 않는다.
- 같은 게임 폴더에 `version.dll`이 존재한다. 기준 소스의 `TraitConfigRuntime.cpp:582` wrapper는 이 파일의 **존재**를 확인하면 자체 기재 runtime tick을 건너뛴다. 설치된 `hid.dll`이 기준 소스로 만들어졌는지와 `version.dll`의 실제 실행 동작은 확인하지 않았으므로 설치 환경의 기재 적용 결과로 단정하지 않는다.

이 대조는 현재 파일의 일반 JSON 해석과 파일 존재 여부다. 기준 C++ 로더 실행, 사용자 설정 변경, 게임 실행 및 빌드는 하지 않았다. 이관 시 저장 데이터 보존과 외부 기재 runtime 공존을 함께 검증한다.

## 맑은 고딕의 저장소 이력과 선택 실패

기준 저장소 이력에서 `Fonts.h`, `malgun.ttf`, `malgunbd.ttf`, `malgunsl.ttf`는 모두 최초 커밋 `3b66385589b66053164fbca40d6aeb7452c26899`에 이미 존재한다. 이후 해당 파일의 도입 출처는 이 이력만으로 알 수 없다. 현재 PC의 `Windows\Fonts`에서 이름이 같은 맑은 고딕 세 파일을 읽기 전용 SHA-256으로 대조했을 때 저장소 파일과 각각 다르다. 예를 들어 regular는 저장소 13,457,164바이트, 시스템 13,459,196바이트이며 시스템 파일 SHA-256은 `7A183CF1C6C56B9609FCC16EDA8B5229FBC11758A21E669EC00343239B02192F`다. 두 bold와 semilight도 크기와 해시가 다르다. 이 비교는 현재 PC 파일의 식별 결과이며 복사 출처나 배포 권한의 증거가 아니다.

`Engine.cpp`의 선택 순서는 DLL 폴더 bold가 존재하면 bold, 없으면 regular, 둘 다 없으면 고정 경로 `C:\Windows\Fonts\malgun.ttf`, 그것도 없으면 메모리의 `RudaBold`다. 파일 경로가 존재하면 `AddFontFromFileTTF`의 반환 포인터를 확인하지 않고 `fontLoaded=true`로 설정한다. 따라서 존재하는 파일을 ImGui가 읽거나 해석하지 못하는 경우에도 다음 파일 또는 메모리 폰트로 자동 전환하지 않는다. DLL 경로 확인 실패는 시스템 경로로 넘어간다. 시스템 폰트 경로는 환경의 Windows 디렉터리를 조회하지 않고 위 문자열을 사용한다.

이관 확인 항목은 bold·regular 부재, 존재하지만 폰트 로드 실패, 시스템 경로 부재, 메모리 폰트 선택, 같은 이름의 서로 다른 버전 및 한글 글리프다. 실제 글꼴 로드·표시는 실행하지 않았다.

### 기본 기재 JSON의 읽기·저장 경로 결정

`ResolveDefaultTraitJsonPath`는 호출할 때마다 DLL 디렉터리의 `S8RPK_traits_default.json`이 일반 파일이면 이를 선택하고, 없으면 현재 작업 디렉터리의 같은 이름을 찾는다. 두 위치 모두에 파일이 없을 때는 DLL 경로를 얻었다면 그 경로를 반환하지만, 읽기는 실패한다. `IDR_JSON_TRAITS_DEFAULT`의 이름과 달리 이 요청은 DLL 리소스가 아니라 같은 경로 선택 함수를 거친 외부 파일 읽기다.

추가 문구 저장은 파일을 읽는 시점과 출력 파일을 여는 시점에 이 선택 함수를 각각 호출한다. 따라서 두 호출 사이 파일 존재 상태나 작업 디렉터리가 바뀌면 읽은 파일과 쓴 파일이 달라질 수 있다. 저장 함수는 쓰기 성공 뒤 기재 runtime의 로드 완료 상태를 초기화하거나 재로드하지 않는다. 앞서 기록한 것처럼 적용 버튼이 런타임 문구를 별도로 게시한다. 경로 결정의 실제 변경 여부는 실행하지 않아 확인하지 않았다.

이관 대조 조건은 DLL 폴더와 작업 폴더 양쪽에 파일이 있는 경우, 한쪽만 있는 경우, 없는 경우, 파일 선택 시점의 변화, 저장 후 적용 전·후와 프로세스 재시작이다. 설치된 사용자 파일은 수정하지 않았다.

## 보주 정의의 출처 표기와 마스크 대조

`Cheats/Civilian/JewelSettingsDefinitions.inc`는 별도 데이터 파일이 아니라 `JewelSettings.cpp`에 include되는 185개 정적 정의다. 각 행의 보조 ID·raw ID·이름·계통과 원본 줄을 [목록](p0/jewel_definitions.csv)에 추출했다. 원본 주석은 업로드된 `version.dll`의 SHA-256 `01bfb8941d58f231231244b5bd6b8073a97e9630b91ea2312db3b9c2bc982c0a`와 파일 오프셋 `0x10F0F0`, 24바이트씩 185개라고 기술한다. 이 내용은 원본 코드의 출처 주장이며, 아래에서 현재 다운로드 폴더의 해시가 일치하는 파일과 별도로 대조했다.

정의 행과 `JewelSettings.cpp`의 두 정적 마스크를 PowerShell로 각각 집합 비교했다. 정의는 185행이고 보조 ID 185개가 모두 서로 다르며 모든 행에서 `raw ID = 보조 ID + 64`다. 34바이트 개방 마스크의 설정 비트는 raw ID 185개와 정확히 같고, 64바이트 보조 정의 마스크의 설정 비트에 1을 더한 집합은 보조 ID 185개와 정확히 같다. 어느 쪽에도 정의에 없는 설정 비트나 마스크에서 빠진 정의가 없었다. 이는 기준 소스의 세 정적 표끼리의 일관성 확인이며 게임 데이터나 원본 DLL과의 일치 증거는 아니다.

계통별 개수는 공통 30, 재야·두령·일반·군사·태수·도독·군주 각 20, 악한·무인·문인 각 5다. 마스크의 ID 기준이 각각 raw ID와 보조 ID-1로 다르므로 이관 시 저장된 선택 비트, 게임 개방 비트와 UI 정의 행의 대응을 함께 보존한다. 실제 선택·개방 동작은 실행하지 않았다.
### 주석에 기록된 DLL과 정적 정의 비교

`C:\Users\lance\Downloads\version.dll`을 실행하지 않고 읽어 SHA-256을 계산한 결과 위 주석의 해시와 일치했다. 이 PE의 ImageBase는 `0x180000000`이며 표의 시작 RVA `0x10FCF0`는 `.rdata`의 파일 오프셋 `0x10F0F0`에 대응한다. 각 24바이트 행의 첫 4바이트 raw ID, `+8` 이름 포인터와 `+16` 계통 포인터를 읽고 포인터가 가리키는 UTF-16 문자열을 정적 정의 185행과 순서대로 비교했다. raw ID, 이름과 계통 모두 불일치는 없었다. 보조 ID는 raw ID에서 64를 뺀 값으로 소스의 각 행과 일치한다.

이는 해시가 일치하는 현재 파일과 체크아웃된 표의 내용 대응을 확인한 결과다. DLL의 작성자·배포 조건, 실제 게임에서 로드되는 파일과 동작, 다른 버전의 데이터 일치까지 확인한 것은 아니다. DLL이나 게임을 실행하지 않았다.
### 설치된 외부 DLL과 보주 정의 기준

현재 `SAN8R` 게임 폴더의 `version.dll`과 다운로드 폴더의 비교 대상은 각각 1,543,680바이트이고 SHA-256이 모두 `01bfb8941d58f231231244b5bd6b8073a97e9630b91ea2312db3b9c2bc982c0a`로 같다. 따라서 이 시점에 디스크에 있는 두 파일은 동일하며, 앞에서 비교한 185개 보주 표는 설치된 파일에도 같은 바이트로 들어 있다. 파일은 읽기만 했다.

기준 소스의 기재 runtime은 게임 폴더에 `version.dll`이 존재하면 자체 tick을 건너뛰지만, 보주 기능의 `JewelSettings.cpp`는 정적 정의 표와 독립된 설치 경로를 사용한다. 파일이 존재한다는 것만으로 외부 DLL이 실제로 로드됐는지, 두 기능이 동시에 실행됐는지 또는 동일한 게임 메모리를 변경하는지는 알 수 없다. 이관 시 설치 파일의 존재, 실제 로드와 기능별 동작을 구분한다.
이 비교 대상의 Windows 파일 버전 정보에서 제품명·설명·버전·회사명·원본 파일명·저작권은 비어 있고, 서명 조회 결과는 `NotSigned`다. 이 메타데이터만으로 작성자나 배포 조건은 확인되지 않는다.
## 파일 경로 문자열 대조 범위

자체 cpp·h·inc에서 따옴표로 직접 적힌 `.json`, `.ini`, `.txt`, `.log`, `.png`, `.ttf` 문자열을 검색해 [후보 위치](p0/file_path_literal_candidates.csv)에 모았다. 26개 위치·서로 다른 문자열 16개이며 실행 경로나 실제 파일 열기를 자동 판정한 목록은 아니다. 외부 라이브러리, 여러 문자열의 조합, 다른 확장자, 실행 중 만들어지는 경로와 리소스 스크립트는 이 검색 범위 밖이다.

명품 정의의 네 외부 후보 중 영어 표기가 다른 파일은 `speciality_definitions.json`과 `specialty_definitions.json`이다. 각 이름을 DLL 폴더에서 먼저, 그 다음 `release` 하위에서 같은 순서로 찾는다. `ReadUtf8TextFile`이 성공한 첫 파일에서 반복을 멈추고, 그 결과가 빈 문자열이면 뒤 후보를 더 읽지 않고 내장 기본 리소스로 넘어간다. 검색에서 나온 `외부 san8r_traits_config.json`은 파일 경로가 아니라 로그에 표시하는 설명 문자열이다. 같은 이름이 문자열로 나온다는 사실만으로 파일 입력으로 집계하지 않는다.
## 내장 대체 폰트 데이터의 소유

외부·시스템 맑은 고딕 경로를 선택하지 못하면 `Engine.cpp:444-447`은 정적 `RudaBold` 배열을 `AddFontFromMemoryTTF`에 전달하기 전에 `FontDataOwnedByAtlas=false`로 설정한다. 기준 ImGui의 `ImFontAtlas::AddFont`는 이 설정을 받으면 전달된 데이터를 자체 할당 버퍼에 복사하고 내부 설정의 소유 flag를 true로 바꾼다. 이후 atlas의 `ClearInputData`는 내부 소유 버퍼를 해제한다. 따라서 이 경로는 정적 배열 자체를 atlas가 해제하는 방식이 아니다.

이는 기준 ImGui 구현의 소스 경로다. 파일 폰트 선택·로드 실패의 fallback 조건과 CPU/GPU atlas 준비는 각각 앞 절과 [오버레이 조사](P0_Overlay.md#dx12-글꼴-atlas-생성과-gpu-texture-연결)를 따른다. 실제 초기화·종료는 실행하지 않았다.

## 맑은 고딕과 내장 폰트의 문자 범위

`Engine.cpp`는 맑은 고딕 파일에는 Latin, 일반 문장 부호, 화살표·도형·기호, CJK 기호, 한글 음절 범위를 전달한다. 내장 `RudaBold` 경로는 `GetGlyphRangesKorean()`을 사용하며 이 목록은 Latin, 한글 호환 자모 `U+3131–U+3163`, 한글 음절 `U+AC00–U+D7A3`, 대체 문자 `U+FFFD`다. 두 요청 범위는 같지 않다. 특히 파일 폰트 쪽 요청 목록에는 한글 호환 자모와 `U+FFFD`가 없고 내장 쪽 요청 목록에는 화살표·도형 등의 범위가 없다.

별도로 기준 `Fonts.h`의 24,848바이트와 `malgunbd.ttf`의 TrueType cmap format 4·12를 읽어 다섯 문자를 표본 대조했다. 두 폰트 모두 `U+0041`에 glyph 매핑이 있다. `U+AC00`, `U+3131`, `U+25B6`, `U+FFFD`는 기준 맑은 고딕 bold에 매핑이 있지만 내장 RudaBold에는 찾지 못했다. 이 표본은 실제 atlas 생성·폰트 fallback·글자 표시를 실행한 결과가 아니며 모든 문자의 지원 여부를 뜻하지 않는다. 이관 시 요청 범위와 실제 폰트 glyph 범위, 외부 폰트 부재 시 한글·기호 표시를 따로 검증한다.

같은 다섯 문자를 Windows의 `GlyphTypeface.CharacterToGlyphMap`으로 독립 대조했을 때도 두 폰트의 매핑 유무가 위 표본과 일치했다. 내장 배열은 검사용 임시 TTF로 만들어 읽은 뒤 삭제했으며 참고 소스는 변경하지 않았다. 이 교차 검사는 폰트 cmap 매핑에 대한 것으로 UI 렌더 결과는 포함하지 않는다.

`GlyphTypeface.CharacterToGlyphMap`의 전체 키를 범위별로 집계하면 내장 RudaBold는 전체 232개 매핑 중 한글 음절 `U+AC00–U+D7A3` 0개, 한글 호환 자모 `U+3131–U+3163` 0개, 화살표 `U+2190–U+21FF` 0개다. 기준 `malgunbd.ttf`는 각각 한글 음절 11,172개, 호환 자모 51개, 화살표 12개 매핑이 있다. 맑은 고딕에서 매핑이 있어도 앞 절의 atlas 요청 범위에 포함되지 않은 문자는 이 코드의 폰트 atlas에 자동 포함된다고 판단하지 않는다. 이 수치는 글꼴 파일의 mapping이며 화면 렌더 검증은 아니다.

## 무장 이름의 인코딩 판정과 정규화

`OfficerData_impl.inc:1610-1650`의 `IsUtf8`은 선행 바이트의 길이 형태와 이어지는 바이트의 상위 비트만 검사한다. 예를 들어 `C0 80`의 과잉 인코딩이나 `ED A0 80`의 surrogate 인코딩도 이 함수의 바이트 형태 검사에는 통과한다. 코드포인트 최소값·surrogate·Unicode 최대값을 검사하는 UTF-8 전체 유효성 검사는 아니다.

`LoadOfficerNames`와 이름 파일 편집 경로는 이름·자를 `AnsiToUtf8`에 전달한다. 위 검사에 통과하면 그대로 반환하고, 실패하면 현재 시스템의 `CP_ACP`로 UTF-16을 거쳐 UTF-8 변환을 시도한다. 이후 `NormalizeUtf8`은 Windows `NormalizeString(NormalizationC)`으로 NFC 정규화를 시도하며, 길이 조회 단계가 실패하면 전달받은 원본 문자열을 반환한다. 변환 호출은 null 종료 문자열을 사용하므로 임베디드 null 뒤는 해당 변환의 입력에 포함되지 않는다. 단순한 인코딩 판정과 완전한 Unicode 유효성 검사를 동일하게 취급하지 않는다.

이 내용은 코드 경로다. 실제 시스템 코드 페이지, 잘못된 파일의 Windows 변환 결과 및 게임 내 표시는 실행하지 않았다. 이관 검증은 정상 UTF-8·ACP 입력, NFC 결합 문자, 잘못된 시퀀스, 임베디드 null과 변환 실패를 포함한다.

이 이름 로더의 `ReadUtf8TextFile`은 이름과 달리 파일을 바이너리 바이트로 읽고 시작 부분의 UTF-8 BOM만 제거하며 파일 전체 UTF-8 유효성을 검사하지 않는다. 이후 줄 단위 파서에서 추출한 `name`·`ja` 각각에 위 변환과 정규화를 적용한다. 내장 JSON 로더도 시작 BOM을 제거한다. 반면 기존 파일을 이름 저장용 map으로 읽는 `ParseCharJsonFileToMap`은 별도의 텍스트 `ifstream`과 줄 파서를 사용한다. 두 읽기 경로의 BOM 제거·문자열 추출을 같은 공통 JSON 파서로 가정하지 않는다. 파일 읽기와 저장을 실제 실행하지 않았다.

### 설치된 이름 파일의 줄 파서 근사 대조

현재 설치본과 기준본에 대해 `LoadOfficerNames`의 줄별 객체 초기화, ID·name·ja 추출과 빈 이름 제외를 별도 스크립트로 근사했다. 둘 다 일반 JSON 1,402개 항목, 근사 표시 후보 1,224개이며 두 후보 map이 서로 같았다. 두 파일 모두 역슬래시가 들어간 줄은 없었다. 이름 값은 문서에 복사하지 않았다.

근사 대조는 Python의 NFC 정규화와 UTF-8 읽기를 사용했다. C++ 함수, Windows 코드 페이지 변환, 실제 파일 저장과 게임 표시는 실행하지 않았으므로 원본 로더의 전체 동작이 같다는 증거는 아니다. 사용자 파일이 바뀌면 이 결과도 재확인해야 한다.

무장 이름의 저장 후 재읽기 차이는 따옴표가 있는 경우 단순히 escape 문자가 남는 데 그치지 않는다. 예를 들어 입력 `A"B`를 기록기는 JSON 문자열 `"A\"B"`로 출력하지만, 두 줄 파서는 역슬래시 여부를 보지 않고 다음 따옴표에서 값을 끊으므로 `A\`까지만 추출한다. 역슬래시나 개행도 각각 escape된 문자 그대로 추출된다. 입력과 파일의 따옴표 위치를 별도 스크립트로 근사 확인했으며 원본 C++ 저장·읽기는 실행하지 않았다. 기존 파일의 안전한 재읽기와 새 JSON 파서로의 호환성을 이관 조건으로 둔다.
