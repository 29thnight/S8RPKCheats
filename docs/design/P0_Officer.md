# P0 무장 조회·편집·성장 조사

기준: S8RPKCheats `068ca1d881edf870f7cf06f935cf50e286004af8`. `P0_Traits.md`의 기재 테이블 외에 무장·관계 데이터의 정적 경로를 기록한다. 게임이 소유하는 객체에 대한 접근 안전성과 실제 실행 순서는 아직 검증하지 않았다.

## 배열과 선택

- `DrawOfficerListWindow`는 무장 배열 기반을 캐시하고 약 2초마다 체인을 재탐색한다. 값이 같은 주소로 재할당된 세대까지 식별하는지와 캐시된 선택 주소를 명령 시점에 다시 확인하는지는 기능별로 확인해야 한다.

- `SpecialAbilityAutoAssign.cpp:280,585`는 분리 worker가 무장 프로필을 읽고 결과를 게시하면 tick이 취소 여부를 확인해 결과를 가져온다. 연말 작업은 UI 상태에 따라 worker를 일시정지한다. 취소 요청은 완료 전에 반영되면 특수능력 변경을 수행하지 않는 경로다. worker 자체의 DLL 수명과 게임 세대 일치는 별도 계약이 필요하다.

## 연간 AI 성장

`Menu::Loops`의 500ms 감시 경로에서 `TickAIOfficerAutoGrowth`를 호출한다. `AIOfficerGrowth.cpp:600`은 실제 12월→1월 전환 후 평정 상태를 기다리고 연도별 처리를 한 번 예약한다. `RunAnnualAIOfficerGrowth`는 무장 배열의 최대 1800 슬롯을 돌며 ID 중복을 제거하고, 대상의 소양·전법·현재 EXP를 계산하고 누적 EXP를 소비한다. `ApplyAIOfficerGrowthResult`는 여러 필드를 순서대로 쓰며 중간 예외 시 이전 필드로 일괄 롤백하지 않는다.

`TickAIOfficerAutoGrowth`는 `RunAnnualAIOfficerGrowth` 호출 전에 `s_lastAppliedGrowthYear`를 설정한다. 따라서 배열 해석 실패 등으로 실제 처리가 실패해도 같은 연도의 자동 재시도는 이 경로에서 예약되지 않는다. 새 구현에서 결과와 재시도 정책을 명시적으로 결정하고 기존 사용자 데이터의 중복 적용을 검증한다.

## 특수능력 자동배정의 판정 기준

`SpecialAbilityAutoAssign.cpp:120`은 전법·특기 레벨을 읽을 때 각 바이트를 최대 3으로 제한한 프로필로 열 가지 능력을 독립 판정한다. 한 무장이 여러 조건을 동시에 만족할 수 있다. 아래 합계는 각 항목에 속한 5개 전법 또는 6개 군사 특기 레벨의 합이다.

| 능력과 키 | 기존 판정 |
|---|---|
| 군악대 `0x1000` | 분기 또는 고무 중 하나가 2 이상이고 두 레벨 합이 4 이상. |
| 무쌍 보병 `0x1001` | 무력 80 이상, 보병 전법 0번 또는 3번 2 이상, 보병 합 + 보장×2가 9 이상. |
| 불꽃 기병 `0x1002` | 무력 80 이상, 기병 전법 0번 또는 3번 2 이상, 기병 합 + 기장×2가 9 이상. |
| 원격 궁병 `0x1003` | 무력 75 이상, 궁병 합 + 궁장×2가 9 이상이고 궁병 전법 3번·4번 중 하나가 2 이상이거나 궁병 합이 8 이상. |

worker는 배열의 앞에서 처음 유효하게 읽은 무장 ID를 사용하고 중복 ID는 건너뛴다. 연간 모드만 시작 시 특수능력 10개 중 양수인 항목이 하나라도 있는 무장 ID를 통째로 제외한다. 수동 모드는 이 사전 제외를 하지 않으며, 결과 적용 시 각 조건 충족 능력의 기존 count가 양수면 유지하고 그렇지 않으면 1로 설정한다. 연간 모드의 사전 제외는 시작 시 snapshot이므로 작업 중 보유 상태가 바뀌는 경우와 수동·연간 차이를 별도로 검증해야 한다.

조건 충족 인원·능력별 건수는 worker 판정 결과이고 실제 신규 부여 건수와 다르다. 신규 항목이 있을 때만 파일 저장을 호출한다. 작업 취소·게임 세대·스레드 수명과 저장 결과는 [worker 조사](P0_Workers.md) 및 [리소스 조사](P0_Resources.md)의 조건을 따른다. 위 표는 정적 코드이며 자동배정을 실행하지 않았다.

## AI 연간 성장의 계산과 완료 표식

`BuildAIOfficerGrowthPreview`는 최대 ID 1800 중 세력 포인터가 있고 주인공 주소·ID가 아닌 무장에 대해 7개 전법 계열을 계산한다. 속도 1·2·3은 각각 계수 3·5·7이며 범위 밖 속도는 1~3으로 제한한다. 다섯 누적 EXP를 각각 10으로 나눠 올림한 값과 특기 레벨(최대 3)을 계열별 식에 넣고, 계열별 소양 증가를 `ceil(기준×계수/7)`로 계산한다. 보병·기병·궁병·함선은 통솔·무력과 해당 특기, 군략은 통솔·지력, 보조는 무력·지력·정치·매력, 둔갑은 지력·정치·매력의 누적 EXP를 사용한다.

기존 5개 전법 레벨은 각각 최대 3으로 읽는다. 전법 승급 후보는 계열별 능력치·특기·일반 전법 합의 조건을 만족해야 하며, 총 레벨이 15 미만이고 소양이 **45 이상**인 동안 최대 15회 가중 선택한다. 일반 전법 비용은 현재 레벨에 따라 7·15·25, 다섯 번째 전법은 15·25·45지만 비용보다 소양이 충분해도 45 미만이면 승급 반복에 들어가지 않는다. 후보가 없으면 반복을 끝낸다. 전법 합이 15 이상이면 남은 소양 전체를, 그 미만이면 200을 넘는 부분을 선택한 능력치의 현재 EXP에 더한다. 현재 EXP는 65535에서 제한되고 남은 소양은 0~255로 제한된다.

연간 실행은 첫 1800개 슬롯에서 중복 ID를 제거하고 연도·ID 기반 seed로 선택한다. ID는 미리보기 유효성·대상 여부를 확인하기 전에 중복 처리 표시되므로, 같은 ID의 첫 슬롯이 대상이 아니거나 미리보기 실패라면 뒤 슬롯은 다시 보지 않는다. 누적 EXP 다섯 개가 모두 0인 무장은 미리보기에서 소양 사용 결과가 계산되더라도 실제 쓰기를 건너뛴다. 누적 EXP가 있으면 다섯 능력치 각각에 대해 현재 EXP를 쓰고 곧바로 해당 누적 EXP를 0으로 만든다. 이어 일곱 계열 각각의 소양과 전법 다섯 값을 쓴다. 도중 예외 시 이미 쓴 값은 되돌리지 않는다. 보호 복원 결과는 성공 반환값에 반영되지 않는다.

미리보기는 원본 전법 바이트가 3보다 크면 `tacticsBefore`와 `tacticsAfter` 양쪽에 3을 넣는다. 누적 EXP가 있어 결과를 적용하는 경우 승급하지 않은 슬롯도 `tacticsAfter`를 전부 쓰므로, 원래 4 이상인 전법 값은 3으로 기록된다. 로그의 변화 여부 비교는 제한된 before와 after를 비교하므로 이 정규화만으로 변화 인원이 증가하지 않을 수 있다. 또한 적용 함수는 미리보기 이후 무장 ID나 기존 EXP·소양·전법 값이 바뀌었는지 재확인하지 않고 미리보기 결과를 쓴다. 실제 4 이상 값이나 동시 편집의 발생은 확인하지 않았다.

무장 상세의 소양 편집 `OfficerDetail.cpp:1044-1050`은 성장 코드와 같은 `+0xC4`~`+0xCA`를 사용한다. `RenderStatRow`의 다중 선택 적용은 같은 오프셋을 선택된 무장 주소에도 기록한다. 따라서 성장 대상 AI 무장을 다중 선택해 편집하는 시점이 background 성장의 미리보기와 적용 사이에 겹치면, 성장 적용이 미리보기에서 계산한 값으로 그 편집을 덮을 수 있다. 성장 대상은 주인공을 제외하므로 주인공 단독 편집과 선택된 AI에 대한 일괄 편집을 구분한다. 실제 동시 실행 순서는 확인하지 않았다.

전법 레벨도 같은 관계다. 성장의 일곱 전법 계열은 `+0x139`부터 `+0x15B`까지 35바이트를 적용하고, 상세 창의 레벨 버튼은 해당 오프셋을 현재 무장과 다중 선택 무장에 직접 쓴다. 같은 AI 무장에 대한 편집이 성장 미리보기와 적용 사이에 들어오면 성장 결과가 그 레벨을 다시 쓸 수 있다. 같은 행의 횟수 버튼은 별도의 `g_customSkillCounts` 맵을 수정하므로 게임 레코드의 전법 레벨 쓰기와 구분한다. 실제 겹침은 확인하지 않았다.

전체 무장 일괄 편집 `StatMonitor.cpp:227`도 같은 전법 35바이트를 렌더 경로에서 수정한다. 대상 슬롯은 ID가 슬롯 번호와 일치하고 지정 신분 조건을 만족해야 하며, 성장 경로는 슬롯과 ID의 일치를 요구하지 않는다. 양쪽 대상에 해당하는 무장에서는 일괄 편집과 성장 적용이 같은 전법 바이트를 쓸 수 있다. 일괄 편집의 특기 `+0x1D0`~`+0x1E7`은 성장이 계산 입력으로 읽는 24바이트이기도 하다. 성장 미리보기의 입력 읽기와 일괄 편집을 묶는 공통 잠금은 해당 경로에 없으므로, 중간에 겹치면 계산 입력이 편집 전후의 혼합 상태가 될 수 있다. 실제 겹침은 확인하지 않았다.

## AI 성장 게임 설정 동기화와 미리보기

`MenuSectionsOfficerEdit.cpp`는 게임 설정 바이트 `exe+0x3BA9850+0x38`의 하위 2비트를 플레이어 세력, 다음 2비트를 다른 세력의 성장 속도로 읽는다. 쓰기는 상위 4비트를 유지하면서 두 하위 필드에 같은 속도 1~3을 기록하고 재읽어 확인한다. 사용자가 ON으로 바꾸면 기존 다른 세력 값이 1~3이면 우선하고, 아니면 플레이어 값, 둘 다 없으면 2를 사용한다. 두 원래 값이 **모두 0**이었는지만 `bAIOfficerGrowthRestoreNone`에 저장한다. OFF에서 이 flag가 참이면 두 값을 0으로 쓰고, 거짓이면 게임 설정을 그대로 둔다. 따라서 ON 전 두 값이 서로 달랐던 상태를 개별적으로 보관해 되돌리지는 않는다.

설정에서 이미 ON으로 로드된 경우의 자동 동기화는 `DrawOfficerEditSection`의 렌더 경로에 있다. 메인 메뉴가 열리고 펼쳐져 있으며 gameBase와 메인 테이블 조건이 맞을 때 이 경로가 실행된다. 한 번 쓰기에 성공하면 지역 static flag를 세우며, 같은 ON 상태에서 게임 설정이나 세대가 이후 바뀌었는지를 다시 비교하는 코드는 없다. 쓰기 실패 시 flag를 세우지 않아 해당 렌더 경로의 다음 실행에서 다시 시도한다. 연간 성장 계산을 호출하는 background loop와 게임 설정을 동기화하는 이 UI 경로는 별개다.

무장 상세의 성장 미리보기는 시나리오 날짜를 읽을 수 있으면 12월에만 다음 연도, 그 외 월에는 현재 연도와 무장 ID로 seed를 만든다. 날짜를 읽지 못하면 0 seed를 넘겨 별도 결정론적 기본 seed를 사용한다. 계산은 읽기 전용이며 실제 연간 적용과 입력 상태가 같을 때 같은 seed가 선택되지만, 이후 누적 EXP·속도·무장 데이터가 바뀌거나 연간 적용의 대상·실행 조건이 성립하지 않으면 표시가 실제 결과를 보장하지 않는다. 특히 누적 EXP가 모두 0이면 미리보기 계산과 달리 연간 쓰기는 건너뛴다.

회귀 조건은 게임의 두 기존 속도 조합, 저장된 ON으로 시작할 때 메뉴 열기·접힘·미열기, 설정 쓰기 실패와 재시도, ON 중 게임 설정·세대 변경, 날짜 12월과 그 외 월의 미리보기, 누적 EXP 0 및 성장 실행 전 데이터 변경이다. 정적 추적이며 UI·게임을 실행하지 않았다.

## 공통 무장 배열 해석의 보장 범위

## 무장 UI 기재 변경의 단일 대기 요청

`SelectOfficercapture.h`의 고속 setter는 고정 포인터 배열에서 요청한 기재를 찾아 슬롯에 바로 쓰고 확인한다. 실패하면 `RequestTraitChangeAsync`를 호출한다. 이 이름의 처리는 별도 worker가 아니라 `MenuT04Maintenance.h`의 렌더 유지 경로에서 최대 200ms 간격으로 진행되며, 한 tick에 읽기 가능한 메모리를 최대 2MiB 검색한다. UI가 모두 닫혀 overlay가 호출되지 않으면 검색도 진행되지 않는다.

요청 함수는 무장 ID와 gameBase를 확인하고 이전 검색에서 찾은 객체 캐시를 먼저 시도한다. 캐시도 실패하면 vtable을 확보한 뒤 전역 `g_pendingTraitChange` 한 개에 새 요청을 대입한다. 이미 다른 분할 검색이 진행 중이어도 새 분할 검색 요청은 기존 요청을 교체한다. `generation`은 새 요청마다 증가해 기록되지만 이 파일에서 적용 전 비교에는 사용되지 않는다. 전체 검색에서 찾지 못하면 같은 gameBase·기재 ID의 요청을 5초간 거절한다.

분할 검색은 매 tick 시작과 발견 후 적용 직전에 현재 gameBase와 무장 주소의 ID가 요청 당시와 같은지 확인한다. 이 검사는 같은 숫자 주소와 ID가 다른 게임 세대에 재사용된 경우를 구분하지 못하며, 현재 슬롯 내용이 요청 이후 바뀌었는지는 검사하지 않는다. 같은 슬롯에 대한 이전 분할 검색이 남아 있는 동안 이후 고속 배열 조회 또는 객체 캐시로 다른 기재 변경이 즉시 성공하면 그 즉시 성공 경로는 대기 요청을 지우지 않는다. 이후 이전 검색이 완료되고 대상 검사도 통과하면 이전 요청의 기재를 다시 쓸 수 있는 코드 순서다. 실제 UI 조작과 발생 빈도는 확인하지 않았다.

회귀 조건은 서로 다른 무장·슬롯의 연속 요청, 같은 슬롯에 분할 검색 뒤 즉시 성공, 요청 중 창 닫기·재개, ID 미발견 후 5초, 무장 ID 변경, 같은 주소·ID 재사용, 발견 후 쓰기 실패와 목록 새로고침이다. 실제 메모리 검색과 게임 실행은 하지 않았다.

### 기재 슬롯 쓰기 경로별 검증 차이

`OfficerDetail.cpp:777`의 `SetTraitObjectFast`는 대상 객체의 주소, vtable 값, 요청 ID 일치와 배정 가능한 ID인지 확인한 뒤 무장 슬롯 포인터를 직접 쓰고 같은 포인터가 읽히는지 확인한다. 배정 가능 ID는 기본 1~70·201·202 또는 사용자 표시 정보에 비어 있지 않은 이름이 있는 ID다. 이 빠른 쓰기에는 `VirtualProtect` 호출과 이전 슬롯 복원이 없다. 분할 검색 결과 적용과 일괄 랜덤 배정이 이 함수를 사용한다.

반면 `SelectOfficercapture.h`의 UI 고속 배열 경로는 기재 객체의 vtable 값과 ID 일치를 확인하지만 위 `IsAssignableTraitId`를 호출하지 않는다. 그 후 슬롯에 직접 쓰고 포인터와 ID를 재확인한다. 따라서 배열에 객체가 있고 ID가 같더라도 사용자 표시 이름이 없는 기재는 이 고속 경로와 `SetTraitObjectFast`에서 서로 다른 판정을 받을 수 있다. 일반 `SetTraitID`는 별도 객체 검색 후 슬롯 보호 속성을 바꾸어 쓰고 `GetTraitID` 결과를 확인하며, 검증 실패 시 이전 포인터를 복원하지 않는다.

기준 자체 cpp·h·inc에서 `SetTraitID(` 표기는 일반 함수의 선언·정의 외에 `SelectOfficercapture_impl.inc`의 두 호출이다. 이 두 호출은 해당 번역 단위에서 `SelectOfficercapture.h`의 매크로로 `SetTraitIDForOfficerUiFast`에 치환된다. 중간의 `OfficerDetail.h`는 자기 선언 동안 매크로를 해제한 뒤 복구한다. 따라서 이 텍스트 범위에서 일반 `SetTraitID`가 UI의 두 호출로 직접 실행된다고 판단하지 않는다. 외부 호출이나 전처리 결과 전체는 확인하지 않았다. 일반 함수 자체의 검색은 읽기 가능한 영역을 순회하다 한 영역의 읽기 예외가 발생하면 해당 영역의 나머지를 검색하지 않고 다음 영역으로 넘어간다. `VirtualQuery`가 실패하면 전체 검색을 중단한다.

회귀 조건은 기본 ID 경계, 이름이 빈 사용자 기재와 정의 파일 차이, 배열 고속 성공·분할 검색 성공·일반 setter, 읽기 가능하지만 쓰기 보호된 슬롯, 쓰기 후 검증 실패, 다른 게임 세대의 객체 주소다. 결과는 소스 대조이며 실제 게임 쓰기는 실행하지 않았다.

### AI 친밀도 가속의 대상·계산·실패 시점

`bAutoAffinityGrowth`는 설정 파일 키이고 실제 flag는 `g_autoAffinityGrowthEnabled`다. 대상은 주인공을 제외한 유효 ID 1~5102 중 지정된 신분 일곱 종류이며, 세력과 도시 포인터가 각각 유효하고 상성 0~149·중시 유형 1~6을 읽을 수 있어야 한다. 중복 ID는 처음 발견한 레코드만 사용한다. 같은 세력·같은 도시로 정렬한 뒤 각 쌍을 한 번씩 살펴보며, 정렬상 왼쪽 무장의 관계 목록에 상대가 부부·의형제·상생·상극·원수·라이벌로 있으면 제외한다.

상성 거리는 150을 주기로 짧은 쪽을 택하고, 거리가 0이면 +15, 이후 5 단위로 +14부터 감소해 71~75는 +0이다. 흥미 바이트의 네 2비트 필드 중 같은 비영 값마다 +3, 중시 유형이 같은 비영 값이면 추가 +3이다. 기존 친밀도를 부호 있는 바이트로 해석해 음수면 건너뛰고, 100 이상도 건너뛴다. 나머지는 합산 후 최대 100으로 제한해 기록하며 관계 자체는 생성하지 않는다.

연월 전이를 감지하면 무장 배열 해석과 관계 읽기·쓰기 권한 확보보다 먼저 마지막 연월을 현재 값으로 갱신한다. 따라서 그 뒤 어느 단계가 실패해도 같은 달 재검사에서는 다시 시도하지 않는다. 여러 달을 건너뛴 경우 현재 달이 1·4·7·10월일 때 한 번 처리할 뿐 중간 분기들을 순회하지 않는다. 날짜가 뒤로 가면 기준을 새 날짜로 바꾸되 그 전이에서는 처리하지 않는다. 실제 대상 집합과 실패 발생 여부는 게임을 실행하지 않아 확인하지 않았다.

회귀 조건은 상성 거리 0·1·5·6·70·71·75, 네 흥미 필드와 중시 일치, 음수·99·100, 왼쪽 관계 목록만의 제외, 중복 ID, 세력·도시 경계, 분기 건너뛰기와 월 감지 뒤 각 단계 실패다.

### 친밀도 가속의 관계 조회 누락과 ID 범위

가속 대상 수집은 ID 1~5102를 허용하지만, 친밀도 배열 계산은 별도의 압축 ID 구간만 지원한다. 예를 들어 1001~2000이나 2101~3000은 대상 수집을 통과하더라도 쌍의 압축 인덱스가 없어 실제 친밀도 쓰기에서 제외된다. 압축 함수는 5101~5200도 정의하지만 가속 대상 수집과 관계 일괄 조회는 5102까지만 받으므로 이 기능에서 5103~5200은 대상이 아니다. 배열은 1650명에 대한 삼각형의 한 바이트 쌍 저장소다.

관계 일괄 조회는 직접 관계 테이블과 숙명 관계 테이블 중 하나만 찾아도 계속한다. 직접 관계는 최대 3000개 슬롯, 숙명 관계는 최대 5000개를 읽고, 각 순회에서 읽기 실패가 나면 그 테이블의 나머지 순회를 중단한다. 그래도 선택된 ID의 결과를 valid로 표시하고 성공을 반환한다. 숙명 관계는 유형 1·2이고 발생 flag가 0인 항목만 반영하며 양쪽 결과에 추가한다. 직접 관계는 슬롯의 최대 다섯 구성원을 서로 연결한다.

일괄 조회가 성공해도 개별 결과의 `valid`가 false일 수 있다. 앞선 대상 수집에서 읽은 ID를 일괄 조회가 무장 주소에서 다시 읽을 때 실패하면 그 행은 빈 결과로 남지만, 다른 ID와 관계 테이블이 유효하면 일괄 조회는 성공한다. 가속 루프는 결과 개수만 확인하고 각 행의 `valid`를 검사하지 않은 채 정렬상 왼쪽 행의 관계 목록을 사용한다. 이 경우 빈 목록은 해당 쌍을 관계 때문에 제외하지 않는다. 실제로 두 읽기 사이 실패가 발생하는지는 확인하지 않았다.

따라서 테이블 하나가 없거나 중간에서 읽기가 끊겨 일부 관계가 누락되어도 가속 호출자는 전체 조회 성공으로 받아들일 수 있다. 빠진 관계는 쌍 제외 판정에 반영되지 않는다. 실제 게임 데이터에서 이런 상태가 발생하는지는 확인하지 않았다. 회귀 조건은 각 압축 ID 경계, 5102·5103, 테이블 한쪽만 존재, 각 순회 중 읽기 실패, 직접·숙명 관계 중복과 양방향 결과다.

## 선택 무장의 부활·도시 이동·재야 전환

`SelectOfficercapture_impl.inc:489-763`의 상세 화면은 읽기 snapshot의 `+0x10` 상태를 기준으로 버튼을 달리 표시한다. 사망 `0x88`에는 주인공 도시 부활과 선택 도시 부활, 재야 `0x58`에는 선택 도시 이동, 미발견 `0x68/0x78`에는 재야 전환 버튼이 있다. 이 상태값과 실제 쓰기 대상 `pGame`은 별개로 다뤄진다.

사망 무장의 두 부활 버튼은 현재 객체에 상태 `0x58`, 몰년 `255`, 행동력 `200`, 사망 flag `0`을 각각 쓰고 같은 ID의 마스터 레코드에도 같은 처리를 시도한다. `PatchMasterData`는 캐시된 배열에서 5102개까지 검색해 첫 유효 ID 일치 항목 하나에만 함수를 적용한다. 주인공 도시 부활은 주인공 도시 포인터를 구하면 그것을 쓰고, 구하지 못하면 도시 포인터 쓰기 없이 나머지 처리를 진행한다. 선택 도시 부활은 도시 배열을 구했을 때 선택 인덱스와 `0x2A0` 간격으로 대상 주소를 계산한다. 현재 객체 도시 포인터에 대한 별도 쓰기 뒤 공통 처리에서도 도시 포인터 쓰기를 다시 시도한다.

재야 무장의 선택 도시 이동은 도시 배열에서 계산한 주소를 현재 객체의 `+0x20`에 직접 쓰며, 이 버튼에는 마스터 검색·동일 쓰기가 없다. 미발견의 단일 재야 버튼은 현재 객체와 첫 마스터 일치 항목의 상태만 `0x58`로 바꾸고 목록 캐시 및 선택을 갱신한다. 개별 재야 버튼과 [목록의 수동 일괄 전환](#무장-목록의-수동-재야-전환)은 대상 탐색 방식이 다르다.

`ModifyStat`은 반환값이 없어 호출자가 개별 필드 쓰기 성공을 모른다. 부활은 여러 필드와 두 객체 사이에서 부분 성공할 수 있으며, 로그와 화면 캐시 갱신은 전체 쓰기 성공을 검증하지 않는다. UI는 부활과 미발견 전환에 저장 후 다시 불러오라는 안내를 표시한다. 실제 게임 반영 조건은 실행하지 않아 확인되지 않았다. 회귀 조건은 각 상태의 버튼 노출, 주인공 도시 미확보, 선택 도시 경계, 마스터 미발견·중복 ID, 필드별 쓰기 실패, snapshot과 실제 객체 상태 차이, 저장·로드와 세대 전환이다.
## 신상 편집과 다중 선택의 대상 차이

`DrawOfficerHeader`는 가능한 경우 상세 snapshot을 읽고 실제 변경은 `pGame`에 수행한다. 이름 편집은 Enter 또는 편집 종료 시 `S8RPK_cheat_char.json`에 저장하며 Escape는 편집을 취소한다. 성별 콤보는 읽은 `+0x30` 값이 1인 경우만 여성을 표시하고 다른 값은 남성으로 표시한다. 변경 시 현재 객체와 첫 번째 ID 일치 마스터 레코드에 0 또는 1을 각각 쓰고 snapshot 동기화와 로그를 수행한다. 목소리는 `+0x68`을 읽어 목록 인덱스로 표시하며 범위 밖이면 화면상 0으로 취급한다. 변경 시 현재 객체와 첫 마스터 일치 항목의 `+0x68`, `+0x70` 두 바이트를 각각 쓴다. 이들은 다중 선택 전체를 순회하는 공통 수치 행과 다른 경로다.

얼굴 번호 `+0x2E` 2바이트, 모델 번호 `+0xA5`와 색상 `+0xA6` 각 1바이트, 등장·생·몰년 `+0x32/+0x34/+0x36` 각 2바이트는 `OfficerDetail.cpp:131`의 공통 `RenderStatRow`를 사용한다. +/-는 즉시 쓰고 직접 입력은 편집 종료 시 쓴다. 선택 무장 ID가 있으면 동일 offset·size·값을 선택 무장 주소들에도 적용한다. 쓰기는 `ModifyStat`을 사용하므로 대상별 성공을 반환받지 못한다. 1·2바이트 쓰기는 값을 해당 정수 폭으로 변환한다.

같은 공통 행은 `DrawOfficerHeader`에서 세력 포인터가 `0x10000`보다 클 때 **세력 색상**에도 호출되며 기본 대상은 세력의 `+0x09`, 크기는 1바이트다. 그러나 다중 선택 분기는 기본 대상의 종류를 구분하지 않고 선택된 각 무장 주소의 동일한 `+0x09`에 같은 값을 쓴다. 이 코드의 무장 ID는 `+0x08`의 2바이트이므로 이 쓰기는 선택 무장 ID의 두 번째 바이트와 겹친다. 선택 목록에 무장이 남은 상태에서 세력 색상 행을 변경할 때 도달 가능한 정적 경로이며 실제 게임에서 발생한 결과는 실행하지 않았다.

회귀 조건은 이름 저장 실패·취소, 성별·음성의 현재 객체와 마스터 불일치, 음성 두 바이트 중 부분 실패, 다중 선택 적용, 세력 색상 편집과 무장 ID 보존, 입력 폭 경계 및 snapshot·게임 세대 교체다. 이관에서는 세력과 무장의 편집 대상을 명시적으로 구분해야 한다.
### 공통 수치 행의 대상별 목록과 세력 색상 읽기

자체 cpp·h·inc의 `RenderStatRow` 호출 표기 중 label·대상·오프셋·크기를 정적으로 추출한 [50개 호출 위치](p0/officer_stat_rows.csv)를 정리했다. `pBase` 43곳, `pGame` 6곳, `forceAddr` 1곳이다. 정의와 선언은 제외했다. 모든 호출이 실제 UI에서 도달 가능한지나 대상 포인터의 게임 세대를 이 텍스트 추출만으로 판정하지 않는다.

공통 행의 읽기 snapshot 선택도 기본 대상이 캡처된 무장 주소 또는 마지막 상세 주소와 같은 경우에만 이뤄진다. 세력 색상 행의 `forceAddr`가 두 주소와 다르면 `pR`은 0으로 남고, 행이 비활성 입력을 현재 세력 메모리에서 읽어 갱신하는 코드는 실행되지 않는다. 이때 표시·+/- 연산은 `SelectOfficercapture_impl.inc`의 초기값 0인 `v_ForceColor` 또는 이전 편집으로 남은 값을 사용한다. 이는 읽기 조건의 소스 경로이며 실제 게임에서 세력과 무장 주소가 어떤 순서로 제공되는지는 실행하지 않았다. 다중 선택 시 무장 `+0x09`에 같은 값을 쓰는 앞 절의 문제와 함께 세력별 실제 색상 표시·변경을 확인해야 한다.
## 전법·특기 행의 레벨과 횟수

`OfficerDetail.cpp:207`의 `RenderCompactSkill`은 선택 객체에 대응하는 snapshot이 있을 때 레벨 바이트와 무장 ID를 읽는다. 병기 전법 오프셋 `0x15C~0x160`을 제외한 항목의 레벨 버튼은 표시값을 `(값+1)%4`로 바꿔 현재 객체에 1바이트로 쓰고, 다중 선택이 있으면 선택 무장에도 같은 오프셋·값을 적용한다. 일반 전법과 특기에 공통인 레벨 편집이며 병기 전법의 레벨 버튼은 표시하지 않는다.

전법 범위 `0x139~0x160`에는 별도 횟수 버튼이 있다. 이 버튼은 게임 레코드를 즉시 쓰지 않고 `GetTargetSkillCount`/`SetTargetSkillCount`로 무장 ID와 오프셋의 설정 맵을 바꾼다. 음수·미설정은 화면에서 0으로 취급하고 버튼을 누를 때 0→1→…→9→0으로 순환한다. 0은 맵에서 항목을 삭제한다. 다중 선택도 각 무장 주소의 ID를 읽어 동일한 횟수를 맵에 넣는다. 실제 전투 레코드에 적용되는 시점과 첫 유효 무장만 선택하는 조건은 [기능 보존표](P0_Feature_Contracts.md#전법-횟수-주입-시점)를 따른다.

이 버튼의 순환은 현재 표시값을 각각 `(값+1)%4`, `(값+1)%10`으로 계산한다(`OfficerDetail.cpp:250-255, 282-296`). 따라서 외부 데이터에서 정상 범위 밖의 양수가 들어오면 먼저 3 또는 9로 제한하지 않고 나머지 연산 결과를 사용한다. 예를 들어 레벨 4는 버튼을 누르면 1, 횟수 15는 6이 된다. 음수 횟수는 앞서 0으로 표시·계산한다. 이 분기는 기존 입력을 설명하며 실제 게임에서 범위 밖 값이 있는지는 확인하지 않았다.

snapshot을 얻지 못한 경우 이 행의 `officerID`는 0으로 남는다. `SetTargetSkillCount`는 ID 범위를 검사하지 않으므로 횟수 버튼이 처리되면 ID 0 항목을 저장 맵에 만들 수 있다. 반면 전투 적용 루프는 읽은 무장 ID가 0 이하이면 건너뛴다. 해당 상태에서 UI 버튼이 실제로 조작 가능한지와 게임 결과는 실행하지 않았다. 회귀 조건은 snapshot 부재, 병기·일반 전법과 특기의 버튼 차이, 다중 선택·중복 ID, 9→0 삭제, 지연 저장 및 전투 재생성 전후다.
## 전법·특기 화면 항목과 저장 위치

[전법·특기 행 목록](p0/officer_research_rows.csv)은 `OfficerDetail.cpp`의 `RenderResearchTab`에 선언된 화면 이름, 무장 구조체 오프셋, 임시 변수와 행별 인자를 원본 순서로 정리한 것이다. 전법은 8개 분류 40개(`0x139`–`0x160`), 특기는 4개 분류 24개(`0x1D0`–`0x1E7`)다. 각 분류의 이름·오프셋·변수 배열 길이가 `RenderResearchRow`의 count와 일치하는지 확인했다. 전법 중 병기 5개는 레벨 버튼이 숨겨진다. 이 목록은 화면의 정적 연결이며 실제 게임 데이터의 의미나 실행 결과를 증명하지 않는다.

특기 네 행은 각각 `0xCB`–`0xCE`를 `expOffset` 인자로 넘기지만, `RenderResearchRow` 본문은 이 인자를 사용하지 않는다. 따라서 이 화면의 특기 행 호출만으로 해당 경험치가 표시되거나 변경된다고 판단하면 안 된다.

별도의 `RenderExpTab`에서는 같은 `0xCB`–`0xCE`를 임무·지모·병과·군사 소양의 1바이트 공통 수치 행으로 직접 편집한다. 전법 소양도 별도로 `0xC4`–`0xCA`의 일곱 1바이트 행으로 편집한다. 이 열한 행의 화면 이름과 쓰기 폭은 [공통 수치 행 목록](p0/officer_stat_rows.csv)에 있다. 기능 탭의 특기 레벨 변경과 소양 탭의 소양 변경은 서로 다른 조작으로 보존해야 한다.

상세 창은 최초 표시, 주소 변경 또는 스냅샷 부재 시 `UpdateOfficerSnapshot`을 호출한다. 유효한 `0x3D0` 바이트를 읽을 수 있으면 로컬 스냅샷과 주소를 갱신하고, 실패하면 `s_hasSnapshot`을 false로 둔다. `RenderCompactSkill`은 전역 캡처 주소가 일치하면 전역 읽기 포인터를 우선 사용하고, 그렇지 않으면 일치하는 로컬 스냅샷만 사용한다. 어느 경로도 선택되지 않으면 무장 ID 초기값 0이 유지된다. 실제 상세 창 진입 시 그 상태가 가능한지는 호출자와 포인터 수명의 추가 확인이 필요하다.

### 두 호출자의 스냅샷 조건

`Menu_impl.inc:1070`은 프레임마다 주인공 상세 창을 호출한다. 창이 열렸을 때 `p1 == 0`이면 안내만 표시하고 기능 탭 전에 반환한다. `p1 != 0`이면 스냅샷 갱신 실패 자체로 반환하지 않으며 `p1 + 0x08`을 직접 읽은 후 기능 탭에서 `RenderResearchTab(p1)`을 호출한다. 따라서 전체 `0x3D0` 읽기 검사가 실패해도 앞의 ID 직접 읽기가 가능한 상황에서는, 일치하는 전역 스냅샷이 없다면 전법 횟수 편집의 ID 초기값 0이 남는 정적 경로가 있다. 이것이 실제 실행 중 발생하는지는 확인하지 않았다.

선택 무장 창의 `SelectOfficercapture_impl.inc:1854-1914,2106-2156`은 `g_capturedOfficerBase == 0` 또는 초기 `IsValidPtr(pBase, 0x3D0)` 실패 시 반환한다. 그 후 주소가 달라졌거나 유효한 목록 스냅샷이 없으면 다시 검사해 복사한다. 두 번째 검사가 실패해도 함수는 반환하지 않고 정적 목록 버퍼 주소를 `g_officerInlineReadPtr`에 넣은 뒤 기능 탭을 표시한다. 별도 변경이 없다면 `pBase == g_capturedOfficerBase`이므로 `RenderCompactSkill`은 이 버퍼를 읽는다. 두 검사 사이 읽기 가능 상태가 바뀌면 버퍼에 남은 이전 값이 표시·ID 선택에 사용되는 정적 경로가 있다. 안정적인 포인터에서는 첫 검사를 통과한 뒤 정상 복사한다. 두 검사 사이의 실제 변경 가능성과 발생 빈도는 검증하지 않았다.

### 주인공과 목록 상세의 같은 무장 편집

`Menu_impl.inc:1070-1072`는 주인공 상세, 단독 선택 무장, 무장 목록 순서로 그린다. 선택 무장 상세는 렌더 후 `g_officerInlineReadPtr`를 0으로 되돌린다(`SelectOfficercapture_impl.inc:2175`). 주인공 snapshot과 선택 무장 snapshot은 서로 다른 정적 버퍼다. `SyncInlineReadBufFromWrite`는 주인공 주소와 일치하면 주인공 버퍼를 갱신하지만, 선택 무장 버퍼는 전역 포인터가 그 버퍼를 가리키는 동안에만 갱신한다.

따라서 두 창이 같은 무장을 표시하고 이전 프레임의 선택 무장 렌더가 전역 포인터를 0으로 돌려놓은 상태에서 주인공 창의 공통 행을 편집하면, 주인공 버퍼는 갱신되지만 선택 무장 버퍼는 그 쓰기에서 갱신되지 않는다. 이어지는 선택 무장 렌더는 같은 주소의 유효 snapshot이 이미 있으면 다시 복사하지 않으므로 이전 값을 표시하는 코드 경로가 있다. 목록 창 재열기·목록 갱신과 단독 선택 창 재열기는 snapshot 주소를 무효화해 재복사를 유도한다. 이는 호출 순서와 코드의 정적 결과이며 실제 UI 재현은 하지 않았다. 회귀 조건은 두 창에서 같은 무장 편집, 양방향 편집, 재열기·목록 갱신과 외부 게임 편집이다.

반대 방향의 직접 편집에서는 선택 무장 상세의 공통 행이 쓰기 직후 `SyncInlineReadBufFromWrite(pBase)`를 호출한다. 주인공 상세 snapshot의 주소도 `pBase`와 같으면 이 호출이 두 버퍼를 동기화하므로, 위에서 확인한 주인공→선택 방향과 다르다.

다중 선택 적용은 기본 대상의 snapshot 동기화 **이후** 선택된 무장 주소들에 `ModifyStat`을 반복하며, 각 선택 대상에 대한 snapshot 동기화는 호출하지 않는다. 예를 들어 기본 대상과 다른 주인공이 선택 목록에 포함되어 있으면 주인공 메모리는 바뀔 수 있지만 주인공 상세의 기존 snapshot은 그 일괄 쓰기에서 갱신되지 않는다. 같은 순서는 수치 행의 증감·직접 입력과 전법·특기 레벨 행에 있다. 쓰기 성공 여부와 화면 표시의 실제 결과는 실행하지 않았다.

## 다중 선택 주소 캐시의 재구축 조건

`SelectOfficercapture_impl.inc:2246-2283`은 선택 ID 집합을 무장 배열 앞에서 순회해 주소 벡터로 바꾼다. 일치하는 슬롯을 찾을 때마다 주소 수를 늘리고, 그 수가 선택 ID 수에 도달하면 중단한다. 이미 찾은 ID인지 따로 확인하지 않으므로 선택 ID가 A·B이고 배열 앞쪽에 A가 두 번 있으면 두 A 주소를 담은 뒤 B를 찾기 전에 중단하는 코드다. 이는 중복 ID가 실제로 존재한다는 주장이 아니라 배열에 중복이 있을 때의 정적 동작이다.

목록 렌더 중 배열 베이스 변경을 감지하면 `s_selectedOfficerBases.clear()`로 주소만 비우고 선택 ID 집합은 유지한다(`:2388-2401`). 이 분기 자체에는 주소 재구축 호출이 없다. 반면 체크박스 변경과 전체 선택·선택 해제는 `RebuildSelectedOfficerBases`를 호출한다. 따라서 베이스 변경 직후 선택 개수는 남아도 캐시가 비어 있으면 `ApplyPatchToSelectedOfficers`는 바로 반환한다. 기본 대상에 대한 단일 쓰기는 별도로 먼저 실행될 수 있다. 회귀 조건은 A·A·B 중복 순서, 새 배열 전환 후 선택 유지와 재선택, 선택 대상이 새 배열에 없을 때, 빈 캐시에서 기본 대상 쓰기다. 실제 게임 전환이나 중복 데이터는 확인하지 않았다.

배열 변경 후 주소 캐시가 비어 있는 상태라도 `선택 무장 재야`는 이 캐시를 사용하지 않고 남아 있는 선택 ID로 현재 `s_stableArrayBase`의 5102개 슬롯을 직접 훑는다. 따라서 같은 선택 배너가 보이더라도 일반 수치·전법의 일괄 편집은 빈 주소 캐시 때문에 선택 대상에 적용되지 않는 반면, 재야 전환은 현재 배열의 일치 ID를 대상으로 실행을 시도한다. 재야 전환은 끝에 선택 ID를 비운다. 두 동작의 서로 다른 경로를 세대 변경 회귀 조건에 포함한다.

## 목록 재구축 중 새 refresh 요청

목록 창 wrapper가 외부 atomic 요청을 소비하면 내부 `s_forceOfficerListRefresh`가 켜진다. 전체 캐시 구축은 첫 프레임 20개, 이후 프레임당 384개씩 처리한다(`SelectOfficercapture_impl.inc:2356-2569`). 이미 구축 중일 때 새 강제 refresh가 들어오면 새 구축을 시작하는 `!s_cacheBuildInProgress` 조건을 통과하지 못하고, 바로 다음 분기에서 강제 flag를 false로 내린 뒤 기존 cursor부터 계속한다. 따라서 이미 읽은 앞부분을 그 요청 때문에 다시 읽지는 않는다. `Menu_impl.inc:1072`는 부속 창 렌더 경로에서 목록 wrapper를 호출하므로 창이 닫혀 있어도 그 경로가 실행되면 wrapper가 외부 atomic 요청을 소비하고 내부 요청 flag를 남긴다. 공개 미발견 watcher는 앞서 확인했듯 이 요청을 직접 내지 않는다.

창을 닫은 상태에서 목록 구현이 호출되면 `s_wasOpen`과 최초 구축 지연 flag는 지우지만 구축 진행 flag·cursor·부분 캐시는 지우지 않는다. 다시 열었을 때 부분 캐시가 비어 있지 않으면 지연 없이 진행 중 구축을 계속한다. 구축이 진행 중인데 부분 캐시가 비어 있으면 재열기에서 `s_deferInitialBuild=true`가 된다. 이 상태에서는 구축 갱신 조건이 false이고, 지연을 해제하는 화면 분기도 `s_cacheBuildInProgress`가 true라 실행되지 않는다. 따라서 이후 별도의 상태 변경이 없다면 구축이 계속 지연된다. 목록 갱신 버튼은 지연 flag를 false로 바꾼다. 이는 닫힌 동안에도 wrapper가 호출되는 경우의 코드 순서다.

목록의 base 재탐색은 창의 `ImGui::Begin`이 true인 경로에서 최초 또는 이전 검사로부터 2초 초과 시 수행한다. 탐색에 실패하면 검사 시각은 갱신하지만 기존 `s_cachedMasterArrayBase`와 `s_hasMasterArray`는 지우지 않는다. 따라서 이전 base가 남아 있으면 실패한 재탐색만으로 배열 변경이나 미발견 상태가 감지되지 않고, 다음 재시도도 2초 초과를 기다린다. 이 주소가 실제로 유효한지는 별도다.

구축 도중 목록에서 새 배열 base를 감지하면 캐시된 base를 새 주소로 교체하고 refresh flag를 세운다. 그러나 위와 같이 진행 중인 구축은 다시 시작하지 않으므로 앞부분은 기존 배열에서 읽은 항목, 나머지는 새 배열에서 읽은 항목이 한 캐시에 섞일 수 있다. 중복 ID 추적 배열도 그 진행 중에는 초기화하지 않아 앞부분에서 본 ID는 새 배열의 뒷부분에서 건너뛴다. 이는 base 변경 감지가 해당 분기에서 일어나고 이후 분할 구축이 계속되는 코드 순서이며 실제 로드 중 발생 여부는 확인하지 않았다.

이관 회귀 조건은 구축 중 앞쪽 레코드 변경과 refresh, 여러 요청의 합쳐짐, 목록 창 닫힘·재개, 세이브 전환과 재구축 완료 전 화면이다. 실제 화면 표시와 데이터 변경은 실행하지 않았다.

### 분할 구축 완료와 필터 목록 순서

전체 캐시는 마지막 chunk를 처리한 뒤 ID순으로 정렬한다. 필터 목록은 필터 변경, 전체 캐시 크기 변경, `s_forceFilterRebuild` 또는 남아 있는 강제 refresh flag에서 다시 만든다(`SelectOfficercapture_impl.inc:2601-2627`). 마지막 chunk에 유효한 새 행이 없으면 정렬 전후 크기는 같고, 다른 필터 갱신 조건도 없을 때 기존 필터 목록이 그대로 남을 수 있다. 이 경우 전체 캐시는 정렬됐더라도 표시용 필터 목록은 정렬 전 순서다. 이후 필터 갱신이 일어나면 정렬된 전체 캐시에서 다시 생성한다. 실제 게임 데이터의 ID 순서와 화면 결과는 확인하지 않았다.

`SelectOfficercapture_impl.inc:2440-2445`의 전체 선택은 클릭 시점에 이미 만들어진 `s_filteredIndices`의 ID만 선택하고 주소 캐시를 재구축한다. 이 버튼 처리는 같은 프레임의 목록 chunk 추가와 필터 갱신보다 앞에 있다. 분할 구축 중 클릭하면 이후 새로 나타나는 무장은 자동으로 선택되지 않는다. 전체 선택이라는 표시와 달리 대상은 클릭 시점의 필터 캐시다. 회귀 조건은 최초 부분 목록에서 선택, 같은 프레임의 chunk 추가, 구축 완료 후 선택 집합과 일괄 적용이다. 실제 UI 조작은 확인하지 않았다.

### 목록 검색의 보류와 빈 필터

이름·ID 검색 요청은 하나의 정적 pending 문자열에 저장되므로 구축 중 새로운 검색이 들어오면 앞선 검색어를 덮는다. 검색은 전체 캐시 구축이 끝나고 현재 필터 목록이 비어 있지 않을 때만 시작한다(`SelectOfficercapture_impl.inc:2689-2737`). 현재 필터에서 못 찾으면 전체 캐시를 찾고, 다른 필터에 결과가 있으면 전체 필터로 바꾼 뒤 다음 검색을 기다린다. 그러나 현재 필터 목록이 빈 상태에서는 전체 캐시에 일치 항목이 있어도 이 전체 검색 분기 자체에 들어가지 않고 요청을 유지한다. 이후 필터에 행이 생기거나 사용자가 필터를 바꾸는 등 실행 조건이 충족되면 처리할 수 있다. 실제 UI 결과는 확인하지 않았다.

검색 결과를 현재 필터에서 찾으면 그 프레임의 목록 표 생성에 성공했을 때 `arrayBase + originalIndex × 0x3D0`을 선택 주소로 설정하고 스크롤을 요청한다. 이 검색 선택 대입에는 일반 행 클릭과 달리 `IsValidPtr(targetBase, 0x3D0)` 검사가 없다. 다만 이후 상세 편집 함수는 선택 주소가 0이거나 0x3D0 범위가 유효하지 않으면 안내 후 반환한다. 이 검사는 주소의 가독성 검사이며 선택 당시 ID나 게임 세대의 동일성을 확인하지 않는다. 스크롤 인덱스는 클리퍼가 대상 행을 표시하고 이름 편집 중이 아닌 행 분기에 도달할 때 지워진다. 그 전까지는 유효한 인덱스 범위에서 다음 표 렌더 때도 선택 주소와 스크롤을 다시 설정한다. 표 생성 실패·대상 행 이름 편집·필터 변경과 오래된 배열 base의 실제 UI 결과는 확인하지 않았다.

### 필터 변경과 자동 선택

목록의 현재 선택이 필터 결과에 포함되는지는 필터 갱신 또는 재선택 요청 시 주소로 비교한다. 하지만 필터 값이 바뀌면 이전 선택이 새 필터에 여전히 포함되어 있어도 `needAutoReselect`가 true다. 다음 선택은 보관된 fallback 주소가 새 목록에 있으면 그 주소이고, 아니면 필터의 첫 행이며, 목록이 비면 선택 주소를 0으로 만든다(`SelectOfficercapture_impl.inc:2639-2686`). 이 자동 선택은 다중 선택 ID 집합을 지우는 동작과 별개다. 필터 변경만으로 `s_selectedOfficerIDs`나 `s_selectedOfficerBases`를 다시 구성하는 호출은 이 분기에 없다. 따라서 다른 필터에서 체크했던 무장이 현재 목록에서 보이지 않아도 선택 ID와 주소 캐시에 남아 있으면 일반 일괄 편집 대상에 남는다. 필터 변경과 fallback, 빈 필터, 같은 무장이 양쪽 필터에 포함되는 경우를 이관 회귀 조건으로 둔다. 실제 UI는 실행하지 않았다.

### 공통 수치 행의 단일·다중 적용 순서

`OfficerDetail.cpp:131-202`의 공통 수치 행은 빼기·입력 확정·더하기에서 현재 상세 대상 `p1`에 먼저 값을 쓰고 snapshot 동기화를 호출한다. 그 뒤 선택 ID가 하나 이상이면 선택 주소 캐시의 각 대상에 같은 절대값을 쓴다. 따라서 현재 상세 대상이 체크 집합에 없어도 먼저 변경되며, 체크돼 있으면 같은 값의 쓰기가 다시 호출된다. `+/-`는 각 선택 무장의 기존 값을 각각 증감하는 것이 아니라 현재 행에서 계산한 하나의 값을 배포한다. 이 공통 행에는 도메인 범위 제한이 없고 `ModifyStatFast`는 1바이트 값을 `unsigned char`, 2바이트 값을 `short`로 변환해 쓴다. 표시에서는 각각 부호 없는 1·2바이트로 읽으므로, 예를 들어 1바이트 값 0에서 빼기를 누르면 쓰기 성공 후 다음 재조회에서 255가 된다. `ModifyStat`은 쓰기 결과를 반환하지 않아 이 행의 후속 호출 여부는 앞선 쓰기 성공에 좌우되지 않는다. 실제 UI 조작은 확인하지 않았다.

## 무장 목록의 중복 ID 채택 순서

전체 목록 캐시는 슬롯을 순회할 때 무장 기본 읽기 성공, ID 범위, 중복 여부, 상태 바이트 주소 유효성을 차례로 확인한 후에만 해당 ID를 `s_cacheSeenIDs`에 표시한다(`SelectOfficercapture_impl.inc:2562-2593`). 따라서 앞 슬롯의 기본 읽기 또는 상태 주소 확인이 실패하면 같은 ID의 뒤 슬롯을 채택할 수 있다. 반면 앞에서 조사한 AI 성장 경로는 대상 여부와 미리보기 전에 ID를 처리 완료로 표시한다. 같은 중복 ID라도 두 기능이 선택하는 슬롯이 다를 수 있으므로 이관 시 각 기능의 기준을 확인해야 한다. 실제 중복 ID와 표시 결과는 확인하지 않았다.

## 다중 선택의 보호 변경 범위

`ApplyPatchToSelectedOfficers`는 선택된 주소만큼이 아니라 `s_stableArrayBase`부터 5102개 레코드 전체 범위의 보호를 한 번 바꾸고 callback들을 순서대로 호출한다. 보호 변경이 성공한 경우 반환받은 한 개의 `oldProt`으로 같은 전체 범위를 복원한다(`SelectOfficercapture_impl.inc:2268-2284`). 범위 내 페이지가 서로 다른 원래 보호 상태를 가졌다면 각 페이지의 상태를 별도로 보관하지 않는다. 보호 변경 실패여도 callback은 실행하고 복원 결과도 검사하지 않는다. 공통 능력치 행과 전법 레벨의 callback은 `ModifyStat`을 호출하며, 이 함수도 각 대상 필드에 `VirtualProtect`를 호출한다(`OfficerDetail.cpp:155-156, 257-258`, `Cheats.cpp:182-200`). 따라서 주석의 전체 보호 변경 한 번이 이 개별 호출을 제거하지는 않는다. 전법 횟수·특수능력 callback은 게임 필드 대신 ID를 읽어 별도 맵을 갱신하지만 같은 전체 범위 보호 변경을 거친다. 실제 페이지 보호 구성과 변경·복원 실패는 실행하지 않았다.

## 무장 이름 편집의 상세·목록 입력 순서

선택 무장 상세의 이름 입력은 Escape를 먼저 검사하고, Escape가 아닌 경우 Enter 또는 편집 후 비활성화에서 저장한다. 저장 실패는 로그를 남긴 뒤 편집을 종료한다(`SelectOfficercapture_impl.inc:245-264`). 전체 목록의 이름 입력은 Enter 또는 편집 후 비활성화에 대한 저장을 먼저 검사하고 그 뒤 Escape를 검사하며, 실패 시 별도 실패 로그 없이 편집을 종료한다(`:2798-2813`). 따라서 같은 프레임에 Escape와 비활성화 조건이 함께 참이 되는 경우 두 코드의 저장 호출 순서가 다르다. ImGui가 실제 입력에서 두 조건을 함께 만들 수 있는지와 파일 오류 표시는 실행하지 않았다. 저장 후 이름 맵과 목록 캐시의 차이는 [리소스 조사](P0_Resources.md#무장-이름-파일의-최초-읽기와-편집-저장)를 따른다.
