## 확인된 저장·읽기 차이

`v_DongtoLv1_Prob`, `v_DongtoLv1_StateProb`, `v_DongtoLv2_Prob`, `v_DongtoLv2_StateProb`는 `ConfigBase.inc:419~442`에서 읽지만 기본 저장 목록에는 없다. `MenuState.cpp:165~168`의 초기값은 순서대로 100, 20, 100, 50이다. `SaveConfigBase`는 기존 파일을 새로 쓰기 때문에 이 키들은 이후 저장에서 사라진다. 이관에서는 기존 파일을 읽는 호환성과 어떤 필드를 앞으로 저장할지 별도로 검토한다.

`bRulerTransferProposal`도 기본 저장 목록과 wrapper의 추가 키 목록에는 없다. 독립 setter가 기존 파일을 수정해 추가하지만 일반 `SaveConfig`의 기본 재작성은 해당 키를 보존하지 않는다. 재시작 전 일반 저장이 일어난 경우의 동작을 회귀 사례로 기록한다.

## 순서와 실패 동작

1. `Source.cpp`와 `ConfigBase.inc:197`은 초기화 초기에 각각 책략 5 활성화와 파일 로그 키를 줄 단위로 찾는다.
2. `Menu::Loops`가 gameBase를 준비한 뒤 `Config.cpp:300`의 `LoadConfig`를 호출한다. 기본 필드를 먼저 읽고 wrapper 필드를 별도로 읽으며 일부 setter를 즉시 호출한다. `ApplyStoredConfigs`는 안정화 및 전투 조건에 따라 기본 표의 setter를 나중에 호출한다.
3. `SaveConfig`는 읽기 전용 속성을 먼저 확인하고 `SaveConfigBase`를 호출한다. 기본 파일을 통째로 새로 쓰고 `config_end`를 출력한 후 wrapper는 키별로 전체 파일을 읽어 `config_end` 앞에 삽입하고 다시 쓴다. 기본 저장 함수는 `void`이므로 실패가 발생해도 호출자가 성공 여부를 받아 중단하는 구조가 아니다.
4. 여러 읽기 함수는 JSON 전체를 파싱하지 않고 줄의 부분 문자열 또는 첫 따옴표를 찾는다. 정수는 `stoi`, 실수는 `stof`에 의존한다. 따라서 현행 코드의 지원 형식과 실제 JSON 문법은 같지 않다. 새 설계에서는 JSON 문법 해석과 도메인 검증을 분리하되 기존 정상 파일을 읽어야 한다.

## 이관 시 확인할 회귀 사례

- 위 네 동토 키와 `bRulerTransferProposal`이 존재하는 기존 파일을 읽고, 새 저장 이후 선택한 이관 정책대로 유지되는지 확인한다.
- `TB`의 저장 대상 132개와 읽기에서만 허용하는 나머지 유효 지형, 15개 전기 설정의 기본·경계값을 확인한다.
- 누락된 파일·키와 오류 값, 한 줄에 여러 키가 있는 유효 JSON, 유니코드 escape, 알 수 없는 키, 읽기 전용 및 쓰기 실패를 확인한다.
- 기본 설정 저장 후 wrapper 실패 또는 독립 setter 저장이 겹치는 상황에서 최종 파일과 사용자에게 보여 주는 실패 결과를 확인한다.

## 기본 설정의 지연 적용과 세대 감지

`ConfigBase.inc:735`의 `ApplyStoredConfigs`는 ClientBGThread 루프에서 호출된다. gameBase가 0이면 이전 안정화 시간이 있을 때 전체 적용 상태를 리셋한다. 0이 아닌 base에서는 최대 1초에 한 번 검사하며 최초 base 감지 후 3초가 지나면 P1 불필요 항목을, 유효 P1 최초 감지 후 3초가 지나면 P1 필요 항목을 처리한다. `isWar` 항목은 추가로 `IsBattleRuntimeReady()`가 참이어야 한다. 표의 `appliedState` 또는 `applyFunc`가 없는 항목은 이 공통 루프에서 적용하지 않는다.

`Menu_impl.inc:517`은 별도로 계산한 `gameBaseReady` 대신 원래 `gameBase`를 그대로 전달한다. `ApplyStoredConfigs`의 base 조건은 0인지뿐이므로 0이 아닌 주소가 읽기 유효성 검사에 실패해도 base 안정화와 P1 불필요 항목 처리 경로를 진행할 수 있다. 반면 P1은 이 함수에서 `IsValidPtr(p1, 0x100)`을 확인한다. 설정 파일의 최초 로드는 별도의 `gameBaseReady` 조건을 사용하므로 두 조건을 같은 것으로 취급하지 않는다. 실제 유효하지 않은 주소가 전달되는지는 실행하지 않았다.

공통 루프는 ON·OFF 호출 직전에 적용 상태를 먼저 true·false로 바꾸고 `void` setter를 호출한다. setter가 내부적으로 실패해도 공통 루프는 그 결과를 받지 못하며 같은 상태에서 자동 재시도하지 않는다. base나 P1의 숫자 주소가 0 또는 유효하지 않은 상태를 거치지 않고 다른 유효 주소로 바로 바뀌는 경우, 이 함수는 이전 주소와 비교하지 않으므로 해당 변화만으로 안정화 시간을 재설정하지 않는다. P1 무효화는 P1 의존 적용 상태와 월 캡처, 군단 자동배치 세션을 초기화하지만 설정 flag를 끄지는 않는다.

P1 안정화 이후 월 캡처는 `bMonthCapture`가 켜져 있으면 `SetMonthCapture`와 시스템 월 hook 설치를 호출한 뒤 적용 상태를 표시한다. 전기 캡처는 이 함수의 지역 static flag가 false일 때 시작하며, 위 reset 함수들은 해당 지역 flag를 초기화하지 않는다. 결과적으로 일반 적용 상태 리셋과 전기 캡처 재설치 조건은 같은 상태 변수를 사용하지 않는다.

회귀 조건은 base·P1의 0/무효 경유와 유효 주소 간 직접 교체, 3초 경계와 1초 폴링, 전투 준비 전후, setter 실패·비동기 설치 실패, P1 리셋 후 월·전기 캡처 재시작이다. 주소 유효성 검사가 게임 객체의 세대나 스레드 안전성을 증명하지는 않는다.

## wrapper 설정의 즉시 적용 순서

`Menu_impl.inc:427`은 gameBase가 `0x6000` 범위까지 유효하다고 판정된 최초 루프에서 `LoadConfig`를 한 번 호출한다. 이때 P1의 3초 안정화를 기다리지 않는다. `Config.cpp:300`의 wrapper는 기본 파일 읽기 후 전기별 15개 허용·기간·쿨다운 설정을 읽고, 미발견→재야 flag가 켜져 있으면 watcher를 시작한다. 이어 AI 전투, 임무 강제배정, 기술도시 표시, 평정 이동·처단, 5번 책략, 단절 영토, 포로 관리 순으로 각 setter 또는 기능 요청을 처리한다. 그 후 특권 옵션을 읽고 도독 포로 처분을 적용하며, 원군 즉시 행동, 책략 게이지 설정·5번 책략 세부값, 게이지 hook을 처리한다.

키 부재 처리도 일률적이지 않다. 평정 이동·처단과 5번 책략은 누락 시 false를 사용해 setter를 호출한다. 단절 영토는 누락 시 true, 포로 관리는 현재 flag로 호출한다. AI 전투·임무·기술도시·도독 포로 처분·원군 즉시 행동은 해당 키를 읽은 경우에만 setter를 호출한다. AI 전투 로그는 setter가 실패 후 flag를 바꾸더라도 읽어온 `savedAIWarImprove`를 출력한다. 따라서 해당 로그 하나로 최종 적용 성공을 판단할 수 없다.

같은 루프의 뒤쪽에서 `ApplyStoredConfigs`가 별도의 base/P1 안정화 조건을 적용한다. wrapper 즉시 setter와 기본 표의 지연 setter를 동일 시점으로 묶으면 시작 순서가 달라진다. 회귀 조건은 설정 키 누락·false·true, base만 준비되고 P1이 없는 시점, setter별 실패 시 flag와 로그, 초기 로드 한 번 뒤 게임 세대 전환이다.

wrapper 로드 후반부는 사망·등용 알림 flag → 상성 표시 setter → 연간 특수능력 flag → AI 성장 flag·속도·복구 flag 순으로 처리한다. AI 성장이 OFF면 앞서 읽은 연간 특수능력을 OFF로 바꾼다. 이어 수비 원군 배치, 단기접전 일수와 활성화, 병력수 공방, 기재 보기, 전체 보주 개방 선호, 보조 보주 마스크를 처리한다. 이 중 상성·수비 원군·단기접전·병력수 공방은 키가 있을 때 setter를 호출하고, 기재 보기는 키가 없어도 true로 setter를 호출한다. 보주 전체 개방 누락은 false 선호로 처리하며, 보조 보주는 새 마스크 키가 없을 때만 구버전 전체 선택 bool을 읽는다.

책략 게이지는 공격·수비 중 하나라도 ON이면 하나의 hook 설치를 시도하며 실패 시 두 flag를 모두 false로 바꾼다. 양쪽이 모두 OFF인 설정 로드 경로에서는 hook 해제 함수를 호출하지 않는다. 이에 대한 구체적인 hook·세션 처리는 [책략 조사](P0_Stratagem.md)에 기록돼 있다. 각 설정의 상세 기능과 실패 경로는 [기능 보존표](P0_Feature_Contracts.md)를 따른다.

## 한 번의 설정 저장이 수행하는 파일 갱신

`Config.cpp:246`의 `SaveConfig`는 읽기 전용 속성을 검사한 뒤 기본 저장을 호출하고, 이어 고정 추가 키 36개와 15개 전기 항목의 3개 키씩 총 45개를 각각 upsert한다. 성공 경로에서 기본 전체 재작성 1회와 추가 키별 전체 파일 읽기·truncate 재작성 81회가 순서대로 일어난다. 각 upsert는 해당 키가 있는 첫 줄을 제거하고 `config_end` 앞에 새 줄을 삽입한다. 기본 저장과 각 upsert는 `void`이며 실패를 보고한 뒤 호출자에게 성공 여부를 반환하지 않으므로 이후 upsert도 계속 시도된다.

일반 저장은 기본 재작성에서 알 수 없는 키와 독립 `bRulerTransferProposal` 키를 지운다. 그 기능의 메뉴는 일반 저장 후 독립 저장을 별도로 호출하지만, 다른 설정 저장에서는 해당 독립 키를 재삽입하지 않는다. 기본 저장 또는 중간 upsert 실패, 프로세스 중단, 서로 다른 호출의 겹침은 최종 파일이 전체 설정의 단일 시점 스냅샷인지 판단할 때 확인해야 한다. 이 소스의 저장 함수 자체에는 여러 단계 전체를 감싸는 파일 잠금이나 임시 파일 교체가 없다. 실제 호출 스레드가 겹치는지와 파일 시스템 실패는 실행하지 않아 확인하지 않았다.

독립 `SaveRulerTransferProposalPreference`와 wrapper의 upsert는 기존 키를 찾으면 해당 키만이 아니라 그 키가 있는 줄 전체를 메모리에서 지운 뒤 `config_end` 앞에 새 줄을 넣는다. 따라서 독립 저장을 여러 키가 한 줄에 있는 파일에 직접 적용하면 같은 줄의 다른 키도 삭제될 수 있다. 기존 키와 `config_end`가 같은 한 줄에 있으면 그 줄을 지운 뒤 `config_end`를 찾지 못해 파일을 열어 다시 쓰기 전에 실패를 반환한다. 메뉴의 일반 저장은 먼저 기본 형식으로 재작성하므로 이 예와 구분하며, 실제 파일 변경은 실행하지 않았다.

읽기 함수도 키가 있는 줄 전체에서 bool `true`를 찾고, 정수·문자열은 그 줄의 첫 콜론부터 해석한다. 한 줄에 여러 키가 있는 JSON은 유효해도 같은 줄의 다른 값이 결과에 영향을 줄 수 있다. 회귀 조건은 82회 갱신 중 각 단계 실패, 독립 키의 저장 순서, 중복 키와 한 줄 다중 키, 동시에 저장을 요청하는 호출이다.

## 조기 로그·책략 설정과 일반 로드의 차이

시작 스레드의 `T00LoadEarlyLogConfig`는 일반 설정 로드보다 먼저 `LoadEarlyLogConfig`로 `bFileLog`가 포함되고 `true`가 포함된 줄을 찾은 뒤 파일 로그 writer를 시작한다. 조기 로그 함수는 그런 줄이 없으면 기존 변수를 false로 설정하지 않고 그대로 둔다. 이어 `ReadEarlyStratagemFiveSetting`은 `bStratagemFiveEnabled`가 있는 첫 줄만 보고 그 줄에 `true`가 있으면 ON으로 판단한다. 파일을 열지 못하거나 키가 없으면 책략은 OFF다. 두 함수 모두 줄 단위 부분 문자열 검사다.

이 조기 책략 값은 시작 시 UI bridge 준비 여부와 100ms 대기 생략에 사용된다. 이후 gameBase 준비 시 `Config.cpp`의 일반 로드는 같은 책략 키를 다시 읽고 별도의 feature setter를 호출한다. 조기 wrapper와 일반 로드는 서로 다른 시점의 별도 파일 열기이므로 그 사이 파일이 바뀌면 두 판단이 달라질 수 있다. 조기 설정은 파일 경로를 `g_hModule`의 디렉터리에서 계산하며 경로 획득 실패를 `GetConfigPath`에서 별도로 처리하지 않는다.

조기 책략 읽기와 일반 wrapper의 `LoadBoolConfigValue`는 모두 해당 키가 처음 나타나는 줄에서 `true` 문자열을 찾고 즉시 반환한다. 따라서 같은 파일 내용이면 중복 키의 첫 줄이 두 판정을 결정한다. 일반 로드는 읽은 값을 `SetStratagemFiveFeature`에 전달하고 false가 반환되면 flag를 false로 바꾸는 분기를 갖는다. 다만 현재 setter(`StratagemSlotProbe.cpp:5495-5513`)는 요청 상태를 저장하고 두 분기 모두 true를 반환하므로 이 호출만으로 실제 적용 성공을 뜻하지 않으며, 그 false 분기는 현재 구현에서 도달하지 않는다. 조기 설정 OFF일 때 시작용 setter wrapper가 enable 요청을 생략하는 것과 일반 로드가 별도 setter를 호출하는 것은 다른 경로다.

회귀 조건은 파일 부재, 키 누락, 중복 키 및 한 줄의 다른 `true`, 조기 읽기와 일반 로드 사이 값 변경, 로그 writer 시작 순서, DLL 경로 확인 실패다. 실제 파일 변경 경합이나 시작 스레드 지연은 게임 실행 없이 확인되지 않았다.

## 전법 확률 입력과 쓰기 폭

`TacticsEditWindow.cpp:222-225,271-274,320-323,381-435`는 천계 확률 3개와 동토 확률·상태 확률 6개를 각각 0~100 슬라이더와 같은 정수 변수를 사용하는 `InputInt`로 편집한다. 숫자 입력 직후 별도의 0~100 제한은 없다. `SetCelestialMod`는 세 확률을 `uint8_t`로 변환해 쓰고, `SetDongto`는 세 기본 확률과 1레벨 상태 확률을 `uint16_t`, 2·3레벨 상태 확률을 `uint8_t`로 변환해 쓴다. setter에도 0~100 제한은 없다. 따라서 숫자 입력으로 범위 밖 값이 남아 적용되면 각 필드 폭에 맞춰 변환된 값이 기록되는 경로다. 슬라이더 조작 및 이후 프레임의 실제 UI 동작은 실행하지 않아 확인하지 않았다.

천계 적용은 설정 저장을 먼저, 동토 적용은 setter를 먼저 호출한다. 두 setter는 대상 포인터 해석 이후 `VirtualProtect` 반환값을 확인하지 않고 쓰며 원래 보호 복구 결과도 확인하지 않는다. 동토의 보호 요청은 `dp`부터 길이 `0x108B`인데 마지막 3레벨 상태 확률 쓰기는 `dp+0x108B`에 있다. 요청 범위의 마지막 바이트 바로 뒤에 쓰는 코드이며, 실제 페이지 보호 효과나 오류 발생 여부는 실행 결과 없이 단정하지 않는다. 회귀 조건은 숫자 직접 입력의 음수·100 초과·각 정수 폭 경계, 슬라이더 조작, 저장·재로드, 각 레벨의 필드와 보호 변경 실패다.

`fDomesticsPlayer`와 `fDomesticsForce`의 초기값은 각각 2.0과 1.25이며 메뉴 슬라이더 범위는 1.0~10.0이다. 기본 설정 로더는 두 값을 파일의 줄 순서대로 `stof`로 읽고 각 줄을 읽을 때마다 현재 두 값을 `SetDomesticsMultiplier`에 전달한다. 로더와 setter는 슬라이더 범위 제한을 적용하지 않는다. 따라서 두 키 사이에는 하나만 갱신된 조합이 전달되고, 파일에서 범위 밖으로 읽힌 값도 그대로 multiplier 변수에 저장되는 경로다. UI 동작이나 게임 적용을 실행한 결과는 아니다.

`DomesticsMult.cpp:174`의 ON은 `g_domesticsRunning=true` 이후 설치 스레드를 만든다. 생성된 경우 핸들을 닫고 worker가 종료 시 flag를 false로 내리지만, 생성 실패 시 flag를 되돌리는 분기는 없다. 이 경우 이후 ON 요청은 실행 중이라고 판단해 반환한다. OFF도 설치가 이미 완료된 상태만 복원하고 실행 중 flag를 내리지 않는다. 회귀 조건은 설정 순서·누락·범위 밖 값, 슬라이더 변경, 스레드 생성 실패, 설치 중 OFF와 재활성화다.

## 배속 선택·활성화·저장 순서

`Menu_impl.inc:834`에서 배속 체크를 바꾸면 먼저 변경 알림을 넣고 `SpeedHack_Update`를 호출한 뒤 설정을 저장한다. 설치에 실패하면 `SpeedHack_Update`가 `bSpeedHack=false`로 바꾸므로 ON 알림이 이미 들어간 뒤 저장되는 체크는 OFF가 될 수 있다. 설정의 배율은 `ConfigBase.inc:317`에서 1.0~5.0 범위의 0.5 간격으로 정규화해 읽는다.

+/-는 별도의 임시 선택값만 바꾸고, 적용 버튼은 선택값을 `g_speedMultiplier`에 반영해 저장한다. 배속이 ON일 때만 그 자리에서 `SpeedHack_Update`를 호출하므로 OFF 상태에서도 다음 활성화에 쓸 배율을 저장할 수 있다. 외부에서 적용 배율이 바뀌면 다음 UI 렌더에서 임시 선택값을 새 적용값으로 덮는다. OFF는 `s_enabled`를 내리고 시계 기준을 초기화하지만 설치한 네 hook을 즉시 제거하지 않는다. 이관 시 체크·선택·적용·설치 실패 상태를 구분한다.

회귀 조건은 OFF에서 배율 선택·저장 후 ON, 미적용 선택 중 외부 값 변경, 설치 실패 후 알림·저장값, 연속 토글과 배율 경계다. 실제 게임 실행은 하지 않았다.

## 설정 저장 실패의 알림 범위

기본 저장과 wrapper upsert는 열기·flush·close 상태를 확인하고 실패 시 `ReportConfigSaveFailure`를 호출한다. 이 함수는 단계·키·경로를 `AddLog`에 전달하고 `RequestConfigSaveErrorPopup`의 atomic 요청 flag를 세운다. 다만 `AddLog`는 디버그 표시와 파일 로그가 모두 OFF면 기록하지 않으며, 여러 실패 요청은 하나의 bool에 합쳐진다. 팝업은 `Menu::Render`가 실행될 때 소비하므로 모든 UI가 닫혀 overlay가 호출되지 않는 동안에는 표시되지 않는다.

기본 저장과 각 upsert는 성공 여부를 `SaveConfig` 호출자에게 반환하지 않고, 기본 저장 실패 뒤에도 wrapper의 나머지 upsert를 시도한다. 따라서 팝업 하나는 실패가 있었다는 사실을 표시하지만 어느 단계까지 저장되었는지 알려 주지 않는다. 로그도 설정에 따라 남지 않을 수 있다. 별도 후방지원·무장 이름 파일의 저장은 이 팝업 경로와 같지 않다. 회귀 조건은 읽기 전용·열기·중간 쓰기 실패, 여러 연속 실패, 디버그·파일 로그 ON/OFF, UI가 닫힌 상태의 실패와 다시 열기다. 파일 오류는 실행해 재현하지 않았다.

`GetConfigPath`는 초기화하지 않은 `char path[MAX_PATH]`를 `GetModuleFileNameA`에 넘긴 뒤 반환 길이나 실패를 확인하지 않고 `std::filesystem::path(path)`를 만든다. 저장 실패를 보고하는 함수도 경로를 다시 얻기 위해 이 함수를 호출한다. 따라서 모듈 경로 조회 자체가 실패하거나 버퍼 경계에 걸린 경우의 경로 구성·오류 표시는 이 코드에서 별도로 처리하지 않는다. 이는 함수의 정적 흐름이며 해당 실패가 실제 발생했는지는 확인하지 않았다.

## 설치된 설정 파일의 키 형식 대조

현재 `SAN8R` 게임 폴더의 `S8RPK_cheat_config.json`을 읽기만 해 기존 키 목록과 비교했다. 사용자 설정값은 기록하지 않았다. 일반 JSON 해석 결과 최상위 키는 339개이며 중복 키는 발견되지 않았다. 파일은 341줄이고 339개 키가 각각 별도의 `"키":` 형식 줄에 있다. 이는 현행 줄 기반 로더에 필요한 형식을 일부 충족한다는 관찰이며, 각 값의 범위와 실제 로드 성공을 검증한 것은 아니다.

기본 bool 62개, 기본 저장 scalar 62개, wrapper 고정 키 36개, 저장 대상 지형 132개, 전기 설정 45개와 `config_end`, `bRulerTransferProposal`이 존재한다. 이 분류에서 목록 밖의 키는 없었다. 기본 로더가 읽지만 일반 저장에서 쓰지 않는 동토 4개 키는 이 파일에 없다. `bRulerTransferProposal`은 존재하므로 앞 절의 일반 `SaveConfigBase` 재작성 시 해당 독립 키가 빠지는 경로는 이 설치 파일에도 관련된다. 이 결과는 파일에 키가 있다는 뜻이며 해당 기능이 활성화됐는지나 실제 저장이 일어났는지는 뜻하지 않는다.

파일 내용이나 게임 상태를 변경하지 않았고 기존 C++ 로더·저장기를 실행하지 않았다. 파일이 이후 변경되면 이 집계는 달라진다.

## 공통 적용 조건이 OFF와 초기화에 미치는 영향

`ApplyStoredConfigs`의 `processEntries`는 `isWar` 항목에서 `IsBattleRuntimeReady()`가 false면 flag와 적용 상태의 ON/OFF 비교보다 먼저 해당 항목을 건너뛴다. 따라서 이전에 공통 적용 상태가 true였고 현재 flag가 false여도 전투 준비가 되기 전에는 이 루프에서 OFF setter를 호출하지 않는다. P1 필요 항목은 P1 안정화가 끝나지 않으면 이 비교 자체를 수행하지 않는다. 이는 공통 자동 적용 경로에 대한 조건이며 모든 사용자 조작에서 OFF가 지연된다는 뜻은 아니다.

예를 들어 `TacticsEditWindow.cpp`의 치료·동토·천계·투석·격류/낙석 체크박스는 바뀐 값으로 각 setter를 즉시 직접 호출하고 저장한다. 이 직접 호출은 공통 적용 상태 변수와 별개다. 따라서 동일한 OFF 요청에 대해 메뉴의 즉시 호출과 이후 공통 루프의 호출 여부·순서는 각각 살펴야 한다. setter가 대상 주소를 찾지 못해 실제 데이터를 변경하지 못한 경우도 `void` 결과만으로 공통 상태에 반영되지 않는다.

P1이 무효가 된 것으로 감지되면 `ResetP1DependentAppliedStates`는 해당 항목의 공통 적용 상태를 false로 지우지만 해당 항목의 OFF setter들을 순회해 호출하지 않는다. gameBase가 0이 된 경우의 `ResetAppliedStates`도 공통 적용 상태를 지우며, 별도 월 캡처 중지와 군단 세션 reset을 수행한다. 예를 들어 적용 상태가 true인 항목의 실제 효과가 남아 있는 상황에서 추적 상태가 먼저 false로 바뀌고 설정 flag도 false라면, 이후 그 공통 항목은 true→false 차이를 보지 못한다. 실제 효과의 잔존 여부는 각 setter와 게임 객체 수명에 따라 따로 확인해야 한다.

회귀 조건은 전투 준비 전후의 OFF, 직접 메뉴 OFF와 자동 적용 상태, P1 무효화 시 ON·OFF 각각의 flag, gameBase 소실, 재안정화와 설정 재활성화, setter 주소 해석 실패 및 별도 전투 초기화 경로의 재호출이다. 실제 전투와 토글 순서는 실행하지 않았다.

## 초기 설정 파일 부재·읽기 실패와 재시도

`Menu::Loops`는 `gameBaseReady`가 처음 true가 되면 `LoadConfig()`를 호출한 뒤 반환 결과 확인 없이 함수 지역 `s_configLoaded=true`로 설정한다. `LoadConfig`는 `void`이며, 기본 `LoadConfigBase`는 파일을 열지 못하면 알림 없이 반환한다. 이 함수가 실패해도 wrapper는 나머지 개별 키 읽기와 기본값 적용을 계속한다. 이후 파일이 생기거나 읽기 가능해져도 같은 지역 flag를 초기화하는 코드는 이 경로에 없어 해당 자동 로드를 다시 시도하지 않는다. 초기 설정 로드 후 gameBase가 사라졌다 돌아오는 경우도 같은 flag를 사용한다.

파일이나 키를 읽지 못할 때 적용되는 값은 항목마다 다르다. 예를 들어 단절 영토 이동 제한과 기재 화면 보기 wrapper는 지역 기본값 true로 각각 setter를 호출한다. 평정 이동 지속·재야 처단·5번 책략은 지역 기본값 false로 setter를 호출하고, 일부 항목은 키를 읽은 경우에만 setter를 호출한다. 따라서 파일 전체를 읽지 못한 상태와 모든 기능을 일괄 OFF한 상태는 같지 않다. 개별 setter가 실패할 때의 flag 조정은 [기능 보존표](P0_Feature_Contracts.md)를 따른다.

`LoadConfigBase`와 개별 키 helper는 파일을 따로 연다. 초기 로드가 진행되는 도중 파일 상태가 바뀌면 호출별로 서로 다른 파일 상태를 관찰할 수 있다. 이 조건과 실제 읽기 실패 빈도는 실행하지 않아 확인되지 않았다. 회귀 조건은 파일 부재·열기 실패 후 파일 생성, 초기 로드 도중 파일 교체, 누락 키별 기본값, 기본 기능 setter 실패, gameBase 소실·복귀 및 명시적 재시도 정책이다.

## 초기 로드와 메뉴 조작의 공통 패치 진입

설정 로드는 `ClientBGThread`의 `Menu::Loops`가 gameBase 준비 후 호출한다. 예를 들어 `Config.cpp:320`은 `bAIWarImprove`를 파일에서 읽으면 전역 flag를 바꾸고 `SetAIWarImprove`를 즉시 호출한다. 동시에 메뉴 렌더 경로의 `MenuSectionsWar.cpp:101`도 같은 flag를 체크박스로 바꾸고 같은 setter를 호출한 다음 설정을 저장한다. 메뉴가 그려지는 것과 초기 로드 완료를 직렬화하는 조건은 이 두 호출 지점에 없다.

`Roadblock.cpp:102`의 AI 전투 setter는 호출별로 네 정적 패치의 현재 바이트를 읽어 지역 snapshot을 만든 뒤 쓰고, 실패하면 그 snapshot으로 복구를 시도한다. 두 hook 설치·해제도 같은 함수에서 묶는다. 이 setter 전체에는 동시 호출을 하나로 묶는 잠금이 없다. 따라서 시작 직후 UI 조작과 로드가 겹치면 한 호출이 확보한 snapshot과 다른 호출의 쓰기가 서로 영향을 줄 수 있다. 실제 겹침이나 결과를 실행해 확인한 것은 아니다. 같은 이름의 `SetRoadBlock` worker 잠금은 이 setter 전체를 보호하는 근거가 아니다.

이관 시에는 초기 설정 읽기·기능 적용과 사용자 변경이 어떤 순서로 확정되는지, 설정 저장이 어느 값을 기록하는지 함께 검증한다. 회귀 조건은 저장된 ON/OFF 각각에서 초기 로드 도중 반대 상태를 선택하는 경우, 패치 확인 뒤 다른 호출이 개입하는 경우와 부분 실패 후 복구다.
## 보조 보주 선택의 세 가지 비트 인덱스

기존 설정의 `secondaryJewelForceMask`는 64비트 word 8개를 낮은 word 인덱스부터 각각 16자리 대문자 16진수로 직렬화한다. 선택 마스크는 **보조 ID 자체**를 비트 번호로 사용한다. 반면 `kDefinedSecondaryJewelMask`의 정의 여부는 **보조 ID-1**, 게임의 34바이트 개방 비트맵은 **raw ID=보조 ID+64**를 비트 번호로 사용한다. 세 인덱스를 동일하게 취급하면 저장된 선택과 게임 개방 검사가 서로 다른 보주를 가리킨다.

| 보조 ID | raw ID | 선택 word와 값 | 정의 마스크 byte와 bit | 게임 개방 bitmap byte와 bit |
|---:|---:|---|---|---|
| 2 | 66 | word 0, `0x0000000000000004` | byte 0, bit 1 | byte 8, bit 2 |
| 63 | 127 | word 0, `0x8000000000000000` | byte 7, bit 6 | byte 15, bit 7 |
| 64 | 128 | word 1, `0x0000000000000001` | byte 7, bit 7 | byte 16, bit 0 |
| 128 | 192 | word 2, `0x0000000000000001` | byte 15, bit 7 | byte 24, bit 0 |

예를 들어 보조 ID 2만 선택하면 저장 문자열의 첫 16자리는 `0000000000000004`이고 나머지 112자리는 0이다. ID 64만 선택하면 첫 word 16자리는 0이고 다음 word 16자리는 `0000000000000001`이다. 정의 표·두 정적 마스크의 전체 집합 대조는 [리소스 조사](P0_Resources.md#보주-정의의-출처-표기와-마스크-대조)를 따른다. 위 예시는 원본의 비트 계산을 수동 대조한 이관 사례이며 기존 C++ 직렬화 코드를 실행한 결과는 아니다.
## 추가 설정 36개의 키 누락 처리

`Config.cpp:300-583`의 고정 wrapper 키 36개를 로드 순서와 대조해 [키별 누락 처리](p0/config_wrapper_missing_policy.csv)를 정리했다. 파일을 열지 못한 경우에도 각 helper가 실패를 반환하므로 해당 키 누락과 같은 분기로 진행하지만, 앞 단계에서 전역값이 바뀐 경우 ‘현재 상태 유지’는 초기값으로 재설정한다는 뜻이 아니다.

- 평정 이동 지속·평정 재야 처단·5번 책략과 공격/수비 게이지는 누락 시 지역 기본값 false를 대입한다. 평정 두 기능과 5번 책략은 그 값으로 setter를 호출하고, 게이지는 둘 중 하나가 ON일 때만 공통 캡처를 요청한다.
- 단절 영토 이동과 기재 보기의 지역 기본값은 true이고 누락 시에도 setter를 호출한다. 포로 관리의 지역 기본값은 현재 flag이며 프로그램 초기 선언은 true다.
- 5번 책략 숫자 아홉 개는 먼저 현재 `Spell5CustomSettings`를 복사하므로 누락된 필드는 현재 값을 유지한 뒤 전체 설정을 정규화해 적용한다. 초기 구조체 값은 대상 1, 효과1 10·위력 40·기간 0, 효과2 0·위력 0·기간 0, 범위 5, 추가 회복 2000이다.
- AI 자동 성장과 연간 특수능력은 각각 읽지만, 로드 후 자동 성장이 OFF면 연간 특수능력도 OFF로 바꾼다. 성장 속도는 키를 읽었을 때 1~3으로 제한하며, 초기 선언은 2다. 단기접전 일수는 로더와 setter 모두에서 범위를 제한하지 않는다. setter는 현재 게임 값이 기본값 또는 요청값인지 확인한 뒤 요청 정수를 기록한다.
- 보조 보주는 문자열 마스크의 존재가 과거 전체 선택 bool보다 우선한다. 마스크가 없을 때만 bool을 읽으며 그마저 없으면 false다. 마스크가 존재하지만 잘못됐거나 필요한 hook을 설치하지 못하면 이전 bool로 대체하지 않고 전체 OFF를 시도한다.

이 표는 초기 선언과 로더의 분기·setter 호출에 대한 정적 목록이다. 각 setter의 성공 여부, 게임 객체의 준비 상태와 실행 결과는 기능별 보존표 및 작업 수명 조사에 따로 기록했다.
추가 정수 설정 11개의 초기값과 값 처리 범위는 같은 CSV의 `numeric_policy`에 기록했다. 책략 효과 ID는 0·3·10·11·12만 유지하고 나머지는 0으로 바꾸며, 대상·위력·기간·범위·추가 회복은 각각 별도 경계로 제한한다. 이 정규화는 `SetSpell5CustomSettings`에서 설정 상태에 먼저 반영되고, 이미 적용된 게임 레코드가 유효할 때 그 레코드 쓰기를 시도한다. 레코드 쓰기가 실패해도 정규화된 설정값 자체는 남는다. 상세 실행 경로는 [책략 조사](P0_Stratagem.md)를 따른다.
추가 bool 키 24개는 위 CSV의 `initial_boolean`에 선언 또는 계산 상태를 연결했다. 직접 flag의 초기값이 true인 것은 단절 영토 이동·포로 관리·기재 보기 세 가지다. 나머지 직접 flag는 false이며, 보주 전체 개방은 별도 선호 atomic의 false, 보조 보주 전체 선택은 0으로 초기화된 선택 비트들의 전체 판정 결과다. 이 초기 상태는 조기 로드·일반 로드·메뉴 조작 이후 값과 구별한다.
## 전체 설정 키 통합 목록

기본 bool·scalar, wrapper 고정 키, 생성형 전기·지형 키와 독립 군주 제안 키를 [통합 목록](p0/config_key_inventory.csv)에 합쳤다. 각 행은 키 이름과 원본 경로, 일반 저장·wrapper upsert·독립 upsert·읽기 전용 여부를 구분한다. 목록에는 서로 중복되는 키가 없다.

총 415개 중 일반 저장과 wrapper가 내보내는 키는 끝 표시 `config_end`를 포함해 338개다. 별도 setter만 쓰는 `bRulerTransferProposal`을 포함하면 저장 경로가 있는 키는 339개다. 나머지 76개는 기본 로더가 허용하지만 일반 저장에서 출력하지 않는 동토 4개와 지형 72개다. 지형 72개는 저장하지 않는 인덱스 6개에 병종 12개를 곱한 수다. `config_end`는 값 설정이 아니라 wrapper가 추가 키를 삽입할 위치를 찾는 기준으로 분류했다.

현재 설치된 설정 파일을 일반 JSON으로 해석한 뒤 **키 이름만** 비교한 결과 339개가 있고, 목록 밖의 키와 저장 경로가 있는 키 중 빠진 것은 각각 0개였다. 값과 사용자 설정 내용은 복사하지 않았다. 이 비교는 정규화된 키 집합 대조이며 중복 키·줄 단위 로더의 해석 결과, 설정 저장 성공 또는 게임 적용을 증명하지 않는다. 일반 저장이 독립 군주 제안 키를 지우는 순서도 앞의 설명 그대로다.
지형 키 204개의 프로그램 초기값과 `기본값 복원` 후 값, 일반 저장 대상 여부를 [지형 값 목록](p0/terrain_initial_and_restore.csv)에 추가했다. 132개가 일반 저장 대상이고 72개는 로더만 읽는다. 열거한 행에서는 `TB_11_16`과 `TB_11_17` 두 값만 초기 배열과 복원 배열이 다르며, 이는 초기 11번 행의 부족한 마지막 원소가 0으로 초기화되는 C++ 배열 규칙을 반영한 결과다. 파일 로드나 게임 쓰기 결과는 포함하지 않는다.
## 생성형 전기 설정의 슬롯과 초기값

15개 전기 항목의 화면 이름, 비연속 게임 슬롯 ID와 세 설정 키를 [전기 설정 목록](p0/tengi_setting_defaults.csv)에 연결했다. 두 평정 UI의 이름 배열은 이 15개 이름과 순서가 같다. 초기값은 모든 항목의 발생 허용 true, 기간 0개월, 쿨다운 -1년이다. 기간 0은 기본 기간, 쿨다운 -1은 기본 쿨다운을 뜻하며 0은 대기 없음이다.

각 키가 누락되면 허용과 기간은 현재 배열 값을 유지한다. 쿨다운은 로드마다 지역값을 -1로 두고, 읽기에 실패해도 그 값을 setter에 전달한다. 따라서 이전에 바뀐 쿨다운이 있을 때는 키 누락으로 -1로 돌아갈 수 있다. 로드한 기간은 0~120, 쿨다운은 setter에서 -1~255로 제한한다. UI도 같은 범위로 편집하며 초안은 저장 버튼에서 실제 배열에 복사된다. 항목의 슬롯과 출처는 원본 코드 기준이며 실제 게임 전기 발생 결과는 확인하지 않았다.
