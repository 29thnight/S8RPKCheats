# P0 기재 데이터와 문자열 수명 조사

기준: S8RPKCheats `068ca1d881edf870f7cf06f935cf50e286004af8`. 원본 소스의 데이터 표현과 호출 경로를 정적으로 확인했다. 게임 객체에 접근하는 안전한 스레드와 저장 포맷의 새 스키마는 아직 확정하지 않았다.

## 데이터 표현과 경계

- `OfficerData.h`의 `TalentInfo`는 16비트 기재 ID와 `TalentEffect` 6개다. 각 효과는 16비트 effectId, val1, val2다. `GetOfficerTalentDetailed` (`OfficerData_impl.inc:1585`)는 무장 `+0x88 + slot*8`의 기재 포인터를 읽고 ID와 효과를 복사한다. 6개 효과를 순서대로 읽다가 처음 `effectId == 0`인 슬롯에서 중단하며 그 슬롯과 뒤쪽은 0으로 남긴다. 호출자가 사용할 slot의 유효 범위는 이 함수에서 검사하지 않는다.
- 설정 runtime (`TraitConfigRuntime_impl.inc:28`)은 최대 254개 기재, 0x40바이트 레코드, ID `+0x08`, 효과 `+0x0A`의 6슬롯 × 6바이트, 메타데이터 `+0x2E`의 0x12바이트를 사용한다. 이것은 기준 게임의 메모리 레이아웃이며 새 domain 타입의 ABI나 소유권을 뜻하지 않는다.
- 현재 새 `src/domain/trait.h`의 ID와 효과 6개 값은 위 조회 데이터와 같은 필드 폭을 표현한다. 기존 메모리의 packing, sentinel 처리, metadata, 문자열이나 파일 스키마를 구현한 것은 아니다.

`GetOfficerTalentDetailed`는 유효 주소 기준을 통과한 뒤 출력 구조를 0으로 초기화하고 읽는다. 읽기 도중 예외가 나면 false를 반환하지만 이미 복사한 ID·효과를 다시 지우지는 않는다. 기준 주소가 `0x10000` 미만이면 출력 초기화 전에 false를 반환한다. 새 값 모델에 필드가 있다는 사실만으로 이 함수의 성공·실패 출력 계약까지 이관된 것은 아니다.

## 외부 설정과 적용

- 기준 저장소 최상위 `S8RPK_traits_default.json`을 JSON으로 읽어 확인한 결과 `version=2`, `traits` 254개, `customNames` 213개다. 실제 런타임 파일은 DLL 폴더 또는 현재 작업 폴더에서 선택되므로 사용자 파일 내용이 이 기준과 같다는 뜻은 아니다.
- `ParseTraitLine` (`TraitConfigRuntime_impl.inc:1684`)은 한 줄에서 index 0~253, id 1~254와 effects 배열 내 6개 `type/value/param` 객체를 읽는다. 각 수는 0~65535다. `EnsureEmbeddedTraitConfigLoaded` (`TraitConfigRuntime.cpp:211`)는 적어도 기재 1개를 요구하고, 존재하는 각 항목의 id가 index+1인지 확인한다. `customNames`의 `name`, `desc`, `cloneSrc`, `bgTrait`, `grade`는 별도 메타데이터다. 현재 파서는 문법 전체가 아니라 줄 배치에 의존한다.
- wrapper `TraitConfigRuntime.cpp:582`는 게임 폴더에 `version.dll`이 있으면 자체 tick을 중단한다. 없으면 외부 기본 JSON을 읽고 게시한 다음 `TickTraitConfigRuntimeImpl`을 호출한다. 내부 구현만 보면 `san8r_traits_config.json`을 주기적으로 찾는 것처럼 보이지만 wrapper의 선행 로드와 probe 시각 설정이 실제 경로에 영향을 준다.
- 내부 tick은 500ms 간격으로 이름·설명 hook을 준비하고 게임 테이블 주소를 찾는다. 테이블 주소가 바뀌거나 sentinel 기재 효과가 달라지면 재적용을 요청한다. `ApplyConfig` (`TraitConfigRuntime_impl.inc:2093`)는 254개 레코드를 복사한 뒤 custom text의 donor 복제, bgTrait 메타데이터 복사, ID와 효과 덮어쓰기를 순서대로 수행하고 전체를 게임 메모리에 쓴다. donor 참조는 순회 중 갱신되는 `records` 배열을 사용하므로 의존 순서를 변경할 때 데이터 동등성을 확인해야 한다.
- 테이블 복사 후 원본 보호 상태 복구와 sentinel 비교를 수행하지만, 쓰기 중 실패 또는 sentinel 불일치 시 전체 레코드 원상 복구는 이 함수에 없다. 이관 시 게임 세대·쓰기가 가능한 callback·실패 결과를 별도 계약으로 확정한다.

기본 기재 파일 경로는 읽기 성공 여부가 아니라 `is_regular_file` 결과로 선택한다(`TraitConfigRuntime.cpp:13-38`). DLL 폴더 파일이 일반 파일로 존재하면 그 경로를 먼저 선택하고, 이후 열기나 내용 검증이 실패해도 그 호출에서 작업 폴더 파일로 다시 시도하지 않는다. DLL 폴더 후보가 없을 때만 작업 폴더 후보를 검사한다. 편집 저장은 먼저 선택한 경로에서 원본을 읽어 결과를 만든 뒤 경로를 다시 선택해 출력 파일을 연다(`:458-521`). 두 선택 사이 파일 존재 상태가 바뀌면 읽기와 쓰기의 선택 경로가 달라질 수 있다. 실제 파일 교체나 읽기 실패는 실행하지 않았다.

## 편집과 문자열

- `TraitTextEditorData.h`는 기본 72개 CT 편집 행과 기재 ID를 가진 별도 custom 행을 구분한다. 유효 UTF-8, NUL 금지, UTF-16 기준 512 code unit 이하, 새 이름 최대 5 code unit, 설명 포맷 토큰의 종류·순서 조건을 선언한다. 기본 행은 `trait_texts.ini`, custom 행은 외부 JSON 편집 경로를 사용한다.
- `PublishNativeTexts`는 UTF-8 이름·설명을 별도 wide 문자열에 할당하고 포인터 배열을 바꾼다. 주석과 구현은 게임이 이전 포인터를 보유할 가능성 때문에 이전 문자열을 즉시 해제하지 않는 방식을 사용한다. 포맷 설명용 문자열은 `%`를 이스케이프한다.
- `TraitTextNameHook.cpp:565`의 이름 편집 detour는 원본 getter의 결과와 기존 이름을 비교해 새 문자열 포인터를 반환한다. `ApplyRuntimeNameOverlay`는 새 표를 `g_generations`에 보관하고 atomic 포인터로 게시한다. 별도 해제 시점과 외부 게임이 문자열 포인터를 보관하는 기간은 unload 설계의 증거가 필요하다.

## 회귀 조건

기재 ID/index 불일치, 6개 슬롯과 0 sentinel, 16비트 경계, 중복·누락 index, donor/bgTrait 참조 순서, 외부 JSON의 줄 배치·유니코드 escape, 기재 테이블 재생성, 적용 실패 후 상태, 원본과 편집 문자열 생존 기간, 기본 72행과 custom 행의 분리, 외부 `version.dll` 존재·부재를 확인한다.

## 사용자 기재 표시 캐시의 별도 파일 경로

`CustomTraitDisplay.h`의 표시 캐시는 runtime 기재 테이블 적용과 별도다. `san8r_traits_config.json`을 DLL 디렉터리, 그다음 현재 작업 디렉터리에서 찾고, 읽은 내용이 비면 게임 폴더의 `version.dll`이 없는 경우에만 `IDR_JSON_TRAITS_DEFAULT` 경로로 대체한다. 이 ID의 실제 공급은 외부 `S8RPK_traits_default.json`이다. 따라서 runtime wrapper가 외부 `san8r_traits_config.json` 단독 적용을 억제한다는 사실만으로 UI 표시 캐시도 그 파일을 무시한다고 판단하면 안 된다.

`TickTraitConfigRuntime`의 외부 DLL 분기는 파일 존재를 확인하면 로그를 남기고 바로 반환한다. 이 분기에는 이전 tick에서 이미 설치된 자체 hook을 비활성화하거나 적용된 테이블을 복원하는 호출이 없다. 따라서 실행 중 파일이 새로 나타나는 경우 이후 자체 tick을 건너뛰는 것과 기존 적용 상태가 제거되는 것은 별개다. 파일이 사라지면 분기는 다시 내부 데이터 로드·tick 경로로 진행한다. 실제 파일 변경이나 모듈 로드 순서는 확인하지 않았다.

외부 파일 여부를 판단하는 runtime·표시 캐시·이름 hook의 세 `HasExternalGameVersionDll` 구현은 각각 실행 파일 경로 조회가 실패하거나 `MAX_PATH` 이상이면 false를 반환한다. `is_regular_file` 오류도 false로 합쳐진다. 호출자는 이 결과를 파일 부재와 구분하지 않으므로, 검사 자체가 실패해도 내부 runtime·표시·이름 hook 경로로 진행한다. 세 검사는 호출 시점이 각각 달라 같은 결과를 공유하는 구조도 아니다. 실제 경로 조회나 파일 상태 검사 실패는 확인하지 않았다.

캐시가 로드된 뒤에는 2초마다 확인하며 외부 파일의 수정 시간이 같으면 기존 내용을 사용한다. 외부 경로가 없고 기본 데이터에서 로드된 상태라면 기본 데이터 파일의 수정 시간을 다시 확인하지 않고 기존 캐시를 반환한다. 외부 파일 내용은 `customNames` 이후의 행을 줄 단위로 읽고 숫자 키를 ID-1 인덱스로 취급한다. 별도 편집 오버레이는 해당 기본 인덱스가 캐시에 존재하고 게임 폴더에 `version.dll`이 없을 때 비어 있지 않은 이름·설명만 덮는다. 기본 인덱스 자체가 없으면 오버레이만으로 조회 성공하지 않는다.

외부 파일이 비어 있지 않지만 인식 가능한 표시 항목이 없으면, 파싱한 빈 맵으로 기존 캐시를 교체하고 외부 파일 수정 시각을 저장한다. 이후 같은 수정 시각이면 빈 캐시를 반환하며 내용을 다시 읽지 않는다. 외부 파일 읽기에 실패하거나 비어 있을 때도 `version.dll`이 있으면 기존 맵을 지우고 실패를 반환하며, DLL이 없으면 기본 데이터 로드를 시도한다. 따라서 이전에 성공한 표시 내용은 이런 실패에서 항상 보존되지 않는다. 실제 파일 수정·읽기 오류는 재현하지 않았다.

`TraitTextEditorWindow.cpp:78-110`의 내장 기재 적용은 검증한 행 중 비어 있지 않고 원문과 다른 이름·설명만 모은다. 게임 쪽 `ApplyEmbeddedTraitTextOverrides`가 실패하면 표시 오버레이는 건드리지 않는다. 성공하면 기존 표시 오버레이를 모두 지운 뒤 변경 항목을 순서대로 다시 넣는다. 변경 항목이 없고 게임 쪽 적용이 성공한 경우에도 기존 표시 오버레이를 지운다. 실제 화면과 게임 메모리의 변경 결과는 실행으로 확인하지 않았다.

runtime 편집 적용은 새 이름·설명 배열을 게시하기 전 이전 배열을 보관한다. 게시 실패 시 이전 배열을 되돌리고 다시 게시하지만 이 재게시의 성공 여부는 확인하지 않는다. 해제는 배열을 먼저 비우고 기본 문구 게시를 시도하며, 게시 실패 시 이전 배열을 복구하지 않는다(`TraitConfigRuntime.cpp:348-408`). 편집 창은 runtime 적용 실패면 표시 캐시 오버레이를 그대로 두지만, 해제에서는 runtime 해제의 성공 여부와 관계없이 표시 캐시 오버레이를 지운다. 따라서 실패 후 두 경로의 표시 상태를 따로 확인해야 한다. 실제 실패는 실행하지 않았다.

표시 캐시와 편집 오버레이는 `CustomTraitDisplay.h`의 함수 지역 static 맵이며 조회·재로드·오버레이 추가·삭제 함수에 mutex는 없다. 확인된 직접 사용에는 무장 상세·기재 목록의 렌더 조회, 일괄 기재 창의 후보 조회, 기재 문구 창의 오버레이 적용·해제가 있다. `OfficerDetail.cpp`의 기재 객체 검증도 이 표시 정보를 사용할 수 있으므로 호출 경로의 실행 스레드를 함께 확인해야 한다. 검색 결과만으로 여러 스레드에서 실제로 동시에 접근한다고 단정하지 않는다.

기준 자체 cpp·h·inc의 `SetTraitObjectFast` 직접 호출은 일괄 기재 적용, UI 요청의 캐시 재사용, `TickTraitChangeAsync`의 검색 결과 적용이다. 일괄 적용과 UI 요청은 렌더 경로이며 `TickTraitChangeAsync`도 이름과 달리 `MenuT04Maintenance.h`의 렌더 유지 호출에서 실행된다. 따라서 확인된 이 세 직접 호출만으로 별도 background worker가 표시 캐시를 읽는다고 결론 내리지 않는다. `SetTraitID` 일반 함수·간접 호출과 실제 Present 호출 스레드, 범위 밖 호출은 별도 확인 대상이다.

회귀 조건은 DLL 폴더·작업 폴더 우선순위, 외부 파일 생성·삭제·수정 시간 유지, 기본 파일 변경, 빈 파일과 `version.dll`, 편집 오버레이의 존재하지 않는 ID, runtime과 표시 내용의 차이다. 파일 변경 감지와 화면 표시의 실제 실행은 확인하지 않았다.

## 기준 기재와 효과 정의의 정적 대조

기준 `S8RPK_traits_default.json`을 일반 JSON으로 해석해 254개 항목을 확인했다. 모든 항목에서 `id=index+1`, 효과 배열 길이 6이며 0 타입 sentinel 뒤에 0이 아닌 효과가 있는 항목은 없다. `customNames` 213개 중 이름이 비어 있지 않은 항목은 182개다. 이는 파일 내용의 구조 대조이며 기존 줄 파서가 이 값들을 모두 읽거나 게임에 적용했다는 결과는 아니다.

기준 효과 정의 87개와 타입 번호를 비교하면 기재 ID 30이 사용하는 타입 114·115가 정의 파일에 없다. `OfficerData_impl.inc:2073`의 효과 설명 함수는 정의 맵에서 타입을 찾지 못하면 빈 문자열을 반환한다. 외부 효과 정의로 해당 타입이 추가된 경우는 별도이므로, 기준 내장 정의 사용과 외부 정의 사용을 나눠 회귀 확인한다. 또한 0 sentinel과 효과 여섯 슬롯, ID·index, 표시 이름이 빈 custom 항목을 함께 검증한다.

## 기재 이름 편집 훅의 두 경로와 해제

`ApplyTraitTextNameHook`는 먼저 편집 행에서 새 이름이 비어 있거나 기존 이름과 같은 행을 제외한다. 나머지는 기존·새 이름을 엄격한 UTF-8로 UTF-16에 변환하고 새 이름을 UTF-16 코드 단위 5개 이하로 제한한다. 동일한 기존 이름이 여러 행에 있으면 런타임 편집 detour는 첫 일치 행을 반환한다. 조회는 기재 ID가 아니라 원래 getter가 돌려준 문자열과 비교한다.

게임 폴더에 `version.dll` 파일이 있으면 `GetModuleHandleW(L"version.dll")`로 같은 이름의 로드된 모듈을 찾고 외부 경로를 선택한다. 찾은 모듈의 파일 경로가 게임 폴더의 파일과 같은지는 이 함수에서 비교하지 않는다. 실행 파일 `+0x170E2D0`의 간접 점프 stub과 찾은 모듈 `+0x5CB0`의 예상 바이트를 확인한 뒤, 실행 파일 `+0x170E2D6`의 포인터가 정확히 해당 모듈의 `+0x5CB0`일 때만 이름 치환 cave로 교체한다. 기존 외부 이름 훅을 먼저 해제한 후 새 cave 생성을 시도하므로 재적용 중 검증·할당·쓰기 실패는 기존 편집을 되돌려 놓지 않는다. 변경 행이 없으면 해제만 수행한다. 실제 로드된 모듈의 경로는 확인하지 않았다.

외부 경로 해제는 현재 포인터가 자신의 cave일 때만 원래 포인터로 쓰며, 다른 값으로 바뀌었다면 충돌로 실패한다. 이미 원래 포인터인 경우에는 내부 적용 상태를 내린다. 자체 복원에 성공한 이전 cave들은 반환 문자열을 보유한 게임 UI를 고려해 목록에 보관하며 이 소스에는 해제 경로가 없다. 원래 포인터로 이미 바뀐 경우도 해당 cave를 즉시 해제하지 않는다. 파일 존재만으로 외부 경로를 선택하므로 파일이 있으나 모듈이 로드되지 않은 경우 오류로 끝나며 런타임 경로로 자동 전환하지 않는다.

외부 파일이 없으면 실행 파일 이름 getter의 `E9`와 relay를 따라 기존 기재 JSON 이름 detour를 찾고, 그 detour를 대상으로 MinHook 연결 훅을 한 번 설치한다. 이름 표는 별도 세대 객체로 보관한 뒤 atomic 포인터로 게시하며 동일한 표 재적용은 새 세대를 만들지 않는다. 변경 행이 없거나 해제하면 활성 표만 비우고 연결 훅은 유지한다. 이미 게시한 세대는 프로세스 수명 동안 보관하는 구현이다. 실제 DLL 언로드 후 게임이 이전 문자열을 계속 사용하는지는 확인되지 않았다.

런타임 경로에서 `MH_EnableHook`이 성공한 **후**에 `g_originalGetter`를 trampoline으로 대입한다. detour는 원본 포인터가 null이면 null을 반환한다. 따라서 활성화와 대입 사이 callback이 실행된다면 이 분기로 들어갈 수 있다. 설치와 callback이 실제로 겹치는지는 정적으로 확인되지 않았다. 외부·런타임 경로 모두 내부 상태와 실제 포인터 또는 훅 상태의 관계, 다른 패치와의 충돌 및 전환 중 실행에 대한 검증이 필요하다.

회귀 조건: 중복 기존 이름, UTF-16 5 코드 단위 경계, 빈 편집, 외부 파일은 있으나 모듈 미로드, 원본 stub·함수·포인터 불일치, 기존 외부 편집 해제 후 재설치 실패, 동일 표 재적용, 편집 해제 후 getter, 훅 활성화와 원본 포인터 설정 사이 callback, 다른 패치가 포인터를 변경한 경우, 게임이 이전 문자열을 보유하는 동안 재적용·종료.

## 일반·특수 기재 설명 훅과 묶음 적용

`TraitTextDescHook.cpp`는 기존 이름이 `괴물`, `잔병첩보`인 행을 제외하고, `TraitTextSpecialDescHook.cpp`는 이 두 이름인 행만 처리한다. 두 경로 모두 새 설명이 비거나 기존 설명과 같으면 행을 제외하고, 나머지 행을 검증해 UTF-16으로 변환한다. cave는 기존 설명 전체를 종료 NUL까지 비교해 일치하는 첫 행의 새 문자열로 교체한다. 이름 편집과 마찬가지로 실제 비교 키는 기재 ID가 아니다.

일반 설명은 실행 파일 `+0x170ACE0`의 원본 10바이트를 확인하고 10바이트 점프로 교체한다. 특수 설명은 `+0x146E5`에서 뒤따르는 조건 분기까지 11바이트를 확인하지만 앞의 5바이트만 점프로 교체한다. 각각 새 설명 문자열을 cave에 넣고 원래 명령의 동작으로 복귀한다. 보호 변경 후 바이트를 쓰고 명령 캐시를 비우지만 보호 속성 복원 결과는 확인하지 않는다.

두 경로 모두 유효한 새 행을 수집한 뒤 기존 적용을 먼저 해제하고 새 hook을 설치한다. 새 대상 원본 검사·cave 생성·설치가 실패하면 기존 편집은 자동으로 다시 설치되지 않는다. 해제는 저장된 게임 기준 주소를 확인한 뒤 원본 바이트를 직접 쓰지만, 현재 바이트가 자기 점프인지 비교하지 않는다. 따라서 중간에 다른 코드가 같은 위치를 바꾼 경우 해제가 그 변경을 덮을 수 있다. 해제된 cave는 즉시 해제하지 않고 보관한다. 적용 여부 조회는 게임 코드 재검사가 아닌 내부 flag를 반환한다.

편집 창의 `ApplyAll`은 모든 기존·내장 행 검증 후 이름 → 일반 설명 → 특수 설명 → 내장 행 순서로 적용한다. 뒤 단계가 실패하면 앞 단계 제거를 시도하지만 제거 결과를 확인하거나 이전 편집 세대를 복원하지 않는다. 자동 적용에서 외부 `version.dll` 때문에 내장 행이 지원되지 않는 특정 오류는 앞의 세 훅을 유지한 채 실패를 반환한다. `RemoveAll`은 내장 → 특수 설명 → 일반 설명 → 이름 순서로 모두 해제를 시도하고 첫 오류를 반환하며, 내장 해제 성공 여부와 관계없이 표시용 오버레이를 지운다. 자동 적용의 조건과 횟수는 [기재 편집 창 조사](P0_Trait_Viewer.md)를 따른다.

회귀 조건: 두 특수 이름과 일반 행 구분, 중복 원본 설명, 빈 설명, 원본 10·11바이트 불일치, 재적용 중 각 단계 실패, 다른 패치 후 해제, 묶음 적용과 제거의 부분 실패, 외부 DLL 예외, 이전 cave의 문자열을 게임이 계속 참조하는 동안 재적용·종료. 실행 스레드와 실제 문자열 보유 기간은 미확인이다.

## 확장 기재 효과 판정과 호환 hook

`FindMatchingCustomTrait`는 먼저 요청한 원본 기재 레코드와 ID를 확인하고 무장의 세 기재 슬롯을 순서대로 읽는다. 보유 기재 ID가 71~254이고 메타데이터의 `cloneSrc` 또는 `bgTrait`가 요청 ID-1과 일치하며, 두 레코드의 0이 아닌 효과 종류가 적어도 하나 공통일 때 첫 보유 기재를 선택한다. 효과 값까지 동일해야 하는 조건은 아니다. 원본 효과 종류가 하나도 없거나 필요한 효과 읽기에 실패하면 일치로 처리하지 않는다.

효과 조회 hook은 원래 판정을 먼저 실행하고 원본이 참이면 그대로 참을 반환한다. 원본이 거짓일 때 지정된 한 호출 위치는 확장 판정을 건너뛰며, 그 밖에 일치한 확장 기재가 있으면 요청 ID·확장 ID·조회 복귀 위치를 스레드별 캐시에 남긴다. 별도의 무장 보유 판정 hook은 원본이 거짓인 경우 요청 ID 11에 대해서만 같은 방식으로 확장한다. 원본이 참인 경우 확장 기재를 우선하지 않는다.

대화 메시지 setter와 데이터 getter는 이 캐시의 요청 ID, 조회·소비 복귀 위치 조합 및 확장 레코드 ID를 확인한 경우에만 확장 ID를 전달한다. 메시지 경로는 허용된 위치 쌍 8개, 데이터 경로는 1개다. 성공 시 캐시를 비우며 알 수 없는 위치 쌍에서는 원래 ID·원래 결과를 유지하고 진단 로그를 스레드당 최대 12회 남긴다. 전근 특수 연출 hook은 두 번째 인물의 원본 기재 26 대응을 확인해 원래 함수를 호출하는 동안 별도 캐시를 설정하고, 호출 후 이전 캐시를 복원한다. 캐시가 `thread_local`이므로 조회와 소비가 다른 스레드로 넘어가면 같은 캐시를 공유하지 않는다. 실제 게임의 호출 위치·스레드 이동은 확인하지 않았다.

월별 보완 hook은 원본 처리를 먼저 호출한다. 설정과 테이블이 준비된 경우 최대 1801개 인물 포인터를 돌며 유효 객체의 확장 기재 세 슬롯에서 효과 타입 166의 부호 있는 16비트 값을 합산한다. 합이 양수일 때만 인물 `+0x300`의 32비트 값에 더하고 최대 99999로 제한해 기록한다. 합이 0 이하이면 변경하지 않는다. 각 훅 설치 조건과 일부 실패는 [훅 조사](P0_Details.md)의 별도 항목을 따른다.

회귀 조건은 원본 우선, 계보만 일치·효과만 일치·둘 다 일치, 여러 슬롯의 첫 일치, 71·254 경계, ID 11 이외의 보유 판정, 등록·미등록 위치 쌍, 같은 스레드의 중첩 조회와 다른 스레드 소비, 전근 전후 캐시 복원, 월별 양수·음수 합과 99999 경계다. 게임에서 재현하지 않았다.

### 기재 재적용 감시의 대표 레코드 범위

외부 `version.dll`이 없는 경로에서 `EnsureEmbeddedTraitConfigLoaded`는 읽은 기재 중 custom text 메타데이터가 함께 있는 첫 인덱스를 대표 감시 대상으로 선택한다. 그런 항목이 없으면 존재하는 첫 기재를 선택한다. 적용 후와 이후 tick의 `ConfigEntryMatches`는 그 한 레코드의 ID와 여섯 효과 슬롯만 설정과 비교한다. 이름·설명, donor에서 복제한 나머지 메타데이터, 다른 기재 레코드는 이 대표 비교에 포함되지 않는다. 따라서 테이블 주소와 대표 레코드가 같더라도 다른 레코드만 바뀐 경우 이 검사만으로는 재적용을 요청하지 않는다.

대표 레코드 불일치나 테이블 주소 변경으로 재적용이 필요하면 `ApplyConfig`는 254개 레코드 전체를 복사·수정해 다시 쓴다. 쓰기 후 대표 레코드 검사에 실패하면 pending을 유지하여 다음 tick에서 다시 시도한다. 쓰기 도중 예외가 발생해도 보호 복구를 시도하지만 이미 기록된 일부 바이트를 이전 스냅샷으로 되돌리는 경로는 없다. 성공 시에도 254개 레코드 전체를 개별 비교하지 않는다. 실제 부분 쓰기나 외부 코드에 의한 값 변경은 관찰하지 않았다.

회귀 조건은 대표 외 레코드만 초기화, 대표 ID·효과 변경, 설명·메타데이터만 변경, 같은 주소 재사용, 전체 쓰기 중 실패와 다음 tick 재시도, 세션 전환 직전 tick이다. 이 조건은 원본 동작과 새 구현의 선택을 대조하기 위한 것이며 실제 게임 실행 결과가 아니다.

### 사용자 기재 설명 테이블의 동기화 수명

`TraitConfigRuntime_impl.inc:685`의 설명 동기화는 인덱스 70~199의 비어 있지 않은 설명을 일반·포맷 테이블에 각각 쓴다. 각 문자열을 확보한 버퍼에 쓰고 해당 테이블 항목에 테이블 기준 32비트 상대 오프셋을 기록한다. 일반 테이블 처리가 성공한 뒤 포맷 테이블을 처리한다. 어느 쓰기에서 실패해도 이전에 쓴 항목을 복구하지 않으며 동기화 완료 flag는 켜지지 않아 다음 tick에서 다시 시도한다. 설명 리소스가 준비되지 않아 실패하더라도 호출자는 효과 테이블 준비·적용을 계속한다.

회귀 조건은 일반·포맷 각각의 부분 쓰기 실패, 재시도, 빈 설명, 70·199 경계와 그 밖의 인덱스, 편집 문구 게시, 효과 테이블과 설명 테이블의 독립 교체다. 정적 조사이며 게임을 실행하지 않았다.

### 추가 기재 편집의 적용·저장·초기화

`TraitTextEditorWindow.cpp:356`의 적용과 저장은 별도 버튼이다. 적용은 현재 편집 행을 검증해 런타임 오버레이를 게시하지만 파일을 저장하지 않는다. 저장은 선택된 편집 종류에 따라 파일 저장 함수만 호출하며 적용 함수를 호출하지 않는다. 추가 기재 저장은 모든 대상 행을 검사하고 기존 기본 JSON의 `customNames` 줄에서 해당 ID를 찾아 이름·설명의 **비어 있지 않은** 새 값만 교체한다. 모든 편집 대상 ID를 찾지 못하면 쓰기 전에 실패한다.

`선택 초기화`와 `전체 기본값`은 편집 행의 새 문자열을 비운다. 이후 추가 기재 저장에서 빈 값은 JSON의 기존 필드를 원래 문자열로 바꾸지 않고 그대로 둔다. 따라서 이미 파일에 저장된 편집을 되돌리려면 빈 행 저장과는 다른 데이터 변경이 필요하다. 런타임 적용도 빈 오버레이 필드에 대해서는 현재 로드된 기본 메타데이터를 사용한다. 저장된 파일을 바꾸는 일과 이미 로드된 런타임 기본 메타데이터를 새로 읽는 일은 별개다.

수동 `적용`이 성공하면 자동 적용 완료 flag를 세우지만 실패하면 그 flag를 바꾸지 않는다. 반면 `적용 해제`는 제거를 시도하기 전에 완료 flag를 세우므로 일부 제거가 실패해도 이후 자동 적용 tick은 재시도하지 않는다(`TraitTextEditorWindow.cpp:356-376`). 선택 초기화·전체 기본값·저장은 이 flag를 바꾸지 않는다. 기존 자동 적용의 진행 상태와 수동 조작 결과를 별도 회귀 조건으로 둔다.

추가 기재 저장은 대상 파일을 truncation으로 열어 전체 텍스트를 다시 쓰고 flush 결과를 검사한다. 쓰기 실패를 알리지만 임시 파일 교체나 기존 내용 복구는 이 함수에 없다. 회귀 조건은 적용만·저장만·저장 후 재시작, 저장된 값의 빈 행 초기화, 일부 ID 누락, 파일 쓰기 실패, 외부 `version.dll` 존재 여부와 설명 테이블 재동기화다. 파일을 수정하거나 게임을 실행하지 않은 정적 조사다.

### 기본 기재 문구 파일 형식과 로드 결과

`TraitTextEditorData.cpp:229`은 기본 72개 편집 행의 새 이름·설명을 먼저 모두 비운 뒤 DLL 폴더의 `trait_texts.ini`를 연다. 모듈 경로를 얻지 못하면 상대 경로를 사용한다. 파일을 열지 못해도 기존 편집 행은 이미 비워진 상태다. 줄은 `ROW:번호:이름의 UTF-8 바이트 hex:설명의 UTF-8 바이트 hex` 형식으로 읽고, 범위 밖 번호·잘못된 hex 등 파싱에 실패한 줄은 건너뛴다. 같은 번호가 여러 번 나타나면 뒤에 읽은 유효 행이 앞 행을 덮는다. 첫 헤더의 존재 여부는 로더가 검사하지 않으며, 열기에 성공했다면 유효 행이 하나도 없어도 성공을 반환한다.

저장은 모든 행을 검증한 다음 `[SAN8RPK_TRAIT_TEXTS]` 헤더와 72개 행을 CRLF로 새로 쓴다. 이름과 설명은 UTF-8 바이트를 대문자 hex로 기록하며 빈 편집도 빈 필드로 출력한다. 파일을 truncation으로 열고 스트림 상태를 검사하지만 임시 파일 교체는 하지 않는다. 로드는 hex 바이트를 행에 넣는 단계에서 UTF-8·이름 길이·설명 형식까지 검증하지 않는다. 그 검증은 별도 적용·저장 경로에서 수행된다.

기본 문구 저장은 행 출력 직후 `file.good()`를 검사하고 성공을 반환하며 명시적 `flush` 또는 `close` 후의 상태는 검사하지 않는다. 따라서 버퍼를 최종 반영하거나 닫는 단계의 실패는 이 반환값에 반영되지 않는다. 창은 반환값이 true면 저장 완료 상태를 표시한다. 검증 실패는 파일을 열기 전에 반환하지만, 열기 이후 쓰기 실패에는 이전 파일 복구가 없다. 실제 디스크 오류는 재현하지 않았다.

`ApplyAll`은 hook을 설치하기 전에 기본 행 전체와 추가 기재 행 전체를 이 순서로 검증하고 첫 실패에서 반환한다. 따라서 로드된 한 행이 잘못되면 다른 정상 행만 따로 적용하는 경로가 아니다. 자동 적용은 이 검증 실패를 별도로 영구 오류로 분류하지 않아 일반 실패와 같이 최대 30회 재시도한다. 반면 기본 문구 저장은 기본 행만 검증한다. 로더가 hex 형식만 맞는 잘못된 UTF-8 등을 행에 보관할 수 있다는 앞의 조건과 함께 이 차이를 확인해야 한다. 실제 자동 적용은 실행하지 않았다.

회귀 조건은 파일 없음으로 인한 기존 편집 초기화, 헤더 없음, 잘못된 줄과 중복 행, 빈 행, 잘못된 UTF-8, 저장 후 재로드와 쓰기 실패다. 원본 파일을 수정하거나 게임을 실행하지 않았다.

### 자동 로드 실패와 수동 창 열기의 상태 차이

`TickTraitTextEditorAutoApply`가 처음 실행될 때 두 파일 로드가 모두 실패하면 `g_autoFinished`를 true로 설정하고 반환한다. 이 실패 분기는 `g_autoLoaded`와 `g_loadedOnce`를 true로 바꾸지 않는다. 따라서 이후 편집 창을 처음 열면 `OpenTraitTextEditorWindow`가 두 파일을 다시 읽을 수 있지만, 자동 tick은 이미 종료 상태여서 그 로드 결과를 자동 적용하려고 다시 시도하지 않는다. 사용자는 창의 적용 버튼으로 수동 적용할 수 있다.

반대로 한 파일이라도 로드에 성공하면 `g_loadedOnce`를 true로 설정한다. 기본 문구 로더는 파일이 열리면 유효 행이 없어도 성공하므로, 내용이 없는 기본 문구 파일도 이 분기를 통과할 수 있다. 두 편집 집합에 변경 내용이 없으면 자동 적용은 종료한다. 이 동작은 저장값 로드 성공과 실제 편집 항목 존재를 분리해 판단한 결과다.

회귀 조건은 두 파일 모두 없음 뒤 파일 생성 및 창 열기, 빈 기본 문구 파일과 추가 기재 로드 실패, 한 파일만 성공, 자동 처리 종료 후 수동 적용이다. 자동 적용의 최초 호출 조건과 3초·30회 제한은 [자동 로드 조사](P0_Trait_Viewer.md#기재-문구-자동-로드와-재시도)를 따른다. 실제 UI 조작은 하지 않았다.

### 기재 설명 형식 토큰의 실제 비교

기본 행과 추가 행의 검증기는 각각 같은 방식으로 `%` 토큰을 수집한다. `%%`는 토큰으로 세지 않고, 플래그 `-+ #0`, 숫자 폭, 선택적 소수점·숫자 뒤에 `diuoxXfFeEgGaAcsp` 중 하나가 오는 표현을 토큰 전체 문자열로 기록한다. 인식하지 못한 `%` 표현은 일반 문자로 넘긴다. 따라서 `%d`와 `%02d`는 변환 종류가 같아도 서로 다른 토큰으로 비교되며, 길이 지정자나 `*`가 들어간 표현을 일반적인 printf 형식 전체로 해석하지 않는다.

새 설명이 비어 있지 않고 원문과 다를 때, 새 설명에서 인식된 토큰이 하나 이상이면 원문의 토큰 목록과 문자열 및 순서가 정확히 같아야 한다. 새 설명의 인식 토큰이 0개면 원문에 토큰이 있어도 허용한다. 이 검사는 인식하지 못한 `%` 표현의 실제 게임 포맷 처리까지 검증하지 않는다. 이름과 설명은 NUL 없는 유효 UTF-8이어야 하고, 변환된 UTF-16의 코드 단위 수를 각각 5와 512로 제한한다.

회귀 조건은 `%d`와 `%02d`, 복수 토큰 순서, `%%`, 토큰 전체 생략, 미인식 표현, 보조 평면 문자에 필요한 UTF-16 두 코드 단위, 잘못된 UTF-8 및 NUL이다. 이 기록은 현재 검증기의 동작이며 실제 게임 포맷 호출 결과는 확인하지 않았다.

### 편집 화면 버퍼와 저장 행의 동기화

`TraitTextEditorWindow.cpp`는 선택 행의 새 이름을 128바이트, 새 설명을 4096바이트의 고정 버퍼에 `snprintf`로 복사한다. 행을 선택할 때 이전 버퍼를 행에 저장한 뒤 새 행을 버퍼에 불러오며, 적용·저장 버튼도 현재 버퍼를 행에 먼저 저장한다. 파일 로드 단계는 앞 절과 같이 기본 문구에 대한 UTF-8과 길이 검사를 하지 않으므로, 외부 파일에 버퍼보다 긴 값이 있으면 선택 시 바이트 단위로 잘린 값이 버퍼에 들어갈 수 있다. 잘린 값은 선택 전환이나 적용·저장에서 원래 행을 대체하며, UTF-8 문자의 중간에서 잘렸다면 이후 검증은 실패한다.

정상 검증을 통과한 새 이름은 UTF-16 5코드 단위 이하, 설명은 512코드 단위 이하여서 이 고정 버퍼보다 작다. 따라서 위 차이는 로드된 비정상·미검증 값의 처리 경계다. 회귀 조건은 버퍼 경계의 외부 파일 입력, 멀티바이트 문자 절단, 행 선택 전환, 저장·적용 시 검증 실패 및 기존 행 보존 여부다. 화면과 파일을 실행·수정하지 않은 정적 조사다.

### 기재 호환 훅의 설치 상태와 재검사

`InstallCompatibilityHook`은 각 대상의 설치 flag가 이미 true면 현재 코드 바이트나 MinHook 등록을 다시 검사하지 않고 성공한다. 설치 전에는 지정된 최대 8바이트의 원본과 실행 가능 주소를 확인하고, 생성한 trampoline의 실행 가능성을 확인한 뒤 원본 주소를 저장하고 훅을 활성화한다. 생성 자체가 실패한 대상은 제거하지 않는다. trampoline 검사 또는 활성화가 실패하면 자신이 생성한 대상을 제거하려 하지만 제거 반환값은 확인하지 않는다.

대상별 `failureLogged`는 실패 메시지 반복만 억제한다. 설치 flag가 false인 동안 상위 tick이 해당 경로에 도달하면 설치는 다시 시도한다. 다섯 대상은 독립적으로 호출되고 그 반환값을 상위 함수가 합산하지 않으므로 일부만 설치된 상태에서도 나머지 대상 설치와 두 조건 바이트 유지가 진행된다. 반대로 설치 flag가 true로 남은 상태에서 외부 요인으로 코드나 등록이 바뀌는 경우 이 함수만으로는 감지하지 않는다.

회귀 조건은 각 대상의 원본 불일치 후 복구, 생성·trampoline·활성화 실패, 부분 설치, 설치 flag와 실제 등록 상태 차이, 조건 바이트와 훅의 서로 다른 준비 시점이다. 실제 외부 변경 및 callback 실행은 확인하지 않았다.

### 기재 사용 조건 바이트의 종료 수명

두 기재 사용 조건 패치는 실행 파일 `+0x17C03E7`, `+0x17C042F`에서 각각 6바이트 `81 FE 95 00 00 00` 중 세 번째 바이트를 `95→01`로 직접 쓴다. 이미 `01`인 경우에도 자신의 쓰기 여부를 구분하지 않고 활성으로 취급한다. 두 위치는 MinHook 등록 대상이 아니므로 전체 `MH_DisableHook`·`MH_Uninitialize`가 이 바이트를 복원하지 않는다.

기준 소스에서 이 두 상수와 유지 함수의 참조를 대조한 범위에는 `01→95` 복구 호출이 없고, `Source_impl.inc`의 정상 종료 경로도 이를 별도로 복구하지 않는다. 따라서 이 코드만을 기준으로 정상 언로드가 두 조건 바이트를 원래 값으로 되돌린다고 판단할 수 없다. 해당 바이트가 이미 다른 코드에 의해 `01`이었던 경우도 있어, 이관에서는 원본 소유와 충돌 여부를 구분해야 한다. 실제 언로드 후 메모리는 확인하지 않았다.

회귀 조건은 원래 `95`, 선행 패치 `01`, 다른 값과 주변 바이트 불일치, 게임 측 재설정, 정상 언로드 및 다른 패치와의 소유권이다.

### 기재 데이터 테이블 적용과 정상 종료

`ApplyConfig`는 게임의 254개 원본 레코드를 지역 배열로 읽지만, 그 배열을 donor 복제·메타데이터·ID·효과를 적용하는 작업 버퍼로 바로 수정한 뒤 같은 게임 영역에 다시 쓴다. 이전 전체 레코드의 별도 장기 백업은 이 함수에 없다. 성공 후 설정의 변경 요청을 끄는 tick도 원래 게임 테이블로 되돌리는 분기가 아니다.

정상 종료의 `Shutdown(false)`는 MinHook 전체 비활성화·해제 및 렌더/입력 정리를 수행한다. 기준 기재 runtime과 정상 종료 경로에서 기재 테이블 254개를 적용 전 스냅샷으로 복구하는 호출은 확인되지 않았다. 따라서 훅 해제와 기재 데이터 복구는 별도 작업이며, 기존 코드의 정상 종료를 데이터 복구 성공으로 취급할 수 없다. 실제 언로드 후 게임이 이 테이블을 다시 초기화하는지는 실행하지 않아 확인하지 않았다.

회귀 조건은 적용 전 비기본 레코드, 부분 설정과 donor 복제, 같은 주소의 테이블 재초기화, 정상 언로드와 게임의 후속 테이블 갱신이다.

### 기재 runtime 문자열 게시와 callback의 관측 범위

`PublishNativeTexts`는 각 이름, 일반 설명, `%`를 두 배로 쓴 포맷 설명을 각각 `VirtualAlloc`으로 만들고 지역 포인터 배열 세 개에 모은다. 전부 준비되면 `RuntimeState`의 이름·일반 설명·포맷 설명 배열을 순서대로 대입한다. 배열은 일반 포인터 배열이며 세 배열의 교체와 게임 getter의 읽기를 묶는 atomic 게시나 공통 잠금은 이 코드에 없다. 이전 할당은 게임이 반환 포인터를 보유할 수 있다는 이유로 이 함수에서 해제하지 않는다.

변환·할당이 중간에 실패하면 기존 배열 대입 전 false를 반환하지만, 그 시도에서 이미 만든 문자열 할당을 해제하는 경로는 없다. 이름 getter는 사용자 이름 포인터를 직접 반환한다. 설명 getter는 원본을 먼저 호출하고 결과가 null인 ID 201~254만 사용자 설명을 thread-local 버퍼에 복사해 반환한다. 일반 설명은 최대 0xFE, 포맷 설명은 최대 0x7FE UTF-16 코드 단위이며 같은 스레드에서 같은 종류의 다음 호출이 버퍼를 덮는다.

회귀 조건은 재게시 중 getter 호출, 이름과 설명 배열의 다른 세대 관측, 중간 할당 실패, 이전 이름 포인터 보유, 동일 스레드 설명 연속 조회 및 언로드 후 포인터 수명이다. 실제 callback 스레드·게임의 포인터 보유 기간은 확인하지 않았다.

### 기본 기재 파일의 중복·누락과 적용 결과

기본 파일 로더는 `customNames` 문자열이 나오기 전의 줄에서 기재 항목을, 그 이후 줄에서 메타데이터를 파싱해 각각 인덱스 배열에 대입한다. 같은 인덱스의 유효한 줄이 여러 개면 마지막 줄이 남지만 `traitCount`·`customCount`는 유효 줄마다 증가하므로 로그의 개수는 고유 인덱스 수와 다를 수 있다. 기재 항목은 최소 한 줄만 성공하면 되고, 254개가 모두 존재하는지 확인하지 않는다. 남은 항목은 마지막으로 저장된 ID가 `index+1`인지 검사한다.

적용 시 누락된 인덱스도 게임의 기존 레코드를 복사한 작업 배열에 포함된다. 해당 인덱스에 사용자 텍스트 메타데이터가 있으면 donor 복제와 배경 메타데이터 복사가 먼저 실행될 수 있고, 기재 항목이 없는 분기는 ID만 `index+1`로 기록한다. 따라서 누락된 효과가 반드시 원래 게임 효과로 유지된다고 단정할 수 없다. 유효 항목을 최소 하나 읽은 부분 파일도 전체 254개 레코드 쓰기 경로에 도달할 수 있다.

회귀 조건은 중복 인덱스의 앞뒤 값, 로그 개수와 고유 항목 수, 부분 파일과 누락 슬롯의 metadata 유무, donor 순서, ID 불일치 및 첫 유효 항목이 없는 파일이다. 기준 파일은 별도로 전체 항목을 확인했으며, 임의 파일이나 게임은 수정·실행하지 않았다.

### 기재 JSON 줄 파서의 숫자·문자열 해석

`ReadJsonIntValue`는 요청 키 뒤 첫 `:` 이후 공백을 건너뛰고 선택적 부호와 연속된 십진 숫자만 읽는다. 숫자 뒤의 구분자나 값 전체의 JSON 문법은 확인하지 않는다. `ReadJsonStringValue`는 키와 `:` 뒤의 첫 따옴표부터 읽으며 `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t`는 변환하지만 `\u`를 포함한 그 밖의 escape는 역슬래시와 다음 문자를 그대로 남긴다. 값이 문자열인지 JSON 구조 전체를 검증하지 않으므로, 다른 형태의 값 뒤에 따옴표가 있으면 그 위치부터 읽으려 한다.

기재 효과 항목은 `index`, `id`와 여섯 효과 객체가 같은 한 줄에 있어야 한다. 여섯 객체를 읽고 나서는 그 뒤 추가 효과가 있는지 검사하지 않는다. 메타데이터는 숫자 키를 첫 따옴표 쌍에서 찾으며 이름·설명·선택 숫자 필드의 읽기 실패를 항목 전체 실패로 처리하지 않는다. 따라서 일반 JSON 파서의 성공·실패 결과와 기존 런타임 파서의 결과는 같다고 보장되지 않는다.

회귀 조건은 줄바꿈된 객체, 5·6·7개 효과, 중복 키, 숫자 접미 문자, `\u` escape, 문자열이 아닌 메타데이터 필드, 읽기 실패한 이름·설명과 기준 파일의 실제 형식이다. 원본 파서나 게임은 실행하지 않았다.

### 기준 파일의 줄 배치 대조

기준 저장소 `S8RPK_traits_default.json`을 PowerShell로 읽기 전용 대조했다. `index`와 `effects`가 같은 줄에 있는 항목은 254줄이며, 각 줄을 독립 JSON 객체로 해석했을 때 모두 `id=index+1`이고 효과가 정확히 6개였다. 숫자 키와 객체 시작이 같은 줄에 있는 메타데이터 후보는 213줄이다. 파일 전체에서 `\u`와 4자리 16진수가 연속된 줄은 0개였다.

이 결과는 기준 파일의 줄 배치와 일반 JSON 해석을 대조한 것이다. C++ 줄 파서를 실행하거나 213개 메타데이터의 각 문자열과 효과 값을 C++ 결과와 비교한 것은 아니다. 사용자 설치본과 수정 파일에도 같은 조건이 성립한다는 뜻은 아니다. 전체 런타임 적용과 게임 결과는 여전히 미확인이다.

### 기준 파일에서 donor 참조 방향의 범위

기준 저장소 `S8RPK_traits_default.json`을 PowerShell 일반 JSON 해석으로 읽고, 이름 또는 설명이 비어 있지 않은 메타데이터 182개에 대해 `ApplyConfig`의 인덱스 조건을 대조했다. 명시 `cloneSrc`가 현재 인덱스보다 앞인 항목은 170개, 뒤인 항목은 7개이며, 누락·자기 자신·범위 밖으로 기본 donor 30을 택하는 항목은 5개다. 같은 182개 중 유효한 `bgTrait`가 현재보다 앞인 항목은 161개, 뒤인 항목은 2개다. 나머지 배경 참조는 자기 자신이거나 누락·범위 밖이다.

앞 인덱스 참조는 이미 작업 배열에서 수정한 레코드를, 뒤 인덱스 참조는 아직 처리하지 않은 레코드를 읽는다. 따라서 기준 파일에도 처리 순서가 결과에 영향을 줄 수 있는 참조 방향이 모두 존재한다. 다만 이 집계는 JSON 값과 코드 조건의 정적 대조이며 각 레코드의 실제 게임 원본 바이트나 최종 결과 차이를 계산한 것은 아니다. 사용자 설치본에는 그대로 적용하지 않는다.

[기준 메타데이터 참조 목록](p0/trait_metadata_reference.csv)은 213개 메타데이터의 인덱스·기재 ID·문구 유무·원본 cloneSrc·기본 donor를 반영한 실제 선택 인덱스·bgTrait 방향을 기록한다. 앞 절의 170·7·5는 기본 donor 대체 **전** 구분이다. 대체 후 실제 donor 방향은 앞쪽 175개, 뒤쪽 7개다. 이 목록은 기준 JSON의 일반 해석을 이용한 정적 계산이며 C++ 파서 실행 또는 게임 레코드 비교 결과는 아니다.

참조 목록의 원본은 `reference/S8RPKCheats`의 `068ca1d881edf870f7cf06f935cf50e286004af8`에 있는 최상위 `S8RPK_traits_default.json`이며 확인 당시 SHA-256은 `1848937DA4E1CF9BF999586FE00E5524723732D574DA57ECEE933D8166C3DA8F`다. 생성 당시 기준 저장소의 변경 사항은 없었다. CSV의 `effective_clone=-1`은 문구가 없어 복제를 하지 않는 경우이고, 문구가 있으면 잘못되었거나 자기 자신인 `cloneSrc`를 30으로 대체한 값이다. `bg_direction=unused`는 `bgTrait`가 없거나 범위 밖이거나 자기 자신인 경우를 뜻한다. background 메타데이터 복사는 문구 유무와 별개로 유효한 참조에 적용된다.

## 기재 상세 조회 실패와 표시 캐시

기준 자체 cpp·h·inc에서 `GetOfficerTalentDetailed`의 호출은 `SelectOfficercapture_impl.inc:1636` 한 곳이다. 호출자는 반환값이 true일 때만 지역 결과를 캐시에 복사하고, false일 때 캐시를 0으로 지우며 효과 설명도 만들지 않는다. 따라서 앞 절의 부분 출력은 이 호출자의 실패 표시 경로에서 그대로 사용되지 않는다. 외부·간접 호출은 이 검색 범위 밖이다.

같은 표시 캐시는 무장 주소가 바뀌거나 강제 갱신이 요청되거나, 세 슬롯의 현재 기재 ID와 캐시된 ID가 달라질 때 다시 읽는다. ID가 유지되는 동안 효과 값만 외부에서 변경되는 경우 이 비교만으로는 변경을 감지하지 않는다. 표시 문자열도 재조회할 때 생성한다. 갱신 버튼과 다른 강제 갱신 경로의 영향, 동일 ID의 효과 변경과 조회 실패 후 회복은 실제 UI에서 확인하지 않았다.

강제 갱신 flag는 기재 직접 선택에서 `SetTraitID`가 성공할 때와 빈 슬롯 랜덤 부여에서 하나 이상 쓰기에 성공할 때 설정한다(`SelectOfficercapture_impl.inc:1496,1591`). 실패만 한 조작은 이 flag를 설정하지 않는다. 자동 ID 비교 또는 강제 갱신 뒤에는 flag를 false로 되돌린다.

상세 캐시 변수는 `DrawOfficerTalents` 함수의 정적 변수 한 묶음이다. 주인공과 선택 무장 창이 서로 다른 주소에 대해 이 함수를 같은 프레임에 호출하면, 각 호출이 직전 주소와 다르므로 각각 세 슬롯을 다시 조회하고 설명을 구성하는 코드 경로다. 두 창의 실제 표시 조건과 프레임 비용은 실행하지 않았다. 회귀 조건은 같은 ID의 효과 변경, 직접 선택·랜덤 부여 성공과 실패, 서로 다른 두 창을 함께 표시하는 경우다.
